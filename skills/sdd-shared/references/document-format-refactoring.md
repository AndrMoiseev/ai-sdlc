# Документы рефакторинга v1

Читай этот раздел при разборе или проверке документов вида `refactoring` вместе
с [общей основой](document-format.md). Формат обычного изменения остаётся в
[нормативных документах](document-format-normative.md) и
[задачах](document-format-tasks.md).

## Выбор схемы

Рабочий корень: `sdd/refactoring/<change-id>/`. Нормативный комплект состоит из
proposal.md, design.md и, на стадии plan, tasks.md. Отдельные specs не нужны.
Каждый документ содержит ровно такие общие метаданные:

```yaml
schema_version: 1
work_kind: refactoring
document_type: design
change_id: sample-refactoring
language: ru
```

Допустимые document_type: proposal/design/tasks. Proposal не содержит машинных
записей. Записи остальных документов следуют непосредственно за `###`, как в
общей основе. Вложенные примеры помещай во внешний четырёхсимвольный fence.

Ключ выбора схемы — `(work_kind, document_type, schema_version)`. Обычные документы
без work_kind означают change; явное `work_kind: change` также допустимо. Отсутствие
поля в скопированном документе не выбирает refactoring. Контекст вызова, объявленный
вид и известный корень должны совпадать. Неизвестный вид даёт
`unsupported_work_kind`, несовпадение — `work_kind_mismatch`, неизвестная версия
внутри известного вида — `unsupported_version`. Исправь выбор/размещение либо
установи согласованный комплект. Парсер сохраняет исходные байты.

## Design: критерии целого и решения

| sdd_record | Обязательные поля сверх id/sdd_record | Необязательные поля |
|---|---|---|
| criterion, ID AC | purpose: result/preservation, scope, conditions, expected | parent, source |
| decision, ID DEC | criteria | supersedes |

`scope` критерия — непустой список текстовых описаний областей. `conditions` и
`expected` — непустой текст. Design содержит хотя бы один result. `parent` связывает
result с другим result этого design; самоссылки и циклы запрещены. Родитель имеет
собственную проверку целого, статус дочерних критериев её не заменяет.

У preservation обязателен `source` по прежнему
[контракту baseline](document-format-normative.md#изменение-baseline): specification
с существующими path/requirement либо evidence с baseline_missing=true,
доступными references, observed и assumptions. Разбитый путь не подтверждает
отсутствие baseline. Применимость и достаточность свидетельств проверяет агент.
Preservation нельзя прекратить через until_task.

DEC.criteria — непустой список критериев design. `requirements` здесь не применяется.
`supersedes`, если указан, — непустой список объектов `{path, id}` для исходного
DEC либо `{path, anchor}` для заголовка исходного решения. Путь относителен корню
проекта и указывает существующий файл; ID должен иметь префикс DEC и присутствовать
в YAML-записи. Anchor — точный заголовок либо его форма в нижнем регистре с пробелами,
заменёнными на дефисы, без пунктуации. Область пересмотра и сохраняемую часть решения
объясни в тексте. Исторический источник сохраняется.

## Tasks: вклад и локальная приёмка

Задача сохраняет ID TASK, number, depends_on, status и необязательный
cannot_parallel_with. Номера образуют перестановку 1..N, зависимости локальны,
самоссылки и циклы запрещены; cannot_parallel_with симметричен.

| Поле task | Контракт |
|---|---|
| scope | Непустой список `{module, paths?}`; module — непустое название, paths — непустой список относительных путей, если они известны |
| contributes_to | Непустой список result-критериев design; один результат может иметь несколько задач-вкладчиков |
| preserves | Список применимых preservation-критериев design; для пустого списка обязателен непустой preservation_reason |
| verification | Непустой список `{id, criteria, test_description, location, run}` |
| test_changes | Необязательный список согласованных изменений групп проверок |

Будущий scope.path допустим; выход за проект, в том числе через существующего
symlink-родителя, запрещён. `covers` и `requirement` в этой модели не применяются.
Каждый result имеет вклад; перечень вкладов не доказывает полноту преобразования.
Смысл области и обоснованность пустого preserves оценивает агент.

Каждая задача имеет хотя бы одну отдельную запись `acceptance` с ID AC, `task`,
непустыми `conditions`/`expected` и `lifetime: persistent|transitional`. ID локальных
AC и критериев design уникальны внутри работы. Каждый локальный AC принадлежит
существующей задаче. Task.verification.criteria содержит только локальные AC этой
задачи и её preserves; объединение проверок покрывает оба набора. ID проверки —
стабильный slug, уникальный в задаче; полный ключ — `TASK-ID/verification.id`.
Форма location/run совпадает с [обычным контрактом](document-format-tasks.md).

Для transitional обязательны `until_task` и непустой `replaced_by`. Until_task —
другая задача, достижимая от владельца по графу последующих зависимых задач.
Заменяющий локальный критерий принадлежит until_task либо её предшественнику и
покрыт проверкой своего владельца. Раннее снятие защиты по проверке result только
в финале запрещено. Самоссылки и циклы замен запрещены. Для persistent поля
until_task/replaced_by не применяются.

Приёмка until_task требует свежих свидетельств заменяющих проверок на её кандидате.
Проверка предшественника сохраняет своё владение: исполнение повторно запускает её
на новом кандидате, а не добавляет чужой локальный AC в task.verification.criteria.
Структурный валидатор проверяет наличие проверок и зависимости; свежесть и
подтверждённое прекращение применимости обеспечивает исполнение.

## Изменение групп проверок

Элемент test_changes содержит уникальный внутри задачи slug `id`,
`action: add|adapt|move|remove`, непустые `group` и `reason`, непустой список
`criteria` на критерии design или локальные AC. Необязательный `decision` ссылается
на DEC этого design, `replacement_criteria` — на критерии нового состояния.

Удаление требует непустую замену либо архитектурное решение об отменённой границе.
При снятии чисто структурной проверки замена может быть пустой; исходную границу
опиши в group, основание — в reason и decision. Сохраняемое обязательство требует
заменяющего критерия, один DEC его не прекращает. Ревью проверяет связь фактических
файлов/проверок с разрешённой группой и достаточность замены.

## Проверки целого

Запись `verification` с ID CHECK содержит criteria/test_description/location/run,
не принадлежит отдельной задаче и допускает необязательный setup_task. Criteria
содержит критерии design и, при необходимости, persistent локальные AC. План имеет
хотя бы одну проверку целого; объединение покрывает каждый критерий design.
Постоянные локальные результаты сохраняют проверки своих задач либо явно
заменяющие проверки целого.

При run.setup_required обязателен существующий setup_task с собственным локальным
результатом. Готовность пути и реальное выполнение проверяются исполнением.
Итоговая проверка целого нужна на финальном интегрированном состоянии. Она не
становится обязательным условием приёмки каждой ранней задачи.

Машинная схема [refactoring.schema.json](../schemas/refactoring.schema.json)
описывает проекцию Document `{meta, records}`. Python-валидатор дополнительно
проверяет междокументные ссылки, графы, покрытие и безопасные пути. Успешная
структура не доказывает полноту области, сохранение поведения или свежесть итоговых
свидетельств.
