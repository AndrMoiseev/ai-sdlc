# Форматы документов sdd

Выбери вид работы до разбора: обычное изменение `change` использует описанные
ниже документы v1; `refactoring` использует отдельный
[формат рефакторинга v1](document-format-refactoring.md). Одинаковый номер версии
не объединяет их схемы. Общие правила Markdown, YAML, ID и ограничений разбора
действуют для обоих видов.

Перед записью прочитайте шаблон соответствующего документа. Пакет использует UTF-8 Markdown: читаемый текст описывает смысл, YAML рядом с элементом хранит идентичность и связи. Отдельного реестра трассировки нет. Текущий OpenSpec-проект не требуется переносить в этот формат.

## Расположение и разбор

Рабочий корень — `sdd/changes/<change-id>/`: proposal.md, design.md, specs/<capability>/spec.md, tasks.md, state.yaml, state.md, decisions.md, questions.md и review/. Capability может иметь несколько kebab-case сегментов через `/`. Proposal и design общие для изменения; tasks появляется только по разрешенному переходу. Журнал и вопросы создаются при наличии соответствующего содержания по [правилам обсуждения](../../sdd-spec/references/discussion.md).

Необязательные производные материалы: explanation.md, дополнительные документы
в explanation/ и все сохраняемые артефакты диаграмм в archify/. Их размещение,
индекс и актуальность определяет [контракт пояснения](../../sdd-spec/references/explanation.md).
Это обычные Markdown и артефакты без нового document_type или kind USER.
Выбор пояснения, область, исходный манифест и выполненную часть сохраняй
в читаемой части state.

Frontmatter нормативного документа содержит ровно `schema_version: 1`, `document_type` (proposal/spec/design/tasks), `change_id`, `language`; spec дополнительно содержит `capability`, совпадающую с каталогом. Основной текст следует языку проекта, иначе запросу; служебные поля не переводятся. Review/decisions/summary имеют те же общие поля и дополнительные метаданные в своих разделах формата. State хранит их в отдельном state.yaml; state.md содержит прозу по формату обсуждения. Индекс линз имеет собственный frontmatter.

Машинная запись: заголовок, пустая строка и fenced-блок `yaml` с `sdd_record` и `id`. Уровень заголовка записи — `###`, кроме иерархии требований и критериев в spec по [нормативному формату](document-format-normative.md).

Текст записи следует за YAML до следующего заголовка записи или заголовка равного либо более высокого уровня.

Примеры с sdd_record помещайте внутрь внешнего четырехсимвольного fence: парсер не воспринимает их как данные. Иные YAML-примеры не являются записями. Не используйте aliases, anchors, merge keys, пользовательские YAML tags, дубли ключей или неизвестные поля. Новая версия требует обновления проверяющего пакета, а не молчаливой интерпретации.

## Загрузка по операции

Эта общая основа нужна каждому флоу. Дополнительный раздел читай перед
соответствующей операцией; при смене операции догружай только недостающее.
Ссылки ниже — условия загрузки, а не требование открыть весь набор.

| Операция | Дополнительный формат |
|---|---|
| Создаёшь, изменяешь или проверяешь proposal/specs/design, в том числе modify/remove baseline | [Нормативные документы](document-format-normative.md) |
| Переносишь завершённую дельту в текущие спецификации | [Текущие спецификации](current-specifications.md) |
| Создаёшь, изменяешь или проверяешь tasks, покрытие AC, граф или verification | [Задачи и проверки](document-format-tasks.md) |
| Обсуждаешь, сохраняешь или восстанавливаешь state, журнал, Q-записи или премортем | [Обсуждение и восстановление](document-format-discussion.md) |
| Готовишь ревью, читаешь отчёты/USER-записи, проверяешь актуальность, разрешение или gate | [Ревью и согласования](document-format-review.md) |

При resume читай все исходные артефакты по его флоу. Условная загрузка
справочников не сокращает проверку истории, отмен и источников разрешения.
Условия перехода проверяй в выбранном флоу; успешная структура их не заменяет.

## Идентичность и трассировка

ID = префикс + `-` + смысловой slug. Slug: `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`, 1–64 символа. Префиксы: REQ, AC, DEC, TASK, Q, USER, FIND. ID уникальны внутри изменения; FIND исключение — уникальность внутри отчета. Полный ключ находки: `<run-id>/<lens-id>/<FIND-ID>`; между изменениями добавьте `<change-id>/`. Ссылки на другие элементы другого изменения: `<change-id>/<ID>`; они дают контекст, но не покрытие местного критерия или зависимость исполнения.

Поля записей и связи описаны в разделе соответствующей операции из таблицы выше.

## Результат check

Пределы разбора: документ до 4 млн символов, отдельный YAML-блок до 1 млн символов и 100 тысяч токенов, вложенность YAML/Markdown до 64 уровней. Превышение сообщает структурную диагностику вместо неограниченного расхода памяти. Необычные скалярные значения и поврежденные URL также возвращают диагностику; содержимое не исполняется.

JSON содержит schema_version, stage, errors, warnings, discussion_status, review_status, approval_status и сведения о задачах при наличии. discussion_status содержит open_questions, blocking_questions и complete: записи разобраны без повреждений и открытых блокирующих вопросов. Это не оценка полноты выявленных вопросов или авторства журнала. Открытый блокирующий вопрос или повреждение списка/существующего state препятствуют approval_status.ready. Отсутствующие legacy state/questions сами по себе не отменяют прежние согласования.

Диагностика: code/path/element_id/message. Код 0 означает корректную структуру; 1 — структурные ошибки (в том числе повреждённый questions.md); 2 — проверка не выполнена для основного комплекта (нечитаемый вход/неподдерживаемая версия/окружение). Статусы обсуждения, ревью и согласования сообщаются отдельно. Даже ready не является доказательством авторства решений или качества анализа: перед переходом агент проверяет смысл, вопросы и волю пользователя.

Шаблоны содержат примеры: замените sample-change, тексты, даты и пустые манифесты реальными данными. Черновой незаполненный шаблон не означает готовый артефакт.
