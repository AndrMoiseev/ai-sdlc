# Final acceptance

Read [checks and evidence](../references/api-checks.md) and installed `finalize` event help if not already loaded.

1. Read current state. Require every planned task accepted with confirmed commits in the execution branch. Inspect final HEAD, normative basis, required commands, AC mappings, and overall scenarios. Stop writers before the final candidate is captured.
2. Launch fresh final verifiers independent of all authors; use [verifier](../agents/verifier.md). For an ordinary change, register a fresh `final_verifier` per task scope and run `check_run` with stage `final`. When additional mandatory project checks apply, also use the [ordinary final project registry](../references/api-checks.md#ordinary-final-project-checks): after task acceptance, register those checks with `task_id: null`, launch a separate run-level `final_verifier`, and run the registry only at `final`. Both task and project evidence remain mandatory. For refactoring, register whole checks using `checks_register` with `task_id: null`, then register the `final_verifier` and run stage `final` with that same null task scope. The engine combines whole checks with confirmed applicable local and project checks. Prepare whole `setup_required` checks through `check_setup` with null task scope while their approved `setup_task` is running after baseline. Missing setup blocks completion. Evidence binds one clean integrated HEAD, normative manifest and applicable registry. Historical task results cannot replace this run; confirmed retired checks retain their reasons and history without being rerun.
3. On a final defect, establish its task owner before editing and use [repair](repair.md), preserving both budgets. For run-level final failures, submit `repair` with failed `final_checks` IDs, reproducible `defect_evidence` and exact owned `paths`; its task ID identifies the authorized repair owner. An unknown owner or out-of-scope path returns `spec_conflict` to sdd-spec. Reopening an author requires that attribution even for a no-change retry. After changes and necessary commits/reviews, rerun the full applicable final set. Unavailable checks leave a partial result.
4. Apply the [review policy](../references/review-policy.md). Submit `finalize`; omitted `recommendation_decisions` defer all technical debt automatically. Debt alone does not block completion. Inspect the returned result: only complete independent evidence and confirmed acceptance permit run status `completed`.
   Explicit recommendation decisions cover every journal finding_id once, with action `defer` or `reject` and a reason. A `fix` action is outside plan finalization; use the scoped follow-up process below.
5. Regenerate the final summary/dashboard using [progress](../references/progress.md) and report TASK-ID to SHA, confirmed and missing AC, raw evidence links, and limitations. If the run is `completed` and the technical debt journal is nonempty, present a brief summary and link, then request explicit user approval for specific follow-up fixes under the review policy. Preserve the completed plan while awaiting that decision; do not fix debt automatically. Preserve a partial result when blocked. Finish with local commits; push, merge, release and deployment are outside this flow.
