# Final acceptance

Read [checks and evidence](../references/api-checks.md) and installed `finalize` event help if not already loaded.

1. Read current state. Require every planned task accepted with confirmed commits in the execution branch. Inspect final HEAD, normative basis, required commands, AC mappings, and overall scenarios. Stop writers before the final candidate is captured.
2. Launch a fresh explorer and a separate fresh `final_verifier`, both independent of all authors, for each applicable final scope. Use [verifier](../agents/verifier.md).
   - Ordinary change: run every task registry at `final` with its task ID. When additional project checks apply, register the [ordinary final project registry](../references/api-checks.md#ordinary-final-project-checks) after task acceptance and run it separately with `task_id: null`. Both scopes remain mandatory.
   - Refactoring: use `task_id: null` for the confirmed union of whole, task and project checks. Prepare whole `setup_required` checks through their approved `setup_task` after baseline. Confirmed retired checks retain their reasons and history; the final set covers design results, preservation and applicable persistent local criteria.
   Complete registered procedures on the clean integrated HEAD before the aggregate: explorer handles deterministic procedures; final_verifier attests behavioral/manual procedures. Explorer then executes `check_run`. Pass its check-run identity, summary and evidence references through the orchestrator to `final_verifier`. The verifier inspects criteria, implementation and tests and reads needed raw objects with `read_object`. Obtain `verification_result` at stage `final` for every scope before role completion. Use its current verification packet basis and exact evidence references. A newer procedure attempt needs a new aggregate run and conclusion; changed inputs need a fresh pair. Earlier task passes, logs and `role_result` cannot supply this pair.
3. On a final defect, establish its task owner before editing and use [repair](repair.md), preserving both budgets. For run-level final failures, submit `repair` with failed `final_checks` IDs, reproducible `defect_evidence` and exact owned `paths`; its task ID identifies the authorized repair owner. An unknown owner or out-of-scope path returns `spec_conflict` to sdd-spec. Reopening an author requires that attribution even for a no-change retry. After changes and necessary commits/reviews, rerun the full applicable final set. Unavailable checks leave a partial result.
4. Apply the [review policy](../references/review-policy.md). Submit `finalize`; omitted `recommendation_decisions` defer all technical debt automatically. Debt alone does not block completion. Inspect the returned result: only complete current execution and passed final conclusions with confirmed acceptance permit run status `completed`.
   Explicit recommendation decisions cover every journal finding_id once, with action `defer` or `reject` and a reason. A `fix` action is outside plan finalization; use the scoped follow-up process below.
5. Regenerate the final summary/dashboard using [progress](../references/progress.md) and report TASK-ID to SHA, confirmed and missing AC, raw evidence links, separate verification_result references, and limitations. If the run is `completed` and the technical debt journal is nonempty, present a brief summary and link, then request explicit user approval for specific follow-up fixes under the review policy. Preserve the completed plan while awaiting that decision; do not fix debt automatically. Preserve a partial result when blocked. Finish with local commits; push, merge, release and deployment are outside this flow.
