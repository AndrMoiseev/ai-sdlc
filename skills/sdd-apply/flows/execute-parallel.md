# Parallel execution

Read [task events](../references/api-tasks.md), [checks and evidence](../references/api-checks.md), and [role coordination](../references/role-coordination.md) if not already loaded. Require the saved execution instruction and working isolation before admission; no separate parallel request is needed.

1. Request `available`; respect accepted dependencies, `cannot_parallel_with`, shared files and mutable resources. Isolate ports, databases, scratch directories and mutable caches per task. A conflict serializes the affected work; free slots alone do not authorize unsafe overlap.
2. Submit `worktree_create` with `workspace` outside skill collections and the task's `resources`. The script creates a registered worktree and local task branch at the execution branch's current HEAD. Register exact checks and project/CI inventory. Launch/register a fresh [executor](../agents/executor.md), pass the worktree and owned paths, then submit `start`. The script owns task commits; the executor edits only its assigned tree.
3. Before writing, launch/register a task explorer with a baseline checks assignment and request `check_run` at stage `baseline` on the clean starting commit. Record planned absence only for approved setup requirements. Implement in the assigned tree. On executor completion, save `role_result` and submit `candidate` to create the local candidate commit. Give the task explorer a new self assignment for that commit and run the complete registered self-check set. Stop writers during checking and review; after fixes, commit a new candidate and repeat the checks.
4. Give the task explorer a new independent assignment and run stage `independent` in that tree. Pass its saved summary and raw evidence references through the orchestrator to a separate [verifier](../agents/verifier.md), who assesses the original AC, implementation and test sources. Reserve `review_start` for a fresh [reviewer](../agents/reviewer.md), or another role ID in the verifier's context only when their [agent selections](../references/subagents.md) have matching launch identities. Record separate verification and review results. Handle failures through [repair](repair.md).
5. Serialize integration into the execution branch. After worktree checks/review pass, call `transfer` then `integrate`. The script owns complete binary packaging and application. Preserve the worktree and package on conflict or ambiguous recovery. Assign semantic conflict resolution within that task; do not overwrite execution files with worktree copies. For a conflicted recorded intent, a registered executor resolves and stages only the conflicted task paths, returns `role_result`, then the orchestrator calls `integration_resolve` with `intent_id`, resolver `role_id`, and `resolution`. This adopts the resolved working candidate for mandatory integration checks and review.
6. Submit `candidate` to commit the integrated result. Give the task explorer a new current-basis assignment and run `check_run` with stage `integration` on the execution branch even if transfer was clean. Reserve and complete a review of that commit, consuming the same task-lifetime review budget. Then call `commit` to confirm the reviewed commit and `accept` in the execution branch. Task commits and integration commits remain local; publishing is a separate action.
7. After acceptance and all roles stop, call `worktree_remove`. The script verifies ownership, saved transfer, accepted commit and absence of unknown data. Preserve a tree when cleanup is rejected. A cleanup failure cannot revoke a valid commit or justify a duplicate one.
8. Continue eligible work while honoring blockers. Either exhausted task budget stops new work across the whole run: bring active roles to a saved stop, reconcile already-started effects, and ask for the concrete decision described in [repair](repair.md). After all tasks are accepted, use [finalize](finalize.md).

If the user changes execution authorization after this flow was loaded, use [resume](resume.md) to reconcile it. Preserve unintegrated worktree candidates; a rejected transition is not permission to integrate after authorization was withdrawn.
