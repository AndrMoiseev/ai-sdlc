# Parallel execution

Read [task events](../references/api-tasks.md), [checks and evidence](../references/api-checks.md), and [role coordination](../references/role-coordination.md) if not already loaded. Require the saved execution instruction and working isolation before admission; no separate parallel request is needed.

1. Request `available`; respect accepted dependencies, `cannot_parallel_with`, shared files and mutable resources. Isolate ports, databases, scratch directories and mutable caches per task. A conflict serializes the affected work; free slots alone do not authorize unsafe overlap.
2. Submit `worktree_create` with `workspace` outside skill collections and the task's `resources`. The script creates a registered worktree and local task branch at the execution branch's current HEAD. Register exact checks and project/CI inventory. Launch/register a fresh [executor](../agents/executor.md), pass the worktree and owned paths, then submit `start`. The script owns task commits; the executor edits only its assigned tree.
3. Before writing, launch/register a task explorer with a baseline checks assignment and request `check_run` at stage `baseline` on the clean starting commit. Record planned absence only for approved setup requirements. The executor implements in the assigned tree and runs local self-checks as often as needed, without consuming the failure budget. On executor completion, save `role_result` and submit `candidate` to create the local candidate commit. The orchestrator checks project instructions, CI and project configuration and assigns the full project test and static-check set, including applicable task checks, to Explorer at stage `independent`. Explorer executes the exact registered commands and deterministic procedures, preserves outputs and reports failures; it does not choose a subset, interpret acceptance, decide repairs or launch reviewers. Stop writers throughout the batch. A failed, unavailable or stale required check prevents reviewer launch; use [repair](repair.md), freeze the repaired candidate and run the full set again.
4. Only after the complete required set has applicable passing execution evidence, launch two independent [reviewers](../agents/reviewer.md) in parallel: `lens_id: verification` and `lens_id: code`, each in a separate fresh context. Register both observed launches, reserve each lens with `review_start` in the same round and dispatch the frozen source and the [lens contract](../references/review-policy.md#review-lenses). Neither receives the other's report. Verification assesses criteria and test evidence and submits `verification_result` plus its review; code assesses architecture and code quality. Both are read-only and execute no checks. Collect both results before deciding the next action. If verification requests more evidence, extend checks from its current conclusion or `more_checks` round. When code, tests, configuration, dependencies and the approved task remain unchanged, Explorer runs only missing checks, retaining applicable original executions. Start a new verification lens in the next round and reuse the passing code verdict through its original reference. If preparing assertions or resolving the gap changes the candidate, freeze it, run the full required set and launch both fresh lenses. A gap alone does not fabricate a test failure or consume a test-repair cycle. Do not repeat checks or reviews whose basis has not changed.
5. Serialize integration into the execution branch. After worktree checks, the criterion conclusion and both review lenses pass, call `transfer` then `integrate`. The script previews the complete binary patch before applying it. A conflict leaves the main tree unchanged and returns `next: worktree_refresh`. Preserve the package and use [worktree recovery](../references/worktree-recovery.md): apply the task patch to a replacement task worktree based on current execution HEAD, assign its conflicts to a registered executor, then record `worktree_refresh_resolve`. Freeze the resolved candidate, run the full required checks and both fresh review lenses, then create a new transfer. Resolve conflicts only in the task worktree. Preserve both trees and the intent when recovery is ambiguous.
6. Submit `candidate` to commit the recorded integration tree and advance to `committing`, then call `commit` and `accept`. Retain the worktree checks, criterion conclusion and both lens reviews with their original commit references. Transfer does not launch Explorer checks or another review round. The script validates transfer integrity and unchanged evidence without producing a new check result. Preserve the worktree until acceptance so its source can be validated. Task commits and integration commits remain local; publishing is a separate action.
7. After acceptance and all roles stop, call `worktree_remove`. The script verifies ownership, saved transfer, accepted commit and absence of unknown data. Preserve a tree when cleanup is rejected. A cleanup failure cannot revoke a valid commit or justify a duplicate one.
8. Continue eligible work while honoring blockers. Either exhausted task budget stops new work across the whole run: bring active roles to a saved stop, reconcile already-started effects, and ask for the concrete decision described in [repair](repair.md). After all tasks are accepted, use [finalize](finalize.md).

If the user changes execution authorization after this flow was loaded, use [resume](resume.md) to reconcile it. Preserve unintegrated worktree candidates; a rejected transition is not permission to integrate after authorization was withdrawn.
