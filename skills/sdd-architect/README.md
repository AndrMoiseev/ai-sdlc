# SDD Architect

Скилл готовит рекомендации по рефакторингу Kotlin/JVM-проекта на Gradle.
Вы получаете до пяти обоснованных изменений, вопросы для дальнейшей проверки и
объяснение отклонённых находок. Приоритеты: модульность, снижение риска регрессий,
скорость разработки.

Запускайте явно: `$sdd-architect` в Codex или `/sdd-architect` в Claude Code.
Без дополнительного текста скилл разбирает текущий проект целиком:

1. Explorer изучает проект и предлагает настройки. Основной агент сохраняет
   их вместе с планом сбора данных.
2. Другой Explorer собирает свидетельства и рассчитывает все предусмотренные
   метрики, включая производные показатели и выборки. Для недоступных данных
   указывает причину. На этом подготовка измерений завершена.
3. Архитектор выбирает от 8 до 12 связанных групп кандидатов. Каждую разбирает
   отдельный архитектор по исходникам и потребителям; затем ещё один сопоставляет
   диагнозы и готовит карточки рекомендаций. Для небольшой области групп может
   быть меньше.
4. Explorer проверяет карточки и упорядочивает готовые рекомендации по их эффектам.
   Равные эффекты дают равный приоритет; зависимости определяют порядок выполнения.
5. Новый архитектор пишет итоговый отчёт по диагнозам, карточкам и результату проверки.

Между этапами дополнительное подтверждение не требуется. Если уже есть отчёты,
агент проверяет их область и полноту измерений в том же цикле. Для разбора только
заданных материалов или одного изменения есть отдельные запросы в таблице ниже.

Аудит использует текущие исходники. Версия кода, чистота рабочего дерева и совпадение
отпечатков не проверяются и не влияют на готовность рекомендации. Когда материалы
позже попадут в коммит, их связь с ним появится в обычной истории репозитория.
После перерыва скилл читает сохранённое состояние работы и продолжает оставшиеся
задачи по текущим исходникам. Дополнительное исследование начинается с конкретного
вопроса и объяснения, как ответ повлияет на рекомендацию.

Настройки анализа сохраняются в `.sdd/architect/collection.json`. Скилл обновляет
их по области запроса и устройству проекта, а в отчёте объясняет изменения.
Итог находится в `docs/reports/{report-name}/report.md`. Рядом остаются раздельные
метрики, исходные отчёты инструментов, план сбора и логи, диагнозы, карточки,
поручения агентам и их результаты. Имя можно задать в запросе; иначе скилл выберет
его по дате и теме, добавив числовой суффикс при совпадении с другим отчётом.

Для выбранных участков скилл подключает точечную диагностику
[sdd-code-design](../sdd-code-design/README.md). Например, сервис часто меняется,
а причина риска находится в используемом им доменном типе. Архитектор прочитает
и этот тип, проверит его контракты и предложит варианты изменения. Известный риск
или предстоящая задача тоже дают основание для диагностики, даже если метрики
не выделяют код.

Границы модулей задают ответственность пакетов, публичные контракты и направление
зависимостей. Для предложенных границ скилл указывает проверки ArchUnit.
Высокое число само по себе не обосновывает рефакторинг: стабильный общий тип может
остаться без изменений. При наличии только отчётов результатом будут гипотезы
и адресные вопросы к исходникам. В каждом отчёте видна исследованная область и
то, что осталось непроверенным; экономию времени по метрикам скилл не обещает.

В AI SDLC такой разбор предшествует планированию. Выбранную рекомендацию можно
передать в [sdd-spec](../sdd-spec/README.md) для подготовки плана рефакторинга.
Обязанности архитекторов и Explorer заданы в [sdd-shared](../sdd-shared/README.md).
Сам `sdd-architect` заканчивает работу отчётом; реализация требует отдельного поручения.

| Задача | Пример запроса | Результат |
| --- | --- | --- |
| Полный цикл по умолчанию | `$sdd-architect` | Метрики текущего проекта, диагностика выбранных участков и очередь рекомендаций |
| Полный цикл для выбранной области | `$sdd-architect собери доступные метрики этого Kotlin/Gradle-проекта и предложи первые изменения. Начни с пакетов заказов и расчёта цен.` | Измерения, проверенные кандидаты и рекомендации для указанной области |
| Разбор готовых отчётов | `$sdd-architect используй отчёты из указанного каталога и проверь находки по текущим исходникам. Особенно интересуют циклы пакетов.` | Проверка области и полноты измерений, диагнозы и варианты изменений |
| Отчёты без исходников | `$sdd-architect доступны только detekt, граф зависимостей и история. Определи, что стоит проверить в коде.` | Очередь проверок с условиями принятия решения |
| Сравнение предложений | `$sdd-architect сравни рекомендации R1 и R2 из отчёта pricing-audit по их доказательствам и текущим исходникам. Объясни, с какой начать.` | Сопоставление последствий, затрат и зависимостей; обоснованный порядок или равный приоритет |
| Разбор изменения | `$sdd-architect оцени изменение между main и текущей веткой, включая потребителей за пределами diff.` | Рекомендации по текущему коду затронутой области и его потребителям |
| Проверка выполненного рефакторинга | `$sdd-architect проверь эффект рекомендации R1 после переноса расчёта цены. Используй исходный отчёт и критерии приёмки из карточки.` | Проверка поведения, границ и связанных метрик; пересмотр неподтверждённых ожиданий |
| Продолжение после перерыва | `$sdd-architect продолжи аудит pricing-audit из docs/reports/pricing-audit и заверши отчёт.` | Продолжение оставшихся задач по текущим исходникам и ссылка на итоговый отчёт |
