# SDD Architect

Скилл исследует архитектуру Kotlin/JVM-проекта на Gradle и предлагает направления
рефакторинга для проработки с человеком в [sdd-spec](../sdd-spec/README.md).
Вы получаете отчёт со свидетельствами, общий план работы с техдолгом и числовой
статус проекта с разбивкой по архитектурным модулям.

В отчёте видны готовые рекомендации, вопросы для проверки и отклонённые находки.
Приоритет учитывает модульность, снижение риска регрессий и затрат на изменение.
Вес каждого эффекта задаётся в настройках. Затраты включают токены агентов,
работу человека и ожидание проверок до принятого результата.

Запускайте явно: `$sdd-architect` в Codex или `/sdd-architect` в Claude Code.
Без дополнительного текста скилл разбирает текущий проект целиком:

1. Основной агент читает текущий план техдолга. Explorer изучает проект и предлагает
   конфигурацию аудита. Основной агент сохраняет её в папке аудита вместе с планом сбора данных.
2. Другой Explorer запускает сбор одной командой проекта из `.sdd/settings.json` и рассчитывает все предусмотренные
   метрики. Скрипты готовят предварительные группы кандидатов и очередь исследования,
   в пределах заданного бюджета. Отложенные группы и пробелы в данных остаются видны.
3. Архитектор уточняет подготовленные группы по исходникам и контексту задачи:
   объясняет объединения, разделения и дополнительные кандидаты. Explorer запускает
   `metrics.py evidence`, чтобы передать архитектору каждой группы сигналы,
   значения измерений и ограничения. По запросу скрипт находит коммиты, затронувшие
   оба указанных файла, или прямые зависимости классов. Архитектор проверяет причину
   по исходникам. Затем другой архитектор сопоставляет диагнозы и готовит карточки рекомендаций.
4. Explorer проверяет карточки и упорядочивает готовые рекомендации по их эффектам.
   Равная сумма оценок даёт равный приоритет, даже если эффекты различаются.
   Зависимости остаются условиями для обсуждения.
5. Новый архитектор пишет итоговый отчёт по диагнозам, карточкам и результату проверки.
6. Основной агент добавляет новые задачи в план и сообщает, какие карточки остались
   только в аудите. Для уже известных проблем он использует прежний разбор, пока
   новые основания не требуют пересмотра.
7. После успешного завершения всех этапов агент полностью заменяет статус проекта
   результатами этого аудита. Если аудит прервался раньше, прежние значения остаются.

Между этапами дополнительное подтверждение не требуется. Полный аудит всегда получает свежие отчёты. Для разбора только
заданных материалов или одного изменения есть отдельные запросы в таблице ниже.

Для полного аудита нужны все источники измерений, в том числе настроенное покрытие
и успешно выполненные тесты. Если источника нет, данные неполны или инструмент
завершился с ошибкой, агент останавливает аудит и предлагает сначала решить
конкретную проблему. Ограниченный разбор выбранных материалов запускается отдельным
запросом и не обновляет общий статус.

Аудит использует текущие исходники. Версия кода, чистота рабочего дерева и совпадение
отпечатков не проверяются и не влияют на готовность рекомендации. Когда материалы
позже попадут в коммит, их связь с ним появится в обычной истории репозитория.
После перерыва скилл читает сохранённое состояние работы и продолжает оставшиеся
задачи по текущим исходникам. Дополнительное исследование начинается с конкретного
вопроса и объяснения, как ответ повлияет на рекомендацию.

Область анализа и пути явно переданных отчётов сохраняются в `collection-input.json` внутри папки
аудита. Все пути в этой конфигурации заданы относительно каталога проекта. При новом
запуске агент проверяет условия заново; прежняя конфигурация помогает исследованию,
но сама по себе не задаёт ограничения нового аудита.

Настройки проекта аудит только читает. Их изменение принадлежит отдельному процессу
[sdd-setup](../sdd-setup/SKILL.md), который запускает пользователь. Согласие на правку
во время аудита не расширяет полномочия `sdd-architect`. Если для запроса нужны свежие измерения, а команда или описание отчётов в
`architect.collection` отсутствуют, аудит останавливается и просит запустить
`sdd-setup`. Готовые отчёты и результаты предыдущего сбора можно разбирать без этой настройки.

Пороги, веса и численные ограничения аудит читает из
`.sdd/architect/analysis-policy.json`; отсутствующие значения берёт из настроек скилла
по умолчанию. Каждый аудит сохраняет применённые значения.
[Политика анализа](references/analysis-policy.md) описывает доступные параметры.
У числа параметров метода есть собственный порог анализатора: минимальный порог
detekt нужен для сбора наблюдений.

Каждый аудит получает папку `memory/tech-debt/audits/{date-time}/`, например
`2026-11-14T14-30-00Z`. Там лежат `report.md`, метрики, исходные отчёты инструментов,
план сбора, логи, диагнозы, карточки и поручения агентам с их результатами.
Прерванный аудит продолжается в своей папке; новый получает другую дату и время.

Рядом с папками аудитов лежат `memory/tech-debt/status.json` и `status.md`.
В JSON сохранены числа, область измерения и параметры расчёта. Markdown собирается
из этих данных по шаблону. Нажмите на название показателя, чтобы открыть его
описание, интерпретацию и источники в соседнем `status-indicators.md`.
Команда публикации обновляет все три файла в конце успешного полного аудита.

Статус включает статистику scc по файлам и строкам, структурную разделимость D,
локальную поддерживаемость L, оценку дублирования U и общий индекс Q. Отдельно
показаны циклы, распространение зависимостей, сложный код, покрытие, методный CRAP
и совместные изменения файлов. Каждый модуль получает собственный расчёт.
Рядом видны связи и повторы через его границы; среднее
оценок модулей не заменяет оценку проекта. [Описание показателей](references/quality-indicators.md)
задаёт их смысл и ограничения.

Общий план находится в `memory/tech-debt/plan/plan.md`. Это таблица задач по
приоритету со ссылками на карточки `tasks/{task-name}/task.md`. В неё автоматически
попадают только новые `ready` и `needs_check`. Все `needs_check` идут после всех
`ready`, даже если возможный эффект ещё не проверенной задачи выше. Карточки
`observe` и `rejected` остаются в аудите; в конце агент сообщает о них и даёт ссылки.
Лимит рекомендаций в отчёте не ограничивает размер общего плана.

Вы можете в любой момент изменить оценку задачи, её статус и приоритет внутри
группы. Отредактируйте план или поручите это агенту: новый аудит для такой правки
не нужен. Последующие аудиты сохраняют ваши решения и содержание существующих
карточек. Если новые свидетельства противоречат прежней оценке, агент сообщит вам
об этом. Пересматривать ли оценку, решаете вы. Историческая карточка аудита останется на месте.

Для выбранных участков скилл подключает точечную диагностику
[sdd-code-design](../sdd-code-design/README.md). Например, сервис часто меняется,
а причина риска находится в используемом им доменном типе. Архитектор прочитает
и этот тип, проверит его контракты и предложит варианты изменения. Известный риск
или предстоящая задача тоже дают основание для диагностики, даже если метрики
не выделяют код.

Границы модулей задают ответственность пакетов, публичные контракты и направление
зависимостей. Аудит объясняет, какую ответственность или зависимость стоит изменить.
Подробные контракты, состав пакетов и проверки ArchUnit прорабатываются в `sdd-spec`.
Высокое число само по себе не обосновывает рефакторинг: стабильный общий тип может
остаться без изменений. При наличии только отчётов результатом будут гипотезы
и адресные вопросы к исходникам. В каждом отчёте видна исследованная область и
то, что осталось непроверенным; экономию времени по метрикам скилл не обещает.

Каждая рекомендация оформлена как текстовая карточка с шестью разделами:

1. Проблема, затронутый участок и сценарий.
2. Свидетельства и их ограничения.
3. Механизм проблемы и проверенное альтернативное объяснение.
4. Предлагаемое направление; схема, если она помогает его понять.
5. Ожидаемые эффекты, затраты, риски и сравнение с альтернативами.
6. Вопросы для `sdd-spec`, требуемое поведение и признаки достижения эффекта.

В AI SDLC такой разбор предшествует проектированию и планированию. Готовая
рекомендация содержит достаточно оснований для обсуждения направления с человеком.
В `sdd-spec` вы выбираете решение, уточняете его устройство и готовите план рефакторинга.
Обязанности архитекторов и Explorer заданы в [sdd-shared](../sdd-shared/README.md).
Сам `sdd-architect` заканчивает полный аудит отчётом, обновлением плана и статуса;
реализация требует отдельного поручения.

## Идея развития

Сейчас зависимости собирает jdeps по скомпилированным JVM-классам. Идея развития -
анализировать связи непосредственно в Kotlin и определять, на какие объявления
ссылается каждый вызов или тип. Это должно точнее связывать исходные декларации,
в том числе при встраивании inline-функций. Для выбора инструмента потребуется
сравнить графы на реальных проектах и оценить поддержку их версий Kotlin.

Иерархия зависимостей DRH, по которой рассчитывается D, строится по описанию
ArchDRH-Re. Проверка на реальных проектах может показать, где нужно доработать
построитель и уточнить интерпретацию D.
