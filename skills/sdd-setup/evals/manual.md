# Проверки sdd-setup

Применяй этот документ только при изменении или проверке самого скилла.

Детерминированные тесты, включая сериализацию обеих сред:

```text
uv run --locked --script "<skill-root>/scripts/test.py" -q
```

Задавай уникальный абсолютный `--basetemp` вне проекта и коллекций скиллов.
Первый прогон после изменения среды выполняй с `-x`. Полный обязательный набор:
все тесты `tests/` последовательно и структурная проверка conductor
`scripts/eval_skill.py <skill-root>`. Измеряй общее реальное время с подготовкой
и установкой зависимостей; лимит одного прогона — 120 секунд. При превышении
останови дерево процессов и сообщи результат, не продолжая работу без нового указания.

`test_project_audit.py` проверяет решения по результатам mise, ошибки/таймаут,
повторную проверку и CLI через подставленные адаптеры, без установки утилит,
сети и новых процессов. Хранение отчёта проверяется в существующей I/O-фикстуре.

Для проверки установки с пустым онлайн-кэшем включи `SDD_SETUP_RUNTIME_TESTS=1`
на время тестового процесса. Эти тесты запускают uv и могут обращаться к PyPI;
они не запускают модели. Нативный Claude Code проверяется отдельно ниже.

## Поведенческие сценарии

Запускай проверки с агентом только после отдельного явного согласия пользователя.
Общее поручение изменить или проверить скилл не разрешает эти запуски.
На каждый сценарий действует лимит 1200 секунд с подготовкой и сохранением
результатов; по таймауту останови его дерево процессов и отметь неуспех.

В [evals.json](evals.json) девять сценариев. Для каждой пары скилл/контроль создай
свежий каталог вне репозитория и коллекций скиллов. Кандидату скопируй полные
`sdd-setup` и `sdd-shared` рядом, сохрани manifest зависимостей вне контекста
исполнителя. Для сценариев настройки архитектурного сбора добавь соседний
`sdd-architect` с его средствами чтения отчётов. Контролю не раскрывай скилл, ответы или критерии. Используй один
хост и модель; записывай недоступную телеметрию как null.

Для микротестов проведи пять независимых повторов fresh-project с инструкциями
и пять без них. Это проверяет формирование диалога; не называй такой тест
подтверждением фактической записи или выбора модели хостом. В полном сценарии
после таблицы ответь «принимаю показанные пресеты» и проверь файлы. Для
stale-plan меняй settings после plan до apply. Discovery пропускается:
скилл вызывается явно.

Для `full-setup` подготовь рабочую mise и неполный набор общих инструментов.
Проверь, что недостающие инструменты установлены до определения стека.
В Kotlin/JVM-сборке на Gradle проверь обязательность обеих интеграций при
сохранении текущих настроек правил. Подготовь 12 изменяемых правил для ktlint
и отдельные расхождения для detekt. Включи два параметра одного правила и унаследованные
совпадения. Первый вопрос должен содержать только число 12 и предложение принять
профиль. При согласии проверь применение всего профиля без поштучных вопросов.
В варианте с отказом ожидай группы 1–5, 6–10 и 11–12. Ответь только за четыре
позиции первой группы и проверь, что агент уточнил пятую. До последнего решения
файлы правил должны сохранять исходное содержимое. По завершении сверь результат
по каждому принятому и отклонённому ключу. Оставь в проекте исходник, нарушающий
принятое правило. Проверь, что после провала ktlint агент назвал конфликт, сохранил
шаг открытым и не начал detekt. После исправления ожидай успешную проектную
проверку, отметку ktlint и паузу. В новой сессии продолжи с отдельного вопроса
по detekt. При запросе аудита проверь, что отметки остаются прежними.
Для остальных сценариев:
`audit-only-missing` и `repair-mise` — отсутствует и в PATH, и в известных местах;
`failed-mise` — найденный файл возвращает ошибку; `mise-outside-path` — рабочая
установка вне PATH. Условия задавай в изолированной среде, не меняя рабочую машину.
Настоящую установку проверяй только в одноразовой среде с разрешённой установкой;
подставленные ответы установщика проверяют диалог, а не реальную установку mise.
Отдельно пройди отказ пользователя от установки и успешный повтор полного
вызова: отказ оставляет этап незавершённым, повтор не переустанавливает mise.

Для JVM проверь настройку по проекту с toolchain 21 и целевым байткодом 17.
После JUnit 5 проверь шаг JaCoCo на проекте с приложением, библиотекой без
собственных тестов и отдельным модулем интеграционных тестов. Подай сводный XML
без библиотеки и проверь, что шаг остался открытым. После исправления найди
в XML класс библиотеки, вызванный интеграционным тестом, и класс, который ни один
тест не вызывал. Проверь, что сбор для аудита и `mise run test` воспроизводят тот же охват.
В отчёте должен фигурировать JDK 21 со ссылкой на источник версии.
Если wrapper стартовал на новом JDK, но тесты прошли на 21, предложение
обновиться преждевременно. При успешной сборке и тестах на новом JDK выбери
«оставить текущую» и проверь, что в рабочем проекте остался JDK 21.

## Нативный Claude Code — запуск пользователем

Работай в отдельном временном проекте. Установи полные `sdd-setup` и `sdd-shared`
рядом в `.claude/skills`, сохрани обычные разрешения среды. Нужны uv и доступ к
моделям, выбранным в диалоге. Не используй реальные ключи в тестовых файлах.

1. В новой сессии вызови `/sdd-setup`. Проверь подготовку mise и семи инструментов
   до определения стека и первого запуска детального аудита.
   Для Kotlin/JVM на Gradle после настройки сбора ожидай шаг `mise-tasks`.
   Проверь, что ошибка ktlint останавливает `lint` до detekt и блокирует `build` и
   `test`. После исправления проверь чистую сборку и свежий отчёт покрытия после
   тестов. В остальных проектах оба шага пропускаются. Затем ожидай шесть общих имён
   и пресеты Claude из `assets/defaults.json`, с выбором модели и effort.
2. Прими показанные пресеты. Проверь шесть `.claude/agents/*.md` и
   `.sdd/settings.json`. Повтори setup с сохранением значений: содержимое
   и время изменения файлов должны остаться прежними.
3. Измени model одного агента, оставив effort. Проверь сохранение тела, комментариев,
   tools и прочих полей. Если определение пользовательское, должна появиться
   только проектная копия.
4. Настрой тем же мастером проект, уже настроенный в Codex. Назначения ролей
   сохраняют имена, TOML-файлы — байты; `.claude/agents` получает пресеты Claude.
5. Проверь агент из plugin/managed/CLI каталога без локального файла. При
   сохранении имени дубликат не создаётся. Попытка изменить модель предлагает
   новое проектное имя или проверку реального источника.
6. Проверь новые имена в Agent tool. При необходимости перезапусти сессию.
   Запусти выбранному агенту задачу «17 + 25» и сохрани реальную трассу,
   имя и модель/effort из метаданных хоста. Самоопределение агента не является
   проверкой. Если метаданные скрыты, отметь их как неизвестные.

В отчёте запиши версию Claude Code, способ установки, пресеты/замены, вывод
inspect/plan/apply, исходный и конечный каталог, изменённые файлы и runtime-поля.
Эти сценарии не выполняются Python-тестами.

## Источники для сопровождения адаптеров

Схема Codex сверена с [документацией custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents),
формат и приоритеты Claude Code — с [документацией subagents](https://code.claude.com/docs/en/sub-agents).
При изменении адаптеров сверяй их с этими источниками.
При разработке Claude Code на машине разработчика не запускался; сценарии
нативной проверки приведены выше.
