# SDD Setup

Запускай по явному `$sdd-setup`, `/sdd-setup` или выбору этого скилла пользователем.
Последующие ответы продолжают настройку без повторного вызова.

## Выбор шагов и продолжение

При `$sdd-setup`, «подготовь проект» или «продолжай» прочитай
`.sdd/settings.json → setup.completed_steps` по [правилам прогресса](references/api.md#progress).
Покажи порядок применимых шагов и начни с первого без отметки. Пропускай
завершённые шаги. Новый ID в текущем порядке автоматически попадает в маршрут.
Неприменимые шаги пропускай без записи. До подготовки mise и общих инструментов
достаточно знать корень и рабочую среду; затем уточни применимость по сборке и CI.

- «Только аудит» — проверь фактическое состояние по [правилам аудита](references/project-audit.md),
  независимо от отметок. Этот вызов только читает проект и не сбрасывает прогресс.
- «Обнови все настройки» — одним действием сбрось все отметки до первого шага.
- «Обнови ktlint и detekt» или другое явное указание настроек — сразу сбрось
  отметки **всех** названных шагов и выполни выбранные в общем порядке.
  Индивидуальные поручения («настрой detekt», «только роли», «настрой сбор»,
  «установи mise») относятся к соответствующему шагу. «Проверь и исправь требования»
  охватывает шаги от mise до TypeSpec. Список запроса действует только для этого
  вызова. Следующее «продолжай» снова использует общий порядок и сохранённые отметки.

## Выполнение шага

1. Установи текущее состояние затронутых файлов. Учитывай уже внесённые правки
   открытого шага при возобновлении. Не приписывай шагу посторонний diff пользователя.
2. Выполни настройку и подтверди критерий из таблицы для всех применимых модулей,
   сборок или пакетов. Проверки выполняй и при нулевом diff. Для отдельного шага
   JVM используй `jvm-step` из [API](references/api.md#jvm-step); полный `audit`
   используй для запроса аудита. Получай только сведения, нужные текущему шагу.
3. При конфликте, провале или пропуске обязательной проверки оставь шаг открытым.
   Назови команду, модуль, файл или правило, фактическую ошибку и возможное
   исправление. Если нужно выбрать между правкой кода и пересмотром правила,
   передай выбор пользователю. После исправления повтори проверку именно этого шага.
4. Только после успеха запиши ID через `progress --complete`. Для ktlint и detekt
   передай фактические коды проектных проверок через `--check-exit-code`. Если шаг менял файлы
   проекта, передай `--project-changed`, сообщи результат проверки и **назови
   следующий применимый шаг, затем закончи вызов**. На последнем шаге сообщи
   о завершении. Коммит и момент продолжения выбирает пользователь.
5. Если единственная запись — отметка о завершении, переходи к следующему шагу
   текущего вызова. Содержательные правки `.sdd/settings.json`, в частности
   `architect.collection` и назначения ролей, считаются изменениями проекта.
   Сброс отметок, временные отчёты и обычные продукты сборки сами по себе паузы не требуют.

## Порядок и критерии завершения

| ID | Применимость | Проверка перед записью отметки |
| --- | --- | --- |
| `mise` | Все проекты | `mise --version` через PATH рабочей среды успешно выводит версию. При необходимости [восстанови доступ](references/project-audit.md). |
| `common-tools` | Все проекты | Каждая команда из [каталога](assets/required-tools.json) предоставляется проектной mise и запускается из корня. Установи недостающее до определения стека. |
| `jdk` | JVM | [Требуемые проектом JDK](references/java.md) предоставляют нужные java и javac для каждой toolchain. |
| `gradle` | JVM | [Gradle](references/project-audit.md#gradle-для-jvm) доступен проектным способом в каждой сборке. После обновления проверь штатный запуск. |
| `junit5` | JVM | [Jupiter 5](references/jvm-test-dependencies.md) настроен. После миграции штатные задачи проходят и выполняют все перенесённые тесты. Для пустого набора проверь движок и конфигурацию. |
| `jacoco` | JVM | [Сводный XML JaCoCo](references/jacoco.md) после успешного прогона тестов содержит измеряемые производственные классы всех JVM-модулей, включая модули без собственных тестов. |
| `archunit` | JVM | [Тестовая зависимость ArchUnit](references/jvm-test-dependencies.md) разрешается в последний стабильный релиз. |
| `ktlint` | Kotlin/JVM | Проведи [настройку ktlint](references/ktlint.md) и отдельный выбор правил. Штатная проверка успешно прошла с выбранными настройками на исходниках всех затронутых модулей. |
| `detekt` | Kotlin на Gradle | Проведи [настройку detekt](references/detekt.md) и отдельный выбор правил. Штатные задачи успешно проверили исходники всех затронутых модулей с выбранной конфигурацией. |
| `typespec` | Все проекты | Проверь [TypeSpec](references/typespec.md) на проектной Node.js. Зафиксируй выбор пользователя; после выбранной правки подтверди версию и успешную компиляцию имеющихся спецификаций. |
| `collection` | Kotlin/JVM на Gradle | Команда сбора успешно сформировала шесть проверенных отчётов, а настройки сбора записаны. |
| `mise-tasks` | Kotlin/JVM на Gradle | Из корня проекта работают [задачи mise](references/mise-tasks.md) `format`, `lint`, `build` и `test`. Сборка и тесты зависят от успешного `lint`, тесты формируют отчёт JaCoCo. |
| `roles` | Полный маршрут или явный выбор | Назначения для текущего хоста прошли проверку после записи согласно шагу ролей ниже. |

### Выбор правил ktlint и detekt

1. Подготовь пронумерованный список правил, у которых меняется действующее
   значение. Объедини параметры одного правила и перечисли затронутые модули
   в его строке. Самостоятельный переключатель набора или общую настройку
   с расхождением учитывай отдельной строкой. Совпадающие унаследованные
   значения исключи из счёта. Каждый шаг имеет собственный итог и нумерацию.
   Обсуждай только текущий инструмент. Переход к detekt подчиняется общему
   правилу паузы после успешно завершённого ktlint.
2. В первом сообщении о правилах укажи только число и задай вопрос:
   «Количество изменяемых правил — N. Принять стандартные настройки целиком?»
   Названия, значения и примеры оставь
   для разбора. При нуле сообщи, что расхождений нет, и заверши выбор без записи.
3. При согласии примени рекомендованные настройки всего профиля и проверь результат.
   Одного ответа достаточно для всех правил.
4. При отказе от пакета покажи первые пять расхождений. Для каждого укажи номер,
   инструмент, правило и модули, объясни назначение правила, действующее значение
   и его источник, рекомендацию и её эффект на конкретном примере. Предложи
   по номерам принять рекомендацию или оставить текущее значение. Если у правила
   несколько параметров или разные значения по модулям, разреши выбрать их отдельно.
5. Дождись решения по всем показанным расхождениям. При неполном ответе уточни
   только пропущенные позиции. Затем покажи следующие пять, в последней группе —
   оставшиеся. Сохраняй нумерацию и принятые решения между ответами. Явный ответ
   для всей показанной группы покрывает каждую её позицию. Когда решения есть
   по всему списку, примени только выбранные изменения и проверь результат.

## Шаг collection. Сбор для архитектурного аудита

Для Kotlin/JVM-проекта на Gradle настрой одну проектную команду по
[правилам сбора](references/collection.md). Для проекта вне области этого аудита
отметь этап как неприменимый. Критерий завершения — проверенные зависимости
в mise, успешный запуск команды, шесть пригодных отчётов и запись в `.sdd/settings.json`.
Создание или изменение задачи, сборки и настроек mise предварительно согласуй
с пользователем. При отказе укажи, что мешает сбору.
После проверки выполни общий порядок завершения шага.

## Шаг roles. Настройка агентских ролей

1. Прочитай условия запуска для ролей. Определи текущую агентскую среду
   по контексту хоста. Выполни `inspect`
   с `--output` по [интерфейсу скрипта](references/api.md). Готово, когда получены
   все роли из общего контракта, текущие значения, пресеты и сведения об агентах.
2. Проведи [диалог настройки](references/dialogue.md) по текущим значениям и
   пресетам из `inspect`. Зафиксируй решение для каждой роли и модель/effort
   каждого уникального агента; согласие на показанную группу покрывает всю группу.
3. Составь request со ссылкой на inspection и выполни `plan --output`.
   Скрипт включит создание отсутствующих агентов в родном формате текущей среды.
   Покажи решения и точный diff из сводки; полные данные храни в файлах.
   Если план соответствует ответам, примени его без дополнительного запроса
   разрешения. Если появился новый существенный выбор, уточни только его.
4. Выполни `apply` по [интерфейсу скрипта](references/api.md).
   Проверь список записанных файлов и повторный `inspect`. Для Claude Code
   сверяй обнаружение с живым каталогом по [правилам сред](references/hosts.md).
   Сообщи, какие роли и агенты настроены, и отдели проверку файлов от проверки
   фактического запуска модели.

### На границе записи ролей

- Все роли из общего контракта имеют явное решение пользователя.
- Модель и effort каждого уникального агента показаны и выбраны.
- Новый вариант имени заново проверен через `inspect --names`.
- План построен из свежего снимка; неизвестные поля проекта сохраняет скрипт.

Записывай настройки ролей только через скрипт. При изменении файлов после обсуждения
повтори чтение и согласуй только изменившиеся значения: устаревший план не
перезаписывает более свежие настройки. Ошибка конфигурации требует исправления
конкретной ошибки, а не замены файла пресетом.

## Область настройки

Скилл подготавливает проект к агентной разработке и единолично изменяет настройки
проекта для `sdd-*`. Настройки зависимостей mise относятся к командам проекта.
Служебные команды скиллов следуют локальным инструкциям проекта, включая `AGENTS.md`.

Установка mise затрагивает рабочую систему пользователя. Остальные глобальные
настройки среды, права доступа, провайдеры, ключи и MCP не входят в эти этапы.
Аудит не зависит от формата агентского хоста. Для настройки ролей неизвестного
хоста выясни формат и поддерживаемый адаптер; скрипт поддерживает Codex и Claude Code.

В завершение перечисли пройденные этапы, подтверждённые требования, исправления
и оставшиеся препятствия. Успешная настройка ролей сама по себе не подтверждает
соответствие проекта требованиям.

Только при изменении самого скилла читай [проверки разработчика](evals/manual.md).
