# JDK для JVM-проекта

## Версия проекта

Определи, какие модули собирают или запускают код на JVM. Проверь цели сборки,
исходники и команды CI. Учитывай Java, Kotlin/JVM, Scala, Clojure и другие языки
JVM независимо от системы сборки. Отдельный пример, фикстура или файл Gradle
сам по себе ещё не устанавливает целевую платформу продукта.

Проследи, откуда штатная сборка получает JDK. Проверь Gradle toolchains и
convention plugins, Maven toolchains и parent POM, настройки sbt, проектные
файлы версий, образы сборки и CI. Раскрой переменные и наследуемые настройки.
Запиши файл и значение, включая поставщика и точную сборку, если проект их задал.
`--release`, `targetCompatibility` и `jvmTarget` задают целевой байткод.
Например, при toolchain 21 и `--release 17` для компиляции требуется JDK 21.
Версия системной Java сама по себе ничего не говорит о требованиях проекта.

Если у модулей разные toolchains, установи нужные версии в соответствующих
областях проектной конфигурации mise и проверь каждую. Учитывай отдельно JVM
запуска сборщика, компилятора и тестов. Если источники одной и той же версии
противоречат друг другу или задают только диапазон без выбранного JDK, проверь
рабочую конфигурацию CI. Если выбор остаётся открытым, укажи источники и уточни
версию у пользователя. До этого аудит с `--jvm` оставляет требование невыполненным.

В режиме исправления используй `use_command` из требования `java` для установки
версии проекта. Повтори `jvm-step jdk` с тем же запросом JDK и проверь `java -version`
и `javac -version` в среде mise. В режиме «только аудит» сообщи результат
и нужные действия. [Настройка JDK в mise](https://mise.jdx.dev/lang/java.html)

## Когда предложить обновление

1. Найди доступный более свежий выпуск у подходящего проекту поставщика.
   Сверь его с ограничениями wrapper, плагинов, зависимостей и среды запуска.
   При известном препятствии опиши его и продолжай настройку на версии проекта.
2. Проверь тот же исходный код и штатные команды CI на конкретном выпуске JDK.
   Подойдёт успешный прогон CI для этой ревизии с подтверждённой версией.
   Иначе используй временную копию вне рабочего проекта и задай JDK через
   `mise exec java@<точный-выпуск> -- <команда>`. Выполни чистую сборку
   и штатные тесты затронутых модулей. Если сборка закрепляет JDK отдельно,
   выбери проверяемый выпуск в toolchain временной копии. Сохрани целевой байткод и параметры
   продукта. В режиме «только аудит» используй имеющиеся результаты проверок.
3. По журналам сборки подтверди JDK компилятора и тестовых процессов.
   Gradle daemon и Maven toolchains могут выбрать собственный JDK. Успех
   сборки на старой toolchain, пропущенные тесты или один вывод `java -version`
   оставляют совместимость неподтверждённой. При сбое или отсутствии проверки
   сообщи причину и заверши настройку на исходной версии.
4. После успешной проверки покажи исходную и проверенную версии, команды и
   результаты. Предложи оставить текущую версию или перейти на проверенную.
   Изменяй настройки рабочего проекта для обновления только после выбора
   пользователя. После перехода повтори `jvm-step jdk` с принятой версией.

Проверяй ограничения для тех версий сборщиков, которые использует проект.
[Gradle toolchains](https://docs.gradle.org/current/userguide/toolchains.html) ·
[Maven toolchains](https://maven.apache.org/guides/mini/guide-using-toolchains.html)
