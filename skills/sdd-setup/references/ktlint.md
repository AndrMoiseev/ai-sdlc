# Автоформатирование Kotlin/JVM через ktlint

1. Для каждого Kotlin/JVM-модуля обязательна работающая проектная интеграция ktlint.
   Определи модули по сборке. Найди команду запуска, версию движка и область файлов `.kt` и `.kts`.
   У Gradle-плагина и самого ktlint свои версии. Учитывай convention plugins,
   Spotless, команды CI и подключённые наборы правил. Встроенная обёртка detekt
   проверяется отдельно на следующем шаге.
2. Используй проектный способ запуска. Для новой интеграции на Gradle предложи
   `org.jlleitschuh.gradle.ktlint` в Kotlin/JVM-модулях, выбери совместимый с
   проектом выпуск плагина и закрепи версию движка через `ktlint.version`.
   Для другой системы сборки используй её интеграцию либо проектную команду
   mise с закреплённым CLI. Покажи команду проверки и команду форматирования.
   Если интеграция отсутствует или не работает, отметь обязательное требование
   как невыполненное. В режиме настройки подключи или восстанови интеграцию.
3. Подготовь профиль настроек для версии проекта. Для движка 1.8.0 возьми
   [шаблон .editorconfig](../assets/ktlint-1.8.0.editorconfig). Для новой интеграции
   предложи эту версию при совместимости с проектом.
   Для уже выбранной другой версии сверь идентификаторы, зависимости правил и
   значения стиля по документации и исходникам соответствующего релиза. Для
   ktlint 1.x получить значения по умолчанию можно штатной командой
   `ktlint generateEditorConfig --code-style=ktlint_official` в чистом каталоге.
   Для сверки возьми поддерживаемые правила шаблона и их стандартные параметры.
   Профиль включает автоисправления, в том числе удаление неиспользуемых импортов,
   преобразование тел функций и упрощение строковых шаблонов. В этом профиле
   `expression-operand-wrapping` включён индивидуально, `no-unit-return` выключен,
   чтобы сохранять указанный автором `: Unit`, а `standard:max-line-length`
   задаёт лимит 140 символов. Правила переноса
   используют этот лимит при форматировании, а ktlint сообщает об оставшихся
   превышениях. Проверки имён выключены.
4. Сравни шаблон с эффективной конфигурацией каждого модуля. Проверь родительские
   и вложенные `.editorconfig`, порядок подходящих секций и переопределения
   плагина. Собери точечные расхождения, включая явно включённые правила вне
   профиля и сторонние наборы. Индивидуальный ключ имеет приоритет над набором.
   В режиме «только аудит» заверши шаг списком расхождений и предлагаемых правок.
5. В режиме настройки проведи [выбор правил](../SKILL.md#выбор-правил-ktlint-и-detekt).
   После завершения выбора объедини принятые ключи и их параметры
   с проектным `.editorconfig`. Для принятого профиля закрепи также совпадающие
   унаследованные значения. Сохрани комментарии, непринятые значения и прочие
   секции. В смешанном репозитории размести секцию `[*.{kt,kts}]` в области
   Kotlin/JVM-модулей. Разреши конфликтующие переопределения в месте их действия.
6. Запусти штатную проверку в затронутых модулях (для указанного Gradle-плагина
   это `ktlintCheck`). Подтверди успешный результат на исходниках каждого
   затронутого модуля с итоговым профилем. При конфликте или нарушении укажи
   правило, модуль, файл, команду и сообщение. До устранения причины и успешной
   повторной проверки оставь шаг открытым, к detekt не переходи.
   Принятые правила проверь на временном примере с той же конфигурацией.
   Для полного профиля проверь удаление неиспользуемого импорта, форматирование
   `val n=1`, сохранение `: Unit` и пустой diff при повторном форматировании.
   Для частичного выбора проверяй соответствующие правила. Сообщи команды и замечания к исходникам. Применяй
   массовое форматирование исходников только по поручению на такое изменение.
