# Тестовые зависимости JVM

Выполняй этот шаг в каждой самостоятельной JVM-сборке после проверки JDK и сборщика.
В режиме «только аудит» используй исходники, доступные графы зависимостей и отчёты CI
для текущей ревизии. Покажи обнаруженную версию, основание и нужную правку.
В режиме настройки внеси изменения и повтори проверку.

## JUnit 5

1. Проверь тестовые задачи CI, включая интеграционные тесты, и их исходники.
   Проследи объявления через каталог версий, BOM, родительский POM и convention plugins.
   Определи версию Jupiter API и движка в тестовом classpath, используемый runner
   и движок, который действительно обнаружил тесты. Один вызов `useJUnitPlatform()`
   допускает и Vintage. Проверь прямые зависимости `junit:junit`, импорты JUnit 4,
   `@RunWith`, `@Rule` и используемый адаптер Kotlin Test. Транзитивный JUnit 4
   в сторонней библиотеке сам по себе не свидетельствует о тестах проекта на JUnit 4.
2. При использовании JUnit 4, в том числе одновременно с Jupiter, зафиксируй перечень
   тестов, параметризованных случаев, пропусков и результат штатных задач до переноса.
   Подключи согласованные API и движок Jupiter **5.x** через действующий механизм версий
   проекта. Настрой обнаружение тестов штатным сборщиком, например `useJUnitPlatform()`
   в задачах Gradle. В проекте без JUnit подключи Jupiter 5 тем же способом.
   При обнаружении Jupiter 6 явно укажи несовпадение мажорной версии; согласуй
   переход на 5.x, если он требует понижения версии существующего стека.
3. Перенеси тесты JUnit 4 на Jupiter с сохранением смысла проверок. Адаптируй
   lifecycle, порядок аргументов assertions, ожидание исключений, тайм-ауты,
   параметры, категории и фильтры CI. Для runners и rules подбери эквивалентные
   расширения. Для Kotlin проверь, какой JUnit-адаптер поставляет `kotlin.test`.
   Удали использованные проектом зависимости JUnit 4 и Vintage после переноса их
   потребителей. Если один из них — ArchUnit, в том же изменении замени
   `archunit-junit4` по правилам ниже до контрольного прогона. Если эквивалент
   для собственного runner пока не найден, зафиксируй
   конкретное препятствие и оставь миграцию незавершённой.
4. Выполни штатные тестовые задачи. Сверь обнаруженные и выполненные сценарии,
   наборы параметров и пропуски с исходным запуском. Зафиксируй исполнение
   перенесённых тестов Jupiter и результаты. Потерянные тесты или ошибки миграции
   оставляют требование невыполненным. Для новой сборки без тестов проверь
   разрешённые API и движок 5.x и конфигурацию запуска, отметь пустой набор.

Сопоставления API и особенности тестовых движков описаны в
[руководстве по миграции JUnit 4 на Jupiter](https://docs.junit.org/5.13.4/user-guide/index.html#migrating-from-junit4).

## ArchUnit

1. Найди тестовый модуль, в котором проект объявляет общие или архитектурные тестовые
   зависимости. Проверь реально подключённые артефакты группы `com.tngtech.archunit`,
   источник их версий и разрешённый тестовый classpath. Запись только в каталоге версий
   или `dependencyManagement` ещё требует подключения к тестам.
2. Возьми `latest_stable` из `jvm-step archunit` или из запрошенного полного аудита. Скрипт проверяет опубликованные версии
   ArchUnit в Maven Central при каждом запуске. Если источник недоступен,
   укажи причину и оставь актуальность неподтверждённой.
3. При отсутствии ArchUnit добавь `com.tngtech.archunit:archunit-junit5` с точным
   номером релиза в проектную тестовую конфигурацию (Gradle `testImplementation`,
   Maven `test`, sbt `Test`). В многомодульном проекте выбери модуль тестов
   или принятую общую конфигурацию. Если библиотека уже есть, обнови версию
   в её действующем источнике и обнови относящиеся к ней записи lock-файла.
   Сохрани выбор базового `archunit` или Jupiter-артефактов проекта. При переносе
   с `archunit-junit4` замени его на `archunit-junit5` и адаптируй уже имеющиеся
   тесты к Jupiter.
4. Проверь точную версию в разрешённом графе тестовых зависимостей. При совпадении
   версии повторный запуск оставляет файлы без правок. Для ArchUnit достаточно
   зависимости. Создание архитектурных правил, тестовых классов и конфигурации
   ArchUnit в этот шаг не входит.

Координаты тестового артефакта приведены в
[руководстве ArchUnit](https://www.archunit.org/userguide/html/000_Index.html#_installation).
