# Проектные проверки detekt

## Определи состояние сборки

Для каждой Kotlin-сборки на Gradle обязательна работающая проектная проверка detekt.
Определи все применимые сборки, включая сборки без плагина. Проверь охват
Kotlin-модулей и подключение через convention plugin. Найди проектную команду проверки и её вызов
из `check` или CI. Запись в каталоге версий, `apply false`, старый YAML или
глобальный CLI сами по себе ещё не подтверждают настройку проекта.

| Наблюдение | Действие |
| --- | --- |
| Проектная проверка отсутствует | Отметь невыполненное требование. В режиме настройки подключи совместимый плагин принятым в проекте способом. Для новой настройки предложи стабильный detekt **1.23.8** с ID `io.gitlab.arturbosch.detekt`. При отказе от подключения этап остаётся незавершённым. |
| Проверка использует detekt 1.x или 2.x | Проверь доступные обновления в той же мажорной ветке. Если есть более свежий выпуск, предложи его до сверки правил. |
| Плагин применён, но задача отсутствует, отключена или разрешение зависимостей завершилось ошибкой | Покажи конкретную причину и предложи восстановить проектную проверку на её версии. |

Версию **анализатора** установи по разрешённой зависимости задачи с учётом
`toolVersion`. Для задач с разными настройками проведи отдельную сверку.
Если версия, порядок YAML или значения вычисляются в Gradle, проверь конфигурацию
самой задачи. В режиме «только аудит» ограничься наблюдениями и предложениями.

## Проверь обновление действующей установки

1. При каждом запуске получи список опубликованных выпусков для мажорной версии
   установленного анализатора. Для 1.x рассматривай только 1.x, для 2.x — только
   2.x. Проверь доступность кандидата в репозитории зависимостей проекта. Версии
   шаблонов ниже служат для сверки правил. Источники выпусков:
   [релизы detekt](https://github.com/detekt/detekt/releases),
   [портал плагина 1.x](https://plugins.gradle.org/plugin/io.gitlab.arturbosch.detekt)
   и [портал плагина 2.x](https://plugins.gradle.org/plugin/dev.detekt).
2. Выбери самую свежую версию по SemVer. Для стабильной установки рассматривай
   стабильные выпуски. Для предварительной установки учитывай также опубликованные
   alpha, beta и RC: например, после `2.0.0-alpha.5` можно предложить
   `2.0.0-alpha.6`, а после выхода `2.0.0` — стабильную версию. Пропускай
   черновики и SNAPSHOT. Проверь совместимость с Gradle, Kotlin и JDK проекта.
   Предлагай обновление только при версии выше установленной. При совпадении
   сообщи, что обновление не требуется. Если источник недоступен
   или новый выпуск несовместим, укажи причину и продолжи сверку на текущей версии.
3. Покажи текущую и предлагаемую версии и предложи выбор «обновить» или
   «оставить текущую». При согласии обнови версию в том месте, откуда её получает
   проект (например, в каталоге версий или в `toolVersion`). Учти отдельно
   закреплённые версии Gradle-плагина и анализатора. Повторно проверь, какую
   версию разрешает задача. Правила сверяй по подтверждённой версии после выбора.

## Сверь эффективные значения

Рекомендуемые значения `active` берутся из [общего YAML](../assets/detekt.yml)
и дополнения для [1.23.8](../assets/detekt-1.yml) или
[2.0.0-alpha.6](../assets/detekt-2.yml). Набор `coroutines` и все его правила
выключены. В обеих ветках профиль включает `naming.VariableMaxLength` с пределом
`maximumVariableNameLength` в 64 символа. Сверяй переключатель и предел
как отдельные ключи. Оставь выключенными `NotImplementedDeclaration`, `MissingUseCall`,
`DataClassContainsFunctions`, `Deprecation` и все правила с именем
на `Forbidden`. Для другого выпуска примени проектные рекомендации к правилам,
которые поддерживает установленная версия. Для остальных возьми её штатные
значения. Часть рекомендованных проверок требует анализа типов. Проверь,
что задача CI получает classpath модуля и выполняет анализ типов.

Профиль отдаёт ktlint проверки пустого тела класса, порядка модификаторов,
перевода строки в конце файла и неиспользуемых импортов. Их аналоги в detekt
выключены, как и проверки скобок у ветвлений и циклов, пробелов в конце строки
и записи функции через выражение. Отключи `style.MaxLineLength` в detekt,
поскольку длину строки проверяет [ktlint](ktlint.md). При сверке другого выпуска проверь
также переименованные правила по тому, какое нарушение они находят.
Если к detekt подключена обёртка ktlint,
рекомендация для всего её набора — `active: false` (`formatting` в 1.x,
`ktlint` в 2.x). При отсутствии обёртки её секция в YAML не нужна.

1. Получи из действующей задачи список YAML в порядке их передачи, наличие обёртки
   ktlint и эффективные Gradle-параметры. Для проектной проверки рекомендуются
   `allRules = false` и `buildUponDefaultConfig = true`. Установи для обоих
   текущее значение и источник. Проверь также режим запуска, отключение
   встроенных наборов и ограничения CI, которые могут перекрыть выбранные правила.
2. Для каждого набора входов выполни [команду сверки](api.md#detekt).
   Она сравнивает значение каждого ключа с учётом слоёв YAML и возвращает
   расхождения и совпадения, требующие явной записи. При отдельном YAML
   без наследования передай `--standalone`. При запуске вообще без своего
   YAML detekt использует встроенную конфигурацию.
3. Различай значение ключа и участие правила в проверке. Например,
   `style.WildcardImport.active: true` действует только при включённом `style`.
   Если задачу меняет `allRules`, фильтр наборов или дополнительный источник
   конфигурации, установи фактические значения затронутых ключей до формирования
   предложения. Учитывай такие ключи отдельно от результата скрипта, в том
   числе при записи `pin`. Сохраняй baseline, исключения путей и параметры
   правил, для которых в шаблоне нет рекомендации.

## Предложи выбор и примени его

В режиме «только аудит» покажи отчёт о расхождениях. В режиме настройки проведи
[выбор правил](../SKILL.md#выбор-правил-ktlint-и-detekt). Для подсчёта возьми
подтверждённые расхождения из полного отчёта и учти параметры Gradle.
Например, изменение `naming.VariableMaxLength.active` и её предела длины
даёт одно правило для обсуждения. Сохрани решение по каждому из двух ключей.

| Результат сравнения | Действие в режиме настройки |
| --- | --- |
| Рекомендация уже задана явно в действующей конфигурации проекта | Оставь существующую запись. |
| Эффективное значение совпадает, но унаследовано | Закрепи его явно при принятии полного профиля или этого ключа. Это также относится к параметрам Gradle. |
| Значение отличается | Меняй только принятые пользователем ключи. При сохранении текущей конфигурации пропусти запись настроек. |

При принятии профиля повтори сверку с `--accept all`. При разборе по пять
передай через `--accept` только принятые YAML-ключи после решения по всему списку.
Объедини полученные `yaml_edits` с действующими файлами по ключам, сохраняя комментарии, прочие
параметры и приоритет настроек модулей. Для нового проекта можно начать с двух
файлов шаблона в `config/detekt/`, если все их значения входят в принятое
решение. Для новой сборки на detekt 1.23.8 с принятыми рекомендациями подключи
файлы из корня сборки, например в Kotlin DSL:

```kotlin
detekt {
    config.setFrom(
        rootProject.file("config/detekt/detekt.yml"),
        rootProject.file("config/detekt/detekt-1.yml")
    )
    allRules = false
    buildUponDefaultConfig = true
}
```

Для уже применённой версии 2.x используй её дополнение. Настраивай обёртку ktlint только
при её наличии. Отдельная задача Gradle `ktlintCheck` имеет собственные настройки.

При принятии изменения общего переключателя или набора проверь итог для каждого
затронутого модуля. Например, включение `buildUponDefaultConfig` меняет слой
умолчаний, а добавление первого YAML в сборку без этого флага может его убрать.
Сохрани прежние эффективные значения отклонённых ключей явными записями, если
это требуется для частичного выбора. Если выбор конфликтует (например, пользователь
хочет запустить правило внутри выключенного набора), покажи зависимость и уточни
только конфликт. Не применяй невыбранное изменение через общий файл.

После записи повтори сверку по фактическим входам задачи. У принятых рекомендаций
должны быть явные значения, у отклонённых — прежние эффективные значения.
Повтор того же выбора должен давать пустой набор правок. Запусти штатную
задачу detekt для всех затронутых модулей. Для завершения подтверди, что
она проверила проектные исходники с выбранными правилами и прошла. При
конфликте назови модуль, файл, правило и результат команды. Провал или пропуск
проверки оставляет шаг открытым до успешного повторного запуска.

Исходные конфигурации для сопровождения шаблонов приведены в репозитории detekt.
[Версия 1.23.8](https://github.com/detekt/detekt/blob/v1.23.8/detekt-core/src/main/resources/default-detekt-config.yml) ·
[Версия 2.0.0-alpha.6](https://github.com/detekt/detekt/blob/v2.0.0-alpha.6/detekt-core/src/main/resources/default-detekt-config.yml).
