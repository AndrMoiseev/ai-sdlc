# Команда сбора для архитектурного аудита

В полном маршруте этот этап применяется к Kotlin/JVM на Gradle. При отдельном
запросе начни с проверки mise в рабочей среде проекта. Служебные скрипты скиллов
запускай по их собственным правилам и локальному `AGENTS.md`.

1. Изучи конфигурацию mise, задачи проекта, сборку Gradle, задачи тестирования,
   отчёты и существующее значение `architect.collection` в `.sdd/settings.json`.
   Найди одну задачу, которую можно вызвать из корня проекта через `mise run <задача>`.
   Проверь её зависимости, включая вложенные скрипты. Задача должна завершаться
   ошибкой при падении любого обязательного шага, в том числе тестов. Проверь,
   что каждый отчёт создаётся задачей либо её зависимостью для текущих входов.
   Файл, оставшийся после другого запуска, сам по себе этого не подтверждает.
2. Составь перечень всех внешних исполняемых файлов в этой цепочке и поставляющих
   их инструментов mise. Учитывай интерпретаторы проектных скриптов. Например,
   JDK поставляет `java` и `jdeps`, Gradle Wrapper и detekt-плагин могут быть
   зависимостями сборки проекта. Проверь объявления и версии в проектной
   конфигурации mise, фактическую установку и разрешение каждого исполняемого
   файла в среде задачи. Исключи обход через жёстко заданный системный путь,
   сброс окружения или незаявленную зависимость из пользовательского PATH.
3. Проверь запуск `mise` по имени из корня проекта в той же среде, где будет работать аудит. Если существующая задача подходит, используй её. Если нужны изменения,
   покажи пользователю имя задачи, файлы, зависимости, версии и предлагаемые
   правки mise и сборки. Получи согласие до создания или изменения задачи,
   конфигурации mise и установки недостающих инструментов. При отказе сообщи,
   какая часть сбора недоступна. После согласия внеси изменения в проект,
   установи согласованные зависимости через mise и повтори проверку.
4. Подготовь запрос по [примеру](../assets/collection.example.json).
   В `collection` укажи команду как массив аргументов и все шесть выходов с
   путями от корня проекта. Поле `tools` сопоставляет имена инструментов в mise
   с запускаемыми программами. В `scope` укажи реальную область проверки
   по [контракту аудита](../../sdd-architect/references/collection.md#establish-the-scope).
5. Выполни `setup.py collection --project-root "<проект>" --request "<запрос.json>"`
   через uv по [условиям запуска](runtime-setup.md). Скрипт сверяет поставщиков
   программ с mise, один раз запускает проектную команду из корня, читает отчёты
   и проверяет их на выбранной области. Только после успеха он сохраняет
   `collection` в `.sdd/settings.json` под ключом `architect.collection`.
   Покажи пользователю рабочую команду и расположение отчётов. При ошибке
   сообщи конкретный шаг и результат проверки.

## Что должна выдавать задача

| Вход | Содержимое |
| --- | --- |
| `dependencies` | Вывод jdeps для скомпилированного рабочего варианта или CSV с колонками `from,to`. Оставь классы доступны для сопоставления с исходниками. |
| `history` | `git-history` JSON по полной истории за окно политики до текущей даты UTC, first-parent, без merge-коммитов, с учётом переименований и размера каждого changeset. Для проектного Python-скрипта под управлением mise можно использовать [готовую функцию](../assets/history_report.py). Передай ей корни, исключения, число дней из политики и исполнитель Git в окружении задачи mise. |
| `sizes` | Пофайловый JSON scc по репозиторию с классификацией языка и счётчиками строк. |
| `complexity` | SARIF проекта с правилами detekt для сложности, длины методов, числа функций и параметров. |
| `kotlin` | JSON профиля `kotlin-tokens-functions-1` версии 2 со всеми производственными Kotlin-файлами, токенами и функциями, включая подавленные и нулевые значения. |
| `coverage` | Объединённый JaCoCo XML по полному набору производственных классов после успешного прогона выбранных тестов. Параметры `complete` и `test_result` описывают гарантии успешного завершения задачи. |

Для Kotlin подключи измеритель к **существующему detekt проекта**. Выбери
совместимый тонкий JAR из [каталога адаптеров](../../sdd-architect/bin/plugins.json).
Закрепи его в зависимостях проекта либо включи в проект с согласия пользователя,
чтобы команда работала из обычного checkout независимо от установки скиллов.
Включи отчёт `sdd-architect-measurements` вместе с SARIF. Передай процессу detekt
свойства JVM `sdd.architect.repository` (корень), `sdd.architect.sourceManifest`
(UTF-8 список измеряемых Kotlin-файлов относительно корня, по одному на строку)
и `sdd.architect.detekt.version` (фактическая версия). Для нескольких модулей
обеспечь полное покрытие файлов без повторов в итоговом отчёте. Сохрани
обычную работу lint-задач вне сбора. Отдельный запуск detekt CLI из скилла
и зависимость проектной задачи от установленного `metrics.py` исключены.

Команды проверки поставщиков описаны в документации mise.
[mise ls](https://mise.jdx.dev/cli/ls.html) · [mise which](https://mise.jdx.dev/cli/which.html)
