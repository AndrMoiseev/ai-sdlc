# Скриптовый интерфейс

Запускай `uv run --locked --script "<skill-root>/scripts/setup.py" <command>`.
Ответ: `{"ok":true,"result":...}` либо `{"ok":false,"code":"sdd_setup","message":...}`
с ненулевым exit code. JSON читается как UTF-8, включая BOM.

Для `audit`, `typespec`, `detekt`, `inspect` и `plan` используй `--output <new-file.json>`: полный результат
сохраняется без оболочки, stdout содержит `result.output_file`, `sha256` файла
и `summary` для обсуждения. Создай рабочий каталог заранее, вне проекта и
коллекций скиллов; существующие файлы и перенаправленные пути отклоняются.
При повторном чтении/планировании выбирай новое имя файла.
Без `--output` сохранён прежний интерфейс: stdout содержит полный `result`.

## progress

В настройке первым делом прочитай прогресс. Все команды ниже — аргументы
служебного `setup.py` из условий запуска.

```text
progress --project-root "<проект>"
progress --project-root "<проект>" --reset ktlint detekt
progress --project-root "<проект>" --reset all
progress --project-root "<проект>" --applicable ktlint detekt --complete ktlint --check-exit-code 0 --project-changed
progress --project-root "<проект>" --applicable ktlint detekt --failed ktlint
```

Состояние проекта — массив ID в `.sdd/settings.json → setup.completed_steps`.
Отсутствующий массив означает пустой список. Чтение не создаёт файлов. Сброс
нескольких ID выполняется одной записью. Скрипт перечитывает настройки под
общей блокировкой setup и атомарно заменяет файл, сохраняя остальные поля.
Ошибка JSON или формата требует исправления исходных данных.

`--applicable` задаёт применимые шаги текущего вызова. Порядок задаёт каталог
`STEPS` в скрипте, результат содержит `completed_steps`, `pending_steps`,
`next_step` и `stop`. До выяснения стека указывай только известные шаги;
после подготовки общих инструментов вычисли применимость следующих. Для сообщения
о следующем шаге после узкого запроса можно прочитать прогресс полного маршрута.
Сохраняй только завершённые ID. При добавлении шага включи его в каталог и таблицу
критериев. Отсутствующий ID окажется среди ожидающих при следующем вызове.

`--complete` подтверждает уже проверенный результат. Для ktlint и detekt передай
фактический код каждой выполненной проектной команды через повторяемый
`--check-exit-code`. При ненулевом коде скрипт возвращает `failed_step`, останавливает
маршрут и оставляет список завершённых без записи. Проверь также охват исходников
и фактическое участие правил. При пропущенной или подавленной проверке используй
`--failed`. Передай `--project-changed`,
если успешно законченный шаг внёс содержательные правки в проект. Он вернёт
`stop: true`, даже когда есть следующий шаг. При провале проверки `--failed`
оставляет прогресс без записи и возвращает `stop: true`. Сначала устрани конфликт
или дождись решения пользователя, затем повтори проверку.

Если служебный uv ещё недоступен, прочитай тот же JSON средствами рабочей среды
до запуска mise. Для необходимой записи начальных отметок или явного сброса
используй тот же протокол средствами хоста: исключительная блокировка
`.sdd/.setup.lock`, повторное чтение и проверка JSON (объект, `schema_version: 1`,
список уникальных строк), изменение только `setup.completed_steps`, атомарная
замена файла через временный файл в том же каталоге. Для нового файла задай
`schema_version: 1`. Проверь, что путь внутри проекта и свободен от перенаправлений;
при занятой блокировке сохрани её и сообщи об ошибке. После подготовки uv используй
`progress`. Чтение или запись прогресса не требует определения стека.

## jvm-step

Проверяет только текущий шаг JVM. Применяй к каждой соответствующей сборке
(`--build-root` относительно `--project-root`), используй те же наблюдения,
что и для полного аудита. Примеры аргументов:

```text
jvm-step jdk --project-root "<проект>" --jdk temurin-21
jvm-step gradle --project-root "<проект>" --build-root backend
jvm-step junit5 --project-root "<проект>" --observation 5.12.1 "<задача и результат>"
jvm-step jacoco --project-root "<проект>" --jacoco-module :app --jacoco-module :core --jacoco :app satisfied "<тесты и классы приложения в XML>" --jacoco :core failed "<классы библиотеки отсутствуют в том же XML>"
jvm-step archunit --project-root "<проект>" --observation missing "<граф тестовых зависимостей>"
```

Команда возвращает строку требования со `status`. После исправления повтори
проверку этого шага. Для готовности требуется `satisfied` во всех областях.

## audit — проверка требований к проекту

```text
uv run --locked --script "<skill-root>/scripts/setup.py" audit --project-root "<project>" --jvm temurin-21 --no-ktlint --no-detekt --output "<workspace>/audit.json"
```

Команда проверяет требования из [аудита проекта](project-audit.md) в текущей
системе без установки и изменения настроек. `--host`, каталог агентов и
`sdd-shared` для неё не нужны. Аудит ищет mise по `PATH` текущего процесса
с учётом рабочего каталога проекта.
Для JVM укажи `--jvm <версия>` по исходникам проекта (в примере — Temurin 21).
Аргумент `--jvm` без значения фиксирует невыясненную версию. Для остальных
проектов используй `--no-jvm`. Для вложенной JVM-сборки используй
`--build-root <каталог относительно корня проекта>`: общие инструменты проверяются
из корня проекта, JDK и Gradle — из корня сборки. Аудит вызывает найденную mise без shell
с таймаутом 10 секунд на команду. Если найдена batch-обёртка, аудит возвращает `failed`.

Результат содержит `project_root`, время `checked_at`, `system`, `machine`,
список `requirements` и общий `compliant`. Для каждого требования указаны `id`,
`required`, `title`, `status` и `evidence`. Для mise отчёт включает версию,
путь к файлу и результат запуска. Для JVM требование `java` содержит
`requested_version`, наблюдение или причину ошибки, а при известной версии —
`use_command`. Оно учитывается в `compliant`. Проверка более свежей версии
и решение пользователя описаны в [правилах выбора JDK](java.md).

При готовом общем наборе и `--jvm` аудит также возвращает обязательное требование `gradle`.
`evidence.wrapper` и `evidence.mise` показывают каждый способ отдельно.
Достаточно одного со статусом `configured`. Если способы дают разные версии,
смотри версии в этих записях. Для известной версии скрипт запрашивает текущий
стабильный выпуск Gradle (таймаут 5 секунд). Более новая стабильная версия
появляется в `suggested_version` соответствующей записи. Ошибка запроса
фиксируется в `release_error`; обновление остаётся выбором пользователя.

В `requirements` после mise идёт обязательная запись для каждой команды из
[каталога](../assets/required-tools.json) с её именем (`id`), `tool_request`,
`use_command` для новой установки, активной версией, статусом и свидетельством.
При недоступной mise команды получают статус `unverified`. Пока общий набор
неполон, `compliant` равен `false`, а JVM-проверки отложены. Подготовку до первого
запуска скрипта выполняй по [правилам аудита](project-audit.md).

При `--jvm` и готовом общем наборе скрипт также включает обязательные требования
`junit`, `jacoco` и `archunit`. Для JaCoCo в `audit` и `jvm-step jacoco`
повтори `--jacoco-module <модуль>` для каждого JVM-модуля из модели сборки.
Передай `--jacoco <модуль> <satisfied|failed|unverified> "<свидетельство>"` по
результатам [сверки классов и тестовых задач со сводным XML](jacoco.md).
Используй уникальный путь с именем сборки для совпадающих путей подпроектов.
Скрипт сверяет наблюдения с переданным перечнем. Пустой перечень или модуль без
наблюдения оставляет проверку неподтверждённой. Ошибка любого модуля даёт `failed`.

Для зависимостей передай наблюдения из [проверки JUnit и ArchUnit](jvm-test-dependencies.md):

- `--junit <версия> "<модуль, задача и результат>"` для каждого используемого JUnit.
  Передавай точную версию Jupiter 5.x после проверки движка и тестов. Для старых
  тестов передай наблюдаемую версию JUnit 4, даже если они выполняются через Vintage.
  При ошибке переноса или потере тестов передай `failed` с причиной.
- `--archunit <версия> "<координаты, модуль и источник>"` для фактически
  разрешённой проектной тестовой зависимости. Для нескольких объявлений повтори
  аргумент. Скрипт сравнит каждую версию с последним стабильным релизом Maven Central.
- Для проверенного отсутствия используй `missing`, для недостаточных данных —
  `unverified`. Пропущенное наблюдение по требованию оставляет его неподтверждённым.
  Вне JVM оба требования пропускаются.

Для каждого Kotlin/JVM-модуля передай `--ktlint <модуль> <статус> "<свидетельство>"`,
для каждой Kotlin-сборки на Gradle — аналогичный `--detekt`. Оба аргумента
повторяемы. Для инструмента вне области применения явно передай `--no-ktlint`
или `--no-detekt`. В примере выше проект на Java без Kotlin. Отсутствие обязательной
интеграции фиксируй как `failed`. Пример работающей интеграции:
`--ktlint :api satisfied "CI этой ревизии выполнил :api:ktlintCheck"`.
Скрипт учитывает переданные наблюдения как обязательные требования. Область
определяет агент по сборке и CI. До проверки используй `unverified` с причиной,
при ошибке запуска, конфликте настроек или провале штатной проверки — `failed`.
Передавай `satisfied` только для успешной проверки исходников данной области
с действующими правилами. Пропущенную проверку отметь `unverified`.

`ok: true` и exit code 0 означают, что аудит выполнен, в том числе с найденными
несоответствиями. Готовность в пределах проверенных требований определяется
полем `compliant`: оно истинно, только если все обязательные требования имеют
статус `satisfied`. Ошибка входных данных или сохранения отчёта возвращает
`ok: false` и ненулевой код. После исправления запускай аудит заново.

## typespec — проверка после настройки mise

```text
uv run --locked --script "<skill-root>/scripts/setup.py" typespec --project-root "<project>" --package-dir "api" --output "<workspace>/typespec.json"
```

По умолчанию проверяется корень проекта. Команда находит Node.js через
`mise which node` в каталоге пакета. Затем сверяет объявление зависимости и
вывод локального компилятора `tsp --version`. Поиск учитывает общий
`node_modules` в пределах проекта. Результат содержит `status` и доступные
свидетельства: `node_version`, `declaration`, `version` или `error`.
Сравнение с реестром и действия по статусам описаны в [проверке TypeSpec](typespec.md).

## detekt

Команда сравнивает YAML одной проектной задачи. Передай фактическую версию
анализатора и соответствующий JAR `detekt-core` или `detekt-cli-…-all.jar`,
содержащий `default-detekt-config.yml`. Допустим и сам файл умолчаний.

```text
uv run --locked --script "<skill-root>/scripts/setup.py" detekt --project-root "<проект>" --version 1.23.8 --defaults "<detekt-core.jar>" --config config/detekt/detekt.yml --output "<workspace>/detekt.json"
```

Повтори `--config` в порядке передачи файлов задаче detekt: последнее объявление
ключа имеет приоритет. Значения из YAML за пределами корня проекта считаются
унаследованными. Пути к проектным YAML отсчитываются от корня проекта. Без этих
аргументов команда сравнивает встроенные умолчания. Передай `--standalone`,
если проект передаёт свои файлы без наследования встроенных умолчаний.
Передай `--ktlint`, только если задача загружает обёртку ktlint.

`explicit_matches` считает уже закреплённые совпадения. `pin` содержит
совпавшие унаследованные ключи, `differences` — расхождения с источником
текущего значения (`null` означает умолчание). Повтори команду с выбранными
ключами, например `--accept style.MaxLineLength.active`, либо с `--accept all`.
Без `--accept` список правок пуст. `yaml_edits` содержит выбранные ключи;
`--accept all` включает также закрепление унаследованных совпадений. Это частичные правки:
внеси их по [правилам настройки detekt](detekt.md). Сама команда только читает проект.

## inspect — чтение настроек ролей

```text
uv run --locked --script "<skill-root>/scripts/setup.py" inspect --project-root "<project>" --host codex --output "<workspace>/inspection.json"
```

Для Claude Code укажи `--host claude-code --available-agents <catalog.json>`.
Дополнительные параметры: `--sdd-shared <shared-root>` (прежний `--sdd-spec`
выбирает соседний sdd-shared), `--user-agent-dir <path>`, `--names <name> <name>`
для имён вне настроек/пресетов.

Сводка содержит все `roles` (`present`, `current`, `default`, `profile_default`),
`agents` (модель, effort, область, путь), корень, среду и `snapshot`.
Полный файл также хранит `inputs` и `evidence`; их переносит скрипт.
Ошибки конфигурации и дубликаты имён требуют исправления; пустой каталог допустим.

## plan — подготовка записи

Запиши request с `inspection_file` (абсолютный путь или путь относительно
request) и `inspection_sha256` из inspect. Добавь `roles` с решением для каждой
роли из inspect и `agents` с моделью/effort каждого уникального выбранного имени:

```json
{
  "inspection_file": "inspection.json",
  "inspection_sha256": "<sha256 из inspect>",
  "roles": {"<каждая роль>": {"action": "default"}},
  "agents": {"<каждое выбранное имя>": {
    "model": {"action": "default"}, "effort": {"action": "default"}
  }}
}
```

Замени условные ключи согласованными решениями из [диалога](dialogue.md).

| Решение | Значение |
| --- | --- |
| `{"action":"keep"}` | Сохранить заданное значение; отсутствующее поле отклоняется |
| `{"action":"default"}` | Принять пресет роли текущей среды |
| `{"action":"set","value":"..."}` | Выбранное имя/модель/effort |
| `{"action":"set","value":null}` | Убрать сопоставление роли или явное поле модели/effort |

Прежняя форма `{"inspection":<полный result>,"roles":...,"agents":...}` допустима.
Смешивать формы нельзя. Хэш защищает файл от подмены; сравнение с новым
`inspect` отклоняет устаревшие настройки и каталог. При расхождении повтори
чтение и согласуй изменившиеся значения, сохранив остальные ответы.

```text
uv run --locked --script "<skill-root>/scripts/setup.py" plan --request "<workspace>/request.json" --output "<workspace>/plan.json"
```

Сводка показывает `selected_roles`, `selected_agents` с моделью/effort,
`operations` с путями и точным diff, предупреждения, `plan_id`. Полный план
содержит request с встроенным inspection, исходные/новые тексты и хэши;
он самодостаточен для apply и восстановления. Читай полные тексты только для
разбора ошибки или восстановления; для обсуждения достаточно сводки.

## apply — запись

Перед записью проверь: решения пользователя покрывают все роли и агенты,
точный diff показан, новых несогласованных изменений нет.

```text
uv run --locked --script "<skill-root>/scripts/setup.py" apply --plan "<workspace>/plan.json"
```

Скрипт пересчитывает план, проверяет пути/исходное содержимое и блокирует
параллельный setup через `.sdd/.setup.lock`. Определения записываются перед
settings; файлы заменяются атомарно, хэши проверяются. При обычной ошибке записи
сделанные изменения откатываются, если их не изменил другой процесс.
Произвольная правка плана отклоняется; пустые созданные каталоги могут остаться.

Авария процесса/питания может оставить часть записей и lock. Проверь PID и
содержимое, восстанови данные из полного плана, повтори inspect. Lock активного
процесса сохраняй. Защита от всех одновременных правок сторонним редактором
не гарантируется.

`changed` перечисляет записанные пути; пустой список означает отсутствие записей.
Повтори inspect после apply. Версия settings фиксирована: 1. Неизвестные верхние
поля сохраняются; неизвестные поля subagents отклоняет контракт `sdd-shared`.

## Настроить сбор для архитектурного аудита

`collection --project-root <проект> --request <внешний-запрос.json>` проверяет
команду и записывает её после успешной проверки. Формат запроса, согласование
изменений и требования к отчётам описаны в [настройке сбора](collection.md).
