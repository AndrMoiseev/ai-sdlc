# Аудит проекта

Проверяй среду, в которой агент будет выполнять команды этого проекта. Windows,
WSL, контейнер и удалённый сервер — разные среды: установка mise на хосте не
подтверждает её наличие внутри контейнера. Зафиксируй выбранную среду в отчёте.

## Требования к проекту

| ID | Обязательность | Критерий соответствия | Исправление |
| --- | --- | --- | --- |
| `mise` | Обязательное | По имени `mise` в `PATH` рабочей среды проекта найден исполняемый файл, а `mise --version` завершился с кодом 0 и вернул версию | Сделать существующую установку доступной через `PATH` или установить mise при её отсутствии. Повторить аудит |
| Команды из [каталога](../assets/required-tools.json) | Обязательна каждая для любого стека | Команда поставляется установленным инструментом проекта через mise и запускается из корня проекта | Установить недостающий инструмент через mise и проверить запуск |
| `java` | Обязательное для JVM | Проектная конфигурация mise предоставляет `java` и `javac` из установленного JDK требуемой версии | Определить версию по исходникам, установить её через mise и повторить аудит. [Выбор и проверка JDK](java.md) |
| `gradle` | Обязательное для JVM | В корне проверяемой сборки настроен Gradle Wrapper либо установленный Gradle доступен из проектной конфигурации mise | Сохранить действующий способ. При отсутствии Gradle показать требуемую настройку |
| `junit` | Обязательное для JVM | Проект использует Jupiter 5, существующие тесты JUnit 4 перенесены и обнаруживаются штатным запуском | [Подключить JUnit 5 и выполнить миграцию](jvm-test-dependencies.md) |
| `jacoco` | Обязательное для JVM | Свежий сводный XML после тестов охватывает производственные классы всех JVM-модулей | [Настроить JaCoCo и сверить модули с отчётом](jacoco.md) |
| `archunit` | Обязательное для JVM | Тестовая зависимость ArchUnit разрешается в последний стабильный релиз | [Добавить или обновить зависимость](jvm-test-dependencies.md) |
| `ktlint` | Обязательное для каждого Kotlin/JVM-модуля | Штатная проверка с выбранными правилами прошла на исходниках модуля | [Проверить настройки и устранить конфликты](ktlint.md) |
| `detekt` | Обязательное для каждой Kotlin-сборки на Gradle | Штатные задачи успешно проверили Kotlin-код затронутых модулей с выбранными правилами | [Проверить настройки и устранить конфликты](detekt.md) |

Зависимости конкретной команды проверяются на этапе настройки сбора. Минимальная версия
пока не задана: работающую установку не обновляй ради «последней версии».
Наличие `mise.toml`, установленные через mise инструменты и активация оболочки
не входят в это первое требование. Не создавай пустой `mise.toml` и не запускай
`mise install`, `mise use`, `mise trust` или задачи проекта ради проверки наличия
самой утилиты. Это отдельные изменения зависимостей и доверия к конфигурации.

При добавлении требования укажи обязательность, наблюдаемый критерий, исправление
и повторную проверку; дополни `scripts/project_audit.py` и его тесты. Только
обязательные требования блокируют полный маршрут. Рекомендации показывай
отдельно и исправляй в пределах выбранных пользователем настроек.

## Подготовка до определения стека

1. Из корня проекта в рабочей оболочке выполни `mise --version`. При ошибке
   используй приведённые ниже правила диагностики и исправления mise.
2. Прочитай [каталог обязательных инструментов](../assets/required-tools.json).
   Ключ — команда, значение — пакет mise для новой установки. Проверь **каждую**:
   поставщика через `mise which <команда> --plugin`, активную версию через
   `mise which <команда> --version`. По `mise ls --current --json` и
   `mise which <команда>` подтверди, что бинарник принадлежит установленному
   инструменту из конфигурации проекта. Проверь запуск `mise exec -- <команда> --version`
   с отключённой автоустановкой (`MISE_AUTO_INSTALL=false`).
3. В режиме настройки установи объявленную проектом версию недостающего инструмента.
   Для новой записи выполни `mise use --path <корень проекта> <пакет из каталога>`.
   Сохрани действующего поставщика и учитывай lock-файл проекта. Повтори проверку.
   Актуальность версии проверь отдельно через `mise latest <запрос поставщика>`;
   решение об обновлении работающего инструмента принимает пользователь.
4. Пока обязательный набор неполон, укажи недостающие команды и заблокированные
   проверки, заверши этап с отрицательным результатом. В режиме «только аудит»
   ограничься проверками и командами исправления. Эта подготовка выполняется
   средствами оболочки, в том числе когда служебный скрипт ещё нельзя запустить.

Источники пакетов и команд приведены в [реестре mise](https://mise.jdx.dev/registry.html),
[описании conda](https://mise.jdx.dev/dev-tools/backends/conda.html),
[релизах scc](https://github.com/boyter/scc/releases) и
[справке по latest](https://mise.jdx.dev/cli/latest.html) и
[настройке автоматической установки mise](https://mise.jdx.dev/configuration/settings.html#auto_install).

После проверок стека выполни [проверку TypeSpec](typespec.md) на проектной Node.js.
Установка и обновление TypeSpec остаются выбором пользователя.

## Gradle для JVM

Проверяй корень сборки, из которого её запускает CI. Общий Wrapper
многомодульной сборки проверяй один раз. Для самостоятельной вложенной
сборки проверяй её собственный корень. Аудит читает файлы Wrapper и сведения
mise. Запуск Wrapper может скачать дистрибутив, поэтому в режиме «только аудит»
достаточно проверки конфигурации.

Если обнаружены оба способа, покажи обе версии и ориентируйся на тот запуск,
который использует проект. Для неполного Wrapper укажи недостающие файлы.
Если Gradle объявлен в mise, но отсутствует на диске, в маршруте с исправлениями
установи объявленную версию. Если оба способа отсутствуют, сообщи о невыполненном
требовании и предложи настроить Wrapper или проектную версию через mise
с учётом JDK проекта. Для проекта на Maven или sbt переход на Gradle как
основную систему сборки требует отдельного поручения.

Аудит сравнивает установленную версию с текущим стабильным выпуском из
[сервиса версий Gradle](https://services.gradle.org/versions/current). Покажи
текущую и предложенную версии, когда `suggested_version` указан у используемого
способа. Учитывай [совместимость с JDK проекта](https://docs.gradle.org/current/userguide/compatibility.html)
и известные ограничения плагинов. Для внутреннего дистрибутива без номера в URL
уточни версию по выводу штатного запуска в CI перед сравнением.
Если данные о выпуске недоступны, сообщи об этом. Проверка актуальности
не влияет на соответствие уже настроенного Gradle.

Обновляй только после выбора пользователя тем способом, которым пользуется проект.
Для Wrapper сохрани тип дистрибутива, зеркало и проверку контрольной суммы,
для mise — поставщика и область проектной настройки. После обновления сверь
версию штатным вызовом `--version` и повтори `jvm-step gradle`. [Обновление Gradle Wrapper](https://docs.gradle.org/current/userguide/gradle_wrapper.html#sec:upgrading_wrapper)

## Полный аудит по запросу

1. После подготовки mise и всего обязательного набора определи стек по исходникам
   и CI. Для JVM передай в `audit` аргумент `--jvm <версия JDK из проекта>`
   (либо `--jvm`, если версия пока не выяснена). Вне JVM используй `--no-jvm`.
   Для JVM передай наблюдения о JUnit и ArchUnit, перечень JVM-модулей из сборки и
   результат проверки JaCoCo по каждому модулю. До проверки используй
   `unverified` с причиной. Все три требования участвуют в `compliant`.
   Для каждого Kotlin/JVM-модуля передай наблюдение о ktlint, для каждой Kotlin-сборки
   на Gradle — о detekt. До проверки укажи `unverified`. Формат и примеры см. в
   [API](api.md). Для вложенной самостоятельной сборки передай `--build-root`,
   сохранив общий `--project-root`.
2. Покажи таблицу «требование / обязательность / наблюдение / соответствие /
   исправление». Для mise приведи путь, версию либо фактическую ошибку. Для JVM
   добавь источник версии JDK, результат проверки и команду исправления при необходимости.
## Диагностика mise

| Статус mise | Продолжение |
| --- | --- |
| `satisfied` | Требование выполнено; повторная установка не нужна |
| `not_found` | Команда не найдена; сначала проверь известное место существующей установки |
| `failed` | Файл найден, но запуск не подтвердил версию; разбери stderr, код выхода или таймаут |

`not_found` по PATH ещё не доказывает отсутствие установки. Проверь сведения
установленного пакетного менеджера и стандартное место официального установщика:
`~/.local/bin/mise` на macOS/Linux, `~\.local\bin\mise.exe` на Windows. Используй
домашний каталог текущего пользователя из API среды. Если файл найден вне
`PATH`, требование остаётся невыполненным. В режиме «только аудит» укажи
каталог, который нужно добавить в `PATH`. В маршруте с исправлениями добавь
его в `PATH` среды, в которой агент выполняет команды проекта, сохранив
остальные записи. Повтори аудит в этой среде.

При нескольких установках укажи, какой файл реально проверен. Не устанавливай
ещё одну копию для устранения ошибки PATH. При `failed` сначала отличи проблему
доступа/окружения от повреждённой установки. `mise doctor` используй для конкретной
диагностики, а не как дополнительное обязательное требование.

## Исправление

Маршрут «только аудит» заканчивается результатом проверки и предложенными
исправлениями: он не разрешает установку или изменение конфигурации. Полный setup
и просьба привести требования в соответствие включают необходимые исправления.
Перед исполнением покажи конкретную команду, источник и область изменений
(например, установка mise в пользовательский каталог). Используй уже данное
поручение; повторное согласие на то же действие не требуется. Новый существенный
выбор, выход за поручение или ограничение среды разрешай штатным способом хоста.

Выбери один способ установки по текущей ОС и существующей установке. Прочитай
актуальную [официальную инструкцию установки](https://mise.jdx.dev/installing-mise.html)
перед скачиванием: способы и требования платформ меняются. При отсутствии доступа
к документации сообщи об этом и используй только уже проверенный источник/способ;
не выдумывай ссылку на бинарник.

| Среда | Способ, подтверждённый документацией |
| --- | --- |
| macOS / Linux | Официальный установщик `https://mise.run` для `sh`; стандартный путь `~/.local/bin/mise` |
| Windows / PowerShell | Официальный установщик `https://mise.run/powershell`; стандартный путь `~\.local\bin\mise.exe` |
| Уже используется пакетный менеджер | Его способ из документации, например `brew install mise` или `winget install jdx.mise` |

Скачай установщик в отдельный внешний временный каталог, проверь успешность
скачивания и прочитай скрипт перед запуском через соответствующий интерпретатор.
Не подменяй проверку скачивания исполнением пустого/ошибочного ответа. Сохраняй
проверки целостности установщика и обычные разрешения среды. Для существующей
установки используй её способ обслуживания; восстановление не должно молча
заменять рабочую копию другим менеджером.

Если пакетный менеджер или установщик меняет пользовательский PATH, отметь это
в плане. Активацию оболочки и изменение shell profile выполняй только по отдельному
запросу. Для выполнения требования достаточно доступности команды через `PATH`.

## Повторная проверка и завершение

После исправления mise повтори прямую проверку в рабочей среде с обновлённым PATH.
При пошаговой настройке повтори только проверку текущего шага. Для JVM используй
`jvm-step`. При отдельном запросе полного аудита выполни `audit`. Для каждого
применимого ktlint и detekt передай фактический результат (область, статус,
команда и наблюдение). В режиме чтения используй подтверждённые результаты CI
для проверяемой ревизии или штатной проверки, доступной без записи. При нехватке
свидетельств укажи `unverified`. Проверь полноту областей и `compliant` по всем
проверенным сборкам. Код возврата скрипта отражает успешное выполнение самого аудита.

При успехе сообщи результат. В режиме настройки выполни правило записи прогресса
и остановки из основной инструкции скилла.
Если пользователь отказался от обязательной установки,
доступ запрещён или исправление не удалось, сохрани отрицательный результат,
назови препятствие и конкретное следующее действие. Полный setup остановлен на
этом этапе; отдельную настройку ролей можно выполнить по новому явному уточнению.

Повторный запрос «только аудит» снова проверяет требования. При выполненном требовании он
оставляет установку и конфигурацию без изменений. Отчёт относится к текущей среде
и проверенному набору требований, а не ко всей будущей готовности проекта.

Источники проверены 2026-11-15: [установка](https://mise.jdx.dev/installing-mise.html),
[запуск без активации оболочки](https://mise.jdx.dev/getting-started.html).
