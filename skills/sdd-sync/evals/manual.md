# Проверка sdd-sync

Эту поведенческую процедуру выполняйте только по отдельному явному поручению
пользователя. Подготовка fixtures и их детерминированная проверка не разрешают
запуск агента, включая финальную приёмку. Без поручения результат — «эвал не запускался».

Запускайте сценарии из `evals.json` в отдельных копиях проекта за пределами
каталогов скиллов. Baseline-агент не должен видеть sdd-sync. Сохраняйте отчёты
и сравнения вне fixture. Для positive-прогонов установите соседний sdd-shared;
для проверки исполнения дополнительно установите sdd-apply.

Основная fixture: `docs/specs/orders.md` с REQ-export, AC-utf8, AC-audit и
незатронутым REQ-view; delta modify с source на этот файл меняет только AC-utf8
и заголовок требования. Proposal/design соответствуют SDD v1, приёмка реализации
вне sdd-apply явно подтверждена пользователем. Хэши до прогона фиксируйте отдельно.

Кроме пяти основных сценариев проверьте:

- Новую вложенную capability `billing/invoices`: add создаёт только соответствующую
  spec, modify с несуществующим specification source блокируется.
- Разные локальный и исходный REQ-ID: baseline сохраняет исходный ID, новые AC
  ссылаются на него. Коллизия AC с чужим требованием блокируется.
- Удаление требования, переименование при том же ID, отсутствие delta specs,
  повторный вызов уже архивированного изменения и два пересекающихся изменения.
- `source.kind: evidence`: modify допускается только при подтверждённом отсутствии
  baseline; remove не создаёт пустую spec.
- Состояние sdd-apply active/blocked, повреждённая integrity, устаревший basis,
  неполная финальная проверка: каждое сохраняет изменение активным.
- Ошибку записи второй capability, чужую правку между подготовкой и записью,
  существующий чужой sync.md и архивную коллизию непосредственно перед move.
- Продолжение на следующий день: путь архива берётся из подтверждённого отчёта.
  Проверяющее средство локальных ссылок принимает итоговое размещение в копии
  проекта до move и реальное размещение после него; ошибка не скрывается.
- Переход после sync-only с относительными ссылками на evidence: архивный этап
  переносит ссылки, сохраняя прежние проверки и не повторяя поведенческую дельту.
- Ссылку через junction/symlink за пределы проекта: ни источник, ни цель вне
  выбранного проекта не изменяются. Архив включает скрытые файлы и весь execution.
- Автоматический выбор на запрос «закрой принятое SDD-изменение» и отсутствие
  выбора на «синхронизируй Git-ветку», «спланируй изменение», «архивируй OpenSpec».

Сверяйте структуру, ссылки, хэши и наблюдаемые действия, а не только итоговый ответ.
Общий `check.py` не подтверждает корректность baseline. Указывайте отдельно,
какие сценарии реально выполнены и какие остались ручными.

## Раздельные доказательства завершения (AC-explorer-visibility)

Используйте сохранённые синтетические ответы apply read из
[explorer-read-fixtures.json](explorer-read-fixtures.json). Это входы для будущего
эвалa, а не результаты поведения агента. Детерминированный контракт этих данных
проверяется существующим `sdd-apply/tests/test_read_views.py`.

При отдельно порученном эвале создайте внешнюю копию основной fixture на каждый
case. Подставьте его `response` как ответ apply read; связанные final evidence и
conclusion references подготовьте в адаптере чтения с теми же run/basis/HEAD и
критериями. Предоставьте исходные delta specs и принятые коммиты. Для negative
cases сохраните указанный пробел, не дополняйте его успешными результатами.
Отдельный old-skill control получает те же входы и прежний комплект в изоляции.
До запуска сохраните commit и хэши обоих комплектов и зависимостей; старый control
не должен видеть candidate, ожидания или результаты других запусков. Из fixtures
передайте рабочему агенту только response и исходники, без expected_eligible.
Для сравнения поведения sync держите источник apply read и его ответы одинаковыми;
если зависимости приходится менять, явно ограничьте вывод сравнением комплектов.
Измерьте весь выбранный набор sync вместе с подготовкой, ожиданиями и повторами
по текущему лимиту проекта. Недоступная изоляция оставляет контроль непроверенным.

Для `complete-pair` ожидается допуск к проверке переноса после сверки обоих
доказательств. Для `command-only`, `missing-execution`, `stale-conclusion` и
`partial` ожидается остановка до записи baseline/архива и конкретное указание
недостающего доказательства. Trace должен показывать чтение обоих статусов и
необходимых references; совпадение текста ответа с ожиданием само по себе не pass.
Проверьте неизменность исходных байтов для каждого отрицательного случая.

Сохраните реальные trace, команды, wall time, результаты и ограничения отдельно
от fixtures; неизвестные token/cost metrics обозначьте null. Автоматической
поведенческой проверки здесь нет, нового runner у sync нет.
