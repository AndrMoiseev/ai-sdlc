# Слияние требований

Текущая спецификация описывает всё действующее поведение capability. Spec внутри
изменения содержит только затронутые требования. Копирование второго файла поверх
первого теряет незатронутое поведение.

## Выбор цели и идентичность

- Для `source.kind: specification` используй точный `source.path` относительно
  проекта и `source.requirement` как ID либо точный заголовок. Совпадение должно
  быть единственным. Это приоритетнее пути по умолчанию.
- Для add найди действующую spec этой capability по правилам проекта. В отсутствие
  такой spec используй `sdd/specs/<capability>/spec.md`. Сохраняй вложенные сегменты,
  например `billing/invoices`. Если проект уже хранит spec в другом каталоге,
  соблюдай его размещение; неоднозначное соответствие уточни до записи.
- Два несогласованных назначения для одной capability или несколько операций над
  одним исходным требованием являются конфликтом. Не заводи параллельную baseline
  в `sdd/specs/`, когда source указывает существующую `docs/specs/`.
- Существующий REQ-ID текущей spec сохраняется даже при другом локальном ID дельты.
  Перенеси AC с правильным `requirement`. Совпавшие AC-ID означают один критерий;
  при новом локальном ID для того же критерия сопоставь содержание и сохрани
  существующий ID. Не склеивай разные критерии по сходному названию. Коллизия ID
  с другим требованием требует решения, а не автоматической перенумерации.

## Операции SDD

| Операция | Результат |
|---|---|
| `add` | Добавь требование и его AC. При идентичном уже существующем содержании ничего не меняй. При совпадении идентичности и отличии содержания примени как неявный modify только если это подтверждено смыслом принятого изменения; иначе сообщи конфликт. |
| `modify` | Обнови текст и указанные AC найденного требования. Сохрани не затронутые изменением AC, ограничения, порядок и соседние требования. |
| `remove` | Удали найденное требование вместе с принадлежащими ему AC. Критерии результата удаления из дельты остаются в истории, в baseline их не переноси. |
| Переименование | В SDD это modify заголовка при стабильном REQ-ID. Изменение текста и заголовка применяй к одному требованию, без копии под новым именем. Отдельного `rename` в schema v1 нет. |

Отсутствие AC в дельте само по себе не разрешает его удаление. Если сохранённый AC
противоречит новому тексту, проверь явно согласованное изменение поведения. При
отсутствии однозначного решения остановись с конфликтом, не угадывай. Полное
предлагаемое содержание требования в SDD не означает разрешения удалить всё,
что автор случайно не перенёс из исходной spec.

У новой capability нет исходных требований: создавай её из add. Modify/remove
с `source.kind: specification`, у которого отсутствует файл или требование,
блокирует перенос. Не заменяй сломанную ссылку на `evidence`. Исключение для повтора
с подтверждённым отчётом описано в процессе переноса.

SDD также допускает `source.kind: evidence, baseline_missing: true`. Сверь
существующие references и приёмку. Для modify создай текущее описание реализованного
требования с AC, если подтверждено отсутствие письменной baseline. Для remove
сообщи отсутствие требования в baseline; новую spec для удаления не создавай.
Это адаптация формата SDD, а не разрешение OpenSpec применять MODIFIED без источника.

Если удаление последнего требования явно означает прекращение всей capability,
удали только её `spec.md`, сохрани прочие файлы каталога и резервную копию старого
содержания. При неясной судьбе capability запроси решение до записи. На повторном
запуске подтверждённое отчётом отсутствие файла считается выполненным удалением.

## Ссылки и содержание

Сохраняй вводный текст существующей spec. Для новой возьми описание capability
из принятой дельты, без выдуманных требований. Убери метаданные операции по
[формату текущих спецификаций](../../sdd-shared/references/current-specifications.md).
Проверь переносимые относительные ссылки: после смены каталога они должны вести
к тем же материалам. Ссылки на change-only evidence направь в будущий архив
(в режиме без архива оставь активный путь). Внешние URL сохраняй.

Изменение завершено только когда повторное применение каждой операции не меняет
результат. После архива не запускай старую дельту поверх более новой baseline.
