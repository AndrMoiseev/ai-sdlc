# Подготовка документов

1. Выбери изменение через [resume](resume.md). Для нового согласованного направления используй понятный свободный kebab-case `change-id`; при коллизии уточни продолжение либо другое имя. Создай каталог непосредственно в `sdd/changes/`, без внешнего генератора. Сохранение черновика не требует отдельного согласования записи и не подтверждает его содержание.
2. Прочитай [формат](../references/document-format.md), шаблон очередного документа и его актуальные зависимости с диска. Исследуй проект соразмерно изменению. Применяй проектные инструкции как ограничения, не копируй их в артефакты. Язык новых документов — язык документации проекта, иначе язык запроса; ключи, пути и префиксы ID остаются английскими.
3. Заполни [proposal](../templates/proposal.md): почему нужна работа, ожидаемый результат, изменения, границы и исключения, новые/изменяемые capabilities, impact. Сначала найди существующие спецификации. Сохраняй полный путь существующей capability; каждой объявленной capability соответствует `specs/<capability>/spec.md`. Детали реализации оставь design.
4. По [spec](../templates/spec.md) опиши контракт каждой capability: наблюдаемое поведение, входы, выходы, ошибки и применимые внешние ограничения. Классы и библиотеки относятся к design, если не являются внешним обязательством. Записывай полное предлагаемое содержание затронутого требования, а не всей capability. У каждого REQ есть AC с условиями и наблюдаемым результатом. Самостоятельный SCN и Given/When/Then необязательны. Для modify/remove укажи baseline или честно опиши его отсутствие и свидетельства поведения; критерии удаления проверяют результат удаления. Неизмененное требование не требует новых задач.
5. Всегда подготовь общий [design](../templates/design.md): текущий контекст, модули и контракты, термины, подход и существенные альтернативы, последствия, риски и применимую миграцию. Ссылайся на proposal/specs вместо повторения. Разделам модулей и терминов не нужны ID. Только формальные DEC имеют стабильные ID и непустую связь с требованиями; наличие DEC не обязательно. Новое внешнее обязательство решения отрази в specs с AC.
6. Закрой блокирующие вопросы через [explore](explore.md). Доступное сейчас исследование кода выполни сейчас: общая будущая задача «исследовать код» не заменяет решение. Если дальнейшее исследование действительно необходимо, привяжи его к конкретному вопросу и объясни отсрочку. Недоступный существенный источник зафиксируй как ограничение, а влияющий на поведение пробел оставь блокирующим.
7. Проверь существование записанных файлов и взаимную согласованность всех существующих артефактов. Выполни documents-проверку по [runtime](../references/runtime-setup.md); уведомь о дефектах, исправь однозначную структуру, повтори проверку. Содержательный выбор вынеси пользователю; структурный waiver недопустим.
8. Сохрани [checkpoint](resume.md). Когда структура корректна и блокирующих вопросов нет, покажи отложенные вопросы с причинами/`return_at`, перечисли все линзы и их предмет по [review](review.md), предложи запуск. До этого продолжай исследование. Tasks здесь не создаются: [plan](plan.md) требует самостоятельной команды и готовности документов.
