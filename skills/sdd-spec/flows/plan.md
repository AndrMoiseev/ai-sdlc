# План и завершение

## Вход

Перед проверкой разрешения и готовности прочитай
[формат ревью и согласований](../../sdd-shared/references/document-format-review.md);
для проверки исходных specs/design — [нормативный формат](../../sdd-shared/references/document-format-normative.md).

Проверь происхождение существенных положений по [discussion](../references/discussion.md),
decisions.md и questions.md, включая старые Q-записи в state. Новые существенные
выборы при детализации плана также верни в обсуждение; сохранять независимую
часть уже порученного плана допустимо.

Перечитай актуальные specs, design, proposal, вопросы, отчеты и решения с диска. До создания tasks одновременно требуются: закрытые блокирующие вопросы; корректная структура documents; согласование текущих specs/design; явная команда создать план. Ревью документов предложи как опцию по [правилам согласования](../../sdd-shared/references/document-format-review.md#опциональное-ревью-и-разрешение-на-реализацию). Согласование документов само по себе не команда. Сохрани `planning_command` с разрешенной областью. При возобновлении уже начатой работы используй проверенное сохраненное поручение без повторного согласия.

Если ревью missing/stale/incomplete, сообщи это без блокировки планирования. Если требуется содержательный выбор, вернись к explore/revise; структурные ошибки исправь прежде дальнейшего перехода. Пока обязательные условия не соблюдены, tasks не создавай.

## Подготовка

Для `refactoring` используй [план рефакторинга](../references/refactoring.md#план-рефакторинга) вместо шагов 1–3 и обычного правила единственного владельца AC в разделе оптимизации. Общие условия входа, структурная проверка и финальный gate остаются обязательными; ревью опционально. Под текущими specs/design для этого маршрута понимай proposal/design.

1. Прочитай [tasks](../templates/tasks.md), [общую основу](../../sdd-shared/references/document-format.md) и [формат задач](../../sdd-shared/references/document-format-tasks.md). Разбей реализацию на проверяемые задачи разумного размера с устойчивыми смысловыми `TASK-...`, отдельным номером 1..N и `status: pending`. У каждой задачи непустой `covers`; каждый AC изменения, включая результат удаления требования, назначен ровно одной задаче. Одна задача может владеть несколькими AC; DEC не заменяет критерий.
2. Включи необходимые кодовые шаги, общие фикстуры, подготовку окружения и тесты внутрь задачи, которой они нужны. Для каждого AC опиши проверку, путь location к её определению и run по [контракту verification](../../sdd-shared/references/document-format-tasks.md#задача-и-ее-проверка). Для будущей проверки или неготового запуска выбери setup_required, даже если команда уже известна; укажи её в описании подготовки. Будущему пути не нужно существовать на стадии плана. Не выделяй последующую задачу «покрыть тестами» и не дублируй AC отдельной интеграционной задачей. Новое поведение интеграции сначала согласуй в specs/AC.
3. Задай `depends_on` по TASK-ID, не номеру. Номер можно менять при перестановке; идентичность и ссылки сохраняются. Проверь отсутствующие зависимости, self-reference и циклы. Граф показывает доступность, но общие файлы/контракты требуют отдельной оценки безопасного параллелизма. Прогресс определяется статусами, не последним номером.
4. Выполни [оптимизацию разбиения](#оптимизация-разбиения), затем check `--stage plan`. Сообщи ошибки, исправь однозначные, повтори проверку. При необходимости выбора состава задач уточни конкретный вопрос. Успех exit 0 означает только корректную структуру, не завершенность ревью и согласований.
5. Сохрани checkpoint и предложи опциональное [независимое ревью](review.md) одному новому рецензенту плана: полнота, размер, критерии, тесты, зависимости, порядок, общие файлы и возможность параллельной работы. При согласии запусти ревью и [покажи находки](user-review.md). Если пользователь вместо ревью согласовал план, сразу примени финальный gate. Если правки затронули specs/design, восстанови их готовность и согласование; актуальность ревью отрази отдельно.

## Оптимизация разбиения

Перед check сравни предварительное разбиение с альтернативой, если в нём есть
цепочка зависимостей, задача с несколькими независимыми AC или конфликт общих
изменений. Проверь разделение по существующим AC, перегруппировку AC вместе
с подготовительными шагами и разделение участков общих файлов в рамках design.
Выбирай разбиение, которое раньше открывает независимую работу и сокращает
обязательные последовательные зависимости. Учитывай объём работы, координацию
и риск конфликтов; при сопоставимом параллелизме выбирай более простой план.
Для одного неделимого AC или неизбежной последовательности сохрани это ограничение.

Проверь выбранный вариант:

- Каждая задача полностью закрывает хотя бы один согласованный AC с учётом
  выполненных зависимостей; каждый AC принадлежит ровно одной задаче. Тесты,
  фикстуры и подготовка входят в соответствующие задачи. Не создавай и не дроби
  AC ради параллелизма и не выделяй подготовительную задачу без собственного AC.
- Для каждого depends_on назови необходимый результат предшественника. Привычный
  порядок работы сам по себе не создаёт зависимости. Если нужен только запрет
  совместного выполнения, используй cannot_parallel_with без навязывания порядка.
- Проверь совместимость изменений файлов, контрактов, миграций и окружения.
  Общий файл допускает независимые участки; разные файлы не доказывают независимость.
  Сохрани реальные зависимости: согласованный интерфейс или mock не заменяет
  результат, необходимый для полной проверки AC.

Запиши обоснование по шаблону tasks: выбранные границы, независимые задачи,
причины зависимостей и ограничений, рассмотренную альтернативу либо причину
сохранения разбиения. Число задач и глубина графа без оценки трудоёмкости
не доказывают ускорение. Если улучшение требует изменения specs/design,
верни существенный выбор в обсуждение по правилам входа в планирование.

## Финальный gate

До предложения финального согласования учти [выбор гуманизации](../references/editorial-pass.md) текущих
tasks и остальных изменённых документов; стилистические правки после ревью
требуют пересчёта его актуальности по общим правилам.

Установи `plan_approved` только когда одновременно проверены:

- Корректная структура текущего комплекта.
- Закрытые блокирующие вопросы обсуждения; состояние ревью и находки показаны отдельно и не входят в условия готовности.
- Явное `plan_approval` текущего комплекта; готовность документов также сохранена.

Явное согласование текущего плана сохрани сразу как `plan_approval`, без дополнительных вопросов о ревью, waiver или запуске реализации. Оно разрешает выполнение по [общему контракту](../../sdd-shared/references/document-format-review.md#опциональное-ревью-и-разрешение-на-реализацию). Если обязательное условие отсутствует, сохрани ответ и сообщи конкретный дефект. При готовности сохрани checkpoint, сообщи пути и ограничения ревью и перейди в [sdd-apply](../../sdd-apply/SKILL.md), передав реальный текст согласования и его источник как instruction. Явную оговорку пользователя «пока не выполняй» соблюдай; после перерыва сверяй актуальность согласования и отсутствие отмены. Baseline sync и архивирование этим согласованием не разрешаются.
