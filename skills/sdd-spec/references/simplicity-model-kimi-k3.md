# Уточнения simplicity для Kimi K3 и K3.1 Pro

Используй последовательность внутри порученного ревью:

1. Установи требуемый результат, ответственность и действующие условия приёмки.
2. Найди существующие способы получить результат с необходимыми полномочиями.
3. Для существенного добавленного механизма установи нарушение без него и полную
   стоимость его сохранения. Реалистичный риск достаточен без истории инцидентов.
4. Проследи последствия удаления для потребителей, данных, контрактов и гарантий.
5. Проверь, не отклоняют ли условия приёмки допустимую работу и не дублируют ли
   обеспеченное подтверждение без нового основания.
6. Дай заключение в формате SDD, разделив находки и недоступные основания.

Это не шесть новых gates и не требование отдельного отчёта по каждому шагу.
Применяй весь релевантный предмет общей линзы, включая retry и жизненный цикл доступов.

Примеры показывают различие, а не задают готовый ответ:

- Публикация независимого лендинга запрещена при любом изменении соседнего сервиса.
  Если связи и соответствующего обязательства нет, предложи убрать лишнее условие,
  сохранив подтверждение публикации самого лендинга.
- Отдельная роль БД ограничивает сервис разрешёнными данными. Общий доступ дал бы
  лишние права: сохрани роль, хотя credentials станет больше.

Для находки укажи механизм, основание, последствия, упрощение и сохраняемую гарантию.
Отсутствие находок допустимо; число примеров не задаёт квоту замечаний.
При отдельном поручении пересмотреть решение сначала рассмотри удаление лишнего
и существующие возможности. Не создавай заменяющую подсистему ради сохранения
ошибочной проверки. Новое объяснение не устраняет прежнюю причину сложности.

Статусы, согласования и разрешение реализации определяются SDD. Дополнение
не вводит запрет реализации по severity находок, отдельный QA-этап или новые роли.
После порученной проверки остановись; расширение требует конкретного основания.
