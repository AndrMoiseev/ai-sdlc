# SDD Spec

Только при доработке самого `sdd-spec` перед изменением инструкций, скриптов,
тестов или эвалов прочитай [правила сопровождения](references/maintenance.md).
При подготовке спецификаций другого проекта этот документ не загружай.

## Начало

Запускай только по явному `$sdd-spec`, `/sdd-spec` или выбору пользователем этого скилла. Последующие сообщения продолжают выбранный процесс без повторного вызова. В новой сессии обычная просьба спланировать изменение не активирует sdd.

Перед работой прочитай [условия запуска](references/runtime-setup.md), [общую основу формата](../sdd-shared/references/document-format.md) и адаптер среды: [Codex](references/codex.md), [Claude Code](references/claude-code.md) или [произвольный агент](references/generic.md), если ни одна из этих сред не установлена достоверно. Разделы формата догружай по операции из выбранного флоу. Выбери изменение через [resume](flows/resume.md): Git-проверка принятой точки и чистого дерева до новых правок; полное восстановление после потери контекста. Затем открой нужный флоу. Завершай проверенные изменения [Git-чекпойнтом](references/checkpoint.md). Принятие состояния сохраняет основание работы, а конкретные действия требуют действующего поручения.

Перед запуском архитектора, explorer, рецензента или редактора примени
[проектный выбор субагентов](../sdd-shared/references/subagents.md): роль выбирает определение
агента из `.sdd/settings.json`; отсутствие настройки сохраняет модель родителя.
Ревью охватывает весь подготовленный комплект: consistency, simplicity, premortem
и проектные линзы; при наличии плана добавь plan. Каждая линза работает в отдельном
чистом контексте, simplicity выполняется один раз.
Для simplicity после выбора модели подготовь [инструкции](references/simplicity-instructions.md).

## Координация и статусы

Основной агент — оркестратор. До содержательного исследования, подготовки,
пересмотра или восстановления документов прочитай [контракт архитектора](references/architect.md).
Назначь `sdd-spec.architect` основным автором всего комплекта и его пояснений.
Архитектор автоматически применяет `fpf-problem-solving` по
[правилам FPF](references/architect.md#применение-fpf).
Флоу читают обе роли: авторские шаги выполняет архитектор; диалог, поручения,
записи решений и состояния, проверки переходов и Git-checkpoint ведёт оркестратор.
Ошибки авторских документов возвращай архитектору. Продолжай его контекст между
итерациями одной работы; проверки и ревью получают завершённую версию без записи.

Перед исследовательским поручением и каждой детерминированной проверкой документов
примени [передачу explorer](references/explorer.md). Research делегируется по
необходимости; documents/plan check выполняет explorer. Сохраняй внешние request/result
и фактический launch, затем ссылки и digest в checkpoint.

До исследования источников, сохранения его результатов или resume прочитай
[контракт исследования](references/research.md). Архитектор сохраняет значимые
результаты в `research.md` выбранного изменения; оркестратор включает документ
в checkpoint. Для первой устойчивой записи определи change-id уже в explore.

Перед работой с субагентами прочитай [общие правила координации](../sdd-shared/references/coordination.md).

## Выбор флоу

Для исследования, черновика, пересмотра и продолжения прочитай
[правила обсуждения](references/discussion.md): явно показывай каждую существенную
развилку в сообщении. Можно обсуждать несколько вопросов сразу; делегирование
действует только на показанный список. При открытых вопросах агент не запрашивает
утверждение. Спецификация и план образуют единый комплект: после закрытия вопросов
предложи написать отсутствующий план или провести ревью; с готовым планом — ревью
либо утверждение всего комплекта. Рекомендации можно игнорировать без действий.

После завершённой порции правок документов, включая черновики, предложи
[гуманизацию через humanizer-ru](references/editorial-pass.md). Запускай её только
по явному согласию пользователя в указанной области. Отказ или отсутствие ответа
не блокируют основной процесс; при продолжении учитывай сохранённый выбор.
Исходные отчёты ревью и ответы пользователя сохраняй дословно.

| Намерение и проверенное состояние | Флоу |
|---|---|
| Исследовать идею, уточнить пробел или блокирующий выбор | [explore](flows/explore.md) |
| Подготовить комплект выбранного маршрута | [draft](flows/draft.md) |
| Пересмотреть существующие документы | [revise](flows/revise.md) |
| Подготовить или обновить пояснение решения, продолжить превью | [explain](flows/explain.md) |
| Запустить согласованное независимое ревью | [review](flows/review.md) |
| Рассмотреть находки, исключения и согласования | [user-review](flows/user-review.md) |
| Создать план по явной команде или согласовать готовый | [plan](flows/plan.md) |
| Продолжить после перерыва или восстановить checkpoint | [resume](flows/resume.md) |

До зависимой работы выбери маршрут по [правилам рефакторинга](references/refactoring.md#выбор-маршрута). Обычное изменение сохраняй в `sdd/changes/<change-id>/`, рефакторинг — в `sdd/refactoring/<change-id>/`. Результат подготовки — согласованный план. Запускай [sdd-apply](../sdd-apply/SKILL.md) только по явному разрешению пользователя выполнить этот план по [общим правилам](../sdd-shared/references/document-format-review.md#опциональное-ревью-и-разрешение-на-реализацию). Утверждение плана само по себе не разрешает выполнение; оба решения могут быть даны одним сообщением. Реализацию веди через sdd-apply; baseline sync и архивирование требуют отдельного поручения.

Примеры: «`$sdd-spec` поясни решение order-export с диаграммами»;
«`/sdd-spec` обнови пояснение order-export»; после начала процесса:
«Продолжи незавершённые превью по сохранённому промпту».
