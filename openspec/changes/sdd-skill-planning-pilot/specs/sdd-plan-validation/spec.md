## Purpose

Проверяет структуру документов изменения, трассировку и однократное покрытие критериев задачами до агентского ревью.

Статус: черновик. Блоки Scenario здесь оформляют критерии по формату текущего OpenSpec; будущий скилл не требует отдельной сущности сценария.

## ADDED Requirements

### Requirement: REQ-requirement-contract

Требования MUST иметь критерии с ID, ссылкой на требование, условиями и наблюдаемым результатом. Отдельная сущность сценария MUST NOT быть обязательной. Данные связей MUST храниться в YAML-блоках Markdown без ручного дублирующего реестра.

#### Scenario: AC-acceptance-record
- **WHEN** записано требование
- **THEN** оно имеет хотя бы один критерий, формат Given/When/Then необязателен; отсутствие SCN-ID не является ошибкой

#### Scenario: AC-delta-operation
- **WHEN** требование добавляется, меняется или удаляется
- **THEN** operation задает add/modify/remove; modify/remove ссылаются на baseline либо явно описывают его отсутствие и свидетельства исходного поведения

#### Scenario: AC-removal-coverage
- **WHEN** требование удаляется
- **THEN** критерии описывают результат удаления и покрываются задачами; неизмененные требования не требуют новых задач

### Requirement: REQ-decision-trace

Только записи DEC MUST иметь ID и ссылки хотя бы на одно требование. Разделы модулей и терминов MUST допускаться без ID и связей.

#### Scenario: AC-descriptive-design
- **WHEN** design содержит модули и термины без записей DEC
- **THEN** валидатор не требует формальных решений или задач для этих разделов

#### Scenario: AC-decision-reference
- **WHEN** запись DEC не ссылается ни на одно требование либо ссылка отсутствует
- **THEN** валидатор сообщает ошибку; требование без DEC само по себе допустимо

### Requirement: REQ-single-task-coverage

Каждый критерий в объеме изменения MUST быть назначен ровно одной задаче, каждая задача MUST иметь хотя бы один критерий. Одна задача может закрывать несколько критериев.

#### Scenario: AC-coverage-errors
- **WHEN** критерий не покрыт, покрыт двумя задачами или задача содержит только DEC
- **THEN** валидатор сообщает конкретные критерии и задачи; ссылка на решение не заменяет критерий

#### Scenario: AC-tests-inside-task
- **WHEN** задача планирует реализацию
- **THEN** необходимые тесты и технические шаги включены в нее; отдельная задача последующего покрытия тестами не создается; будущие тестовые файлы не обязаны существовать

### Requirement: REQ-identity-dependencies

Элементы MUST иметь уникальные в изменении стабильные смысловые ID. Задачи MUST иметь отдельные номера 1..N и зависимости по ID. Скрипт MUST выявлять неверные ID, ссылки, номера, зависимости на себя и циклы.

#### Scenario: AC-reorder-tasks
- **WHEN** задачи переставлены
- **THEN** номера могут измениться, ID и ссылки стабильны; номер не является зависимостью, прогресс считается по статусам

#### Scenario: AC-invalid-graph
- **WHEN** в зависимостях указан отсутствующий ID, сама задача либо цикл
- **THEN** проверка завершается ошибкой с указанием нарушенных связей

#### Scenario: AC-parallel-candidates
- **WHEN** у нескольких задач выполнены зависимости
- **THEN** они доступны по графу, но безопасность параллельных правок дополнительно проверяет рецензент

### Requirement: REQ-structural-repair

При ошибках агент MUST уведомить пользователя и автоматически исправить однозначные структурные ошибки без изменения согласованного смысла, повторить проверку и сообщить результат.

#### Scenario: AC-safe-repair
- **WHEN** ошибка имеет однозначное структурное исправление
- **THEN** агент исправляет ее без отдельного согласия и проверяет результат

#### Scenario: AC-semantic-repair
- **WHEN** исправление требует выбора поведения или состава задач
- **THEN** агент исправляет остальное и задает конкретный вопрос; исключение из структурных правил не допускается и ревью не запускается
