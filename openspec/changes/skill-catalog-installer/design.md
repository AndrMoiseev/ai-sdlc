## Context

Мотивация и границы — в [proposal](proposal.md). В репозитории есть три исходных пакета в `skills/`, рабочие установки в `.agents/skills/` и ручная инструкция подключения в `skills/sdd-spec/README.md`. Корневого установщика и каталога нет; `openspec/specs/` пока пуст. Пакеты содержат не только `SKILL.md`, но и скрипты, references, templates, метаданные агентов и собственные lock-файлы. Python 3.11+, uv и pytest уже используются для `sdd-spec`.

Основная ветка считается проверенной по решению пользователя. Каталог является явным перечнем рекомендаций: присутствие файла в репозитории или установленной копии не добавляет скилл в него автоматически. Согласованное использование OpenSpec для этого change не отменяет ADR-0002: поставляемый установщик не зависит от OpenSpec.

Обязательные пользовательские контракты находятся в [каталоге](specs/skill-catalog/spec.md) и [установке](specs/skill-project-installation/spec.md). Детали форматов ниже — предлагаемые технические решения первой версии, а не дополнительные решения пользователя.

## Goals / Non-Goals

**Goals:**
- Отделить вычисление состава от скачивания и изменения проекта, чтобы проверять правила на локальных Git-фикстурах без доступа к агентам.
- Зафиксировать всё необходимое для восстановления пакетов и определения локальных правок в переносимых файлах проекта.
- Иметь одну точку управления обеими копиями, сохраняя общий исходный пакет.

**Non-Goals:**
- Автоматически адаптировать поведение скиллов между агентами, оценивать качество, запускать их инструкции или настраивать MCP и runtime-зависимости.
- Разрешать semver-диапазоны, несколько версий одного скилла, необязательные зависимости, наследование наборов и пользовательские исключения из `all`.
- Предоставлять команды удаления каталога, публикации, глобальной установки или автоматического слияния локальных правок.

## Decisions

### 1. Собственный небольшой CLI

По решению пользователя реализуется собственный установщик. Предлагаемый стек — Python-пакет `tools/skill-catalog/` с console entry point `skill-catalog`, отдельным `pyproject.toml`, `uv.lock` и тестами. Это использует существующий стек репозитория и не превращает установщик в ещё один скилл. Загрузку точных коммитов выполняет Git; парсинг YAML — библиотека с закреплённой зависимостью. Установщик не зависит от пакета `sdd-checks`.

Доставка первой версии — запуск пакета из публичного Git-источника через uv/uvx, с закреплённой версией самого CLI. Предварительно нужны uv и Git; точную однострочную команду проверить при подготовке поставки и затем поместить в README. Git remote репозитория сейчас указывает на `AndrMoiseev/ai-sdlc`; публичную доступность и команду загрузки нужного подкаталога следует подтвердить, а не выводить из наличия remote. До публикации коммита CLI используется установка из локального checkout в чистый тестовый проект. Публикация в PyPI/npm не требуется и не входит в этот change.

Проверки установки по SHA, воспроизведения состава, обновления и сохранения локальных правок входят в обычные тесты реализации. Отдельного этапа выбора установщика перед разработкой нет.

### 2. Один явный каталог и зарезервированный набор all

Предлагаемый `catalog.yaml`:

```yaml
schema_version: 1
skills:
  sdd-doc:
    source:
      kind: catalog
      path: skills/sdd-doc
    requires: []
  sdd-skill-conductor:
    source:
      kind: catalog
      path: skills/sdd-skill-conductor
    origin:
      repository: https://github.com/smixs/skill-conductor.git
      path: .
      base_commit: null
      note: Уточнить по сохранённым сведениям импорта; не угадывать SHA.
    requires: []
bundles:
  all:
    include: '*'
```

Это иллюстрация формата, не окончательный начальный каталог. В рабочий каталог войдут все три исходных пакета; происхождение `sdd-spec` также опирается на его `references/openspec-origin.md`. Реальные обязательные связи записываются только после чтения инструкций: упоминание другого скилла не доказывает зависимость. Для внешнего пакета `source.kind: git` дополнительно требует `repository`, полный `commit` и `path`. Для другого набора `include` — явный список идентификаторов; только `all` принимает `'*'`.

У `kind: catalog` нет собственного SHA: пакет берётся из того же коммита, что и каталог. Это исключает необходимость заранее знать коммит, в который попадёт сам файл каталога. У внешних пакетов SHA фиксирует сопровождающий каталога; команда `update` в проекте не подбирает его самостоятельно. `origin` описывает происхождение и не участвует в скачивании.

Имена — переносимые lowercase kebab-case, совпадающие с `name` в `SKILL.md`. Дубликаты YAML-ключей, пути вне источника, отсутствующий `SKILL.md`, неизвестные зависимости и циклы — ошибки данных. Они не являются оценкой готовности или совместимости. Резолвер возвращает отсортированный состав с замыканием зависимостей; один идентификатор означает один пакет в выбранном состоянии каталога.

### 3. Манифест намерений и lock фактической установки

`skill-catalog.yaml` в проекте хранит `schema_version`, URL каталога, путь `catalog.yaml`, имя отслеживаемой основной ветки, выбранный набор и список агентов. При первом подключении основная ветка определяется из remote HEAD и записывается явно. CLI принимает `--project` (по умолчанию текущий каталог), чтобы не угадывать корень установки по вложенной директории.

`skill-catalog.lock.json` хранит:
- версию схемы, версию CLI и зафиксированный снимок выбора из манифеста;
- URL, путь и полный коммит каталога;
- для каждого пакета: идентификатор, прямые зависимости, точные repository/commit/path, происхождение и digest пакета;
- для каждой установленной копии: относительную директорию назначения и перечень файлов с SHA-256 содержимого и признаком executable, когда файловая система его поддерживает.

Никаких временных путей и timestamps, меняющихся при каждом запуске. Контрольные суммы считаются по исходным байтам без нормализации переводов строк; digest пакета включает отсортированные относительные пути и файловые суммы с однозначным кодированием. Windows ACL и Unix uid/gid не входят в сравнение. Манифест, lock и копии пакетов коммитятся в проект. Если Git checkout изменяет байты из-за autocrlf, `status` честно показывает различие; README документирует настройку атрибутов устанавливаемых директорий, но CLI не переписывает `.gitattributes` сам.

Неподдерживаемая схема, единственный оставшийся учётный файл или несогласованный lock не считаются пустой установкой. Ручное изменение желаемого набора/агентов разрешается применить через `update`; `install` сообщает о необходимости этой команды. Смена источника каталога существующего подключения в v1 не поддерживается, чтобы не подменять его молча.

### 4. Содержимое пакета — дерево файлов выбранного коммита

Git-источник извлекается в staging по полному SHA без применения локальных пользовательских преобразований checkout к байтам пакета. В пакет входят файлы его каталога, включая скрытые файлы, tests, evals, scripts, references, assets, собственные lock-файлы и лицензии. Рабочее дерево разработчика, `.git`, неотслеживаемые кэши и результаты прогонов не копируются. Лицензионные материалы, необходимые для распространения, должны входить в пакет; при отсутствии их сопровождающий исправляет комплектность до добавления источника.

Первая версия работает с обычными файлами и директориями; gitlinks/submodules и симлинки в исходном пакете вызывают понятную ошибку неподдерживаемой структуры. Скрипты из скачанного скилла не исполняются. Обеим целям поставляется одинаковое содержимое, без подстановки метаданных под агента.

### 5. Команды и план применения

Предлагаемый интерфейс после запуска CLI:

```text
skill-catalog install all --catalog <public-git-url> [--agents codex claude-code] [--project <path>]
skill-catalog install [--project <path>]
skill-catalog update [--project <path>]
skill-catalog status [--project <path>]
```

Первое подключение разрешает ветку один раз. Повторный `install` сверяет локальные копии с lock; скачивает только необходимое для полностью отсутствующих пакетов, не обращаясь к текущему состоянию ветки. `update` читает новое состояние отслеживаемой ветки и вычисляет добавления, замены и удаления. Если обе цели или состав изменились, новый lock отражает новый выбор; лишние ранее управляемые копии удаляются по тем же правилам сохранности. Неизменное состояние не переписывает учётные файлы.

Установщик разделяется на чтение/валидацию форматов, резолвер состава, получение снимков Git, построение плана изменений и применение к проекту. План содержит все затрагиваемые пути и ожидаемое прежнее состояние. Сначала загружаются все нужные пакеты, проверяются суммы и обе копии каждого назначения; непосредственно перед записью прежнее состояние сверяется повторно. Изменение одной копии останавливает всю операцию. Посторонние пакеты не входят в план.

При первой установке точное совпадение ранее ручной копии позволяет принять её под управление. Любое отличие требует сохранить/перенести локальные правки вручную; автоматического merge и `--force` нет. При повторной установке полностью отсутствующий пакет восстанавливается, но удаление отдельного файла внутри существующего пакета считается локальной правкой.

Для обрабатываемой ошибки записи используются staging и резервные копии только затронутых пакетов и учётных файлов; новый lock публикуется после успешного применения. Обычная ошибка вызывает откат. Незавершённая операция оставляет маркер и резервные данные; последующая мутация отказывается продолжать до восстановления, а `status` объясняет состояние. Полная атомарность нескольких каталогов при отключении питания не обещается. Успешная операция очищает временные данные; конкурентные запуски в одном проекте блокируются.

`status` читает только локальные данные и выводит состояния `unchanged`, `missing`, `modified`, а также ошибки установки. Предлагаемые exit codes: 0 — успех/нет отклонений; 1 — ошибка или конфликт, а для `status` обнаруженные отклонения; 2 — неправильные аргументы. Отсутствие подключения у `status` — нормальный информационный результат с кодом 0.

## Risks / Trade-offs

- Две физические копии увеличивают Git diff → общий lock, одинаковое содержимое и проверка обеих целей; симлинки не обязательны на Windows.
- Upstream может удалить доступный коммит → уже закоммиченные копии продолжают работать; восстановление без источника завершается ошибкой, без перехода на latest.
- Кэши и локальные правки внутри установленного пакета блокируют обновление → сообщать точные пути, не удалять такие данные автоматически.
- Содержимое Git checkout может отличаться по переводам строк → проверка исходных байтов и документация `.gitattributes`; включить этот случай в межплатформенную проверку.
- Собственный CLI требует сопровождения → ограничить первую версию двумя целями, одним источником каталога и зависимостями по идентификаторам без диапазонов версий.
- Пользовательские/глобальные скиллы могут влиять на обнаружение агентом → установщик отвечает за проектные файлы; не заявлять доказанное поведение агента по результату копирования.

## Migration Plan

1. Создать пакет собственного CLI с точкой входа, закреплёнными зависимостями и тестовым окружением.
2. Реализовать форматы, резолвер и операции, проверяя их на локальных Git-фикстурах. В интеграционных тестах использовать `sdd-doc`, `sdd-skill-conductor` и неизменённый публичный пакет с закреплённым SHA. Для графа использовать тестовую связь, явно не выдавая её за реальную зависимость этих скиллов.
3. Добавить рабочий каталог трёх исходных пакетов и инструкции запуска. Не включать тестовый сторонний пакет в рекомендации автоматически.
4. Проверить полный `all` в чистом проекте. Подключение самого `ai-sdlc` выполнять только после сравнения существующих копий; различающиеся копии и настройки сохранить. Если исходники скиллов меняются, следовать действующему порядку в `AGENTS.md`.
5. Откат подключённого проекта — восстановить из Git согласованный комплект манифеста, lock и управляемых директорий. CLI сам не создаёт коммиты и не публикует изменения.
