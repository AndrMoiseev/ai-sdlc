## Context

Мотивация и границы - в [proposal](proposal.md). В репозитории есть три исходных пакета в `skills/`, рабочие установки в `.agents/skills/` и ручная инструкция подключения в `skills/sdd-spec/README.md`. Корневого установщика и каталога нет; `openspec/specs/` пока пуст. В пакетах есть `SKILL.md`, скрипты, references, templates, метаданные агентов и собственные lock-файлы. Для `sdd-spec` уже используют Python версии 3.11 и выше, uv и pytest.

По решению пользователя основная ветка считается проверенной. Каталог явно перечисляет рекомендации. Наличие файла в репозитории или установленной копии не добавляет скилл в каталог автоматически. Использование OpenSpec для этого change не отменяет ADR-0002: поставляемый установщик не зависит от OpenSpec.

Обязательные пользовательские контракты описаны в [каталоге](specs/skill-catalog/spec.md) и [установке](specs/skill-project-installation/spec.md). Ниже предложены технические решения для форматов первой версии. Они не добавляют решений от имени пользователя.

## Goals / Non-Goals

**Goals:**
- Отделить вычисление состава от скачивания и изменения проекта, чтобы проверять правила на локальных Git-фикстурах без доступа к агентам.
- Зафиксировать всё необходимое для восстановления пакетов и определения локальных правок в переносимых файлах проекта.
- Управлять обеими копиями из одной точки, сохраняя общий исходный пакет.

**Non-Goals:**
- Автоматически адаптировать поведение скиллов между агентами, оценивать качество, запускать их инструкции или настраивать MCP и runtime-зависимости.
- Разрешать semver-диапазоны, несколько версий одного скилла, необязательные зависимости, наследование наборов и пользовательские исключения из `all`.
- Предоставлять команды удаления каталога, публикации, глобальной установки или автоматического слияния локальных правок.

## Decisions

### 1. Собственный небольшой CLI

По решению пользователя разрабатываем собственный установщик. Предлагаемый стек - Python-пакет `tools/skill-catalog/` с console entry point `skill-catalog`, отдельным `pyproject.toml`, `uv.lock` и тестами. Стек уже используется в репозитории, а установщик остаётся отдельным инструментом. Git загружает точные коммиты; библиотека с закреплённой зависимостью разбирает YAML. Установщик не зависит от пакета `sdd-checks`.

Первую версию запускаем из публичного Git-источника через uv/uvx, закрепив версию самого CLI. Предварительно нужны uv и Git. Точную однострочную команду нужно проверить при подготовке поставки и затем поместить в README. Git remote репозитория сейчас указывает на `AndrMoiseev/ai-sdlc`. Публичную доступность и команду загрузки нужного подкаталога нужно подтвердить: наличия remote для этого недостаточно. До публикации коммита CLI устанавливаем из локального checkout в чистый тестовый проект. Публикация в PyPI/npm не требуется и не входит в этот change.

Обычные тесты реализации проверяют установку по SHA, воспроизведение состава, обновление и сохранение локальных правок. Отдельного этапа выбора установщика перед разработкой нет.

### 2. Один явный каталог и зарезервированный набор all

Предлагаемый `catalog.yaml`:

```yaml
schema_version: 1
skills:
  sdd-doc:
    source:
      kind: catalog
      path: skills/sdd-doc
    requires: []
  sdd-skill-conductor:
    source:
      kind: catalog
      path: skills/sdd-skill-conductor
    origin:
      repository: https://github.com/smixs/skill-conductor.git
      path: .
      base_commit: null
      note: Уточнить по сохранённым сведениям импорта; не угадывать SHA.
    requires: []
bundles:
  all:
    include: '*'
```

Это иллюстрация формата, не окончательный начальный каталог. В рабочий каталог войдут все три исходных пакета; сведения о происхождении `sdd-spec` также берём из его `references/openspec-origin.md`. Реальные обязательные связи записываем только после чтения инструкций. Упоминание другого скилла не доказывает зависимость. Для внешнего пакета `source.kind: git` дополнительно требует `repository`, полный `commit` и `path`. Для другого набора `include` - явный список идентификаторов; только `all` принимает `'*'`.

У `kind: catalog` нет собственного SHA: пакет берём из того же коммита, что и каталог. Поэтому заранее знать коммит с файлом каталога не нужно. У внешних пакетов SHA фиксирует сопровождающий каталога; команда `update` в проекте не подбирает его самостоятельно. `origin` описывает происхождение и не участвует в скачивании.

Имена - переносимые lowercase kebab-case, совпадающие с `name` в `SKILL.md`. Дубликаты YAML-ключей, пути вне источника, отсутствующий `SKILL.md`, неизвестные зависимости и циклы - ошибки данных. Эти проверки не оценивают готовность или совместимость. Резолвер возвращает отсортированный состав с замыканием зависимостей; один идентификатор означает один пакет в выбранном состоянии каталога.

### 3. Манифест намерений и lock фактической установки

`skill-catalog.yaml` в проекте хранит `schema_version`, URL каталога, путь `catalog.yaml`, имя отслеживаемой основной ветки, выбранный набор и список агентов. При первом подключении CLI определяет основную ветку из remote HEAD и записывает её явно. CLI принимает `--project` (по умолчанию текущий каталог), чтобы не угадывать корень установки по вложенной директории.

`skill-catalog.lock.json` хранит:
- версию схемы, версию CLI и зафиксированный снимок выбора из манифеста;
- URL, путь и полный коммит каталога;
- для каждого пакета: идентификатор, прямые зависимости, точные repository/commit/path, происхождение и digest пакета;
- для каждой установленной копии: относительную директорию назначения и перечень файлов с SHA-256 содержимого и признаком executable, когда файловая система его поддерживает.

В этих файлах нет временных путей и timestamps, меняющихся при каждом запуске. CLI считает контрольные суммы по исходным байтам без нормализации переводов строк. Digest пакета включает отсортированные относительные пути и файловые суммы с однозначным кодированием. Windows ACL и Unix uid/gid не входят в сравнение. Манифест, lock и копии пакетов коммитим в проект. Если Git checkout изменяет байты из-за autocrlf, `status` показывает различие. README описывает настройку атрибутов устанавливаемых директорий, но CLI не переписывает `.gitattributes` сам.

Неподдерживаемая схема, единственный оставшийся учётный файл или несогласованный lock не считаются пустой установкой. Изменённый вручную выбор набора/агентов можно применить через `update`; `install` сообщает, что нужна эта команда. В v1 нельзя сменить источник каталога существующего подключения, чтобы не подменять его молча.

### 4. Содержимое пакета - дерево файлов выбранного коммита

CLI извлекает Git-источник в staging по полному SHA. Локальные пользовательские преобразования checkout не применяются к байтам пакета. В пакет входят файлы его каталога, включая скрытые файлы, tests, evals, scripts, references, assets, собственные lock-файлы и лицензии. CLI не копирует рабочее дерево разработчика, `.git`, неотслеживаемые кэши и результаты прогонов. Лицензионные материалы, необходимые для распространения, должны входить в пакет. Если их нет, сопровождающий дополняет пакет до добавления источника.

Первая версия работает с обычными файлами и директориями; gitlinks/submodules и симлинки в исходном пакете вызывают понятную ошибку неподдерживаемой структуры. CLI не исполняет скрипты из скачанного скилла. Обе цели получают одинаковое содержимое, без подстановки метаданных под агента.

### 5. Команды и план применения

Предлагаемый интерфейс после запуска CLI:

```text
skill-catalog install all --catalog <public-git-url> [--agents codex claude-code] [--project <path>]
skill-catalog install [--project <path>]
skill-catalog update [--project <path>]
skill-catalog status [--project <path>]
```

Первое подключение разрешает ветку один раз. Повторный `install` сверяет локальные копии с lock; скачивает только необходимое для полностью отсутствующих пакетов, не обращаясь к текущему состоянию ветки. `update` читает новое состояние отслеживаемой ветки и вычисляет добавления, замены и удаления. Если обе цели или состав изменились, новый lock отражает новый выбор; лишние ранее управляемые копии удаляются по тем же правилам сохранности. Неизменное состояние не переписывает учётные файлы.

В установщике отдельно работают чтение/валидация форматов, резолвер состава, получение снимков Git, построение плана изменений и применение к проекту. План содержит все затрагиваемые пути и ожидаемое прежнее состояние. Сначала установщик загружает все нужные пакеты, проверяет суммы и обе копии каждого назначения. Непосредственно перед записью он повторно сверяет прежнее состояние. Изменение одной копии останавливает всю операцию. Посторонние пакеты не входят в план.

При первой установке точное совпадение ранее ручной копии позволяет принять её под управление. Любое отличие требует сохранить/перенести локальные правки вручную; автоматического merge и `--force` нет. При повторной установке полностью отсутствующий пакет восстанавливается, но удаление отдельного файла внутри существующего пакета считается локальной правкой.

На случай обрабатываемой ошибки записи установщик использует staging и резервные копии только затронутых пакетов и учётных файлов. Новый lock записывает после успешного применения. Обычная ошибка вызывает откат. Незавершённая операция оставляет маркер и резервные данные. До восстановления установщик блокирует следующие изменения, а `status` объясняет состояние. Полная атомарность нескольких каталогов при отключении питания не обещается. После успеха установщик очищает временные данные; конкурентные запуски в одном проекте блокируются.

`status` читает только локальные данные и выводит состояния `unchanged`, `missing`, `modified`, а также ошибки установки. Предлагаемые exit codes: 0 - успех/нет отклонений; 1 - ошибка или конфликт, а для `status` обнаруженные отклонения; 2 - неправильные аргументы. Отсутствие подключения у `status` - нормальный информационный результат с кодом 0.

## Risks / Trade-offs

- Две физические копии увеличивают Git diff. Используем общий lock, одинаковое содержимое и проверку обеих целей; симлинки не обязательны на Windows.
- Upstream может удалить доступный коммит. Уже закоммиченные копии продолжают работать; восстановление без источника завершается ошибкой, без перехода на latest.
- Кэши и локальные правки внутри установленного пакета блокируют обновление. Нужно сообщать точные пути, не удаляя такие данные автоматически.
- Содержимое Git checkout может отличаться по переводам строк. Проверяем исходные байты, документируем `.gitattributes` и включаем этот случай в межплатформенную проверку.
- Собственный CLI требует сопровождения. Первую версию ограничиваем двумя целями, одним источником каталога и зависимостями по идентификаторам без диапазонов версий.
- Пользовательские/глобальные скиллы могут влиять на обнаружение агентом. Установщик отвечает за проектные файлы; результат копирования не доказывает поведение агента.

## Migration Plan

1. Создать пакет собственного CLI с точкой входа, закреплёнными зависимостями и тестовым окружением.
2. Реализовать форматы, резолвер и операции, проверяя их на локальных Git-фикстурах. В интеграционных тестах использовать `sdd-doc`, `sdd-skill-conductor` и неизменённый публичный пакет с закреплённым SHA. Для графа использовать тестовую связь, явно не выдавая её за реальную зависимость этих скиллов.
3. Добавить рабочий каталог трёх исходных пакетов и инструкции запуска. Не включать тестовый сторонний пакет в рекомендации автоматически.
4. Проверить полный `all` в чистом проекте. Подключение самого `ai-sdlc` выполнять только после сравнения существующих копий; различающиеся копии и настройки сохранить. Если исходники скиллов меняются, следовать действующему порядку в `AGENTS.md`.
5. Для отката подключённого проекта восстановить из Git согласованный комплект манифеста, lock и управляемых директорий. CLI сам не создаёт коммиты и не публикует изменения.
