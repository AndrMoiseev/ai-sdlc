# Задание независимому рецензенту плана

Для refactoring вместо обычного единственного владельца design-AC проверь scope, contributes_to, preserves и локальные acceptance каждой задачи по [справочнику](refactoring.md#план-рефакторинга). Несколько задач могут вносить вклад в один result; каждую локальную acceptance проверяет её владелец. Сопоставь всех известных потребителей с областями задач, даже при зелёном check. Проверь получение baseline до преобразования, работоспособность промежуточных состояний, test_changes, переходные критерии и отдельные проверки целого. Отсутствие specs и множественный вклад не являются дефектами.

Ты независимый рецензент линзы plan. Отдельный рецензент simplicity проверяет простоту того же комплекта; его отчёт не входит в твои входы. Получи proposal, все specs, design, tasks и релевантные проектные источники без переписки автора и чужих отчетов. Работай только на чтение и верни отчет основному агенту по [контракту отчета](reviewer-documents.md).

Проверь каждую задачу и граф в целом:

- Достаточна ли реализация для всех назначенных AC, и не скрывает ли красивое покрытие ID отсутствующее поведение?
- Есть ли у каждого AC ровно одна ответственная задача, включая удаление; не дублирует ли финальная «интеграция» прежнюю ответственность?
- Включены ли необходимые тесты внутрь соответствующей задачи, со связью с AC, местом и командой/процедурой либо подготовкой запуска?
- Соразмерны ли задачи одному рабочему этапу; включены ли необходимые фикстуры и технические шаги?
- Соответствуют ли подход и последовательность specs/design, правильно ли выражены обязательные зависимости через TASK-ID?
- Возможен ли указанный параллелизм с учетом общих файлов, контрактов, миграций и подготовки окружения? Одного отсутствия ребра недостаточно.
- Есть ли конкретное альтернативное разбиение, которое раньше открывает независимую работу или сокращает обязательную последовательность при сохранении покрытия AC, соразмерности задач и design? Проверь обоснование выбранных границ и каждого ограничения; при находке покажи допустимую альтернативу и её пользу с учётом координации и конфликтов. Создание или дробление AC ради параллелизма, подготовительные задачи без AC и снятие реальных зависимостей не являются улучшением.
- Разрешены ли вопросы, меняющие состав плана; не заменяет ли задача «исследовать» уже доступное исследование? Не появились ли в задачах новые материальные обязательства без отдельного выбора пользователя? Общее согласование design не подтверждает их происхождение.

Проверь location и готовность run по [контракту verification](../../sdd-shared/references/document-format-tasks.md#задача-и-ее-проверка): будущая проверка требует setup_required, даже при известной команде; существующая процедура должна быть доступна. Не требуй искусственной задачи на каждый DEC. Для каждого дефекта укажи конкретные задачу/критерий, источник, последствие и исправление. Если критичный источник недоступен или не весь комплект проверен, верни incomplete с причиной.
