# Start an execution

Read [start API](../references/api-start.md); use installed operation help for request fields.

1. Resolve the selected change and reuse its current plan approval as `instruction: {text, source}` under the [shared approval contract](../../sdd-shared/references/document-format-review.md#опциональное-ревью-и-разрешение-на-реализацию). Read the actual response and its message or saved USER-record source; “Согласовываю план” is sufficient without an added “приступай”. This authorization covers task worktrees, parallel workers, required checks, reviews and local task commits. Check for a later cancellation, replacement or explicit pause. Use the public `validate` operation to inspect readiness without changing normative files. Missing or invalid approvals, unresolved blocking questions, ambiguous ownership, or incompatible sdd-shared stop admission. Return specification work to sdd-spec, naming the concrete missing condition rather than asking to approve the same plan again.
2. Check local execution branch, HEAD, Git identity, pre-existing staged/unstaged/untracked work, and commit capability. Preserve existing work. Execution authorization includes local task commits; it does not authorize mixing unrelated changes into them.
3. Invoke `initialize` with validated input arguments and the actual orchestrator identity. Pass `isolation: true` after verifying task worktrees. Execution is parallel and requires isolation. If worktrees are unavailable, report the blocker before implementation. For an existing execution use resume instead. The script captures basis and baseline and generates the initial dashboard before any task starts.
4. Read the saved state and show the dashboard link using [progress](../references/progress.md). Return to the router to load the parallel execution flow. Continue authorized tasks autonomously until completion or a concrete blocker.
