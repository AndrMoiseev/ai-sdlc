# Встраивание премортема в sdd-spec

## Контекст и границы

Цель и исключения определены в proposal, наблюдаемое поведение
в спецификации premortem.
Исходные explore и
draft уже направляют агента на
проверку предположений, доступных источников и рисков. Новая capability
добавляет обязательную проверку условий, от которых зависит ожидаемый результат.

В sdd нет исходной спецификации премортема. Существующая capability
solution-explanation описывает другую возможность. Все требования этого
изменения добавляются; общие правила Q-ID, согласований и ревью сохраняются.

Исходный пакет находится в skills/sdd-spec, установленный в .agents/skills/sdd-spec.
Установленная копия отстаёт от исходной по возможности пояснения решения.
Планируемое изменение относится к исходному пакету; копирование установленной
версии поверх него потеряло бы уже сделанные дополнения.

## Термины

Премортем рассматривает возможный провал изменения до подробной спецификации.
Под провалом понимается отсутствие ожидаемого результата, даже если реализация
работает. Предпосылка описывает условие, от которого зависит этот результат.

Находка премортема связывает провал, предпосылку, основания и дальнейшее действие.
Это не FIND-запись независимого ревью. Для вопроса, который возникает
из находки, используется существующий Q-ID. Существенная неопределённость
может изменить цель, объём, поведение или выбранный подход.

## Модули и контракты

| Часть исходного пакета | Ответственность после изменения |
|---|---|
| flows/explore.md | Выполнить короткую проверку после установления цели и контекста; применить правила вопросов |
| flows/draft.md | До подробной спецификации использовать актуальный разбор либо выполнить проверку |
| flows/revise.md | Пересмотреть затронутые основания при изменении цели или предпосылок и обновить зависимые документы |
| flows/resume.md | Прочитать итог и документ по ссылке, проверить актуальность и восстановить недостающее |
| references/premortem.md, новый файл | Содержать общий порядок проверки, сохранения и работы с находками |
| references/document-format.md | Описать premortem.md как материал исследования и краткую запись в state |
| templates/premortem.md, новый файл | Задать контекст разбора и четыре части находки без обязательного количества |
| templates/state.md | Показать два варианта краткого итога; вопросы оставить в существующем формате |
| references/editorial-pass.md | Явно включить русскую авторскую прозу premortem.md в редактуру |
| evals/manual.md и поведенческие сценарии | Проверять полезную находку, отсутствие лишних вопросов, хранение и продолжение |

Подробные инструкции загружаются по ссылке из соответствующего флоу.
SKILL.md сохраняет роль карты существующих флоу. Отдельная команда премортема
не требуется. Сценарии проверки и временные результаты хранятся вне исходных
и установленных каталогов скиллов по правилам sdd-skill-conductor.

### Место проверки в процессе



Премортем выполняется в текущем флоу после чтения доступных источников и
установления цели. При прямом входе в draft действует та же проверка.
Актуальный сохранённый итог позволяет продолжить без повторного разбора.
Новый отдельный флоу добавил бы переход и риск пропуска при прямом запросе
документов. Проверка только по запросу пользователя противоречила бы принятому
решению проводить короткий премортем всегда.

### Хранение результата



При отсутствии находок новый файл не создаётся. Если находки есть, агент
записывает их в `sdd/changes/<change-id>/premortem.md`; state.md содержит
короткий итог со ссылкой. Это согласованный пользователем вариант.
Полный разбор увеличил бы объём state.md; обязательный пустой
документ не добавил бы сведений.

premortem.md - обычный Markdown без нового document_type и sdd_record.
У каждой находки есть заголовок, позволяющий сослаться на неё, и четыре части
из спецификации. Находки не требуют отдельного пространства машинных ID.
Если нужен вопрос, из документа ведёт ссылка на соответствующий Q-ID в state.
Запись Q управляет блокировкой и возвратом; причина отсрочки и условие возврата
отражаются в разборе с той же формулировкой.

Агент обновляет итог находки при её разрешении и сохраняет основания.
Когда открытых находок больше нет, state кратко отмечает это и сохраняет
ссылку на premortem.md. Документ не удаляется автоматически: он нужен,
чтобы отличить проверенное решение от потерянной истории.

### Граница нормативных документов



premortem.md хранит исследование. Выбранные внешние обязательства переходят
в specs с AC, цель в proposal, подход в design. В premortem.md остаются ссылки
на результаты. Решения пользователя подтверждаются реальным ответом;
новый вид USER-записи не вводится. Для находок независимого ревью сохраняется
существующий протокол finding_disposition, который не применяется автоматически
к авторским находкам премортема.

snapshots.py перечисляет
proposal.md, design.md и specs, а на стадии plan добавляет tasks.md.
premortem.md не включается в этот список. Изменение только материала исследования
не делает ревью автоматически устаревшим, поэтому агент обязан проверять,
не изменился ли смысл нормативного комплекта. При таком изменении обновляются
нормативные документы и срабатывают существующие правила актуальности.

Включение premortem.md в манифест потребовало бы менять контракт проверки версий
и расширило бы область изменения. Выбранный подход сохраняет схему SDD v1.
Структурный check не доказывает, что агент выполнил мысленную проверку или нашёл
все существенные предпосылки; это проверяется поведением на сценариях.

### Продолжение без формальной версии премортема



Актуальность определяется сопоставлением текущей цели и источников с сохранённым
разбором. Дополнительный манифест хешей не вводится. При краткой отметке
«находок нет» агент использует контекст изменения из state и доступных документов.
Если установить область прежней проверки нельзя, он повторяет короткий разбор
без автоматического интервью. Это позволяет сохранять согласованную краткость
state, хотя при недостаточных основаниях потребует повторной работы агента.

## Совместимость и миграция

Читаемая отметка в state и дополнительный Markdown не меняют YAML-схему.
Проверяющие скрипты и хранилище runtime не требуют изменений. Старые изменения
не переписываются массово: при продолжении применяется правило восстановления
из REQ-premortem-resume. Отсутствие премортема в старой версии само по себе
не отменяет прежние согласования; обнаруженное изменение нормативного поведения
обрабатывается по обычным правилам пересмотра.

## Проверка подхода

При реализации нужны сценарии для всех AC: новая идея, малое исправление,
прямой draft, ответ в доступном источнике, недоступный источник, блокировка,
отсрочка, предлагаемая новая функция, закрытая находка и продолжение.
Отдельно проверяются позднее изменение предпосылки и отсутствие записи
в старом изменении. Наблюдаемый итог проверки фиксируется в артефактах;
подробные внутренние рассуждения агента не требуются.

Сравнение текущего скилла с кандидатом должно выявлять пропущенные предпосылки
и учитывать лишние вопросы, необоснованное расширение объёма и повторную работу.
Обе версии получают одинаковые вводные в отдельных рабочих каталогах.
Порядок сравнительных и контрольных прогонов задаёт sdd-skill-conductor.
Локальные проверки связей и формата дополняют эти прогоны. Показатели времени
и токенов записываются только при наличии измерений. Эти испытания ещё не выполнены.

## Риски и открытые вопросы

Риски самого дополнения записаны в premortem.md: формальная
отметка без полезной проверки, лишние вопросы и потеря актуальности.
Они ограничены правилами спецификации, но результат требует поведенческой
проверки. Вопрос о подтверждении пользы отложен до испытаний кандидата:
Q-premortem-benefit. Блокирующих вопросов нет.
