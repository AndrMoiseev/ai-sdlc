# Дизайн отчёта

Черновик. Технология и архитектура не выбраны.

## Контекст, цели и исключения

Основания и объём: [proposal](proposal.md); известный контракт: [spec](specs/delivery-report/spec.md). Доступны docs/report.md и пакет sdd-spec. Подтверждённых сведений о модулях, хранилище и планировщике продукта нет.

Ранний выбор — действие диспетчера после получения отчёта. Без него нельзя обосновать достаточность времени и полей для снижения просрочек.

## Модули и контракты

Предложение агента: запуск по расписанию → чтение среза → выборка просроченных → CSV → передача диспетчеру. Это логические обязанности, а не решение создавать отдельные сервисы.

| Граница | Ответственность | Неопределённость |
|---|---|---|
| Запуск | Ежедневное формирование | Часовой пояс, смысл 09:00, пропущенный запуск |
| Данные | Сведения о доставке, сроке и ответственном | Источник, полнота, свежесть, момент среза |
| Выборка | Определить просрочку и её длительность | Статусы, сроки, округление минут |
| CSV | Представить три запрошенных поля | Кодировка, разделитель, пустые значения |
| Передача | Предоставить результат диспетчеру | Канал, адрес, повторы и ошибки |

## Термины

Получатель — диспетчер доставки; роль известна, адрес и канал неизвестны. Значение responsible не позволяет пока установить, идёт ли речь об исполнителе или иной роли. Формула overdue_minutes не определена. Срез — момент, к которому относятся данные; он не обязательно совпадает с получением CSV.

## Подход и альтернативы

Время 09:00 сохраняется по запросу. Эскалация просроченных доставок или пересмотр назначений после 09:00 — возможные действия, предложенные агентом, а не решения пользователя.

Отчёт до 08:30 мог бы поддерживать первоначальное назначение, но меняет явное расписание. Отчёт в 09:00 только для наблюдения сохраняет расписание, но не объясняет, как снижать просрочки. Выбор зависит от Q-report-action.

API, база данных и готовая выгрузка — возможные источники; ни один не подтверждён. Выбор зависит от доступных полей и свежести. Формальные DEC не записаны: оснований для технического решения недостаточно.

## Риски и открытые вопросы

Главный риск: отчёт приходит после назначения и не вызывает полезного действия. Для проверки нужен пример одного утра: что изменит диспетчер после чтения строки? Это Q-report-action в [state](state.md).

Неверная просрочка или устаревший ответственный приведут к ошибочному действию: Q-data-contract. Ошибка источника, представленная как пустая выборка, скроет проблему: Q-failure-contract. Без часового пояса нельзя проверить время: Q-delivery-contract.

## Миграция и проверка

Изменения хранения и миграция пока не обоснованы. После уточнения контрактов нужны контрольные данные для выборки, проверки CSV, расписания и ошибок передачи, а также проверка возможности принять выбранное решение по отчёту. План реализации не создаётся; код не изменяется.
