# Исследование delivery-report

Статус: черновик исследования, 2026-10-06. Цель пользователя — снизить просрочки. Решение о новом процессе пока не принято.

## Источники и границы

Единственный предметный источник в рабочей папке — [docs/report.md](../../../docs/report.md), строки 1–2. Остальные доступные файлы относятся к пакету sdd-spec. Исходников продукта, тестов, конфигурации расписания, статистики доставок и сохранённых изменений SDD нет. Поэтому ниже описано документированное поведение, а не проверенная работа системы. Код и конфигурация продукта не менялись.

## Наблюдаемые факты

По docs/report.md получатель отчёта — диспетчер доставки. Отчёт приходит ежедневно в 09:00, исполнителей диспетчер назначает в 08:30. По списку он выбирает исполнителей для просроченных доставок. В CSV указаны поля `delivery_id`, `overdue_minutes`, `responsible`. Документ связывает отчёт с целью снижения просрочек, но не задаёт величину улучшения или способ измерения.

## Главный вывод

При условии одного дня и одного часового пояса отчёт приходит на 30 минут позже назначения исполнителей. Если список нужен для назначения в 08:30, текущий отчёт не может обеспечить это решение свежей информацией. Это разрыв между временем получения информации и временем действия, а не доказательство технической ошибки расписания.

Документ не уточняет, используется ли вчерашний список, происходит ли повторное назначение после 09:00 и можно ли изменить уже выданные задания. Эти объяснения нельзя считать установленными фактами. Часовой пояс и дата среза также не указаны.

## Проверка возможного провала

Сценарий: отчёт исправно доставляется каждый день, однако просрочки не уменьшаются. Вероятная причина по имеющемуся описанию — диспетчер уже назначил исполнителей до получения списка. Признак: доставки из отчёта не вызывают действий после его получения или ждут следующего назначения. Проверка: сопоставить время доступности списка, его просмотра, назначения и фактического действия по доставке.

Даже более ранний отчёт не гарантирует результат. Список может быть устаревшим; исполнителей может не хватать; поле `responsible` может отражать уже назначенного человека; причина задержки может не зависеть от назначения. Это гипотезы, для проверки которых нужны наблюдения, а не дополнительные столбцы сами по себе.

Есть и различие целей: обработка уже просроченных доставок может уменьшать длительность опоздания, но не предотвращать сам факт просрочки. Для уменьшения доли просроченных доставок может потребоваться выявление риска до дедлайна. Наличие таких данных текущий документ не подтверждает.

## Варианты для обсуждения

| Вариант | Как должен помогать | Ограничение |
|---|---|---|
| Предоставлять актуальный список до 08:30 | Диспетчер учитывает его при исходном назначении | Нужны своевременные данные и запас времени для просмотра; точное время пока не определено |
| Сохранить 09:00 и определить повторное распределение | После отчёта диспетчер корректирует назначения для проблемных доставок | Нужны полномочия и доступные исполнители; переназначение может нарушать текущую работу |
| Сохранить отчёт как контрольный | Отчёт показывает состояние доставок и помогает разбирать причины | Без отдельного действия связь со снижением просрочек не подтверждена |

Рекомендация агента: сначала проверить ранний список до 08:30, поскольку источник прямо связывает список с назначением исполнителей. Не следует автоматически переносить сам процесс назначения на более позднее время. Отчёт должен быть доступен до решения с запасом на просмотр; конкретное время определяется готовностью данных и работой диспетчера. Пользователь этот вариант не согласовывал.

## Как проверить пользу

Предлагаемый небольшой пилот после выбора процесса: сравнить работу с ранним списком и текущий процесс на сопоставимых сменах, учитывая объём доставок, загрузку и состав исполнителей. До пилота определить период, целевое улучшение и допустимые побочные эффекты.

Для каждой проблемной доставки сопоставить время среза данных, доступности отчёта, просмотра, назначения или переназначения и завершения. Проверить цепочку: список получен вовремя → диспетчер принял решение → исполнитель выполнил действие → результат доставки изменился. Одна успешная отправка CSV не подтверждает пользу.

Кандидаты метрик: доля доставок, завершённых после обещанного срока, среди доставок с дедлайном в выбранном периоде; длительность просрочки; время от обнаружения проблемы до назначения. Для незавершённых доставок нужен отдельный учёт, иначе исключение их из расчёта может скрыть ухудшение. Контрольные показатели — нагрузка диспетчера и задержки других доставок после перераспределения. Это предложения для проверки, а не утверждённые критерии приёмки; числовой baseline отсутствует.

## Ближайший выбор и оставшиеся пробелы

Блокирующий выбор Q-action-window: отчёт должен помогать назначению до 08:30 или запускать повторное распределение после 09:00? Ответ определит наблюдаемое поведение и границы будущей спецификации.

После этого нужно уточнить смысл снижения просрочек, готовность данных до назначения, значение `responsible`, дату и часовой пояс среза, полномочия диспетчера и наличие свободных исполнителей. Эти детали пока не подменяются предположениями об API или модели данных.
