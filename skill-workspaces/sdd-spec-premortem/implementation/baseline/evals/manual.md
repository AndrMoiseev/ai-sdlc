# Ручные проверки инструкций

Это воспроизводимые процедуры оценки пакета, а не отчет о полном пилоте. Для каждой строки запишите дату, версию среды, входной fixture, фактически прочитанные файлы, действия/ответ агента и pass/fail с цитатой. Чтение инструкции подтверждает наличие правила; выполнение в чистом контексте подтверждает поведение только этого прогона. Не записывайте непроведенный прогон как успешный.

Для поведенческой проверки используйте отдельный временный проект с копией полного пакета и синтетическим изменением; эталон без скилла не должен обнаруживать пакет через родительские каталоги. Начинайте явно `$sdd-spec`/`/sdd-spec`, если строка не проверяет отсутствие запуска. Не реализуйте код фикстуры. Сохраняйте transcript и выводы check/snapshot вне нормативного комплекта. Для повторного независимого ревью сначала моделируйте новое согласие пользователя.

## Исследование, подготовка и пересмотр

| Случай и вход | Проверяемый результат |
|---|---|
| В коде/тесте уже есть ответ на фактический вопрос | Explore читает источник до вопроса, сообщает факт со ссылкой |
| Неизвестна продуктовая граница, от которой зависит API | Один вопрос о границе с причиной; рекомендация опирается на факты; зависимые детали ожидают |
| Открытое обсуждение либо достаточная ясность | Нет принудительной анкеты/предложения; вопросы прекращаются, checkpoint сохраняет выводы |
| Две capabilities с общим подходом | Два spec.md, один design; текущие зависимости прочитаны с диска, ограничения проекта не скопированы |
| Capability с двумя требованиями и несколькими критериями у каждого | Заголовок capability `#`, требования `##`, их критерии `###` внутри соответствующего требования; YAML requirement совпадает с родительским REQ-ID; documents-проверка проходит |
| Существенный источник недоступен; вопрос меняет поведение | Ограничение обозначено, вопрос blocking; файлы могут быть черновиками, ревью не объявлено готовым |
| Доступный код снимает вопрос, агенту предлагают «потом исследовать» | Исследование выполнено сейчас; допустимая отсрочка привязана к Q с причиной/return_at |
| Правка design меняет обязательство и границу proposal | Проверены specs/proposal/tasks в обоих направлениях; новая содержательная область согласована |
| При revise отсутствует tasks или новый capability-файл | Отсутствие сообщено, файл не создан под видом согласованности |
| При revise изменяется сама цель | Предложено отдельное изменение, старое не подменено |
| Согласованный комплект уже согласован и непротиворечив | Файлы не переписаны, хеши совпадают |

## Независимое ревью

| Случай и вход | Проверяемый результат |
|---|---|
| Нет индекса либо `lenses: []` | Предложена только consistency |
| Индекс содержит две линзы и в каталоге есть посторонняя | Предложены consistency и ровно две индексированные линзы, каждая с предметом |
| Индекс поврежден, ID дублирован или path недоступен | Ошибка до запуска, а не молчаливый пропуск |
| Пользователь согласовал один document_review | Новый чистый контекст на каждую линзу; один общий манифест; нет истории/рассуждений автора и чужих отчетов |
| Доступен один слот | Линзы идут последовательно без правок входов между ними |
| Ревью плана | Один новый рецензент проверяет критерии, тесты, размер, граф и конфликты общих файлов |
| Агент упал, критичный источник недоступен или отчет неверен | Сохранен доступный результат с incomplete и причиной, успешный вывод не выдуман |
| Нормативный файл изменен между snapshot до/после и затем возвращен | Отчет запуска stale даже после возврата; оба манифеста сохранены |
| Изменены state/review/внешний источник | Автоматический манифест не меняется; влияние внешнего источника оценивается вручную |
| Новая линза при прежних документах | Missing review выявлен независимо от совпадающих хешей |

## Решения и повторные проверки

| Случай и вход | Проверяемый результат |
|---|---|
| Дубли двух линз и противоречащие рекомендации | Сводка сохраняет все полные ссылки и явно показывает расхождение |
| «Исправь эти две находки», затем прерывание после первой | USER перечисляет обе ссылки; выполнение отдельно; после resume вторая исправляется без повторного согласия |
| Молчание в ответ на сводку | Нет disposition, waiver или approval |
| Отклонение/отсрочка | Причина записана; у отсрочки конкретный return_at |
| Повторная находка с прежним локальным FIND-ID | Новый полный ключ, related_to в сводке; старое решение не унаследовано |
| Правка одного документа, затем просьба повторить одну из трех линз | Все три stale перечислены; запуск только выбранной; остальные требуют отдельного waiver текущей версии |
| Согласовано исправление, но ревью повторно не разрешено | Исправление выполнено, повтор предложен и ожидает нового consent |
| Waiver старой версии или другой стадии | Не применяется; структурные ошибки waiver не обходятся |

## Продолжение и отмена

| Случай и вход | Проверяемый результат |
|---|---|
| Одно незавершенное изменение | Выбрано автоматически после явного входа, состояние сверено с файлами |
| Несколько изменений без выбора | Показан список, ожидается выбор без изменения произвольного каталога |
| Отсутствующий/поврежденный state или потерянная ссылка USER | Документы сохранены, черновой checkpoint восстановлен, неизвестные разрешения не придуманы |
| Есть tasks, но нет planning_command | Наличие файла не объявлено разрешением |
| Начатое планирование после перерыва | Сохраненное поручение действует в прежнем scope, готовность и ревью проверены отдельно |
| Ожидание согласия на ревью/команды планирования | Новая сессия сохраняет ожидание |
| Необъясненные внешние правки | Уточняется затронутая область, остальные проверенные поручения не отменены автоматически |
| Исправить A и B, A выполнено, затем «отмени B»; resume | Отмена сохранена с происхождением, B не возобновлена из раннего USER, A сохранено |
| Команда планировать scope X, затем «замени поручение на обсуждение Y»; resume | Старое планирование не продолжается; новая область не получает старые разрешения/waiver |
| Достоверная метрика 70%, затем 71% | 70% не вызывает порог; 71% сохраняет checkpoint и предупреждение |
| Метрика отсутствует | Смысловые сохранения продолжаются, измеренный процент и hook не выдуманы |

## План и завершение

| Случай и вход | Проверяемый результат |
|---|---|
| Документы согласованы, команды плана нет | tasks не создается; ожидание сохранено |
| Команда при stale/missing/incomplete ревью | Предложены проверки, команда не превращена в waiver |
| Находка без решения либо fix не завершен | Переход к плану блокирован конкретным условием |
| Корректные основания и явная команда | План pending, каждый AC ровно у одной задачи; тесты/фикстуры внутри задачи; check plan проходит |
| Неизвестна команда теста | Задача включает подготовку запуска, будущий путь не требует существования |
| Поочередно уберите структуру, review/waiver, disposition, выполненный fix, return_at, approval | В каждом случае plan_approved не ставится и названо недостающее |
| Актуальное ревью + решения + выполненные fixes + approval | plan_approved; код, baseline и архив не изменены |
| Отдельный waiver plan_review текущей версии + остальные условия | plan_approved; waiver сохранен отдельно от approval |
| Только «план согласован» при незавершенном ревью | Нет выдуманного waiver или disposition, статус остается черновым |

## Редактура через humanizer-ru

Сравни старую и новую версии инструкций в свежих контекстах на одинаковых
документах. Проверяй фактический diff и вызовы редактора, а не обещания его вызвать.

| Случай | Ожидаемый результат |
|---|---|
| Новый русский proposal/spec/design, затем немедленная передача пользователю | Каждый созданный документ прошёл humanizer до check и снимка версии |
| Одна фраза изменена в уже рассмотренном spec, времени мало | Повторная редактура, прежние ревью stale, нет обхода ради срока |
| AC содержит отрицание, число и условие в YAML; рядом код и цитата | Смысл и защищённые участки сохранены; редактируются только разрешённые текстовые значения |
| Чистый документ проходит повторно | Нет принудительных правок и повторного цикла из-за работы редактора |
| Изменены checkpoint и summary, рядом исторический USER и отчёт | Авторская проза проверена; история и исходный отчёт не переписаны |
| Английский документ или смешанный текст | Пропуск с причиной или обработка только русской прозы |
| Недоступен humanizer либо чистый субагент | Черновик сохранён, проход незавершён, готовность не заявлена |
| Исходник изменился во время редактуры | Устаревший патч не применён, проверена новая версия |

## Пакет и хосты

Статически проверь метаданные, доступность локальных ссылок/шаблонов и отсутствие обязательных openspec-вызовов командой `python skills/sdd-spec/scripts/run.py test -k package_contract`. Для среды отдельно проверь: явный вызов загружает карту; следующий обычный ответ продолжает процесс; новая сессия без вызова не запускает его; отсутствие чистого субагента дает incomplete, а не саморевью.

Технически 2026-09-29 прочитаны `codex --version` (0.159.0), `codex exec --help` и официальные страницы обоих хостов. Claude Code отсутствовал в PATH; реальный прогон в нем не выполнен. Проверка текста адаптеров и порога не равна runtime-пилоту. Фактические результаты поведенческих запусков ведите отдельно от этой процедуры.

## Пояснение решения: подготовка парных прогонов

Ниже определены сценарии, а не результаты их выполнения. Для каждого случая
из evals.json подготовь отдельную фикстуру. Сравни сохранённую прежнюю версию
пакета с новой на одинаковом входе, в одной среде и на одной модели.
Следуй runtime-setup и процедуре IMPROVE скилла sdd-skill-conductor:
сохрани разбиение train/held-out до правок, выполни независимое оценивание,
слепое сравнение и разбор результатов. Проверка автоматического выбора
не нужна: каждый запуск явно вызывает sdd-spec.

Храни фикстуры, prompt.txt и результаты вне исходных и установленных пакетов.
Для пары сделай две независимые копии исходной фикстуры. Проверь каталоги
проекта, родителей и пользовательских скиллов: прежний пакет не должен
обнаруживать новый через каталог или унаследованный контекст. Не меняй
глобальные установки пользователя ради изоляции. Если native-запуск
не изолирован, используй CLI по conductor; если изоляция недостижима,
зафиксируй ограничение сравнения.

В prompt.txt включи только явный вызов, путь назначенного SKILL.md и prompt
случая, затем конкретный запрос очередного шага. Assertions и ответы другой
версии исполнителю не передавай. После проверки uv, версии и авторизации
выбранного CLI выполни из внешнего рабочего каталога:

```text
uv run <conductor-root>/scripts/run_task.py --harness codex --prompt-file <prompt.txt> --workspace <fixture-copy> --output-dir <run-artifacts> --allow-writes
```

Подставь фактические абсолютные пути; для Claude Code выбери `claude-code`
в обеих половинах пары. Сохрани trace, response, run.json и timing.json,
входные/выходные хеши, фактически прочитанные инструкции и ограничения.
В отчёте приведи pass/fail/incomplete по assertions с наблюдаемым основанием;
недоступные метрики оставь null. Недоступная среда означает непроведённую
проверку, а не успех. Не подменяй прогон описанием предполагаемого поведения.

### Общая фикстура и варианты

Создай валидный `sdd/changes/sample-change/` из шаблонов назначенного пакета:
proposal.md, design.md, specs/orders/spec.md, specs/refunds/spec.md и state.md
с происхождением поручений. Зафиксируй один исходный комплект для обеих версий.
Заказ: API сохраняется, новый worker принимает асинхронное сообщение;
повтор ключа возвращает прежний заказ, отказ в оплате завершает процесс.
Возврат: прежний платёжный сервис получает изменённое сообщение, возвращает
подтверждение, устаревший retry endpoint удаляется. Добавь неизменённую связь
к БД, изменённую связь между прежними компонентами и новую связь к worker.
Исходное поведение внешнего обработчика обозначь неизвестным. Отдельный
сценарий меняет только текст сообщения пользователю: архитектурное
представление для него должно получить причину неприменимости.

Храни исходные кодовые свидетельства только там, где они действительно
существуют. Будущее состояние подтверждают документы изменения;
не выдавай его за реализованный repository-backed код. Все производные
артефакты сценария располагаются в `sample-change/archify/`.

| Случай | Подготовка и отдельные варианты |
|---|---|
| explanation-content | Общая фикстура; отдельный вариант с обнаруженным новым обязательством, которого нет в specs, проверяет возврат в revise |
| explanation-missing-archify | Чистая среда без доступного пакета archify; проверка отсутствия зависимости документирована, глобальная установка не удаляется |
| explanation-portable-layout | Запроси обзор и два документа; создай две версии проверки одной диаграммы и другую диаграмму; после прогона скопируй весь change в новый корень |
| explanation-preview-reuse | A: текущий HTML, привязанный receipt, осмотренный читаемый PNG; B: те же источники SDD, но HTML изменён и PNG старый; C: только browser-check без снимков |
| explanation-no-browser | A: HTML есть и archify действительно не может запустить браузер; B: HTML не создан; C: отдельного browser-tool нет, но archify может использовать локальный Chrome/Chromium |
| explanation-check-failure | Раздельные фикстуры: ошибка геометрии; ошибка выполнения при доступном браузере; успешный захват с обрезанными или нечитаемыми метками |
| explanation-stale-inputs | От исходного готового пояснения независимо: изменить байты design; добавить specs/new-capability/spec.md; удалить specs/refunds/spec.md. Каждый вариант продолжить через revise, resume и preview-handoff |
| explanation-offer-decline-resume | После первого предложения отдельные ветки: «Не нужно», отсутствие ответа о пояснении с продолжением основного процесса, «Набор документов». После отказа запусти свежий resume той же версии, затем «Теперь создай пояснение» |
| explanation-existing-request | Отдельно: действующее поручение; частично готовое пояснение после перерыва; явная отмена; просьба расширить область без разрешения на новую область; нерешённый blocking-вопрос основного комплекта |

Многошаговые ветки получают новые CLI-запуски с сохранёнными файлами предыдущего
шага. Мутации fixture и очередные пользовательские ответы выполняет ведущий
прогона, одинаково для обеих версий. До мутации сохрани копию и хеши; не смешивай
несколько независимых вариантов в одном состоянии.

Подставленные ответы допустимы для ветвления: явно назови режим `mocked`,
сохрани входной ответ инструмента и способ его подачи. Такой прогон оценивает
выбор действий, диагностику и текст. Он не подтверждает выполнение archify,
создание HTML, визуальную читаемость или доступность браузера. Случаи ниже
проверяются на реальных артефактах и в реальной среде; отчёт разделяет оба режима.

### explanation-markers

Критерий: AC-visible-independent-statuses.

1. Найди установленный archify через каталог среды и прочитай его SKILL.md,
   схемы выбранных типов и delivery-contract. Зафиксируй путь и версию.
   Подготовь architecture, workflow и sequence по общей фикстуре.
2. Передай явные пути внутри `sample-change/archify/<diagram-id>/`.
   Для текущего интерфейса используй команды ниже; пути и type подставляются
   из текущего сценария. При отличии установленной версии следуй её контракту
   и сохрани фактическую команду.

   ```text
   node <archify-root>/bin/archify.mjs finalize <type> <candidate.json> <diagram.html> --quality showcase --json
   node <archify-root>/bin/archify.mjs visual-check <diagram.html> --out-dir <diagram-dir>/visual-check-1 --summary --require-provenance
   ```

   `--repo-root <fixture-root>` добавляй к finalize только для настоящего
   repository-backed кандидата с необходимыми доказательствами.
   Успешный finalize сам по себе не создаёт PNG и не подтверждает осмотр.
3. Открой HTML и PNG из путей реального receipt. Проверь в светлой и тёмной
   теме видимость меток: прежний компонент с изменённой связью; новая связь;
   изменённое сообщение прежнего участника; неизменённая связь. Проверь,
   что tag/sublabel/label/note сохраняют назначение, условия, возврат
   и асинхронность. Удаление отражено в «До», отсутствие в «После» объяснено.
4. Сохрани перечень осмотренных снимков и наблюдение по каждой метке.
   Pass требует реального осмотра всех трёх типов. Ошибка или отсутствие
   браузера сохраняется как ограничение; подставленный PNG этого не закрывает.
   Если режим чтения скрывает tag, продублируй статус в видимом sublabel
   либо label, сохрани назначение узла, повтори проверки и осмотр. Успешные
   автоматические проверки сами по себе не доказывают видимость метки.

### explanation-checked-preview

Критерий: AC-preview-from-check.

1. Используй реальные HTML предыдущей процедуры. Сохрани SHA-256 HTML
   и receipt; сверь точную привязку по provenance archify. Получи снимки
   через visual-check, если актуального набора ещё нет.
2. Осмотри PNG по путям из ответа. Если одна картинка обрезает существенную

   внутри исходного tool receipt остаются историческими сведениями,
   навигация комплекта использует относительные пути.

### explanation-cross-environment-resume

Критерий: AC-handoff-idempotence; вход проверяет AC-no-browser-placeholder.
