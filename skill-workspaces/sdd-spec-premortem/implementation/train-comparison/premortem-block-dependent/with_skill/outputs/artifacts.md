# Дизайн delivery-report

## Контекст, цели и исключения

[Proposal](proposal.md) задаёт цель и открытую границу изменения. В проекте доступен только docs/report.md; текущую архитектуру и интеграции проверить невозможно. Это частичный дизайн, а не выбранный способ реализации.

## Модули и контракты

Предлагается отделить формирование CSV от действий над назначениями. Формирование использует общий [контракт колонок](specs/delivery-report/spec.md). Конкретные модули, хранилища и API пока не выбраны: сведений для этого нет.

## Альтернативы

| Режим | Поведение | Нерешённые последствия |
|---|---|---|
| Только отчёт | Выдаёт CSV диспетчеру без автоматического назначения | Нужно определить действие после получения в 09:00 |
| Отчёт и автоматическое назначение | Дополнительно изменяет назначения исполнителей | Нужны правила выбора исполнителя и взаимодействия с назначениями диспетчера в 08:30 |

Обе альтернативы сохраняют три колонки CSV. Описание альтернатив не является решением пользователя. Выбор и зависимые технические решения остаются открытыми.

## Термины

Диспетчер доставки — получатель отчёта. delivery_id, overdue_minutes, responsible — согласованные имена колонок. Типы и правила заполнения не установлены источником.

## Риски и открытые вопросы

[Премортем](premortem.md) описывает риск позднего отчёта и расширения объёма. [Вопросы в state](state.md) блокируют завершение зависимой части. Схему данных, обработку ошибок и необходимость миграции нужно определить после выбора поведения и уточнения источника данных.


# sdd/changes/delivery-report/premortem.md

# Премортем delivery-report

## Контекст

Цель — снизить просрочки доставки. Проверены все доступные материалы проекта: [исходные требования](../../../docs/report.md) и запрос пользователя. Реализация, тесты и сведения об операционных решениях после 09:00 отсутствуют. Исследуются оба режима; пользователь ещё не выбрал один из них.

## Отчёт может опоздать к решению

**Возможный провал:** корректный ежедневный CSV не снижает просрочки, поскольку поступает после назначения исполнителей.

**Предпосылка успеха:** после получения отчёта диспетчер может принять конкретное решение, влияющее на просрочки.

**Основания:** в docs/report.md указаны назначение исполнителей в 08:30 и отчёт в 09:00. Это подтверждённые факты. Бесполезность отчёта не доказана: возможны последующие действия диспетчера, но они не описаны. Автоматическое назначение также не подтверждено как способ снижения просрочек.

**Дальнейшее действие:** [Q-report-action](state.md#действие-по-отчёту) — выяснить, какое решение принимается по отчёту после 09:00. До ответа не менять время и не обещать снижение просрочек как доказанный эффект.

## Автоматизация может изменить объём без решения пользователя

**Возможный провал:** в спецификацию попадает автоматическое назначение, хотя пользователь хотел только отчёт; либо оно исключается без выбора.

**Предпосылка успеха:** граница между информированием и изменением назначений выбрана явно.

**Основания:** источник и запрос оставляют режим открытым. Три колонки CSV согласованы для обоих вариантов; открытый режим не мешает описать этот контракт.

**Дальнейшее действие:** [Q-delivery-mode](state.md#режим-работы). Сохранить обе альтернативы в design, не закреплять ни одну как решение. Независимый контракт описать в REQ-csv-columns и AC-csv-columns.

# Ежедневный отчёт доставки

Черновик: режим работы не выбран, документы не согласованы.

## Проблема и результат

По [исходным требованиям](../../../docs/report.md) диспетчеру нужен ежедневный отчёт в 09:00. Цель — снизить просрочки. Назначение исполнителей происходит в 08:30; действие по более позднему отчёту пока неизвестно. [Премортем](premortem.md) фиксирует риск недостижения цели.

## Объем

Новая capability [delivery-report](specs/delivery-report/spec.md) описывает общий контракт CSV: delivery_id, overdue_minutes, responsible. Этот контракт применим к обоим режимам.

Открытый выбор: только отчёт либо отчёт с автоматическим назначением исполнителей. Ни один вариант не принят по умолчанию. Зависимое поведение будет добавлено после ответа на [вопросы](state.md).

## Исключения

Текущий черновик не определяет правила автоматического назначения и не разрешает их реализацию. Изменение времени отчёта также не согласовано. План реализации не запрошен.

## Влияние

Выходной интерфейс — CSV для диспетчера. Автоматическое назначение, если будет выбрано, затронет состояние назначений; источник данных, права и правила изменения пока неизвестны. Существующих спецификаций и кода в рабочей папке нет.

# Delivery report

Частичный черновик общего контракта. Источник: [docs/report.md](../../../../../docs/report.md). Открытые вопросы не отменяют согласованный состав CSV.

## Три колонки CSV

```yaml
sdd_record: requirement
id: REQ-csv-columns
operation: add
```

Отчёт для диспетчера доставки должен иметь формат CSV с ровно тремя колонками: delivery_id, overdue_minutes, responsible. Состав колонок одинаков для режима только отчёта и режима с автоматическим назначением исполнителей.

### Состав колонок не зависит от режима

```yaml
sdd_record: acceptance
id: AC-csv-columns
requirement: REQ-csv-columns
conditions: Сформирован отчёт в любом из двух рассматриваемых режимов.
expected: CSV содержит ровно три колонки — delivery_id, overdue_minutes, responsible; дополнительных колонок нет.
```

Проверка применяется к каждому режиму, который войдёт в выбранный объём. Этот критерий не требует реализовать оба режима.

## Границы черновика

В источнике зафиксирована ежедневная выдача в 09:00. Часовой пояс, способ доставки файла, выборка строк, расчёт overdue_minutes, представление responsible и ошибки не описаны. Это пробелы контракта, а не свобода реализации; см. [Q-report-contract](../../state.md#детали-контракта).

Поведение автоматического назначения не специфицировано до [выбора режима](../../state.md#режим-работы).

## Сохраненные основания

Изменение новое: прежних документов, ревью и согласований нет. Источник — [docs/report.md](../../../docs/report.md). Пользователь явно указал, что режим не выбран, а три колонки согласованы для обоих вариантов. Выбор за пользователя не сделан. Предлагаемое разделение формирования CSV и назначения в design — предложение агента.

### Режим работы

```yaml
sdd_record: question
id: Q-delivery-mode
text: Нужен только отчёт или также автоматическое назначение исполнителей?
blocking: true
status: open
```

Ответ определяет объём и наличие изменений назначений. Он не блокирует общий контракт трёх колонок CSV.

### Действие по отчёту

```yaml
sdd_record: question
id: Q-report-action
text: Какое решение диспетчер принимает по отчёту в 09:00, если исполнители уже назначены в 08:30?
blocking: true
status: open
```

Ответ нужен, чтобы связать отчёт с целью снижения просрочек; перенос времени не согласован.

### Детали контракта

```yaml
sdd_record: question
id: Q-report-contract
text: Каковы часовой пояс 09:00, источник и выборка данных, правила заполнения колонок, способ выдачи CSV и поведение при ошибках?
blocking: true
status: open
```

Эти сведения отсутствуют в доступных материалах. Уточнять после ближайшего выбора режима; не подменять их выдуманными значениями. Для сохранения частичного контракта ответы не требуются, для готового комплекта нужны.
