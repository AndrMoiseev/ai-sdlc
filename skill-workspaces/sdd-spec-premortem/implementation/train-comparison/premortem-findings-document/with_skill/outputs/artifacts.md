# Премортем delivery-report

## Контекст

Цель пользователя — снизить просрочки доставок. Исследование выполнено по [docs/report.md](../../../docs/report.md); это единственный найденный материал продукта. Исходников, тестов, конфигурации расписания, статистики доставок и прежних SDD-документов в рабочей папке нет. Фактическое исполнение расписания проверить нельзя.

Документ описывает ежедневный отчёт в 09:00 для диспетчера доставки. CSV содержит delivery_id, overdue_minutes, responsible. Диспетчер назначает исполнителей в 08:30 и по списку выбирает исполнителей для просроченных доставок. Назначение отчёта известно, повторно уточнять его не требуется.

Ни расписание, ни цель не изменены. Ниже — выводы исследования и предложения агента, а не согласованные требования. Статус документа: черновик; обязательная редактура humanizer-ru недоступна.

## Отчёт поступает после назначения исполнителей

**Возможный провал:** отчёт исправно отправляется в 09:00, но просрочки не сокращаются: решение о назначении исполнителей уже принято в 08:30 без сегодняшнего отчёта.

**Предпосылка успеха:** сведения о просрочках доступны диспетчеру до решения, на которое они должны повлиять, с достаточным временем для чтения и выбора исполнителей.

**Основания:** [docs/report.md](../../../docs/report.md) прямо задаёт оба времени и действие диспетчера. Отчёт поступает на 30 минут позже назначения. Гипотеза: речь идёт о назначении по отчёту текущего дня в одном часовом поясе. Источник не описывает использование вчерашнего списка, повторное назначение после 09:00 или время готовности данных. Поэтому отсутствие пользы вообще не доказано, но влияние на назначение в 08:30 не обеспечено.

**Дальнейшее действие:** разрешить [Q-report-timing](state.md#q-report-timing). Предложение агента — доставлять список до 08:30 с запасом для работы диспетчера, если данные доступны. Точное время пока не выбирать: нужно проверить готовность данных и длительность разбора списка. Альтернатива — сохранить 09:00 и определить действенное повторное назначение после отчёта; это меняет рабочий процесс и требует подтверждения возможности такого действия. Перенос утреннего назначения тоже затрагивает процесс доставки и без основания не рекомендуется. До ответа расписание остаётся открытым решением.

## Отправка отчёта не доказывает снижение просрочек

**Возможный провал:** отчёт читают и исполнителей назначают, но ожидаемый результат нельзя подтвердить или просрочки не сокращаются.

**Предпосылка успеха:** назначение позволяет ускорить доставку, а эффект измеряется по заранее выбранному показателю относительно сопоставимого исходного периода.

**Основания:** в [docs/report.md](../../../docs/report.md) указаны цель и поле overdue_minutes, но нет определения успешного снижения, исходного уровня, периода наблюдения и данных о результате назначений. Нехватка исполнителей или другие причины задержек — возможные гипотезы, а не установленные причины. Список уже просроченных доставок может помочь сократить длительность задержки, но сам по себе не подтверждает предотвращение новых просрочек.

**Дальнейшее действие:** разрешить [Q-success-measure](state.md#q-success-measure) при продолжении работы. Причина отсрочки: сначала нужно выбрать момент и действие диспетчера; метрика не меняет установленный конфликт расписаний. Условие возврата: перед завершением proposal и критериев приёмки. Предложение агента — согласовать показатель длительности просрочки либо доли просроченных доставок, исходный период, целевое изменение и период наблюдения; затем проверить на сопоставимых доставках цепочку «получение списка → назначение → завершение». Численные цели и результат такого сравнения сейчас неизвестны.
