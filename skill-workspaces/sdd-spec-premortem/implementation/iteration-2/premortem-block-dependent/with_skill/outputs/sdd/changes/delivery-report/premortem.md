# Премортем delivery-report

## Контекст

Цель — снизить просрочки доставки. Проверены все доступные материалы проекта: [исходные требования](../../../docs/report.md) и запрос пользователя. Реализация, тесты и сведения об операционных решениях после 09:00 отсутствуют. Исследуются оба режима; пользователь ещё не выбрал один из них.

## Отчёт может опоздать к решению

**Возможный провал:** корректный ежедневный CSV не снижает просрочки, поскольку поступает после назначения исполнителей.

**Предпосылка успеха:** после получения отчёта диспетчер может принять конкретное решение, влияющее на просрочки.

**Основания:** в docs/report.md указаны назначение исполнителей в 08:30 и отчёт в 09:00. Это подтверждённые факты. Бесполезность отчёта не доказана: возможны последующие действия диспетчера, но они не описаны. Автоматическое назначение также не подтверждено как способ снижения просрочек.

**Дальнейшее действие:** [Q-report-action](state.md#действие-по-отчёту) — выяснить, какое решение принимается по отчёту после 09:00. До ответа не менять время и не обещать снижение просрочек как доказанный эффект.

## Автоматизация может изменить объём без решения пользователя

**Возможный провал:** в спецификацию попадает автоматическое назначение, хотя пользователь хотел только отчёт; либо оно исключается без выбора.

**Предпосылка успеха:** граница между информированием и изменением назначений выбрана явно.

**Основания:** источник и запрос оставляют режим открытым. Три колонки CSV согласованы для обоих вариантов; открытый режим не мешает описать этот контракт.

**Дальнейшее действие:** [Q-delivery-mode](state.md#режим-работы). Сохранить обе альтернативы в design, не закреплять ни одну как решение. Независимый контракт описать в REQ-csv-columns и AC-csv-columns.
