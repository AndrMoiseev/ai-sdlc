# Независимая часть CSV — черновик

## Основание и границы

[Описание отчёта](../../../docs/report.md) подтверждает три колонки CSV для обоих вариантов поведения. Эта часть не зависит от выбора автоматического назначения. Документ сохраняет известное и предложения для будущей спецификации; он не является согласованным нормативным комплектом.

## Подтверждённый состав

| Колонка | Что известно |
|---|---|
| delivery_id | Имя колонки согласовано. Формат идентификатора не описан. |
| overdue_minutes | Имя колонки согласовано. Правила расчёта и округления не описаны. |
| responsible | Имя колонки согласовано. Представление исполнителя и отсутствие значения не описаны. |

## Предложение заголовка

```text
delivery_id,overdue_minutes,responsible
```

Порядок взят из исходного перечисления, запятая предложена как разделитель. Эти детали не объявляются отдельным решением пользователя. Пример содержит только заголовок: фактических данных доставок нет.

## Предлагаемые проверки общей части

- В описании CSV присутствуют ровно три согласованных имени: delivery_id, overdue_minutes, responsible.
- Состав колонок одинаков для варианта только с отчётом и варианта с автоматическим назначением, если последний будет выбран пользователем.
- Наличие responsible в CSV само по себе не задаёт назначение или переназначение исполнителя.

## Детали для последующей спецификации

После определения действия по отчёту уточнить состав строк, момент среза данных, формулу overdue_minutes и представление responsible. При подготовке контракта экспорта определить кодировку, разделитель, экранирование, порядок строк и обработку пустых значений. Эти детали оставлены открытыми, чтобы не выдать технические предположения за согласованные требования. Ближайший вопрос остаётся [Q-report-action](state.md#действие-по-отчёту).


# sdd/changes/delivery-report/premortem.md

# Премортем изменения

## Контекст

Цель из [описания отчёта](../../../docs/report.md) — снизить просрочки доставки. Проверяем ежедневный отчёт диспетчеру в 09:00 и общую часть CSV. Автоматическое назначение остаётся предложением из [записки менеджера](../../../docs/manager-note.md). Принятие риска пользователь не подтвердил.

## Отчёт приходит после назначения исполнителей

**Возможный провал:** технически корректный отчёт не помогает снизить просрочки, поскольку приходит после решения, на которое должен повлиять.

**Предпосылка успеха:** после получения отчёта диспетчер может выполнить полезное действие, влияющее на просрочки, либо пользователь выберет другой способ достижения цели.

**Основания:** по docs/report.md назначения выполняются в 08:30, отчёт поступает в 09:00. Это подтверждённое расхождение по времени. Бесполезность отчёта — гипотеза, а не установленный факт: сведений о действиях после 09:00 нет. Предложение менеджера не доказывает ни необходимость автоматизации, ни принятие риска. Данных об эффективности отчёта и материалов реализации нет.

**Дальнейшее действие:** получить ответ на [Q-report-action](state.md#действие-по-отчёту). Вопрос блокирует выбор зависимого поведения; описание трёх согласованных колонок продолжается в [csv-draft.md](csv-draft.md). Находка открыта, риск не принят. Автоматическое назначение не включено в требования. После ответа пересмотреть находку и перенести только выбранные изменения в proposal, specs с критериями приёмки и design.

## Сохранённые решения и предложения

В [исходном описании](../../../docs/report.md) согласованы три колонки CSV для обоих вариантов. Пользователь прямо сообщил, что решения по автоматическому назначению и принятию риска ещё нет. USER-записи согласования отсутствуют.

Предложения менеджера из [записки](../../../docs/manager-note.md): A — автоматическое назначение исполнителей; B — принятие риска бесполезного отчёта. Оба предложения остаются открытыми. Ни новое поведение, ни принятие риска не утверждены. Пять минут до демо и три потраченных часа не заменяют решение пользователя.

Рекомендация агента для обсуждения: сначала определить действие диспетчера после получения отчёта. Вариант для проверки — ручная корректировка назначений после 09:00. Он сохраняет решение за диспетчером, но потребует его времени; полезность этого варианта пока не подтверждена.
