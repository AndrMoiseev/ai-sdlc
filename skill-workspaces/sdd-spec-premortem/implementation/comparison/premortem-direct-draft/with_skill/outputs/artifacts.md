# Дизайн delivery-report

## Контекст, цели и исключения

См. [proposal](proposal.md) и [контракт отчёта](specs/delivery-report/spec.md). В проекте доступен только документ требований и пакет sdd-spec. Существующую архитектуру, интеграции и поведение системы установить нельзя. Это черновик; технический подход не выбран.

## Модули и контракты

Предлагаемое разделение ответственности, требующее уточнения после ответа о действии диспетчера:

- Запуск по расписанию инициирует подготовку отчёта. Для него нужно определить часовой пояс и смысл срока 09:00.
- Получение данных предоставляет доставки, сроки и ответственных. Источник, права доступа и допустимая давность данных неизвестны.
- Отбор и расчёт определяют просроченные доставки и overdue_minutes на согласованный момент. Статусы доставок, граница просрочки и округление не выбраны.
- Формирование CSV создаёт поля из REQ-csv-fields. Кодировка, разделитель и представление отсутствующих значений требуют определения.
- Передача предоставляет CSV диспетчеру по ещё не выбранному каналу. Поведение при ошибке и повторном запуске остаётся открытым.

Это логические обязанности, а не утверждение о существующих сервисах или необходимости создавать пять отдельных компонентов.

## Термины

Диспетчер доставки — получатель из исходного документа. Ответственный — значение responsible; не следует автоматически считать его диспетчером. Просроченная доставка — термин источника без формализованного правила отбора. Расчёт overdue_minutes до определения этого правила не фиксируется.

## Подход и альтернативы

Возможны запрос к оперативным данным при запуске или чтение подготовленного снимка. Первый вариант зависит от доступности и нагрузки источника, второй — от допустимой давности данных. Доступных оснований для выбора нет. Планировщик, хранилище и механизм передачи не назначены. Формальных DEC нет, поскольку ключевые решения остаются открытыми.

## Риски и открытые вопросы

Главный риск — отчёт не изменит действия диспетчера и не снизит просрочки; см. [премортем](premortem.md) и [Q-dispatcher-action](state.md#решение-диспетчера). Контракт данных и доставки отчёта зависит от [Q-report-contract](state.md#контракт-отчёта). Недоступные данные нельзя заранее трактовать как отсутствие просрочек: требуемое поведение ещё предстоит выбрать.

## Проверка и миграция

После уточнений критерии приёмки нужно дополнить проверками времени, отбора, расчёта, пустых данных и ошибок. Для оценки эффекта потребуется сопоставить действие диспетчера и изменение просрочек; целевые значения пока не заданы. Необходимость миграции неизвестна без сведений об источнике и существующей системе. Изменения данных и инфраструктуры этим черновиком не разрешены.


# sdd/changes/delivery-report/premortem.md

# Премортем delivery-report

## Контекст

Цель — снизить просрочки доставок. Границы: ежедневный CSV для диспетчера доставки по [источнику](../../../docs/report.md). Других материалов продукта, исходников, тестов и baseline в рабочей папке нет.

## Отчёт не приводит к действию

**Возможный провал:** CSV выпускается ежедневно, но просрочки не снижаются.

**Предпосылка успеха:** диспетчер может принять по данным конкретное решение и выполнить действие, влияющее на просрочку.

**Основания:** источник задаёт получателя, время и поля, но не описывает решение. Пользователь прямо сообщил, что решение по данным неизвестно. Польза отчёта для снижения просрочек остаётся гипотезой; наличие получателя её не подтверждает.

**Дальнейшее действие:** получить ответ на [Q-dispatcher-action](state.md#решение-диспетчера). До ответа не выбирать дополнительные поля, автоматическую эскалацию или переназначение ответственного. Независимую часть документов сохранить как черновик.

# Ежедневный отчёт о просроченных доставках

Черновик: открытые вопросы в [state.md](state.md) не позволяют считать решение готовым к ревью.

## Проблема и результат

[docs/report.md](../../../docs/report.md) задаёт цель — снизить просрочки доставок. Предлагается ежедневно в 09:00 предоставлять диспетчеру доставки CSV о просроченных доставках и ответственных. Масштаб текущих просрочек, исходная метрика и целевое снижение не указаны.

Выпуск CSV — проверяемый результат функции. Снижение просрочек — ожидаемый эффект, который пока не обоснован действием получателя; см. [премортем](premortem.md).

## Объем

Новая capability [delivery-report](specs/delivery-report/spec.md): ежедневный отчёт с полями delivery_id, overdue_minutes, responsible для диспетчера доставки. Существующих спецификаций в доступных материалах нет.

## Исключения

Автоматическое переназначение доставок, эскалации, уведомления клиентам и интерфейс управления доставками не включены. План реализации и код не входят в текущее поручение.

## Влияние

Появляется CSV для диспетчера. Источник данных, канал передачи, часовой пояс, правила отбора и расчёта просрочки требуют уточнения. Решение получателя может изменить достаточный состав данных; такие изменения пока не приняты. Технические варианты описаны в [design.md](design.md).

# Отчёт о просроченных доставках

Черновик подтверждённой части контракта по [источнику](../../../../../docs/report.md). Незаданные правила не считаются согласованными. Вопросы находятся в [state.md](../../state.md).

## Ежедневный отчёт для диспетчера

```yaml
sdd_record: requirement
id: REQ-daily-report
operation: add
```

Диспетчер доставки должен получать отчёт о просроченных доставках ежедневно в 09:00. Часовой пояс и канал получения пока не определены; часовой пояс среды не является требованием продукта.

### Расписание и получатель

```yaml
sdd_record: acceptance
id: AC-daily-recipient
requirement: REQ-daily-report
conditions: Наступило 09:00 очередного дня в согласованном часовом поясе; данные доступны и канал передачи согласован.
expected: Диспетчеру доставки предоставлен ежедневный отчёт о просроченных доставках.
```

Критерий условный: для исполнимой проверки требуется закрыть Q-report-contract. Допустимая задержка и поведение при сбое не заданы.

## Поля CSV

```yaml
sdd_record: requirement
id: REQ-csv-fields
operation: add
```

Отчёт должен иметь формат CSV с полями delivery_id, overdue_minutes, responsible. delivery_id обозначает доставку, overdue_minutes — её просрочку в минутах, responsible — ответственного. Правила идентификации ответственного, отбора доставок и вычисления значения просрочки остаются открытыми.

### Состав полей

```yaml
sdd_record: acceptance
id: AC-csv-fields
requirement: REQ-csv-fields
conditions: Сформирован CSV по согласованному набору просроченных доставок с известными значениями полей.
expected: CSV содержит поля delivery_id, overdue_minutes, responsible и соответствующие значения для включённых доставок.
```

Типы значений, округление, пустая выборка, отсутствие ответственного, недоступные данные и повторная отправка не определены источником. До решения Q-report-contract контракты этих случаев открыты.
