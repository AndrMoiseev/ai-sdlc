# Дизайн delivery-report

## Контекст, цели и исключения

Основание — [proposal](proposal.md) и [общий контракт](specs/delivery-report/spec.md). В проекте доступен только docs/report.md; существующая реализация и техническая архитектура не представлены. Ниже предложены логические границы, а не обнаруженные модули кода.

## Модули и контракты

Предлагаемый контур отчёта: запуск по расписанию → получение данных доставок → формирование CSV → предоставление диспетчеру. Источник данных, способ запуска и канал предоставления пока не выбраны. Формирование CSV сохраняет три согласованные колонки при любом будущем решении о назначениях.

Контур назначения зависит от Q-delivery-mode. Он не включён в обязательный поток черновика и не исключён из будущего объёма. Побочные эффекты формирования отчёта до выбора режима не определяются.

## Термины

`delivery_id` — колонка идентификатора доставки; `overdue_minutes` — колонка просрочки в минутах; `responsible` — колонка ответственного. Форматы значений, момент расчёта и представление отсутствующего ответственного требуют согласования.

## Альтернативы, требующие выбора

| Вариант | Поведение | Последствия |
|---|---|---|
| Только отчёт | Предоставление CSV; назначения остаются у диспетчера | Меньший объём изменения; требуется понять, как отчёт в 09:00 помогает после назначений в 08:30 |
| Отчёт и автоматическое назначение | Предоставление CSV и изменение назначений системой | Нужны правила выбора исполнителей, время запуска, приоритет ручных назначений и обработка конфликтов |

Обе альтернативы сохраняют CSV-контракт. Таблица не является решением пользователя. Рекомендация агента — начать с только отчёта, если цель именно информирование диспетчера; она не закрывает вопрос о полезности времени 09:00.

## Риски и открытые вопросы

[Q-delivery-mode](state.md#выбор-режима) блокирует требования и архитектуру назначений, но не описание трёх колонок CSV. Отчёт выходит на 30 минут позже ручного назначения: без уточнения рабочего действия диспетчера можно создать корректный CSV, который не помогает снизить просрочки.

[Q-report-contract](state.md#детали-контракта) фиксирует оставшиеся пробелы отчёта. Не следует выводить правила отбора, расчёта или обработки сбоев только из названий колонок. Миграция и восстановление после ошибок пока не определены; для автоматического режима потребуется отдельно рассмотреть отмену назначений и повторный запуск.

# Ежедневный отчёт о доставках

## Проблема и результат

По [исходным материалам](../../../docs/report.md) цель изменения — снизить просрочки доставок. Получатель ежедневного отчёта — диспетчер доставки. Отчёт предусмотрен в 09:00, назначения диспетчер выполняет в 08:30. Связь отчёта с решением о назначениях требует уточнения: отчёт за этот день поступает после назначения. Снижение просрочек пока является целью, а не доказанным результатом.

## Объем

Общая для обоих вариантов capability — [delivery-report](specs/delivery-report/spec.md): ежедневный CSV с тремя согласованными колонками. Этот контракт можно зафиксировать до выбора режима.

Объем изменения остаётся открытым: только отчёт или отчёт вместе с автоматическим назначением исполнителей. Ни один вариант не принят по умолчанию. Зависимые требования к назначениям появятся после ответа на Q-delivery-mode в [state.md](state.md).

## Исключения

В текущем черновике не определены алгоритм назначения, права на изменение исполнителей и обработка конфликтов с ручным назначением. Это нерешённая часть объёма, а не окончательное исключение автоматизации. План реализации и изменения кода не входят в текущее поручение.

## Влияние

Выходной интерфейс — CSV для диспетчера. Автоматический режим дополнительно затронет данные назначений; конкретные системы и интеграции в материалах не указаны. Код и конфигурация продукта отсутствуют, поэтому техническая совместимость не подтверждена.

# Отчёт о доставках

Источник: [docs/report.md](../../../../../docs/report.md). Черновик описывает общую часть обоих вариантов. Правила автоматического назначения не определены.

## Ежедневный отчёт диспетчеру

```yaml
sdd_record: requirement
id: REQ-daily-report
operation: add
```

Система должна ежедневно предоставлять диспетчеру доставки отчёт в 09:00. Часовой пояс и способ предоставления требуют уточнения в Q-report-contract; часовой пояс среды агента не считается часовым поясом продукта.

### Время и получатель

```yaml
sdd_record: acceptance
id: AC-daily-report
requirement: REQ-daily-report
conditions: Наступило 09:00 очередного дня в часовом поясе продукта, который предстоит согласовать.
expected: Диспетчеру доставки предоставлен ежедневный отчёт согласованным способом.
```

Этот критерий частичный: до уточнения часового пояса и канала его нельзя использовать для окончательной приёмки.

## Три колонки CSV

```yaml
sdd_record: requirement
id: REQ-report-csv
operation: add
```

Отчёт должен иметь формат CSV ровно с тремя колонками в согласованном порядке: `delivery_id`, `overdue_minutes`, `responsible`. Состав колонок не зависит от выбора между только отчётом и автоматическим назначением исполнителей. Дополнительная колонка для режима или результата назначения не предусмотрена.

### Состав и порядок колонок

```yaml
sdd_record: acceptance
id: AC-csv-columns
requirement: REQ-report-csv
conditions: Сформирован CSV-отчёт о доставках.
expected: CSV содержит ровно три колонки в порядке delivery_id, overdue_minutes, responsible.
```

### Независимость от режима

```yaml
sdd_record: acceptance
id: AC-csv-mode-independent
requirement: REQ-report-csv
conditions: При дальнейшей проработке выбран любой из двух обсуждаемых режимов.
expected: Состав и порядок колонок CSV остаются delivery_id, overdue_minutes, responsible.
```

Критерий не требует поддержки переключения режимов: продуктовый выбор ещё не сделан. Правила отбора строк, расчёта просрочки, значения responsible и обработки ошибок остаются открытыми в Q-report-contract.

status: open
