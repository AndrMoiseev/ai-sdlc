# Формат документов sdd v1

Перед записью прочитайте шаблон соответствующего документа. Пакет использует UTF-8 Markdown: читаемый текст описывает смысл, YAML рядом с элементом хранит идентичность и связи. Отдельного реестра трассировки нет. Текущий OpenSpec-проект не требуется переносить в этот формат.

## Расположение и разбор

Рабочий корень — `sdd/changes/<change-id>/`: proposal.md, design.md, specs/<capability>/spec.md, tasks.md, state.md, decisions.md, questions.md и review/. Capability может иметь несколько kebab-case сегментов через `/`. Proposal и design общие для изменения; tasks появляется только по разрешенному переходу. Журнал и вопросы создаются при наличии соответствующего содержания по [правилам обсуждения](discussion.md).

Необязательные производные материалы: explanation.md, дополнительные документы
в explanation/ и все сохраняемые артефакты диаграмм в archify/. Их размещение,
индекс и актуальность определяет [контракт пояснения](explanation.md).
Это обычные Markdown и артефакты без нового document_type или kind USER.
Выбор пояснения, область, исходный манифест и выполненную часть сохраняй
в читаемой части state.

Frontmatter нормативного документа содержит ровно `schema_version: 1`, `document_type` (proposal/spec/design/tasks), `change_id`, `language`; spec дополнительно содержит `capability`, совпадающую с каталогом. Основной текст следует языку проекта, иначе запросу; служебные поля не переводятся. State/review/decisions/summary имеют те же общие поля и дополнительные метаданные ниже. Индекс линз имеет собственный frontmatter.

Машинная запись: заголовок, пустая строка и fenced-блок `yaml` с `sdd_record` и `id`. В spec используй иерархию `#` capability → `##` требование → `###` критерий приемки. Размещай все критерии сразу внутри своего требования, до следующего `##`; поле `requirement` каждого критерия должно совпадать с ID родительского требования. Так связь видна и в тексте, и в оглавлении. В остальных документах заголовок записи имеет уровень `###`.

Текст записи следует за YAML до следующего заголовка записи или заголовка равного либо более высокого уровня. Критерии образуют подразделы требования, каждый со своим текстом. Для совместимости парсер также читает прежние spec, где все записи имеют уровень `###`. Новые spec оформляй с требованиями `##`; при переводе существующего файла перенеси все его требования и критерии вместе, сохраняя ID и связи.

Примеры с sdd_record помещайте внутрь внешнего четырехсимвольного fence: парсер не воспринимает их как данные. Иные YAML-примеры не являются записями. Не используйте aliases, anchors, merge keys, пользовательские YAML tags, дубли ключей или неизвестные поля. Новая версия требует обновления проверяющего пакета, а не молчаливой интерпретации.

## Премортем

`premortem.md` в каталоге изменения хранит исследование по
[контракту премортема](premortem.md); создавай его только при находках по
[шаблону](../templates/premortem.md). Это обычный Markdown без frontmatter,
нового document_type, sdd_record или вида USER. Заголовки находок служат
якорями; вопросы используют Q-ID в questions.md, а не FIND ревью.

Раздел «Премортем» в state содержит краткий итог: отсутствие находок либо
наличие находок со ссылкой на документ. Закрытые находки и ссылка сохраняются.
Разбор не входит в манифест documents или plan. Выбранные изменения цели,
поведения и подхода переноси в proposal, specs с AC и design; после нормативной
правки действуют обычные правила актуальности ревью и согласований.
Завершение проверки не заменяет условия перехода к плану.

## Идентичность и трассировка

ID = префикс + `-` + смысловой slug. Slug: `[a-z][a-z0-9]*(?:-[a-z0-9]+)*`, 1–64 символа. Префиксы: REQ, AC, DEC, TASK, Q, USER, FIND. ID уникальны внутри изменения; FIND исключение — уникальность внутри отчета. Полный ключ находки: `<run-id>/<lens-id>/<FIND-ID>`; между изменениями добавьте `<change-id>/`. Ссылки на другие элементы другого изменения: `<change-id>/<ID>`; они дают контекст, но не покрытие местного критерия или зависимость исполнения.

| sdd_record | Где | Поля сверх id/sdd_record |
|---|---|---|
| requirement | spec | operation: add/modify/remove; source обязателен для modify/remove |
| acceptance | spec | requirement: REQ-ID, conditions: текст, expected: текст |
| decision | design | requirements: непустой список REQ-ID |
| task | tasks | number, covers, depends_on, status, verification; необязательный cannot_parallel_with |
| question | questions; legacy state | text, blocking: boolean, status: open/resolved; reason и return_at для открытого неблокирующего; resolution для закрытого в questions |
| finding | review | source, target, severity, problem, impact, suggestion |
| user | review/decisions | kind, scope, response, date, inputs; дополнительные поля ниже |

Каждый REQ имеет хотя бы один AC. Каждый AC принадлежит одному REQ; на стадии plan его покрывает ровно одна задача. DEC ссылается хотя бы на одно требование; REQ без DEC допустим. Модули, контракты и термины в design — обычные разделы, искусственные DEC не нужны.

### Изменение baseline

Для modify/remove сохраните полное предлагаемое содержание затронутого требования; не копируйте всю неизмененную capability. Remove сохраняет критерии результата удаления и их покрытие задачами. Переименование заголовка при стабильном ID — modify.

`source` имеет один из вариантов:

```yaml
kind: specification
path: docs/specs/orders.md
requirement: REQ-existing-order
```

`path` относительно корня проекта, `requirement` — существующий ID или точный заголовок. При действительно отсутствующем baseline:

```yaml
kind: evidence
baseline_missing: true
references: [src/orders.py, tests/test_orders.py]
observed: Подтвержденное исходное поведение
assumptions: Допущений нет
```

Неработающую ссылку на baseline нельзя скрывать заменой на evidence. references содержит существующие локальные источники или HTTP(S) URL; скрипты не обращаются к сети. Проверку смысла выполняет агент.

### Задача и ее проверка

`number` — перестановка 1..N; `depends_on` — TASK-ID того же изменения. Циклы, зависимости на себя и отсутствующие задачи ошибочны. `cannot_parallel_with` — симметричное ограничение без навязывания порядка. Наличие общего файла само по себе не запрещает параллельную работу: рассмотрите разделение участков и контракты.

`status`: pending/in_progress/done/blocked; новый план начинает с pending. Прогресс определяется количеством done, не максимальным номером; статус не доказывает прохождения тестов. Пилот не исполняет план.

`verification` — непустой список объектов `criteria`, `test_description`, `location`, `run`. criteria — непустое подмножество covers; объединение покрывает все covers. run — mapping ровно с одним ключом command, procedure или setup_required и непустым текстом. command — проектная команда; procedure — ссылка на существующий файл проектной процедуры (возможен #anchor); setup_required — подготовка запуска внутри этой задачи. Будущий location теста может отсутствовать. Тесты, включая интеграционные, входят в задачу реализации критерия.

## State и вопросы

Дополнительные поля state: phase, awaiting, updated_at (quoted ISO UTC), document_links, review_links, approval_refs. Phase: discovery/drafting/document_review/user_review/planning/plan_review/plan_approved. Awaiting: none/clarification/review_consent/planning_command/final_approval. Пути относительны изменению, approval_refs содержит USER-ID. Читаемая часть хранит следующий шаг, предложения, решения-ссылки и состояние проверок, без дублирования specs/design.

Поврежденный state восстанавливается как черновик по документам и доступным проверенным решениям. Phase не подтверждает разрешения. Отмена или замена последним ответом пользователя прекращает старое поручение; наличие tasks не восстанавливает его.

## Журнал решений и вопросы

Журнал `decisions.md` в корне изменения — обычный Markdown по
[шаблону](../templates/discussion-decisions.md), без frontmatter, sdd_record и
новых ID. Устойчивые заголовки связывают авторство предложения, статус, автора
принятия и основание с вопросами и нормативными документами. Этот журнал
не заменяет USER-записи в `review/decisions.md`.

`questions.md` имеет ровно общие поля frontmatter: schema_version: 1,
document_type: questions, change_id и language. Каждая Q-запись содержит text,
blocking и status; открытая неблокирующая требует reason и return_at.
Для status: resolved обязательно resolution — непустая строка с относительным
путём от каталога изменения к существующему файлу основания, при наличии `#`
якорь должен быть непустым. Например, `decisions.md#режим-выполнения`.
Путь остаётся внутри изменения; внешний источник сначала зафиксируй
в локальном исследовании со ссылкой и результатом проверки. Скрипт проверяет
файл и форму ссылки; наличие якоря и смысл основания проверяет агент.
У legacy-вопросов в state resolution необязателен. Дубликат Q-ID между
questions.md и state — ошибка, включая совпадающие записи.
Перенос и восстановление выполняй по [discussion](discussion.md).

## Линзы, отчеты и сводка

Индекс `sdd/arch-lenses/index.md`: frontmatter `schema_version: 1`, `lenses: [{id, title, path}]`. Пути относительно каталога индекса. Нет файла или lenses: [] — только consistency; поврежденный существующий индекс ошибочен. consistency и plan зарезервированы. Содержимое линзы: предмет, вопросы, ограничения, источники.

Отчет: `review/<run-id>/<lens-id>.md`; для плана lens-id=plan. Run-id — UTC-время с уникальным суффиксом. Дополнительный frontmatter: run_id, stage (document_review/plan_review), lens_id, result, started_at, finished_at, inputs, inputs_after, freshness, limitations. Все даты заключайте в кавычки. result: completed_no_findings/completed_with_findings/incomplete; limitations — список строк. Находка имеет source (текст), target: {path, element_id?}, severity: blocker/recommendation, problem/impact/suggestion (непустой текст). target.path относительно изменения.

Манифест — отсортированный список `{path, sha256}`; пути относительно изменения, хеши SHA-256 сырых байтов. Документная стадия включает proposal/design/все specs/**/spec.md; плановая добавляет tasks. State, decisions.md, questions.md, review, premortem.md, внешние источники и инструкции линз исключены. Снимок до/после и текущий должны совпасть; гонка внутри запуска оставляет отчет stale даже при возврате исходных байтов. Сохраненное freshness — историческое значение, при чтении вычислите актуальность вновь. Изменение общего комплекта устаревает для всех линз стадии; новый индекс может потребовать недостающую линзу независимо от хешей.

explanation.md, explanation/ и archify/ также исключены из нормативного манифеста,
включая index.md, candidate, HTML, снимки и промпт продолжения. Замена только
превью, заглушки или прозы пояснения сохраняет согласование неизменённого
основного комплекта. Новое обязательство из пояснения требует обычного revise
с пересчётом актуальности ревью и согласований нормативных документов.

Сводка `review/summary.md`: общий frontmatter document_type: summary плюс findings — список `{finding, related_to, duplicates}` с полными ключами. Для отсутствующих связей используйте []. Сохраняйте исходные отчеты; объединяйте дубли только в сводке, показывайте расхождения отдельно. related_to не переносит решения.

## USER-решения и область разрешения

`review/decisions.md` имеет document_type: decisions. USER-запись содержит kind, scope, response (реальный явный ответ), date (quoted ISO с timezone), inputs (манифест исходной версии). Необязательны message (ссылка при наличии), status (active/completed/cancelled), supersedes (список USER-ID).

| kind | scope сверх stage | Применимость |
|---|---|---|
| review_consent | run_id, lenses | Только указанный запуск |
| review_waiver | lenses | Точная версия, стадия и линзы |
| document_approval | — | Точная версия document_review |
| planning_command | work: ограниченный объем | document_review; поручение сохраняется при ожидаемых правках |
| plan_approval | — | Точная версия plan_review |
| finding_disposition | findings: полные ключи | Только перечисленные находки, без автоматического переноса |

У disposition дополнительно action: fix/reject/defer; reject/defer требуют reason, defer — return_at. Выполнение fix храните отдельно в completion: `[{finding, path}]`, path существующего измененного документа относительно изменения. Исторический response не переписывайте. Для отмены пометьте status: cancelled и сохраните свидетельство отмены в читаемом тексте/ссылке; для замены новая датированная запись указывает supersedes. Механика не доказывает авторство пользователя: при продолжении агент сверяет последнюю явную волю, объем и происхождение правок.

Согласование и waiver действуют только при совпадении версии. Поручение исправить или спланировать сохраняется при ожидаемых правках до завершения, отмены/замены или изменения объема. Необъясненные внешние правки требуют уточнить затронутую область. Разрешение работы не обходит отдельные условия готовности и не охватывает новые находки.

## Результат check

Пределы разбора: документ до 4 млн символов, отдельный YAML-блок до 1 млн символов и 100 тысяч токенов, вложенность YAML/Markdown до 64 уровней. Превышение сообщает структурную диагностику вместо неограниченного расхода памяти. Необычные скалярные значения и поврежденные URL также возвращают диагностику; содержимое не исполняется.

JSON содержит schema_version, stage, errors, warnings, discussion_status, review_status, approval_status и сведения о задачах при наличии. discussion_status содержит open_questions, blocking_questions и complete: записи разобраны без повреждений и открытых блокирующих вопросов. Это не оценка полноты выявленных вопросов или авторства журнала. Открытый блокирующий вопрос или повреждение списка/существующего state препятствуют approval_status.ready. Отсутствующие legacy state/questions сами по себе не отменяют прежние согласования.

Диагностика: code/path/element_id/message. Код 0 означает корректную структуру; 1 — структурные ошибки (в том числе повреждённый questions.md); 2 — проверка не выполнена для основного комплекта (нечитаемый вход/неподдерживаемая версия/окружение). Статусы обсуждения, ревью и согласования сообщаются отдельно. Даже ready не является доказательством авторства решений или качества анализа: перед переходом агент проверяет смысл, вопросы и волю пользователя.

Шаблоны содержат примеры: замените sample-change, тексты, даты и пустые манифесты реальными данными. Черновой незаполненный шаблон не означает готовый артефакт.
