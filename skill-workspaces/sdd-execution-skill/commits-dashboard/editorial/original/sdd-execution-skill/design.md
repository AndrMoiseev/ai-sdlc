# Устройство скилла выполнения плана

## Контекст

Цель и границы описаны в [proposal](proposal.md), поведение в
[spec](specs/sdd-execution/spec.md). Основания заимствований и отличий от
NeoPilot находятся в [research](research.md). Это черновой дизайн;
пользователь подтвердил автономное выполнение всего плана, последовательный
режим по умолчанию и параллельный режим только по явному запросу.
Скилл работает в паре с `sdd-spec`, заканчивает работу набором коммитов
по задачам и с первой версии предоставляет HTML-дашборд. Подготовка
спецификаций и автоматическое переписывание проектных инструкций исключены
из его назначения.

В новом пакете короткий SKILL.md с выбором действий: начало,
исполнение, исправление, возврат к спецификации, продолжение и приёмка.
Инструкции ролей и адаптеры среды загружаются по необходимости.
Детерминированные операции отвечают за разбор данных и проверку условий
перехода. Решения о смысле требований и качестве реализации остаются
за агентами.

## Термины

**Основание исполнения**: проверенный манифест плана, согласования
и поручение выполнять выбранное изменение.

**Попытка**: запуск исполнителя с определёнными входами и границами работы.
Исправление продолжает попытку; новая попытка сохраняет причину её замены.

**Приёмка задачи**: подтверждение критериев задачи проверками и независимым
ревью на определённой версии с последующей фиксацией коммита в ветке
исполнения. Сообщение исполнителя и коммит без проверок сами по себе
не подтверждают приёмку.

## Модули и контракты

| Часть | Ответственность | Результат |
|---|---|---|
| Вход и продолжение | Найти изменение, проверить основание через установленный sdd-spec, сверить состояние проекта | Проверенное основание или конкретная блокировка |
| Выбор задач | Прочитать граф и ограничения из tasks, сопоставить с принятыми результатами | Список задач, которые можно выполнять сейчас |
| Оркестратор | Запускать роли, сохранять результаты и управлять исправлениями | Актуальная запись исполнения |
| Исполнитель | Реализовать одну задачу в заданной области и выполнить её verification | Изменения и ссылки на доказательства по AC |
| Рецензент | Проверить соответствие и качество определённой версии | Замечания с основаниями и условиями устранения |
| Приёмка результата | Проверить все AC и общий сценарий на итоговой версии | Полный или частичный результат |
| Коммиты задач | Проверить состав изменений и сохранить принятый результат в ветке исполнения | Связь TASK-ID с SHA коммитов |
| HTML-дашборд | Показать сохранённый прогресс и обновлять снимок | Живое представление и HTML для просмотра без сервера |
| Адаптер среды | Запускать чистые контексты, определять доступность ролей и изоляции | Реальные возможности Codex или Claude Code |

Исполнитель получает пути к задачам, связанным REQ/AC, обязательным решениям
design, инструкциям проекта и сводке готовых интерфейсов. Возвращает статус,
принадлежащие ему файлы, результаты verification, незакрытые критерии
и ограничения. Длинные логи хранятся отдельно; краткий результат ссылается
на них. Формат записи исполнения описан ниже; это предложение для первой
версии, которое предстоит проверить на примерах запуска и продолжения.

## Формат записи исполнения

Каталог `execution/` содержит `state.json`, `summary.md`, `dashboard.html`
и каталог `runs/`. Источником состояния служит JSON; Markdown-сводка
и дашборд строятся из него и ссылок на доказательства. Ручная правка
сводки или HTML не меняет прогресс.
У каждой записи есть `schema_version: 1` и `change_id`; неизвестная версия
останавливает разбор с понятной диагностикой.

`state.json` хранит номер `revision`, активный `run_id`, состояние запуска,
ссылку на основание, режим `sequential` или `parallel`, ссылку на явный
запрос пользователя для `parallel`, записи задач и следующий шаг. Задача определяется
по TASK-ID; её запись содержит состояние, номер попытки, причину блокировки,
ссылки на доказательства, принятый снимок кода и коммиты с SHA.
Состояния задачи: `pending`, `running`, `reviewing`, `repairing`,
`committing`, `blocked`, `accepted`.
Состояния запуска: `active`, `blocked`, `completed`. Завершённая с ошибкой
попытка остаётся в истории, а её задача становится `blocked`.

Для запуска создаётся `runs/<run-id>/input.json`: манифест нормативного
комплекта, ссылки на согласования, поручение пользователя, ветка исполнения, исходный HEAD,
снимок исходных локальных изменений и бюджет исправлений. Новый согласованный
комплект создаёт новый запуск, сохраняя связь с предыдущим. Доказательства
лежат в `runs/<run-id>/tasks/<TASK-ID>/<attempt>/`; их записи хранят вид
проверки, связанные AC, команду или процедуру, рабочий каталог, время,
результат, код выхода при наличии, ограничения, путь и хеш лога.

Снимок кода содержит основание diff, список путей и SHA-256 проверенных
байтов; удаления отмечаются отдельно. Для проверки, зависящей от других
модулей или конфигурации, фиксируется и эта область. Коммит обязателен
для принятой задачи, но не заменяет снимок проверенной рабочей копии.
Перед приёмкой состав коммита сопоставляется с этим снимком. Неизвестная
область зависимости требует повторной проверки перед приёмкой.

Состояние записывает только оркестратор. Скрипт перехода получает ожидаемый
`revision`, захватывает блокировку конкретного изменения, перечитывает
состояние и проверяет переход. Запись выполняется через временный файл
и атомарную замену, после чего увеличивается `revision`. Конфликт версии
или занятая блокировка возвращает ошибку без перезаписи. Устаревшая
блокировка снимается лишь после проверки отсутствия владельца; возраст
файла сам по себе этого не доказывает. Два активных оркестратора не могут
одновременно вести одно изменение.

`accepted` требует проверок всех назначенных AC, актуального независимого
ревью, отсутствия блокирующих замечаний и подтверждённого коммита
в ветке исполнения. `completed` требует приёмки всех задач, их коммитов
и итогового результата. Условия проверяются по записям и существующим
доказательствам; их содержательную достоверность устанавливают агенты.
Пути записей ограничены каталогом изменения, пути исходников и команд
разрешаются относительно явно указанного корня проекта. Произвольные пути
из результатов исполнителя не становятся разрешением записи.

### Отдельное хранение исполнения

```yaml
sdd_record: decision
id: DEC-separate-execution
requirements: [REQ-approved-input, REQ-execution-record, REQ-resume-execution]
```

Предлагается каталог `sdd/changes/<change-id>/execution/` с основанием
запуска, прогрессом, результатами ролей и доказательствами. Изменения
нормативного комплекта здесь не хранятся. Исходный `state.md` остаётся
точкой продолжения `sdd-spec`; у исполнения своя точка продолжения.

Так сохраняются существующие хеши и согласования. Альтернатива требует
изменить правила вычисления манифеста `sdd-spec`, проверить миграцию
и обновить ранее сохранённые основания. Для первой версии это лишняя
связь с другим пакетом.

### Последовательное выполнение как исходный режим

```yaml
sdd_record: decision
id: DEC-controlled-concurrency
requirements: [REQ-autonomous-execution, REQ-independent-review]
```

При новом исполнении режим по умолчанию `sequential`. Оркестратор ведёт
одну задачу до приёмки или блокировки, включая проверки, ревью и исправления,
затем выбирает следующую доступную задачу. Автономное продолжение не требует
подтверждения каждой задачи. Работа над следующей задачей не перекрывается
с ревью предыдущей.

Режим `parallel` включается только по явному запросу пользователя для этого
исполнения. Перед запуском оркестратор сохраняет запрос и его область.
Наличие независимых задач, изоляции или свободных слотов не меняет режим
автоматически. Даже при явном запросе параллельный запуск допустим только
в отдельных рабочих копиях с контролируемой интеграцией, по зависимостям
и ограничениям плана. Сначала проверяется результат задачи в её копии,
затем результат интеграции. Если изоляция недоступна, оркестратор сообщает
причину и продолжает последовательно.

При продолжении того же исполнения проверяются сохранённый запрос и его
область, включая позднюю отмену или замену. Действующий выбор не запрашивается
повторно. Без подтверждённого разрешения режим `parallel` не восстанавливается.
При возврате к `sequential` активным задачам дают завершиться или зафиксировать
блокировку; новые задачи до этого не запускаются. Переходы состояния
проверяют выбранный режим и не разрешают второй активный цикл задачи
в `sequential`.

Оркестратор сохраняет исходный HEAD, исходные локальные изменения
и принадлежность новых файлов. Для ревью материал включает новые,
индексированные и неиндексированные изменения конкретной задачи.
Общий `git add -A` не используется как способ выделить её результат.
После проверок и ревью коммит задачи обязателен; создание коммитов входит
в поручение исполнить план. Детали фиксации результата описаны ниже.

### Коммиты как итог исполнения

```yaml
sdd_record: decision
id: DEC-task-commits
requirements: [REQ-task-commits, REQ-execution-record, REQ-final-acceptance, REQ-resume-execution]
```

До запуска сохраняются локальная ветка исполнения и её исходный HEAD,
проверяется возможность создавать коммиты. По умолчанию используется текущая
локальная ветка, если пользователь или правила проекта не определили другую.
Отсутствие Git, доступной ветки или необходимых настроек записи блокирует
реализацию с конкретной причиной. Глобальные настройки Git скилл не меняет.

Оркестратор переводит задачу в `committing`, фиксирует ожидаемого родителя
и состав проверенных изменений. Он добавляет только файлы и участки задачи,
проверяет индекс перед коммитом, сохраняет TASK-ID в сообщении и SHA
в состоянии. Чужие индексированные изменения сохраняются отдельно от этой
операции и не попадают в коммит. Если разделить изменения надёжно нельзя,
задача блокируется до разрешения конфликта принадлежности.

В последовательном режиме результат сразу фиксируется в ветке исполнения.
В параллельном режиме рабочие копии изолируют реализацию, а оркестратор
переносит результаты в ветку исполнения по одной задаче и проверяет
интеграцию. Итоговый SHA относится к этой ветке. Вспомогательный коммит
исполнителя до переноса не закрывает задачу. Merge с целевой веткой проекта
не выполняется: ветка исполнения остаётся локальным результатом.

При потере сессии в `committing` продолжение сверяет историю после
сохранённого родителя, TASK-ID и фактическое содержимое коммита. Найденный
результат связывается с задачей без повторного коммита. Неоднозначность
остаётся блокировкой. Ошибка Git не позволяет перевести задачу в `accepted`.
Исправление уже принятой задачи снова проходит проверки и ревью и получает
дополнительный коммит с тем же TASK-ID. Автоматические amend и переписывание
истории не используются.

Итоговая приёмка проверяет совокупный результат коммитов. Отчёт и дашборд
содержат их список по задачам. Служебные материалы исполнения сохраняются
в `execution/`; они не создают отдельного этапа финальной актуализации
проектных инструкций или отдельного коммита обслуживания проекта.

### Дашборд из состояния исполнения

```yaml
sdd_record: decision
id: DEC-live-dashboard
requirements: [REQ-progress-dashboard, REQ-execution-record, REQ-portable-package]
```

Дашборд создаётся из собственного шаблона пакета до первой задачи.
Из NeoPilot берётся принцип общего источника данных и встроенного снимка,
а не его HTML или `sync.py`. Генератор получает `state.json`, проверяет схему
и создаёт `dashboard.html` со встроенным снимком и номером `revision`.
Тексты задач и сообщений экранируются; HTML не исполняет код из состояния.
Секреты и полные логи проверок в данные панели не включаются.

Локальный просмотр использует небольшой сервер на loopback-интерфейсе,
который отдаёт только дашборд и разрешённые данные этого исполнения.
Страница опрашивает JSON состояния каждые две секунды и обновляет элементы
без перезагрузки документа. В обычном активном окне новый сохранённый статус
отображается не позднее следующего успешного опроса. Разрешения на команды
и изменение состояния через панель не добавляются: это средство наблюдения.

Верхняя часть показывает изменение, режим, число принятых задач и общее
состояние. Таблица задач содержит TASK-ID, название, статус, текущий этап,
проверки, ревью, блокировку и SHA. Отдельно видны время последнего обновления
и ограничения проверки. Число завершённых задач считается по `accepted`,
а не по последнему номеру задачи. При потере связи сохранённые данные остаются
видимыми с отметкой об отсутствии обновлений.

После каждого сохранённого перехода генератор атомарно обновляет HTML-снимок.
Ошибка генерации или просмотра фиксируется отдельно от результата задачи;
скилл показывает причину и доступный путь к последнему снимку. На продолжении
он сверяет `revision`, восстанавливает снимок и локальный просмотр. Если
автоматически открыть браузер нельзя, пользователь получает путь или URL.
После завершения создаётся финальный снимок. Сервер текущего исполнения
останавливается с проверкой принадлежности процесса; чужие серверы не трогаются.
При открытии сохранённого HTML без сервера видны итоговые данные и отметка
снимка; запущенное выполнение не изображается как продолжающее обновляться.

### Роли с проверяемыми результатами

```yaml
sdd_record: decision
id: DEC-fresh-roles
requirements: [REQ-autonomous-execution, REQ-independent-review, REQ-final-acceptance, REQ-portable-package]
```

Работа над каждой задачей начинается в новом контексте. Исправления можно вернуть
её исполнителю, пока контекст доступен. Рецензент запускается отдельно
и получает необходимые исходные материалы, без истории автора. Для первой
версии предлагается свежий рецензент задачи, который раздельно оценивает
соответствие и качество. Итоговый проверяющий также получает чистый контекст.

В NeoPilot два рецензента сохраняют контекст между задачами. Это может уменьшать повторное
чтение и помогать замечать расхождения между задачами. Здесь сначала
проверяется более простой вариант со свежим контекстом; связи между задачами
доступны через design, код и сводку интерфейсов. Выигрыш от длительного сохранения контекста
рецензентов требует сравнительного испытания.

Адаптер различает недоступный механизм запуска, временно занятые слоты
и потерянного агента. Запуск встроенными средствами среды предпочтителен; отдельный CLI допустим,
если подтверждены чистый контекст, доступ к файлам и аутентификация.
Нельзя объявлять инструкцию «только чтение» жёстким ограничением прав среды.

### Доказательства определяют завершение

```yaml
sdd_record: decision
id: DEC-evidence-completion
requirements: [REQ-execution-record, REQ-independent-review, REQ-final-acceptance]
```

Состояния исполнения отражают работу, ревью, исправление, блокировку
и приёмку. Только принятое состояние удовлетворяет зависимость.
Ошибка предшественника сохраняет блокировку потомков. Проверяющий механизм
отклоняет недопустимый переход, а не ограничивается предупреждением.

Для verification используется согласованная команда, процедура или
предусмотренная подготовка запуска. Число тестов и exit 0 не заменяют
проверку того, что нужный AC действительно проверен. Исходно падающая
проверка фиксируется отдельно; обязательный неподтверждённый AC остаётся
открытым. Набор регрессионных проверок выбирается по плану и затронутым
контрактам; повтор полного набора обосновывается интеграцией или новой правкой.

Бюджет исправлений задаётся до исполнения и сохраняется в состоянии.
Начальный предлагаемый предел: два цикла исправления на задачу; дальнейшая
попытка требует разбора причины и нового основания. Этот предел -
проверяемая настройка процесса, а не обещание качества. Значение
и поведение при исчерпании проверяются в испытаниях скилла.

### Изменение согласованного контракта

```yaml
sdd_record: decision
id: DEC-return-to-spec
requirements: [REQ-spec-revision, REQ-resume-execution]
```

Возврат содержит ссылку на критерий или решение, наблюдаемую проблему,
минимальное воспроизведение и список затронутых задач. Это материал для
`sdd-spec`, без правки нормативного комплекта. После пересмотра новый
манифест образует новое основание исполнения. Совпадающие TASK-ID помогают
найти прежнюю работу, но не доказывают применимость старой приёмки:
сверяются критерии, зависимости и версия кода.

## Зависимости и установка

Пакет обнаруживает установленный `sdd-spec` через возможности среды
и использует его штатные read-only check/snapshot. Код парсера SDD
не копируется в новый пакет. Недоступная или несовместимая версия зависимости
даёт явное ограничение, а не упрощённую проверку по заголовкам.

Собственные скрипты исполнения получают явные корни проекта и изменения.
Если им нужно окружение, запускатель размещает его и кэши в пользовательском
каталоге ОС с разделением по копиям пакета. Сохраняемые результаты пишутся
в каталог изменения или явно выбранную рабочую область. Относительные
пути пользовательских данных разрешаются от указанного корня проекта.

## Проверка реализации и риски

До написания инструкций нужен изолированный прогон одного согласованного
плана без нового скилла. Затем сравниваются исполнение, продолжение,
ложный DONE, устаревший план, неуспешный предшественник, потеря агента
и возврат к спецификации. Детерминированные проверки должны отклонять
недопустимые переходы; испытания агентов должны показывать реальное
соблюдение процесса. Установка проверяется из отдельной копии и стороннего
рабочего каталога, включая отсутствие runtime-файлов внутри пакета.

Риски разобраны в [premortem](premortem.md). Формат записи исполнения
требует проверки на тестовых запусках при реализации. Миграция
существующих SDD-изменений не требуется: новый запуск
добавляет материалы исполнения только выбранному изменению.
