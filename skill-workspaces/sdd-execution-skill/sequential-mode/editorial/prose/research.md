

Нужен отдельный скилл, который выполняет задачи по спецификации и плану,
подготовленным через `sdd-spec`. Пользователь предложил изучить NeoPilot,
выбрать полезные решения и определить изменения, без копирования реализации.
Рабочее имя нового скилла: `sdd-apply`. Пользователь выбрал автономное
выполнение всего плана и последовательный режим по умолчанию. Параллельный
режим включается только по его явному запросу. Имя и остальные предложения
пока не согласованы.

Проверены исходники NeoPilot из ветки `main`, коммит
`63c509177f425b3a5e5edc382d4fff36a4567bae`, полученный 6 октября 2026 года.
Метод: чтение инструкций, скрипта состояния и его тестов. Сам процесс
разработки NeoPilot и его тесты не запускались. Заявленные автором расходы
токенов и выигрыш во времени в нашей среде не проверены.

Локальное основание: репозиторий на коммите
`e9d54255d069e9f9afe4e66972f3f69b27eac081`, установленный пакет
охватывает путь до плана. Здесь рассматриваются выполнение, ревью,
исправления, восстановление после перерыва и итоговая приёмка.
Старое сравнение не отражает уже добавленный в `sdd-spec` премортем.


1. Оркестратор берёт карточки задач с зависимостями и зонами файлов.
   Для каждой задачи запускает отдельного исполнителя с чистым контекстом.
   Передаёт пути к карточке, нужным разделам спецификации, общим интерфейсам
   и инструкции исполнителя. В обычном режиме оркестратор сам код не пишет.
   Для малых изменений T0 предусмотрен отдельный путь без карточек.
2. Исполнитель проверяет исходное состояние тестов, реализует критерии задачи,
   запускает проверки и возвращает краткий результат: статус, файлы, тесты,
   интерфейсы, выполненные требования и ограничения.
3. Оркестратор обновляет `interfaces.md`. Его читает каждый следующий
   исполнитель, чтобы использовать готовые контракты и функции.
4. Два рецензента проверяют задачу: первый по требованиям и спецификации,
   второй по качеству кода и тестов. Пару рецензентов сохраняют между задачами.
   Они не исправляют код. Блокирующие замечания возвращают исполнителю;
   остальные сохраняют для итогового разбора.
5. После ревью и полного набора тестов оркестратор делает отдельный коммит
   задачи. Только после этого задача считается завершённой и разблокирует
   зависимые задачи. Независимые задачи могут выполняться одновременно.
6. При ошибке различаются исправление в прежнем контексте, новая попытка
   и передача незавершённой задачи другому исполнителю. Для каждого вида
   предусмотрен отдельный счётчик с ограничением. При невозможности выполнить
   план оркестратор может поправить спецификацию и оставшиеся карточки.
7. В конце новый проверяющий получает исходные слова пользователя и проект,
   запускает основной сценарий и оценивает результат без чтения спецификации.
   Отдельные агенты готовят описание проекта и архитектурные решения.
   Итоговый отчёт может содержать невыполненные требования и непроведённые
   проверки; завершение процесса само по себе не означает полную приёмку.

Основной процесс NeoPilot задан Markdown-инструкциями. `sync.py` обновляет
состояние, время этапов, счётчики и снимок HTML-панели; он также обслуживает
локальный сервер. Это не самостоятельный исполнитель графа задач.

В `apply_edit` запуск задачи с незакрытым предшественником записывает новый
статус и добавляет предупреждение. `main` печатает до пяти замечаний `audit`.
Следовательно, эти проверки помогают агенту заметить нарушение, но не
запрещают переход. Тест `test_in_progress_open_blocker_warns` проверяет именно
предупреждение. Кроме того, проверка в `apply_edit` считает `failed`
закрытым предшественником, хотя инструкция исполнения запрещает запуск его
потомков. Это расхождение кода и инструкции нужно учитывать при заимствовании.

В `save` есть повторное чтение перед записью и замена временного файла.
Это обнаруживает часть посторонних правок, но не является блокировкой:
между сравнением и заменой файла другой процесс может записать своё состояние.
Вывод основан на чтении функции; гонка экспериментально не воспроизводилась.


| Решение NeoPilot | Польза для нового скилла | Предлагаемая адаптация |
|---|---|---|
| Отдельный исполнитель на задачу | Ограничивает накопление контекста и задаёт ясную ответственность | Давать TASK-ID, связанные REQ/AC, решения design, проверки и границы записи; передавать материалы по путям |
| Краткий результат исполнителя | Позволяет продолжить работу без чтения всей истории | Хранить ссылки на доказательства проверок каждого AC; сообщение DONE само по себе не закрывает задачу |
| Общие интерфейсы | Уменьшает вероятность несовместимых реализаций | Вести краткую сводку фактически готовых контрактов со ссылками на код; проектные источники остаются авторитетными |
| Независимое ревью | Находит расхождения с требованиями и дефекты, пропущенные автором | Разделять соответствие спецификации и качество кода; проверять конкретную версию изменений |
| Разделение исправления, повтора и передачи работы | Не даёт смешивать разные причины незавершённости | Сохранять причину, сделанное, отвергнутые подходы и следующий шаг; повторять попытку при появлении новых оснований |
| Выполнение по зависимостям | Позволяет использовать независимые задачи плана | Брать граф из `depends_on` и `cannot_parallel_with`; разрешать старт только после принятия предшественников; параллелизм включать только по явному запросу пользователя |
| Итоговая проверка работающего сценария | Выявляет ситуацию, когда отдельные тесты проходят, а результат не работает целиком | Проверять согласованные AC на итоговой версии проекта и сохранять ограничения запуска |
| Короткие сообщения о прогрессе | Пользователь видит результат и причины остановок | Показывать выполненные задачи, активную работу, блокировки и следующий шаг без обязательной HTML-панели |



`sdd-spec` вычисляет SHA-256 сырых байтов нормативных документов, включая
`tasks.md` на стадии plan. В этом же файле у задачи есть поле `status`.
Даже замена `pending` на `in_progress` меняет манифест и делает прежнее
согласование плана неприменимым. Считать такую правку безусловно безопасной
новый скилл по текущему контракту не может.

Предложение: сохранить согласованный комплект неизменным, а прогресс,
попытки, результаты проверок и точки продолжения вести отдельно, например
в `execution/` внутри изменения. Запуск связывать с манифестом плана и
TASK-ID. `state.md` существующего процесса не получает выдуманную фазу
исполнения: его схема заканчивается на `plan_approved`.
Понадобится объяснить, почему статусы в исходном плане остаются `pending`,
и где читать фактический прогресс. Альтернатива: отдельное изменение формата
`sdd-spec`, отделяющее содержимое задач от прогресса при согласовании.


В NeoPilot оркестратор может сам изменить спецификацию после обнаружения
технического ограничения. Для согласованного комплекта SDD предлагается
другая граница: исполнитель сохраняет доказательство проблемы и список
затронутых задач; зависимые действия приостанавливаются. Изменение поведения,
критериев или согласованного подхода проходит через `sdd-spec` и новое
согласование. Локальные решения реализации в пределах документов остаются
на усмотрение исполнителя. Незатронутую работу можно продолжать, если её
независимость подтверждена. [NeoPilot repair][repair], [SDD resume][resume].


В текущем формате `sdd-spec` нет обязательного дословного исходного brief.
Поэтому нельзя обещать аналог слепой проверки G4, подставив вместо brief
написанный агентом proposal. Для первой версии предлагается независимая
приёмка по согласованным specs/AC и реальному поведению. Проверка по словам
пользователя возможна дополнительно, если такой источник сохранён; её
противоречие с согласованной спецификацией требует разбора, а не расширяет
объём автоматически. Обязательное сохранение brief потребует отдельного
изменения `sdd-spec`. [NeoPilot G4][final], [формат SDD][format].


NeoPilot предлагает параллельные задачи в общей рабочей копии, а для ревью
использует `git add -A` и `git diff --cached`. Разные зоны файлов уменьшают
вероятность конфликта записи, но не изолируют индекс Git и полный запуск
тестов от соседней задачи. Это риск смешать результат двух исполнителей
или чужие незакоммиченные изменения; в этом исследовании не проверялось,
происходил ли такой сбой в NeoPilot. [Исполнение][crew], [ревью][review].

Пользователь выбрал последовательный режим по умолчанию и параллельный
режим только по явному запросу. Доступность независимых задач и изоляции
не разрешает автоматически переключать режим. Для разрешённого параллельного
выполнения предлагаются отдельные рабочие копии с определённой процедурой
интеграции и повторной проверки. Для каждого ревью сохранять основание diff и версию
проверенных файлов. Новая правка затронутого кода требует соответствующей
повторной проверки. Коммит полезен как контрольная точка, но не должен быть
единственным доказательством приёмки. Политику коммитов ещё нужно определить.


В NeoPilot финальный отчёт допускает непроведённую приёмку или обнаруженное
расхождение. В новом скилле предлагается отдельно обозначать завершение
сеанса и выполнение плана. Непроверенный обязательный AC остаётся
неподтверждённым; открытый дефект не превращается в принятую задачу.
Отчёт о частичном результате допустим, статус полного выполнения в таком
случае недопустим. [NeoPilot final][final].

Отсутствие субагентов, потеря исполнителя, исходно падающие тесты, недоступная
внешняя система и несогласованный план требуют разных путей восстановления.
При продолжении нужно сверять документы, код и сохранённые доказательства,
сохранять чужие изменения и проверять, достижимы ли прежние агенты.
Фиксированные числа NeoPilot, включая 50 вызовов инструментов и лимиты
повторов, не переносятся без испытаний. [Передача работы][executor],


Вход: явный запуск для выбранного изменения, действующее согласование плана,
готовые документы и разрешение выполнять реализацию. Само наличие
`tasks.md` или `phase: plan_approved` недостаточно.

Выход: проверенная реализация согласованных задач, результаты ревью,
свидетельства по AC, список ограничений и состояние для продолжения.
Предлагается завершать на локальном проверенном результате. Обязательная
панель, автоматическое переписывание AGENTS.md, доводка сверх AC, публикация,
слияние ветки, синхронизация baseline и архивирование в эту версию
не предлагаются. Это предложение границ, а не решение пользователя.

Пользователь выбрал автономное выполнение всего плана, см.
задачи исключена из основного процесса. Разделение ролей и порядок
исполнения предложены в [design.md](design.md).


- Согласованный план с зависимыми задачами: исполнить AC, провести ревью,
  подтвердить итоговый результат; не менять байты согласованного плана.
- План есть, но его согласование отсутствует или устарело: показать причину
  и сохранить состояние, не начинать реализацию.
- Сессия прервана после частичных правок: установить, что действительно
  выполнено, сохранить чужую работу и продолжить оставшееся.
- Реализация выявила невозможность согласованного решения: сохранить
  доказательство, остановить затронутую цепочку и подготовить возврат
  в `sdd-spec` без самостоятельной подмены требований.
- Исполнитель заявил DONE, но проверка AC не запускалась или ревью относится
  к прежней версии кода: оставить задачу непринятой.
- Предшественник завершился ошибкой: зависимая задача не запускается.
  При параллелизме результаты и файлы соседней задачи не попадают в её ревью.
- Несколько задач независимы и изоляция доступна, но параллельный режим
  не запрошен: задачи выполняются по одной, включая их ревью.
- Пользователь явно запросил параллелизм: запрос сохранён, запуск учитывает
  зависимости и изоляцию. При продолжении проверяется, действует ли запрос;
  запись режима без подтверждённого запроса не разрешает параллельную работу.

Это кандидаты для будущих испытаний. По `sdd-skill-conductor` до написания
скилла нужен прогон без него на изолированном примере, затем сравнение
поведения, проверки ошибочных путей и чистоты исходного и установленного
пакетов. Окружения, кэши и временные результаты должны находиться вне
каталогов скиллов. Эти испытания сейчас не проводились.
