# proposal.md

## Объём

Все операции исполнения с однозначными правилами выполняются скриптами
пакета. Это обязательный принцип: проверка переходов и запись состояния,
расчёт доступных задач, сбор результатов команд, работа с Git и worktrees,
перенос изменений, восстановление и генерация панели. Агент передаёт
структурированное намерение; скрипт проверяет условия и выполняет операцию
либо возвращает отказ без изменения прогресса. Прямое редактирование
состояния агентом не является штатным способом работы. За агентами
остаются реализация, интерпретация требований и содержательное ревью.

Добавляется capability [sdd-execution](specs/sdd-execution/spec.md):
вход по согласованному плану, исполнение отдельными агентами, независимое
ревью, исправления, коммиты по задачам, сохранение доказательств
и восстановление после перерыва. Проверка общего результата по согласованным
критериям подтверждает готовность итогового набора коммитов.

HTML-дашборд входит в обязательный объём с первой версии. Он показывает
режим выполнения, задачи и их состояния, прогресс, результаты проверок
и ревью, причины блокировок и созданные коммиты. Данные обновляются
из записи исполнения; после завершения доступен итоговый снимок.

Скилл вызывается явно для выбранного изменения. Поддерживаются Codex
и Claude Code через адаптеры среды. По умолчанию одна задача проходит
реализацию, проверки, ревью и коммит до приёмки; только затем выбирается
следующая доступная задача. Блокировка текущей задачи останавливает
весь последовательный запуск. После устранения причины продолжается
та же задача; независимые задачи до её приёмки не запускаются. Явный запрос
пользователя разрешает параллельный режим; независимость задач и доступные
слоты сами по себе его не включают. При невозможности безопасного
параллельного запуска работа продолжается последовательно с сохранением
независимости ревью.

Инструкции оркестратора разделены на последовательный и параллельный
режимы и загружаются только для выбранного режима. Общие контракты
и скрипты используются совместно, когда это не смешивает порядок работы.
При конфликте между сокращением повторов и изоляцией инструкций
приоритет имеет изоляция; допустимы необходимые локальные повторы.

Изоляция параллельных задач строится на Git Worktrees: отдельное рабочее
дерево в detached HEAD на задачу, без ветки задачи и коммитов исполнителя.
Оркестратор последовательно переносит незакоммиченные изменения,
проверяет интеграцию, создаёт коммит в рабочей ветке и удаляет worktree.
Общие ресурсы тестов также требуют разделения. Исполнитель запускает
проверки для своей работы; перед приёмкой независимый проверяющий сам
запускает обязательные тесты и линтеры. Рецензент оценивает достаточность
тестов по AC. После переноса проверяется интегрированный результат,
а перед завершением плана проводится итоговая независимая проверка.
Отчёт автора или непройденная обязательная проверка не разрешают приёмку.

На задачу допускается суммарно не более трёх раундов код-ревью, включая
первый. Если после третьего раунда остаются блокирующие замечания
или для приёмки нужен ещё один раунд,
исполнение всего плана останавливается до явного решения пользователя.
Счётчик сохраняется при смене агента и продолжении сессии. Пользователь
получает историю попыток и может разрешить ограниченное число дополнительных
раундов, направить контракт на пересмотр в `sdd-spec` либо завершить работу
с частичным результатом. Непройденные проверки не превращаются в приёмку.

HTML открывается с диска и по таймеру обновляет элементы из соседнего
`dashboard-state.js`. Этот файл генерирует скрипт из состояния исполнения.
Локальный сервер нужен только как запасной вариант просмотра в среде,
которая блокирует загрузку соседнего файла.

# design.md

### Детерминированные операции через скрипты


Скрипты пакета содержат единые правила исполнения. Если операция описывается
схемой, таблицей переходов, сравнением файлов или последовательностью
команд с проверяемыми условиями, она реализуется в скрипте. Агент вызывает
готовую операцию, получает структурированный результат и выбирает следующий
содержательный шаг. Отсутствие готового скрипта означает пробел реализации
скилла; инструкция «сделай то же вручную» этот пробел не закрывает.

| Операция | Что делает скрипт | Что остаётся агенту |
|---|---|---|
| Входы и граф | Вызывает штатные check/snapshot sdd-spec, сверяет манифест, разбирает зависимости, вычисляет доступные задачи и ограничения режима | Разрешает смысловую неоднозначность входов |
| Состояние | Проверяет событие, переход, зависимости, бюджет, основания приёмки; записывает состояние и историю | Подаёт событие с причиной и ссылками на материалы |
| Роли | Готовит входной пакет, регистрирует запуск и результат, проверяет разделение автора и проверяющего | Запускает роль средствами адаптера среды и выполняет содержательную работу |
| Проверки | Запускает заданную команду без её подмены, сохраняет stdout/stderr, код выхода, длительность и снимки входов | Проверяющий инициирует независимый запуск и оценивает достаточность проверок вместе с рецензентом |
| Git и worktrees | Создаёт и учитывает деревья, собирает полный пакет изменений, применяет его, сверяет индекс, создаёт коммит и проверяет условия удаления | Определяет принадлежность неоднозначной правки, разрешает смысловой конфликт |
| Продолжение | Сверяет файлы, процессы, версии и Git, находит выполненные операции и устаревшие доказательства | Решает обнаруженные неоднозначности и содержательные блокировки |
| Представления | Генерирует summary, dashboard-state.js и HTML, вычисляет счётчики и следующий доступный шаг | Объясняет пользователю результат и ограничения |

Прямая поддержка запуска агентов зависит от среды. Если этот запуск доступен
только как инструмент оркестратора, скрипт готовит и проверяет его данные,
а адаптер вызывает инструмент. Скрипт не имитирует недоступного агента.
Готовые механизмы Git, тестовые инструменты и валидатор sdd-spec вызываются
из скриптов; их логика не переписывается внутри пакета.

Команда состояния получает `event_id`, `run_id`, TASK-ID при наличии,
`expected_revision`, тип события, идентификатор роли и ссылки на доказательства.
Типизированные события выражают действие: начало задачи, передача кандидата,
результат проверки, результат ревью, запрос исправления, перенос, фиксация
коммита, блокировка, продолжение или завершение. Универсального назначения
произвольного статуса и режима обхода проверок нет. Обновление доказательств,
счётчиков, режима и причин блокировки также проходит этот интерфейс,
даже если статус задачи не меняется.

Скрипт проверяет схему и известные ID, текущую версию, допустимость события,
зависимости и ограничения режима, бюджет исправлений, актуальность снимка,
результаты обязательных команд, независимость зарегистрированных ролей,
отсутствие блокирующих замечаний и фактический коммит, когда он нужен.
Скрипт проверяет наличие и структуру заключения; за истинность
содержательного вывода отвечает независимый агент.
Программа не превращает произвольное поле `passed` от исполнителя
в доказательство успешного запуска команды.

Основные переходы задачи заданы таблицей. События могут дополнять материалы
в текущем состоянии, но также проходят проверку и запись версии.

| Переход | Условие |
|---|---|
| `pending` в `running` | Приняты предшественники, действуют входы, доступны роль и ресурсы, соблюдён режим; в sequential все ранее начатые задачи приняты, заблокированной текущей задачи нет |
| `running` или `repairing` в `verifying` | Зафиксирован кандидат, передан состав изменений, исполнитель прекратил запись |
| `verifying` в `reviewing` | Независимый запуск обязательных проверок успешен на текущем кандидате |
| `reviewing` в `verifying` | Рецензент запросил дополнительные проверки того же кандидата |
| `reviewing` в `integrating` | В параллельном режиме проверки и ревью разрешают перенос |
| `reviewing` в `committing` | В последовательном режиме кандидат в рабочей ветке прошёл проверки и ревью |
| `integrating` в `committing` | Перенос завершён; актуальны независимые проверки интеграции и ревью затронутых правок |
| `committing` в `accepted` | Подтверждён коммит нужного состава в рабочей ветке и сохранены все основания приёмки |
| `verifying`, `reviewing`, `integrating` или `committing` в `repairing` | Есть замечание или изменившийся кандидат и не исчерпан бюджет; затронутые доказательства помечены устаревшими |
| Любое незавершённое состояние в `blocked` | Сохранены причина, материалы и условие продолжения; в sequential блокировка задачи также переводит весь запуск в blocked |
| `blocked` в разрешённое состояние продолжения | Скрипт сверил фактическую фазу работы, устранение блокировки и условия целевого состояния |
| `accepted` в `repairing` или `blocked` | Новое доказательство выявило дефект или потерю актуальности; коммиты сохранены, затронутые зависимости пересчитаны |

Для перехода из `active` в `completed` требуются приёмка всех задач и итоговая проверка.
Если продолжение невозможно, запуск становится `blocked`; возврат к `active`
требует устранённой причины. В последовательном режиме заблокированная
текущая задача всегда блокирует запуск. Возврат к `active` разрешает
продолжить эту задачу; новую можно начать только после её приёмки.
Новое подтверждённое нарушение после
`completed` открывает исправление или блокировку по тому же правилу,
сохраняя прежнюю историю. Автоматический аудит может снять применимость
доказательства и заблокировать работу, но не выдать новое согласование
или успешную приёмку. У зависимых задач с изменившимся основанием
прежние доказательства также проверяются на применимость.

Отклонённое событие возвращает ненулевой код выхода, код причины и список
невыполненных условий; состояние и `revision` остаются прежними. Скрипт
может сохранить отдельный диагностический лог, не изображая переход
успешным. Повтор уже выполненного `event_id` с теми же данными возвращает
сохранённый результат без повторного эффекта; тот же ID с другими данными
отклоняется. При конфликте версии агент перечитывает состояние, а не
перезаписывает его. Прямая правка или повреждение записи при продолжении
вызывает проверку согласованности с историей, снимками и Git; неподтверждённое
состояние не принимается за новое основание. Это контроль процесса,
не криптографическая защита от агента с произвольным доступом к файлам.

Для операций с внешним эффектом, включая перенос и коммит, скрипт сначала
сохраняет намерение и проверяемое исходное состояние, затем выполняет
операцию и фиксирует наблюдаемый результат. После сбоя он сверяет Git
и файлы, чтобы продолжить без повторного эффекта. Запись JSON и Git-коммит
не объявляются одной атомарной транзакцией. Сбой генерации панели после
успешной записи состояния исправляется повторной генерацией, без отмены
выполненной задачи и без повторного коммита.

Имена команд и разбиение скриптов определяются при реализации. Правила
переходов и изменения состояния имеют одну реализацию, общую для всех
адаптеров среды. Проверки скриптов включают запрещённые переходы, гонку
двух запросов, повтор события, устаревшее доказательство и сбой между
внешней операцией и записью её результата.

# design.md

### Последовательное выполнение как исходный режим


При новом исполнении режим по умолчанию `sequential`. Оркестратор ведёт
одну задачу до приёмки с проверенным коммитом, включая проверки, ревью
и исправления. Только после приёмки он выбирает следующую доступную задачу.
Автономное продолжение не требует подтверждения каждой задачи.
Блокировка текущей задачи останавливает весь последовательный запуск,
даже если в плане есть независимые задачи. Скрипт сохраняет её правки,
материалы и условие продолжения; после устранения причины возобновляется
та же задача. Остановка не разрешает пропустить её или начать другую
в отдельной рабочей копии. Нужды освобождать общую рабочую копию ради
следующей задачи нет: до приёмки текущей она не запускается.
Необходимость код-ревью сверх лимита раундов в любом режиме останавливает
весь запуск до решения пользователя, включая независимые доступные задачи.

Режим `parallel` включается только по явному запросу пользователя для этого
исполнения. Перед запуском оркестратор сохраняет запрос и его область.
Наличие независимых задач, изоляции или свободных слотов не меняет режим
автоматически. Даже при явном запросе параллельный запуск допустим только
в отдельных Git Worktrees с контролируемой интеграцией, по зависимостям
и ограничениям плана. Сначала проверяется результат задачи в её копии,
затем результат интеграции. Если изоляция недоступна, оркестратор сообщает
причину и продолжает последовательно.

При продолжении того же исполнения проверяются сохранённый запрос и его
область, включая позднюю отмену или замену. Действующий выбор не запрашивается
повторно. Без подтверждённого разрешения режим `parallel` не восстанавливается.
При возврате к `sequential` сохраняют работу всех ранее начатых задач.
Их доводят до приёмки до запуска новых; блокировка любой из них сохраняет
остановку запуска. Переходы состояния проверяют выбранный режим
и не разрешают второй активный цикл задачи в `sequential`.
После смены сессии скрипт восстанавливает текущую незавершённую задачу;
наличие независимой задачи не меняет условия продолжения.

Оркестратор сохраняет исходный HEAD, исходные локальные изменения
и принадлежность новых файлов. Для ревью материал включает новые,
индексированные и неиндексированные изменения конкретной задачи.
Общий `git add -A` не используется как способ выделить её результат.
После проверок и ревью коммит задачи обязателен; создание коммитов входит
в поручение исполнить план. Детали фиксации результата описаны ниже.

# design.md

### Раздельные инструкции оркестратора


Оркестратор получает отдельный сценарий для выбранного режима.
Предлагаемое разбиение пакета: `flows/execute-sequential.md` и
`flows/execute-parallel.md`. Короткий входной раздел SKILL.md выбирает
один сценарий по проверенному состоянию и поручению пользователя.
Входной раздел содержит правила выбора и ссылки, без обоих алгоритмов.
При обычном последовательном запуске параллельный сценарий не читается,
даже если независимые задачи и свободные агенты доступны.

Последовательный сценарий описывает полный цикл одной задачи до приёмки
и переход к следующей только после приёмки; блокировка останавливает
весь последовательный запуск до продолжения текущей задачи.
Параллельный сценарий описывает
допуск одновременных задач, worktrees, координацию ролей, последовательную
интеграцию и остановку активных задач. Это два самостоятельных документа;
общий большой сценарий с условием режима на каждом шаге не заменяет разделение.
Ссылки выбранного сценария не должны косвенно загружать алгоритм другого.

Общими остаются схема состояния, программные правила переходов, контракты
ролей и доказательств, критерии приёмки, лимит ревью и скрипты операций.
Такие материалы подключаются по необходимости и не содержат инструкций
запуска другого режима. Общий шаг выносится в отдельный ресурс, только
если его смысл и условия одинаковы в обоих сценариях. При разном порядке
действий или риске смешения допускается повтор короткой инструкции внутри
каждого сценария. Приоритет изоляции выше сокращения повторов; копировать
реализацию скриптов и заводить расходящиеся источники правил не требуется.

При продолжении входной раздел снова выбирает сценарий по сохранённому
режиму и действующему разрешению. Если режим меняется после загрузки
его инструкций, прежний оркестратор сохраняет работу и передаёт управление
свежему контексту с состоянием, общими контрактами и новым сценарием.
История инструкций прежнего режима не переносится. Активная работа
завершается или сохраняется по уже определённым правилам смены режима;
блокировка владения запуском допускает только одного оркестратора.
Недоступность свежего контекста фиксируется как ограничение продолжения,
а не как обещание удалить уже прочитанный текст. Если недоступность
параллельной изоляции выявлена до загрузки сценария, входной раздел
сразу выбирает последовательный сценарий и сообщает причину.

При проверке пакета нужно проследить фактически загруженные инструкции
для каждого режима и смены режима. Проверяется отсутствие алгоритма
другого режима в контексте и сохранение единых контрактов и скриптов.
Поведение дублирующихся коротких инструкций должно оставаться согласованным.

# specs/sdd-execution/spec.md

## Автономное исполнение графа


После запуска скилл выполняет весь согласованный план без подтверждения
каждой задачи. По умолчанию используется последовательный режим: одновременно
ведётся одна задача, включая реализацию, проверки, ревью, исправления и коммит.
Следующая задача начинается только после приёмки текущей с проверенным
коммитом. Блокировка текущей задачи останавливает весь последовательный
запуск, в том числе независимые задачи. Её незавершённые правки сохраняются;
после устранения причины скилл продолжает ту же задачу до приёмки.
Остановка из-за лимита код-ревью блокирует выполнение всего плана
в любом режиме до решения пользователя.

Параллельный режим включается только по явному запросу пользователя для
текущего исполнения. Просьбы работать автономно или быстрее, независимые
задачи и доступные ресурсы таким запросом не считаются. Разрешение допускает
параллелизм при соблюдении зависимостей и изоляции; если это невозможно,
скилл сообщает причину и продолжает последовательно. Выбранный режим
и основание сохраняются. При продолжении того же исполнения прежний явный
запрос действует, пока не отменён; без подтверждённого запроса применяется
последовательный режим. Новое исполнение начинается с последовательного
режима, если пользователь явно не указал иное. При возврате к последовательному
режиму новые задачи не запускаются до приёмки всех ранее начатых задач.
Блокировка любой из них сохраняет остановку последовательного запуска;
продолжение завершает ранее начатую работу до выбора новой задачи.

Скилл использует TASK-ID, связи `depends_on`, `cannot_parallel_with`
и критерии `covers`. Задача доступна только после приёмки всех предшественников.
Каждая задача получает отдельного исполнителя с чистым контекстом, нужными
разделами документов, границами записи и условиями проверки. Оркестратор
ведёт исполнение и передаёт исправления исполнителям.

Последовательный и параллельный режимы имеют отдельные инструкции
оркестратора. Входной раздел загружает только сценарий выбранного режима.
Общие материалы и скрипты переиспользуются, если не вносят порядок работы
другого режима в контекст. Изоляция инструкций важнее сокращения повторов;
необходимые короткие повторы допустимы, расходящиеся реализации общих
правил не создаются. При смене уже загруженного режима управление
передаётся свежему контексту с выбранным сценарием и сохранённым состоянием.

### Переход между задачами

[AC-continue-plan/conditions] Предыдущая задача принята, осталась доступная задача согласованного плана
[AC-continue-plan/expected] Следующая задача запускается без нового согласия пользователя и с необходимыми входами
### Неуспешный предшественник

[AC-block-dependents/conditions] Предшественник заблокирован, завершился ошибкой или ещё проходит ревью
[AC-block-dependents/expected] Зависимая задача не запускается; в последовательном режиме никакая следующая задача не начинается до приёмки текущей, а в параллельном независимые доступные задачи могут продолжаться, если весь запуск не остановлен
### Разделение изменений

[AC-isolated-work/conditions] Пользователь явно запросил параллельный режим, но изоляция изменений или проверок недоступна
[AC-isolated-work/expected] Скилл сообщает причину и выполняет задачи последовательно с соблюдением ограничений плана
### Последовательный режим по умолчанию

[AC-sequential-default/conditions] Несколько независимых задач готовы к запуску и изоляция доступна, но пользователь не запрашивал параллельный режим
[AC-sequential-default/expected] Одновременно ведётся одна задача, включая проверки, ревью, исправления и коммит; следующая задача начинается только после её приёмки
### Блокировка текущей последовательной задачи

[AC-sequential-blocked-stop/conditions] В последовательном режиме текущая задача оставила незавершённые правки и заблокирована; в плане есть независимая задача
[AC-sequential-blocked-stop/expected] Задача и весь запуск становятся blocked, правки и доказательства сохраняются; скрипт отклоняет запуск следующей задачи, в том числе после перезапуска сессии; после устранения причины продолжается текущая задача, следующая начинается только после её приёмки с проверенным коммитом
### Явный выбор параллельного режима

[AC-explicit-parallel/conditions] Пользователь явно запросил параллельное выполнение, есть независимые задачи и доступна изоляция
[AC-explicit-parallel/expected] Скилл сохраняет запрос как основание режима и может запускать задачи одновременно в пределах зависимостей и ограничений изоляции
### Режим при продолжении

[AC-mode-resume/conditions] Скилл продолжает прерванное исполнение с сохранённым режимом
[AC-mode-resume/expected] Параллельный режим сохраняется только при подтверждённом действующем явном запросе пользователя; иначе используется последовательный режим, новые задачи ждут приёмки всех ранее начатых, блокировка любой из них сохраняет остановку запуска
### Изоляция инструкций режима

[AC-mode-instruction-isolation/conditions] Оркестратор начинает исполнение в последовательном либо явно разрешённом параллельном режиме
[AC-mode-instruction-isolation/expected] Загружен отдельный сценарий только выбранного режима; входной раздел и общие ссылки не загружают алгоритм другого режима, единый сценарий с постоянными развилками не используется
### Общие материалы без смешения сценариев

[AC-mode-shared-contracts/conditions] Оба сценария используют общие проверки, контракты ролей или инструкции с разным порядком действий
[AC-mode-shared-contracts/expected] Общие контракты и скрипты имеют единую реализацию; ресурс с общими инструкциями подключается только при одинаковых условиях и смысле, при угрозе смешения режимов необходимые инструкции повторяются локально
### Смена инструкций при продолжении

[AC-mode-context-handoff/conditions] Пользователь меняет режим после загрузки инструкций либо исполнение продолжается в новой сессии
[AC-mode-context-handoff/expected] Выбран сценарий действующего режима; при смене уже загруженного режима создан свежий контекст без инструкций прежнего, состояние и работа сохранены, одновременно действует один оркестратор; недоступность нужного контекста обозначена как ограничение
# premortem.md

## Проверки относятся к чужой версии кода

**Возможный провал:** задача получает успешное ревью, но в принятую версию
попадают непроверенные или чужие изменения.

**Предпосылка успеха:** у каждой задачи определены принадлежащие ей изменения
и версия, к которой относятся проверки.

**Основания:** [NeoPilot review](https://github.com/Atlantic83/neopilot/blob/63c509177f425b3a5e5edc382d4fff36a4567bae/skills/neopilot/phases/6-review.md)
использует общий индекс Git, тогда как задачи могут работать параллельно.
Риск следует из устройства процесса; фактический сбой не воспроизводился.

**Дальнейшее действие:** автономная модель выбрана в
[Q-execution-model](state.md#модель-выполнения). Позднее пользователь ограничил
параллелизм явным запросом, см. [режим выполнения](state.md#режим-выполнения).
В черновике предложены
[DEC-controlled-concurrency](design.md#последовательное-выполнение-как-исходный-режим),
AC-isolated-work и AC-review-freshness в [spec](specs/sdd-execution/spec.md).
AC-sequential-default, AC-explicit-parallel и AC-mode-resume проверяют
выбор режима и основание параллельного запуска. Включить в испытания
отсутствующий и отменённый запрос, параллельные правки и чужие незакоммиченные файлы.

В последовательном режиме похожий риск возникает, если после блокировки
задачи с частичными правками начать другую в той же рабочей копии.
Пользователь выбрал остановку всего последовательного запуска до завершения
текущей задачи. Это правило внесено в REQ-autonomous-execution,
DEC-controlled-concurrency и AC-sequential-blocked-stop. Проверить,
что независимая задача не запускается до приёмки текущей, её правки
сохраняются, а после смены сессии продолжается та же задача.

# research.md

Пользователь выбрал последовательный режим по умолчанию и параллельный
режим только по явному запросу. Доступность независимых задач и изоляции
не разрешает автоматически переключать режим. По уточнению пользователя
последовательный режим разрешает следующую задачу только после приёмки
текущей. Её блокировка останавливает весь запуск; после устранения причины
продолжается та же задача с сохранёнными правками. Для разрешённого параллельного
выполнения предлагаются отдельные рабочие копии с определённой процедурой
интеграции и повторной проверки. Для каждого ревью сохранять основание diff и версию
проверенных файлов. Новая правка затронутого кода требует соответствующей
повторной проверки. По уточнению пользователя коммиты по задачам обязательны
и являются итогом исполнения. После проверок и ревью создаётся отдельный
коммит задачи; позднее исправление получает дополнительный коммит с тем же
TASK-ID. Сам коммит без проверок не доказывает приёмку. Работа заканчивается
локальным набором коммитов, без последующих этапов доставки.
