# Code Quality: принцип работы и применимость к SDD

Наиболее полезное заимствование — автоматический сбор конкретных свидетельств: что изменилось в тестах, какие новые строки исполнялись, какие функции стали рискованными и какие проверки фактически не состоялись. В `sdd-apply` уже есть независимые проверяющие, контроль целостности тестов и привязка доказательств к кандидату. Поэтому целесообразно усилить их инструментами, сохранив существующий порядок принятия решений.

Исследован исходный код версии **1.3.3**, коммит `0e160eadf7d1bfffb75a14bed88876d6f7bffbc7` от 4 октября 2026 года. Важное расхождение: GitHub About продолжает описывать блокирующий quality gate, но актуальная реализация работает как **советник**. Находки сами по себе не запрещают commit, push или окончание хода агента. Это подтверждают [версия пакета][package], [обработчики hooks][hooks-advice] и [shell-обертка pre-commit][precommit]. Обычный CLI сохраняет ненулевой код завершения для автоматизации.

Исследование статическое: выполнено чтение публичного репозитория и локальных контрактов; установка плагина, запуск его тестов, анализаторов и hooks не проводились. Временная копия расположена вне репозитория и пакетов скиллов, в системном TEMP. Применены требования [sdd-skill-conductor][conductor] и [SOP][sop] к разделению исполняемых механизмов и инструкций. Это отчет об устройстве инструмента, без сертификации сторонних скиллов или изменения наших пакетов. Ссылки на upstream закреплены за исследованным коммитом; локальные ссылки относятся к `local_commit` в заголовке.

## 1. Как устроен инструмент

Плагин состоит из трех слоев: точки запуска в Git и агентских средах, общий TypeScript CLI на Bun и набор анализаторов. Дополнительно поставляются скиллы `code-quality` для работы с отчетами и `acceptance` для организации приемки. Реализацию полезно рассматривать отдельно от этих инструкций: CLI умеет измерять и сообщать, а приемочный скилл поручает агентам интерпретировать результаты и выполнять дополнительные проверки. [CLI][cli], [acceptance][acceptance].

Основная последовательность:

1. Загрузить `.quality.toml`, определить языки, исходные каталоги, базовую ревизию и область изменения.
2. Разобрать Git diff в добавленные и удаленные строки, участки изменения и затронутые функции.
3. Получить допустимые данные покрытия либо отметить их отсутствие; по специальной команде самостоятельно запустить тесты.
4. Запустить применимые анализаторы, сопоставить часть находок с накопленным долгом.
5. Сначала вывести опасные сигналы `RED FLAG`, затем находки, ограничения и ссылку на Markdown-отчет. При включенном Jev добавить отдельные вероятностные замечания. [Конвейер][pipeline], [формирование отчета][report].

| Точка запуска | Фактическое действие |
|---|---|
| `check` | Быстрый анализ изменения; свежий LCOV используется при наличии. Сам по себе тесты не запускает |
| `check --since <base> --tests` | Выбирает связанные с изменением тесты, запускает их с покрытием и анализирует изменение в том же процессе |
| CLI без подкоманды | Анализ всего дерева, обычно с полным запуском тестов; `--update-baseline` сохраняет снимок долга |
| `pre-commit` | Анализ staged diff, затем запуск ранее установленных hooks |
| `pre-push` | Проверки диапазонов push, поиск связанных тестов, их запуск при подходящем checkout, проверки безопасности |
| Stop / UserPromptSubmit | Проверка после работы агента; полный отчет передается следующему сообщению один раз либо непосредственно через адаптер |
| PreToolUse / `guard-bash` | Предупреждение о командах обхода hooks |

Команда `check` возвращает `0`, если нет учитываемых находок и ошибок проверок, иначе `1`; необработанная ошибка CLI дает `2`. Git-обработчики выводят совет и завершаются с `0`; shell-обертка также пропускает обычную ошибку CLI. Прерывание процесса и собственный hook проекта могут остановить Git. Следовательно, гарантия относится к политике этого плагина, а не к успешности любого commit. Stop дедуплицирует детерминированный результат; изменение вероятностного замечания не считается новым вердиктом. [CLI][cli], [hooks][hooks-advice], [Stop][stop], [pre-commit][precommit].

## 2. Область проверки, конфигурация и долг

Приоритет настроек: CLI, затем `.quality.toml`, затем defaults. В worktree без собственного конфига используется конфиг основного checkout; baseline по умолчанию также общий. Неизвестные ключи конфигурации отвергаются. Defaults включают CC 10, CRAP 30 и 80% покрытия добавленных исполняемых строк. Результаты обычно пишутся в `.scratch/quality`. Эти числа — настройки автора инструмента, а не общепринятое доказательство качества и не действующие правила нашего SDD. [Конфигурация][config].

Области существенно различаются. Обычный `check` сравнивает рабочее дерево с merge-base базовой ветки и включает untracked-файлы. `--staged` берет индекс, `--since X` — diff **`X..HEAD`**, `--all` — отслеживаемые файлы целиком. При чистом удалении строк затронутыми считаются соседние строки, чтобы не потерять функцию. При этом анализаторы читают файлы рабочего дерева: наличие `--since` само по себе не фиксирует проверяемые байты. Частично staged-файл дает отдельное предупреждение. [Diff][diff], [pre-commit][hooks-advice].

Baseline хранит метрики функций, известные циклы, нарушения слоев, неиспользуемый код и находки языковых инструментов. Для последних действует правило «не добавлять новый долг». Если снимка нет, часть долга вычисляется на merge-base во временно распакованном дереве. `--all` игнорирует baseline и показывает весь долг. Однако **измененная старая функция проверяется по абсолютному порогу CC/CRAP**, даже если раньше была сложнее: baseline не освобождает ее от планки. Средний CRAP репозитория и ухудшение неизмененных функций служат диагностикой. [Логика baseline и порогов][baseline].

Здесь два разных значения слова baseline. В Code Quality это сохраненный долг анализаторов. В `sdd-apply` исходная baseline-проверка — реальный запуск обязательных проверок до изменений. Один механизм не заменяет другой. [Выполнение SDD][execution].

## 3. Что именно измеряется

**Целостность тестов.** Детектор анализирует diff тестовых файлов: удаление файла или блока теста, skip/only/todo/xfail, уменьшение числа assertions внутри hunk, замены строгой проверки на слабую для того же выражения. Например, `expect(result).toEqual(expected)` → `expect(result).toBeTruthy()` дает находку. Также обнаруживаются некоторые подавляющие комментарии анализаторов и изменение baseline/защитной конфигурации вместе с исходниками. Моки и локальные заглушки дают дополнительные замечания. Это сочетание шаблонов и эвристик, не семантическое доказательство намеренного обхода. [Tamper][tamper], [assertions][assertions], [защита baseline][tamper-baseline].

Предусмотрены объясненные исключения. Например, `qg:test-removed <reason>` принимает удаление тестов и hunk, в котором только уменьшилось число assertions, но не замену сильного assertion слабым; объяснение остается в отчете. Это полезный образец прозрачного учета исключения. Для SDD такая строка не должна автоматически становиться пользовательским разрешением или доказательством допустимости изменения. [Исключения][tamper-bypass].

**Сложность и покрытие.** Для TS/JS используются ESLint и AST, для Python — Radon; Lizard выступает общим анализатором и fallback. Покрытие берется из LCOV; собственные строки функции считаются без тел вложенных функций. Формула:

`CRAP = CC² × (1 − coverage)³ + CC`.

При CC 10 и покрытии 50% получается 22,5; при нулевом покрытии — 110. Проверка CC остается отдельной: хорошее покрытие не отменяет превышение сложности. Без пригодного LCOV основной CRAP-порог не применяется; если LCOV используется, а функция в нем отсутствует, риск оценивается как при нулевом покрытии. Это делает явное состояние измерения важнее одного итогового числа. [Извлечение функций][complexity], [расчет CRAP][crap], [порог][baseline].

**Покрытие изменения.** Знаменатель — только добавленные строки, которые LCOV признал исполняемыми. Обычный `check` сообщает о недостаточном покрытии замечанием, тогда как `check --tests` и полный режим применяют более строгую политику находок. Отсутствие свежего LCOV дает `not run`, а не искусственный результат 0% или доказанный успех. Freshness полного покрытия проверяется по fingerprint diff и untracked-файлов под `project.src`; конфигурация тестов и зависимости вне этих каталогов не входят в такой fingerprint. [Diff coverage][diffcov], [метаданные покрытия][coverage].

**Другие анализаторы.** Конвейер объединяет циклы и границы слоев, мертвый код, дублирование через jscpd, структурные правила ast-grep/Semgrep, форму функций, секреты, зависимости, документацию и словарь проекта. TS-ветка использует dependency-cruiser и Knip; языковые адаптеры нормализуют результаты в общую находку `rule/file/line/msg`. Gitleaks проверяет историю `project.base..HEAD`, быстрые regex-проверки отдельно просматривают добавленные строки. Часть внешних пакетов закреплена по версиям, часть вызывается как установленный бинарник. [Конвейер][pipeline], [инструменты][tools], [security][security].

## 4. Тесты изменения, мутации и Jev

Выбор тестов имеет два режима. Pre-push ищет тесты по именам и прямым импортам, по умолчанию ограничивая список 40 файлами. Приемочный `check --tests` использует неограниченное транзитивное замыкание импортов и реэкспортов, дополнительные соглашения об именах, aliases и workspace packages. Но граф импортов строится **для TS/JS**; для остальных адаптеров основной механизм — имена файлов. Это не универсальный анализ влияния изменений для всех 12 языков. Вычисляемые пути загрузки и внешние потребители также не получают гарантированного покрытия. [Выбор тестов][touched].

Приемочный запуск пишет покрытие и лог в отдельный `touched/run-*`, не смешивая его с полным LCOV. Ошибка тестов, timeout и некорректный LCOV различаются. После успешной тестовой полосы временный каталог удаляется, даже если другие анализаторы нашли проблемы. Для SDD потребуется заранее обеспечить сохранение исходных логов и покрытия: существующего Markdown-отчета недостаточно для воспроизводимого доказательства. Pre-push отдельно проверяет соответствие отправляемого коммита HEAD и отсутствие незакоммиченных изменений в выбранных путях. [Приемочный запуск][accept-tests], [покрытие][coverage], [очистка][runcheck], [pre-push][prepush].

`mutant` проверяет конкретную гипотезу: заменяет одно точное вхождение текста, запускает выбранные тесты и восстанавливает файл. Сначала эти же тесты должны пройти на исходных байтах и действительно выполниться. После мутации результат `KILLED` требует распознанного падающего теста: произвольный ненулевой exit code не считается успехом. Есть lock, оригинальные байты, hashes, обработка SIGINT/SIGTERM и восстановление после погибшего процесса. При чужом изменении файла инструмент сохраняет состояние для разбирательства, вместо безусловной перезаписи. Полноценный разбор test summary предусмотрен для Node, Bun, Vitest и pytest. Это точечный эксперимент, а не полный mutation score всего проекта. [Mutant][mutant].

Jev — необязательный внешний вероятностный классификатор. Ему отправляются ограниченные фрагменты изменения и вопросы с критериями ответа: ослаблен ли тест, скрывает ли mock поведение, проверяется ли ошибка, не тавтологична ли property-проверка. Есть вопросы об исходниках, спецификации, UX и агентском коде. Результаты с вероятностями сравниваются с порогами и журналируются. Провайдеры — TypeSafe, OpenRouter либо совместимый endpoint; стандартный предел — 12 hunk-запросов плюс запрос по спецификации, timeout 5 секунд. Ошибка дает `not available`; ответы не меняют детерминированный вердикт. [Jev][jev], [вызовы и журнал][jev-results].

Jev не стоит включать первым: автор приемочного скилла сам сообщает о ложных замечаниях в двух своих проектах и исключает его из штатной приемки. Это свидетельство автора, не измеренный нами показатель качества. Кроме того, механизм отправляет код внешнему сервису. Поля `review.llm` и `escalate.paths` выглядят как будущая интеграция: общий LLM reviewer в текущем коде прямо обозначен как неподключенный. [Ограничения приемки][acceptance-limits], [неподключенные возможности][runcheck].

## 5. Что уже есть в sdd-apply

| Механизм upstream | Текущее состояние SDD | Практический вывод |
|---|---|---|
| Замороженный кандидат, независимые проверяющие | Уже предусмотрены в выполнении, verifier и reviewer | Сохранить существующий процесс |
| Поиск ослабления тестов | Reviewer уже требует отдельный `test_integrity`, изучает удаленные файлы, skip/xfail/only, assertions, fixtures и команды | Добавить автоматически найденные участки как вход reviewer |
| Разделение исправлений и будущего долга | Review policy блокирует доказанное нарушение принятого требования; рекомендации идут в technical debt | Не переводить пороги upstream в обязательные правила автоматически |
| Проверки перед приемкой | `check_run` исполняет полный реестр обязательных проверок; ненулевой exit становится failed | Для advisory-отчета нужен отдельный сборщик или новая согласованная семантика |
| Финальная приемка | Полный обязательный набор на конечном HEAD | Touched tests пригодны для ранней обратной связи, не заменяют final |

Источники: [reviewer][reviewer], [verifier][verifier], [review policy][review-policy], [реализация check_run][verification], [finalize][finalize].

Upstream `acceptance` полезен как источник отдельных приемов: сценарии blind QA выводятся из спецификации до чтения diff; проверяются потребители за его пределами; таблица отказов связывает требования с проверками; мутации показывают чувствительность тестов. Копировать весь оркестратор нецелесообразно. Он добавляет собственные роли, требования к разным семействам моделей, терминальным панелям и двухраундовому процессу. У нас уже действуют пять циклов repair и три раунда review на TASK-ID, а финальная проверка имеет собственные обязательные правила. [Upstream acceptance][acceptance], [локальный repair][repair].

## 6. Предложения по внедрению

Ниже предложения, а не реализованные возможности.

**P0. Сборщик свидетельств о качестве для существующего reviewer.** Начать с детерминированных сигналов изменения тестов и защитной конфигурации. Выход: правило, файл и строка, before/after, основание обнаружения, статус инструмента, ссылка на сырой лог. Reviewer связывает сигнал с AC, архитектурой или правилом проекта и оформляет доказательство нарушения по текущей policy. Ослабление теста само по себе остается поводом разобраться: удаленная функциональность может законно требовать удаления теста.

Сборщик стоит вынести в самостоятельный исполняемый компонент; `sdd-apply` получает короткий контракт вызова. Не следует напрямую добавлять upstream `check` в обязательный registry: exit 1 из-за рекомендуемого порога станет блокировкой. `|| true` тоже непригоден, поскольку стирает различие между находкой и аварией. Нужны отдельные состояния `completed`, `unavailable`, `error` и список находок. Для обязательной принятой проверки отсутствие инструмента должно блокировать по правилам SDD; для advisory-сборщика оно явно ограничивает вывод. [Текущий check_run][verification], [policy][review-policy].

Есть два способа реализации. Адаптер закрепленной версии upstream CLI быстрее проверяет полезность целого инструмента, но приносит Bun, внешние анализаторы, их кэши и необходимость сохранять удаляемые evidence. Перенос узкого детектора test-integrity уменьшает зависимости и лучше ограничивает MVP, но делает нас владельцами его эвристик и регрессионных тестов. Рекомендация: сначала эксперимент с закрепленным CLI на временных fixtures, затем выбрать по результатам; не переносить весь пакет заранее. При переносе Python-скриптов соблюдать наш запуск через `uv` и требования к runtime-хранилищу. Upstream опубликован под MIT: при копировании кода сохранить уведомление об авторских правах и текст лицензии. [Runtime conductor][conductor], [инструменты upstream][tools], [LICENSE][license].

**P0. Полный паспорт результата.** Привязать новые свидетельства к base SHA, кандидату/хешу дерева, версии инструмента, конфигу, командам, списку выбранных тестов и provenance покрытия; сохранить raw logs и hashes. У SDD уже есть привязки кандидата и evidence, поэтому расширять нужно содержание нового артефакта, а не создавать второй журнал исполнения. Запускать анализ по неподвижному снимку или чистому checkout проверяемой ревизии. Upstream fingerprint только под `src` недостаточен, чтобы подтверждать неизменность всего тестового окружения. [Verification API][verification], [upstream coverage][coverage].

**P1. Скилл `sdd-test-strength` либо модуль verifier.** Сценарий: «докажи, что тест ловит эту регрессию». Независимый проверяющий выбирает 1–3 реалистичные мутации по рискам/AC после изучения готовых тестов. Запускает baseline, мутацию и восстановление в изолированном одноразовом worktree, возвращает результаты `killed/survived/inconclusive` с логами. Полезны отмена проверки прав, пропуск сохранения, изменение границы, подавление ошибки. Если тест падает из-за синтаксической ошибки вместо нужного поведения, это не достаточное доказательство. Собственный цикл приемки такому скиллу не нужен. [Mutant][mutant], [acceptance][acceptance].

**P1. Расширение сборщика метриками изменения.** После test-integrity добавить diff coverage и CC/CRAP измененных функций как рекомендательный вход reviewer. Показать непокрытые строки и отсутствие данных отдельно; пороги настраивать для проекта. Превращать показатель в обязательную проверку только после принятия соответствующего правила. Это компактнее полного аудита репозитория и позволяет оценить пользу каждой метрики отдельно. [Метрики upstream][diffcov], [policy SDD][review-policy].

**P1. Скилл `sdd-quality-audit` для отдельного запроса о техническом долге.** Полный анализ сложности, покрытия, циклов и дублей с сортировкой по риску и частоте изменений; результат — обоснованный список кандидатов на улучшение. В `sdd-apply` передавать только сведения о текущем изменении. Пороговые значения согласовать для проекта после пилота; baseline долга обновлять отдельным прозрачным действием. Так приемка небольшой задачи не превращается в незаказанный рефакторинг. [Baseline][baseline], [приоритизация upstream][report], [локальная policy][review-policy].

У upstream hotspots ранжируются по числу коммитов за 12 месяцев, умноженному на сумму CRAP рискованных функций файла. Для нас новизна такого скилла — измерения, ранжирование и ссылки на доказательства; рекомендации по дизайну и сложности уже есть в [code-that-fits-in-your-head][design-heuristics]. Предлагаемые задачи должны ссылаться на существующий журнал долга. [Расчет hotspots][report].

**P2. Выборочные дополнения приемки.** Blind QA и проверку реального пользовательского пути подключать как задания существующим ролям по риску задачи. Использовать структуру «условие отказа → ожидаемое поведение → воспроизводимая проверка» в принятой спецификации. Если появится отдельный `sdd-acceptance-qa`, его границей должны быть сценарии и доказательства, без замены `sdd-apply`. Jev, автоматические hooks и полную поддержку 12 языков отложить до подтвержденной потребности. Ранний пилот проще контролировать через явный CLI. [Acceptance][acceptance], [существующий verifier][verifier].

## 7. Ограничения и план пилота

`CLEAN` означает отсутствие учитываемых находок, а не факт выполнения всех возможных проверок. Отсутствующие Gitleaks и языковые инструменты часто дают notice; недоступная OSV database также может дать `not run`. Иные ошибки инструмента могут стать `ERROR`. Нужна матрица реально выполненных проверок. Детекторы assertions эвристические; jscpd сравнивает измененные файлы и может не увидеть дубль с неизмененным. Наличие 12 адаптеров не обеспечивает одинаковую глубину анализа. Windows здесь не проверялась: hooks используют `#!/bin/sh`, внешние команды и окружение требуют отдельного пилота. [Security][security], [адаптеры][adapters], [дубли][dup], [shell hook][precommit].

Предлагаемый пилот — 12–20 небольших изменений в TS и Python, включая реальные прошлые дефекты и легитимные изменения тестов. Сравнить текущий SDD с SDD плюс сборщик на одинаковых снимках. Обязательные случаи: skip/xfail, ослабленный assertion, допустимое удаление функции и теста, изменение baseline вместе с кодом, устаревший LCOV, отсутствующий анализатор, частично staged-файл, непрямой импорт, незапущенные тесты и ошибка восстановления мутации.

Измерять отдельно полезные находки, ложные тревоги, пропуски, время до сигнала, общее время приемки, число повторных запусков и токены при доступной телеметрии. Проверять, что недоступная проверка не становится PASS, рекомендательная находка не превращается в автоматический blocker, а конечные evidence относятся к текущему кандидату. Для мутаций отдельно учитывать долю `inconclusive` и корректность восстановления. Критерии перехода к внедрению определить до запуска; экономия времени и повышение качества пока являются гипотезами.

Первая практическая поставка: **сборщик test-integrity + паспорт свидетельств**, затем эксперимент с точечными мутациями. Она дополняет существующие сильные стороны `sdd-apply`, имеет ограниченную область изменения и дает измеримый ответ, полезна ли дальнейшая интеграция.
