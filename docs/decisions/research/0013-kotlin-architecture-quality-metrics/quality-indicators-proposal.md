# Интегральные показатели архитектуры и качества кода

Предлагается автоматический профиль из трёх составляющих: **структурная разделимость D, локальная поддерживаемость L и оценка дублирования U**. Из них рассчитывается общий индекс **Q**. Основой локальной сложности служит **cognitive complexity**. Покрытие и производная CRAP описывают тестовую защиту отдельно и не входят в Q.

Для запуска не нужны карта предметных областей, объявленные архитектурные модули, экспертные оценки или подготовленные сценарии изменения. Входы — исходники, сведения сборки, извлечённые зависимости и, для дополнительных показателей, результаты тестов и история Git. Настройки задаёт единый профиль измерения, одинаковый для проектов соответствующего стека.

Показатели должны дополнять друг друга. Укрупнение файлов может улучшать файловый граф, но ухудшать оценку размера. Копирование реализации может уменьшать зависимости, но увеличивать дублирование. Представительность проверяется на совокупности показателей; ни один из них не объявляется исчерпывающим измерением архитектурного качества.

[Исследование](research.md) содержит каталог инструментов и альтернатив. [Процедура рефакторинга](refactoring-workflow.md) объясняет, как переходить от сигналов к рекомендациям. Настоящее предложение расширяет набор измерений этой процедуры: ограничения её текущего пилотного состава не означают, что DL или дублирование уже реализованы.

## Принятые решения

| Вопрос | Решение для первой версии |
| --- | --- |
| Основная сложность | Cognitive complexity по закреплённой реализации detekt 1.23.8; MCC не участвует в L или Q |
| Архитектурная составляющая | Формула Decoupling Level на файловом графе и автоматически построенной DRH; вариант построения иерархии входит в паспорт |
| Локальная поддерживаемость | Cognitive complexity и размер функций, классов и файлов; без суммирования коррелирующих предупреждений |
| Дублирование | Повторяющиеся последовательности токенов; объединение занятых ими позиций |
| Покрытие | Branch coverage как основной показатель ветвлений; instruction coverage как обязательное дополнение; line coverage для отчёта |
| CRAP | Дополнительная диагностика по методам; для доступных счётчиков JaCoCo определяется собственный вариант CRAP_exec |
| Общий индекс | Геометрическое среднее D, L и U; тестовое покрытие не компенсирует ухудшение структуры |
| Нормирование | Постоянные параметры профиля, а не новые процентили каждого снимка |
| Неизвестные данные | Отдельный статус и охват; отсутствие измерения не означает ноль или благополучие |

Нарушения объявленных границ и архитектурные инварианты остаются проверками допустимости изменения. Они не начисляют баллы Q. Число подпроектов Gradle также не влияет на оценку.

## Область и единицы измерения

Первый профиль рассчитан на production-код Kotlin/JVM. Его исходная область P — явно перечисленные `.kt`-файлы production source sets выбранной ревизии. Тесты, зависимости, ресурсы и подтверждённые результаты генераторов исключаются. Наличие слова `generated` в произвольном имени само по себе не служит основанием исключения. В паспорте сохраняются правила включения, исключения и количество исключённого кода.

Смешанный Kotlin/Java-проект требует отдельного профиля с фиксированным Java-анализатором cognitive complexity. До этого результат по Kotlin называется оценкой Kotlin-части, а доля Java и межъязыковые зависимости показываются отдельно. Нельзя присвоить всей смешанной базе индекс, молча исключив неподдерживаемый язык.

Область фиксируется по исходникам, включая файлы без зарегистрированных рёбер. Граф не восстанавливает полный перечень файлов из концов рёбер. Пустой проект получает `not_applicable`, а не 100 баллов.

**Токен кода** — непустой токен закреплённого Kotlin-лексера, кроме whitespace, комментариев и токенов директив `package`/`import`. Идентификаторы и литералы сохраняются; строковый литерал учитывается по правилам лексера. Аннотации и тела деклараций входят в область. Один токен задаётся путём файла и смещениями начала и конца. Форматирование и комментарии не увеличивают знаменатель. Изменение лексера меняет версию профиля.

Обозначения:

- `T` — множество токенов области P; `W = |T|`.
- `F` — именованные функции с телом, не вложенные в другую именованную функцию. Методы, top-level и extension functions входят в F. Вложенные функции и лямбды остаются внутри содержащей их функции.
- `w(f)` — число токенов полного тела `f`; токены вложенных функций учитываются в нём один раз.
- `C(f)` — cognitive complexity `f`, включая вложенные конструкции согласно выбранному анализатору.
- `size(e)` — число токенов внутри тела функции, полного объявления класса/объекта или файла после общих исключений.
- `N` — число файлов в области графа; `a → b` означает, что код a зависит от b.

Отдельные значения вложенных функций сохраняются для диагностики, но не добавляются вторым весом к среднему внешней функции. Инициализаторы свойств, блоки `init` и отдельные accessors, не являющиеся именованными функциями в этом профиле, входят в оценку размера. Их cognitive complexity не подменяется нулём: эта часть находится вне области C и её объём показывается отдельно. Расширение на неё требует определённого правила извлечения, а не синтетической обёртки с незаметно изменённой вложенностью.

## Общие правила нормирования

Для величины x с начальным ориентиром t применяется непрерывная функция превышения:

```text
p(x; t) = max(0, x / t − 1),  t > 0
score(R) = 100 / (1 + R),     R ≥ 0
```

Ниже t штраф отсутствует; при удвоении t штраф равен 1, при утроении — 2. Функция не насыщается при первом большом превышении. `score(0) = 100`, `score(1) = 50`, `score(3) = 25`. Баллы являются координатами принятой оценочной модели; 80 баллов не означают «80% правильного кода».

Стартовые параметры:

| Параметр | Значение | Основание |
| --- | ---: | --- |
| Ориентир cognitive complexity | 15 | Порог правила detekt используется как стартовая опора, не как доказанная граница качества |
| Размер функции | 300 токенов | Предложенный параметр модели |
| Размер класса или объекта | 3 000 токенов | Предложенный параметр модели |
| Размер файла | 5 000 токенов | Предложенный параметр модели |
| Минимальная длина клона | 100 токенов | Предложенный параметр модели |
| Опора нормирования дублирования | 0.10 | При 10% дублирования U равно 50; это выбранная чувствительность |
| Размер малой группы в формуле DL | 5 файлов | Параметр авторской формулы DL |

Пороговые значения токенов не являются переводом порогов строк detekt. Это самостоятельные настройки. Их меняют по результатам проверки методики на разных проектах; ручная настройка под желаемый балл отдельного проекта не допускается.

## Структурная разделимость D

### Построение графа

1. Построить полный список файлов P и таблицу соответствия исходных деклараций, JVM-классов и файлов.
2. Извлечь статические зависимости: вызовы, обращения к полям, использование типов в сигнатурах и телах, наследование и реализацию интерфейсов. Записать источник и вид связи. Один лишь текст неиспользуемого импорта не создаёт ребро.
3. Спроецировать связи деклараций на файлы. Между двумя файлами оставить одно направленное ребро независимо от числа обращений. Саморёбра удалить; исходные внутренние связи сохранить для диагностики.
4. Внешние зависимости и ссылки на исключённые файлы учитывать в отчёте охвата. Они не превращаются в отсутствующие внутренние зависимости.
5. Построить DRH закреплённым алгоритмом. Подмена файлов пакетами, классами или подпроектами Gradle создаёт другой ряд измерения.

Файловая модель чувствительна к распределению деклараций по файлам. Именно поэтому D используется совместно с размером и cognitive complexity. Reflection, строковые имена, DI и межъязыковые связи ограничивают граф в зависимости от сборщика; их отсутствие в выгрузке не доказывает независимость.

### Получение DRH

Выбранный кандидат — **ArchDRH-Re** из работы об архитектурном восстановлении, без ручной карты модулей и без дополнительных Bunch/ACDC-разбиений. Алгоритм сворачивает SCC, выделяет общие поставщики функциональных подграфов, формирует слои и группы, объединяет группы с одинаковым набором непосредственных дизайн-правил. Рекурсивный шаг отделяет управляющие элементы и повторяет разбор; опубликованные условия остановки включают `|E| < |V|` и `|E| > |V|^1.5`. Точное описание шагов и рекурсии находится в [локальной статье, §4](sources/archdrh-qosa2013.pdf); доступен [текст для поиска](sources/archdrh-qosa2013.txt).

Контракт результата для расчёта D:

- каждый файл присутствует ровно в одной конечной группе;
- для каждой группы известны файлы и номер слоя;
- межгрупповые зависимости направлены из нижних слоёв в верхние; разные группы одного слоя независимы;
- вложенная иерархия имеет явное преобразование в слои и непересекающиеся группы; предки не считаются повторно вместе с потомками;
- изолированные файлы включаются отдельными группами последнего слоя;
- параметры, условия остановки, порядок разрешения неоднозначностей и версия построителя сохраняются.

Выбор ArchDRH-Re, правила разворачивания его вложенного результата и включение изолированных файлов должны быть проверены на примерах авторских работ до публикации D. Формула DL определена ниже полностью, но произвольная корректная топологическая сортировка не гарантирует того же значения. Пока этот контракт построителя не подтверждён, выводить `D = unknown`, а не приблизительный DL. Это условие готовности общей реализации измерителя; проектной разметки оно не требует.

Текущий `pilot/scripts/drh.py` снимает слои и циклические ядра другой процедурой и не является готовым построителем для этого расчёта.

### Формула и нормирование

Пусть слои пронумерованы от верхнего 1 до последнего n; `M_i` — группы слоя i, `s(M)` — число файлов группы. Для `i < n`:

```text
b_i = число файлов во всех слоях ниже i
d(M) = число разных файлов ниже i, достигающих хотя бы одного файла M
D_i = Σ по M из M_i [s(M) / N × (1 − d(M) / b_i)]
```

Для последнего слоя:

```text
g(s) = 1,               если 1 ≤ s ≤ 5
       ln(5) / ln(s),   если s > 5
D_n = Σ по M из M_n [s(M) / N × g(s(M))]
D = 100 × Σ D_i
```

Влияние на нижние файлы определяется объединением достижимости, поэтому один файл не считается несколько раз из-за нескольких путей. При единственном слое применяется только последняя формула. Область непуста, группы непусты, а у непоследнего слоя `b_i > 0`. Диапазон D — от 0 до 100. [Авторская формула, §3.1](sources/decoupling-level-icse2016.pdf), [текст](sources/decoupling-level-icse2016.txt).

Контроль арифметики для одного слоя из 100 файлов: 25 независимых групп по 4 файла дают 100; 4 группы по 25 дают 50; одна группа из 100 даёт примерно 34.95. Эти примеры проверяют расчёт по готовой иерархии и отдельно не подтверждают корректность её построения.

Рядом с D сохраняются N, число рёбер, состав групп и их вклады. PC и SCC служат раскрытием структуры; в Q они не получают ещё два веса за тот же граф.

## Локальная поддерживаемость L

### Почему используется cognitive complexity

Cognitive complexity предназначена для оценки трудности чтения управления потоком, включая вложенность. Её исходная мотивация и определения сохранены в [описании SonarSource](sources/cognitive-complexity-sonarsource-2023.pdf).

Cyclomatic complexity характеризует другую сторону управляющего графа. Большое число простых ветвей не обязательно означает трудный для понимания код. Например, замена ясного `when` на набор косвенных вызовов может уменьшить MCC и одновременно увеличить навигацию и связанность. Поэтому MCC не входит в основной индекс и не используется для автоматического требования уменьшить сложность.

Cognitive complexity также можно улучшить чрезмерным дроблением. Её дополняют граф, размеры и дублирование; одно уменьшение C(f) не подтверждает улучшения Q.

### Извлечение cognitive complexity

Для Kotlin фиксируется реализация [detekt 1.23.8 CognitiveComplexity](sources/detekt-1.23.8-CognitiveComplexity.kt), вызываемая [правилом CognitiveComplexMethod](sources/detekt-1.23.8-CognitiveComplexMethod.kt). В общих чертах учитываются нарушения линейного чтения, дополнительная вложенность, логические последовательности, помеченные переходы и распознаваемая реализацией рекурсия. `when` не получает надбавку просто за каждую альтернативу; его тела всё ещё могут быть сложными. Для точных Kotlin-случаев определяющим является закреплённый код анализатора, а не пересказ общей формулы SonarSource.

Сборщик обязан получить полный ряд C(f), включая нулевые значения. В указанном правиле условие выдачи — `complexity >= threshold`; порог сбора 0 позволяет включить нули, но ещё требуется обойти suppressions и baseline либо отдельно показать пропуски. Производственный CI-конфиг не изменяется: измерительный проход получает собственную конфигурацию или вызывает вычислитель напрямую.

Идентификатор функции включает ревизию, относительный путь, владельца, имя и сигнатуру. Значение извлекается из метрики, а не из числа предупреждений. Пилотный SARIF с порогом 1 не является полным рядом cognitive complexity: отсутствие строки нельзя автоматически считать нулём.

### Расчёт составляющей сложности

```text
R_cog = Σ по f из F [w(f) × p(C(f); 15)] / Σ по f из F w(f)
C_score = 100 / (1 + R_cog)
```

При полном наборе функций с C(f) не выше 15 получается 100. При средней взвешенной величине превышения 1 получается 50. Токены служат весом, поэтому добавление большого числа крошечных функций не имеет того же эффекта, что невзвешенное среднее по функциям.

Если все F действительно отсутствуют, C_score неприменим и общий Q не публикуется. Если часть C(f) неизвестна, показывается частичная оценка с перечнем функций и охватом, но она не подставляется в полный Q.

Дополнительно сохраняются максимум и взвешенный p95 C(f), доля токенов функций с C(f) > 15, абсолютный объём таких функций и список крупнейших вкладов. Взвешенный p95 — минимальное значение, на котором накопленный вес отсортированных функций достигает 95%. Эти величины раскрывают оценку и не складываются с ней как независимые сигналы.

### Расчёт составляющей размера

Для каждого токена t рассматриваются содержащие его функция, классы/объекты и файл. Если контейнер данного вида отсутствует, он не участвует в максимуме:

```text
p_size(t) = max(
  p(size(function); 300),
  p(size(class_or_object); 3000),
  p(size(file); 5000)
) по всем применимым контейнерам t

R_size = Σ по t из T p_size(t) / W
S_score = 100 / (1 + R_size)
L = sqrt(C_score × S_score)
```

Размеры включают вложенные тела, но штраф каждого токена берётся один раз по максимуму. Поэтому один большой метод внутри большого класса и файла не получает три одинаковых штрафа. Для top-level функций работает функция и файл, для декларативных данных — класс и файл. Список функций и размер файла извлекаются независимо: файл с сотней коротких методов не исчезает из оценки.

В `L` сложность и размер имеют равный вес по семействам. Это политика первой версии, а не утверждение об их статистической независимости. При частичном измерении размера действует то же правило неполного Q.

## Дублирование U

Область — то же множество токенов T. Сравниваются их тип и исходное значение после общих исключений. Имена, числа и строки не нормализуются к одному символу. Порядок файлов и их пути не участвуют в содержимом последовательности; последовательность не пересекает границу файла.

1. Найти одинаковые непрерывные последовательности длиной не менее 100 токенов.
2. Каждая группа повторов должна иметь как минимум два различных вхождения. Внутри одного файла требуются непересекающиеся вхождения; сравнение фрагмента с самим собой запрещено.
3. Расширить найденные совпадения до максимальных одинаковых фрагментов. Пересекающиеся результаты объединить по исходным позициям.
4. Пусть `T_dup` — объединение всех токенов во всех вхождениях повторяющихся фрагментов. Каждая позиция учитывается один раз, включая первое вхождение.

```text
d = |T_dup| / W
U = 100 / (1 + d / 0.10)
```

При 0%, 5%, 10% и 20% повторяющихся токенов U равно 100, 66.67, 50 и 33.33 соответственно. Показываются и исходная доля d, и абсолютное число повторяющихся токенов. Это собственная оценочная шкала, а не SIG Rating.

Минимальный контракт детектора — точное совпадение токенов. Если инструмент использует другие правила или обнаруживает клоны с переименованиями, его вывод не смешивается с этим рядом без смены профиля. Содержательно одинаковая логика с другим написанием может остаться необнаруженной. Это известная слепая зона первой версии, а не основание назначать ручные исключения проекту.

## Общий индекс Q

```text
Q = (D × L × U)^(1/3)
```

Все составляющие имеют направление «больше лучше». При известном нуле одной составляющей Q равно нулю; при неизвестной составляющей Q неизвестен. Веса не перераспределяются автоматически. Не допускается публиковать среднее двух доступных составляющих под прежним именем Q.

Равные веса означают равное влияние трёх семейств в логарифмической шкале. Это стартовая политика мониторинга. Она не заменяет порядок выбора рекомендаций «модульность → риск регрессий → скорость» из процедуры рефакторинга. Пример: D=80, L=75, U=90 дают Q≈81.43. D=90, L=90, U=20 дают Q≈54.51; слабая составляющая заметно снижает общий результат.

Основная строка отчёта содержит Q и все три составляющие. Изменение на один балл не трактуется как процент ускорения разработки. Категории LOW/MEDIUM/HIGH до калибровки диапазонов не назначаются.

## Покрытие тестами

### Выбор вида покрытия

| Вид | Что различает | Применение |
| --- | --- | --- |
| Line coverage | Выполнялась ли хотя бы одна инструкция, сопоставленная строке | Человекочитаемый отчёт и навигация |
| Branch coverage | Выполненные исходы ветвлений по модели анализатора | Основной показатель проверки ветвлений |
| Instruction coverage | Выполненные инструкции, включая код без ветвлений | Дополнение к branch coverage и вход CRAP_exec |
| Condition coverage | Истинные и ложные исходы отдельных булевых условий | Отдельная метрика при наличии соответствующего сборщика |
| MC/DC | Независимое влияние каждого условия на итоговое решение | Отдельный режим, не входит в начальный профиль |

JaCoCo получает счётчики из байткода. Его branch coverage относится к `if`/`switch`, а обработка исключений не считается ветвлением. Строка считается выполненной при выполнении хотя бы одной её инструкции. Поэтому называть branch coverage JaCoCo покрытием условий или MC/DC нельзя. [Документация счётчиков](sources/jacoco-coverage-counters.html). Определение MC/DC сохранено [из NIST](sources/nist-modified-condition-decision-coverage.html).

Например, выполнение одной альтернативы в `fun sign(x: Int) = if (x >= 0) 1 else -1` может дать покрытую строку при непокрытой альтернативе. А два теста исходного решения `A && B` с результатами true и false ещё не устанавливают, что проверено независимое влияние обоих условий. Конкретные дополнительные прыжки Kotlin-байткода нужно читать по выбранному анализатору.

Выбор первой версии: **публиковать branch coverage и instruction coverage парой**. Высокое line coverage недостаточно для оценки ветвлений. Одного branch coverage также недостаточно: непроверенный код может не иметь ветвей. Слияние процентов в один средний процент не требуется.

### Агрегация проекта

Для каждого включённого метода m доступны количества `B_cov`, `B_total`, `I_cov`, `I_total`. Один и тот же байткод учитывается один раз, даже если его покрыли разные тестовые задачи; объединяется информация выполнения, а не складываются дублированные totals.

```text
branch_project = 100 × Σ B_cov(m) / Σ B_total(m)
instruction_project = 100 × Σ I_cov(m) / Σ I_total(m)
line_project = 100 × covered_source_lines / executable_source_lines
```

Последние две величины для строк считаются по уникальным парам «файл, строка» выбранной области. Их нельзя получать сложением пересекающихся строк JVM-методов. Для ветвей и инструкций используются непересекающиеся множества методов после фильтров. При нулевом знаменателе показатель неприменим.

В паспорт входят ревизия, JVM/Kotlin compiler, версия и фильтры анализатора, набор тестовых задач и их результат. Отчёт должен содержать также неисполненные классы, а не только загруженные в тестах. Ошибка прогона или отсутствующий отчёт — неизвестность. Метод, присутствующий в полном корректном отчёте с нулём выполненных инструкций, имеет измеренное нулевое покрытие.

Покрытие показывает выполнение кода. Качество assertions и способность обнаруживать заданные ошибки требуют других свидетельств; наличие покрытия не повышает D, L или U.

## CRAP как дополнительный показатель

### Исходная метрика и выбранный вариант

В исходном описании для метода m используются cyclomatic complexity `v(m)` и доля покрытия базисных путей `c(m)`:

```text
CRAP(m) = v(m)^2 × (1 − c(m))^3 + v(m)
```

Автор приводит порог 30 для своей модели. [Первоисточник Alberto Savoia](sources/crap-alberto-savoia-2011.html). Произвольная замена MCC на cognitive complexity или покрытия путей на другой счётчик не сохраняет исходную калибровку.

Поэтому для JaCoCo вводится явно обозначенная **производная CRAP_exec**, а исходный порог 30 не используется как норматив качества. MCC сохраняется только внутри этой дополнительной диагностики. Новую метрику с cognitive complexity вместо MCC в первой версии не вводим.

Единица CRAP_exec — включённый в отчёт JVM-метод с телом, идентифицируемый именем класса, именем метода и descriptor. `v(m)` берётся как сумма covered и missed счётчика `COMPLEXITY` JaCoCo того же метода. Его не смешивают с MCC detekt. Влияние Kotlin lowering и фильтрации фиксируется версиями; несколько JVM-методов одного исходного выражения не объединяют в одну сложность перед возведением в квадрат.

Методы с подтверждённым происхождением из исключённого generated-кода удаляются по общей политике. Синтетический флаг сам по себе не позволяет удалять всё содержимое лямбд или корутин. Несопоставленные с областью P методы учитываются как пробел охвата. Нулевая или отсутствующая `COMPLEXITY` у ожидаемого исполняемого метода требует проверки данных.

Для пригодного метода:

```text
c_I(m) = I_cov(m) / I_total(m)
c_B(m) = B_cov(m) / B_total(m), если B_total(m) > 0

c_exec(m) = min(c_I(m), c_B(m)), если ветви существуют
            c_I(m),             если ветвей действительно нет

CRAP_exec(m) = v(m)^2 × (1 − c_exec(m))^3 + v(m)
e(m) = CRAP_exec(m) − v(m)
```

Минимум — выбранная консервативная политика сочетания двух счётчиков. Она сохраняет сигнал непроверенных ветвей и непроверенных инструкций, включая последовательный код. Отсутствующие сведения о ветвях не равны установленному `B_total=0`. Если нужный счётчик неизвестен, неизвестен и CRAP_exec.

Даже при полном покрытии CRAP_exec равен v. Поэтому его полное значение одновременно отражает MCC и отсутствие исполнения. **Для оценки пробелов тестирования основным дополнительным сигналом выбирается превышение e**, которое равно нулю при полном c_exec.

### Нормирование на весь проект

Пусть M — полный набор пригодных методов области P. Сначала рассчитываются значения каждого метода, затем выполняется агрегация:

```text
total_crap = Σ по m из M CRAP_exec(m)
total_excess = Σ по m из M e(m)

excess_density = 1000 × total_excess / W
E_CRAP = 100 × Σ e(m) / Σ v(m)^2
```

`excess_density` имеет единицу «баллы превышения CRAP_exec на 1000 исходных токенов». Она позволяет отслеживать нагрузку с поправкой на размер, сохраняя влияние абсолютной сложности. `E_CRAP` находится в диапазоне 0–100 и характеризует непокрытость с весом v²: 0 при полном c_exec всех методов, 100 при нулевом c_exec всех методов. Это не вероятность дефекта и не общий процент покрытия. Меньшие значения обоих показателей благоприятнее.

Эти показатели нужны **вместе**. В E_CRAP относительная непокрытость может быть одинаковой у простого и сложного проекта; excess_density показывает разницу нагрузки. `total_excess` позволяет увидеть, что снижение плотности вызвано добавлением кода, а не устранением прежней проблемы. Дополнительно выводятся число методов, p95 CRAP_exec и самые большие e(m).

Нельзя сначала сложить сложности методов и подставить среднее покрытие в формулу. Два метода с v=5 и c_exec=0.5 дают суммарно 16.25. Применение формулы к v=10 и тому же покрытию даёт 22.5. Перенос этих методов между файлами должен оставлять первый результат неизменным.

Другой контроль: при v=4, c_exec=0.5 получаются CRAP_exec=6 и e=2; при v=10, c_exec=0.8 — 10.8 и 0.8. Вместе `E_CRAP = 100 × 2.8 / 116 ≈ 2.41`. При W=1000 excess_density равно 2.8. Числа иллюстрируют формулы и не являются измерением пилота.

Нормирование `e(m) / v(m)^2` **до невзвешенного усреднения** удаляет сложность: остаётся `(1 − c_exec(m))^3`. В E_CRAP отношение вычисляется после суммирования, поэтому веса v² сохраняются.

Если M неполон, E_CRAP можно показать только с меткой частичной области и её составом. Для частичной excess_density знаменатель должен ограничиваться исходными файлами, в которых подтверждена полнота всех включаемых методов; все остальные файлы исключаются из обоих суммирований. При невозможности выделить такую область плотность неизвестна. Полная масса W проекта не должна разбавлять известные превышения при пропущенных методах.

CRAP_exec и его агрегаты не входят в Q: иначе MCC вернулась бы в основной индекс, а высокая тестовая активность могла бы скрыть структурное ухудшение. Они служат отдельным числовым сигналом выбора участков для проверки тестов.

## Диагностические показатели и история

Следующие величины раскрывают профиль, но не получают дополнительных весов в Q:

| Показатель | Точное правило |
| --- | --- |
| PC | Для того же файлового графа: число достижимых упорядоченных пар, включая диагональ, делённое на N² |
| Доля циклических файлов | Число файлов в SCC размера больше 1, делённое на N; рядом размер крупнейшей SCC |
| Входящая видимость файла | Число достигающих его файлов плюс он сам, делённое на N |
| Доля сложного кода | Сумма весов w(f) функций с C(f)>15 / сумма w(f) |
| Доля дублирования | Число уникальных токенов в повторяющихся фрагментах / W |

При доступной истории можно добавить необязательное представление совместных изменений. Используется окно 180 дней до снимка, первая родительская линия выбранной ветви, без merge-коммитов; единица наблюдения — коммит этой линии, а не бизнес-задача. Отдельно указать число наблюдений. Из рассмотрения исключаются изменения более 30 production-файлов; они остаются отдельным счётчиком. Переименования сопоставляются с текущими путями, неизвестная идентичность не подменяется удалением проблемы.

Для пары файлов a,b на **одном отфильтрованном наборе коммитов**:

```text
r_a, r_b = числа изменений каждого файла
s_ab = число совместных изменений
coupling(a,b) = 2 × s_ab / (r_a + r_b)
```

Показываются пары с `s_ab ≥ 5`, `(r_a+r_b)/2 ≥ 5` и coupling≥0.30. Дополнительная сводка — доля токенов текущих файлов, имеющих хотя бы одного такого партнёра. Это экспозиция совместным изменениям, без направления «всегда меньше лучше»: ожидаемые пары тоже попадут в выборку. Нулевой результат при недостаточной истории не означает независимости. При short history сводка маркируется как ограниченная. История не меняет определение базового Q и не требует ручного сбора сценариев.

## Полнота измерения и сравнение во времени

Для каждого снимка сохраняются commit, рабочий diff или его hash, время сбора, профиль и его параметры, версии инструментов, исходная область, исключения, пути к артефактам и ошибки. У разных показателей отдельные статусы: `known`, `partial`, `unknown`, `not_applicable`.

Показатели охвата не складываются в «уверенность 87%». Нужны конкретные числители и знаменатели:

- файлы графа относительно полного списка P, сопоставленные декларации и неразрешённые связи;
- функции с измеренным C(f) относительно всех F, их токены и область кода вне F;
- токены, обработанные детектором клонов, относительно W;
- классы/методы с пригодными счётчиками покрытия относительно полного инвентаря ожидаемого байткода;
- методы и исходные файлы, включённые в CRAP_exec, с причинами пропусков.

Для полного Q требуются полные входы каждой определённой составляющей и пригодный граф в рамках заявленной модели статических связей. Недоступность runtime-связей остаётся ограничением модели; пропуск доступных файлов — дефект сбора. Частичные составляющие не перераспределяют веса Q.

Сравниваются снимки с одинаковым профилем. При изменении анализатора, алгоритма DRH, тестовых задач, фильтров или параметров пересчитываются обе сравниваемые ревизии либо начинается отдельный ряд. Сохраняются исходные значения, а округление до одного десятичного знака делается только при отображении.

В отчёте рядом с нормированными оценками показываются абсолютные массы проблем. Рост проекта способен улучшать долю при неизменной старой проблеме. Для объяснения изменения автоматически разделяются сохранившиеся, добавленные и удалённые файлы. При сравнении прежних файлов графовые пути через новый код сохраняются: механическое отсечение новых узлов может скрыть новые зависимости.

## Проверка совокупности показателей

Набор ниже относится к проверке **измерителя**, а не к предварительным знаниям о каждом проекте. Он не требует поддерживать предметные сценарии пользователя.

| Преобразование | Ожидаемая реакция |
| --- | --- |
| Переименование каталогов или объявленных модулей при том же графе и телах | Основные оценки сохраняются после сопоставления сущностей |
| Изменение форматирования и комментариев | Токенные размеры, веса и дублирование сохраняются |
| Слияние нескольких файлов в огромный файл | Возможное улучшение D сопровождается ухудшением размера |
| Разделение файла на тесно связанные фрагменты | Уменьшение размера сопоставляется с реакцией D; улучшение Q не предполагается автоматически |
| Копирование общей реализации потребителям | Возможное улучшение D сопровождается ухудшением U при обнаружимом клоне |
| Выделение независимых частей без копирования логики | Ожидается улучшение разделимости без штрафа за новые клоны |
| Замена ясного `when` искусственной цепочкой косвенных вызовов | Уменьшение MCC не даёт самостоятельного выигрыша Q |
| Уменьшение вложенности с сохранением понятных локальных правил | Проверяются C_score и отсутствие ухудшения D/U |
| Добавление тестов без изменения production-кода | Q сохраняется; покрытие и CRAP_exec могут улучшиться |
| Перенос неизменённых методов между файлами | Сумма CRAP_exec сохраняется при одинаковом байткоде и покрытии |
| Исчезновение отчёта или усиление suppressions | Ухудшается охват, а не улучшается индекс |
| Добавление большого простого участка | Отчёт различает изменение состава проекта и состояние прежних проблем |

Не требуется монотонность каждого показателя во всех случаях. Проверяется, обнаруживает ли весь профиль существенную цену преобразования. Если простое преобразование устойчиво улучшает все оценки без полезного изменения структуры, модель пересматривается. Пороги и веса также проверяются на чувствительность; выигрыш только при одном узком наборе настроек не считается устойчивым.

## Порядок внедрения

1. Реализовать единый инвентарь исходников, токенов, функций и связей; сохранить ревизию и происхождение записей.
2. Получить полный ряд cognitive complexity и размеры; вычислить C_score, S_score и L.
3. Добавить детектор повторяющихся токенов и U.
4. Выбрать и проверить реализацию ArchDRH-Re и преобразование её результата в вход DL. Затем вычислять D и Q. До этого публиковать доступные составляющие без подмены D или перенормирования Q.
5. Расширить сбор покрытия до непересекающихся JVM-методов со счётчиками инструкций, ветвей и сложности. Добавить CRAP_exec, excess_density и E_CRAP.
6. Проверить арифметику, общие преобразования и затем динамику нескольких проектов без настройки порогов под отдельные желаемые результаты.

Пилот даёт графы классов/пакетов, часть рядов detekt, размеры файлов, историю и пофайловое покрытие. Он ещё не даёт требуемых токенных весов, полного ряда нулевых cognitive complexity, проверенного DRH для DL, клонов и методных входов CRAP_exec. Старые `crap-*.csv` не используются для нового проектного агрегата: они возводят в квадрат сумму MCC файла и применяют файловое line coverage.

## Источники и основания

Локальный [каталог источников](sources/README.md) содержит исходные PDF, HTML, версии исходников, текстовые извлечения PDF, URL и контрольные суммы. Для повторного чтения сначала используется этот каталог. Обновление источника рассматривается отдельно от изменения снимка кода.

Формула DL и идея DRH заимствованы из работ Mo/Cai и соавторов. Cognitive complexity определяется SonarSource и выбранной реализацией detekt. Исходный CRAP описан Savoia. Счётчики исполнения определяет JaCoCo. Подход к распределениям размера, сложности и повторов сопоставлялся с [моделью SIG](sources/sig-maintainability-model-2007.pdf).

Функция p, токенные веса и пороги, нормирование U, сочетание L и Q, c_exec и проектные агрегаты CRAP_exec являются **предлагаемой моделью этого исследования**. Ссылки на первоисточники не означают, что ими подтверждены эти новые комбинации.

Из FPF применены [C.16 — правила измерения](../../../../.agents/skills/fpf-problem-solving/sections/09-part-c---kernel-extension-specifications/27-c-16---measurement-metrics-characterization.md), [C.16.IR — различающая способность показания](../../../../.agents/skills/fpf-problem-solving/sections/09-part-c---kernel-extension-specifications/29-c-16-ir---determine-what-a-measurement-indication-can-resolv.md), [C.25 — составные утверждения о качестве](../../../../.agents/skills/fpf-problem-solving/sections/09-part-c---kernel-extension-specifications/47-c-25---q-bundle-express-a-quality-claim-as-one-characteristi.md) и [C.31 — характеристики модульности](../../../../.agents/skills/fpf-problem-solving/sections/09-part-c---kernel-extension-specifications/71-c-31---modularity-and-reusable-structure-characteristics.md): определение объекта и шкалы, различение измерения и оценки, проверка слепых зон и сохранение составляющих общего результата.
