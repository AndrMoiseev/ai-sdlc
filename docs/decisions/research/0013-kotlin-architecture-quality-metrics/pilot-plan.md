# План пилота: первичная оценка архитектуры Kotlin-проекта

**Начать с готовых отчётов проекта, затем использовать Code Maat для частоты и совместных изменений и detekt CLI для локальной сложности.** Результаты помогают выбрать участки для предметного архитектурного разбора. Первый полезный результат должен появиться за половину рабочего дня: несколько проверенных наблюдений, их последствия для сопровождения и конкретные следующие действия. Подключение ArchUnit с новым запускателем и экспортом отложено за пределы первого этапа.

Основание — [исследование метрик](research.md). Здесь выбран один сценарий: оценка текущего состояния существующего проекта. Приоритеты отличаются от исследовательской программы: готовый инструмент с пригодным стандартным выводом, короткий путь до объяснимой находки и небольшая стоимость подключения важнее полноты каталога. Наличие алгоритма в библиотеке само по себе не означает готовности инструмента для пилота. Это план проверки метода; инструменты на целевом проекте ещё не запускались, оценки затрат ниже предварительные.

## 1. Какое решение должен дать пилот

Получатель результата — технический лидер и разработчик, знакомый с проектом. Вопрос: **«Какие участки архитектуры стоит исследовать первыми, почему и что именно проверить?»**

Итог — до пяти приоритетных находок. Каждая содержит конкретные зависимости или фрагменты кода, объяснение риска для одного реального сценария сопровождения и решение: исследовать, оставить как оправданное устройство либо признать недостаток данных. Если подтверждённых проблем меньше, не дополнять список ради количества.

Первый объект — один Kotlin/JVM + Gradle проект, один commit, production-код выбранного приложения и его собственных модулей. История Git желательна, но не обязательна. Для базового анализа исходников и Git сборка приложения не является предварительным условием. Для смешанного Kotlin/Java проекта история охватывает оба языка, а detekt — Kotlin; непроверенную Java-часть указывать явно. Android и KMP требуют отдельного определения variant/source sets; вывод о выбранной части нельзя распространять на всю систему.

Первый результат — архитектурный разбор выбранных участков по косвенным сигналам и коду. Code Maat и detekt не дают полного статического графа зависимостей, Ca/Ce или перечня циклов. Если соответствующего готового отчёта в проекте нет, эти измерения остаются пробелом, который явно показывается в заключении.

В этот пилот не входят оценка PR, динамика деградации, автоматический рефакторинг, поиск оптимальной декомпозиции и рейтинг архитектуры 0–100. Одного снимка достаточно для первичного разбора, но недостаточно для утверждения «архитектура ухудшается».

## 2. Как выбираем метрики

Применены два положения FPF:

- **C.11.MV, практическая ценность метода:** сравнивать пользу с полной стоимостью подключения и разбора; сохранять вариант обычного чтения кода, если дополнительный инструмент не меняет решения.
- **C.16.MR, связь измерения с вопросом:** для каждого числа фиксировать объект, способ получения и допустимый вывод. Например, повторяющиеся совместные изменения файлов дают повод проверить связь ответственностей, но не доказывают ошибочность их разделения.

Порядок выбора: сначала сигнал должен помогать конкретному решению; среди полезных вариантов сначала рассматриваем **готовые OSS-инструменты со штатным запуском и пригодным отчётом**. Затем сравниваем стоимость настройки и понятность результата. Взвешенный балл «полезности» не вводим: до пилота нет измеренных оснований для весов.

Граница готовности для первого этапа:

- Допустимы установка готового релиза, штатные CLI-команды или существующие Gradle-задачи, документированные параметры, конфигурация встроенных правил, стандартный экспорт Git-log и перенаправление вывода в файл.
- Результаты читаются в штатном отчёте. Для короткого списка допустимо вручную сопоставить файлы и наблюдения в итоговом документе.
- Новые запускатели, адаптеры, парсеры, конвертеры форматов, собственные правила и экспортёры в первый этап не входят. Если без них результат непригоден, инструмент переносится в отдельное продолжение. Ограничение относится и к коду, который быстро сгенерирует агент.
- Уже настроенные архитектурные проверки можно использовать сразу, если есть актуальный результат или штатная команда без доработки. Наличие одной зависимости ArchUnit в сборке этому условию не соответствует.

| Очередь | Сигнал и инструмент | Понятная ценность | Что придётся настроить |
|---|---|---|---|
| **0, переиспользование** | Актуальные отчёты уже настроенных OSS-анализаторов, включая архитектурные проверки | Получить полезные свидетельства без внедрения | Проверить commit, охват и настройки отчёта |
| **1, при наличии истории** | Частота изменений файлов: Code Maat `revisions` | Найти участки, с которыми команда часто работает | Готовый JAR, документированный Git-log, стандартный CSV |
| **1, тот же вход** | Совместные изменения: Code Maat `coupling` | Найти пары разных ответственностей для проверки скрытых связей | Тот же log, встроенные фильтры, стандартный CSV с подробностями |
| **1, локальное уточнение** | Сложность функций, длина и вложенность: detekt CLI | Найти трудную логику в активных или критичных участках | Готовый CLI, конфигурация встроенных правил, штатный отчёт |
| **2, по вопросу** | Дубли между ответственностями: PMD CPD | Проверить гипотезу о расходящихся копиях одного правила | Штатный CLI и отчёт совпадений |
| **3, отдельное продолжение** | Циклы и Ca/Ce через новую интеграцию ArchUnit | Уточнить статические связи, если они нужны для нерешённого вопроса | Потребуется разработка запуска/правил/экспорта; сначала оценить готовые альтернативы |

ArchUnit предоставляет готовые проверки и расчёты через библиотечный API. Получение таблицы Ca/Ce через новую интеграцию требует собственного кода и не удовлетворяет условию первого этапа. Его возможности остаются кандидатами дальнейшего анализа. [Руководство ArchUnit](https://www.archunit.org/userguide/html/000_Index.html).

Базовый OSS-набор: detekt — Apache-2.0, Code Maat — GPL-3.0. Использовать готовые дистрибутивы либо уже работающие интеграции и закрепить совместимые версии. Не обновлять стек ради пилота и не собирать анализатор из исходников, если есть готовый релиз. Штатные способы запуска: [detekt CLI](https://detekt.dev/docs/1.23.8/gettingstarted/cli/), [Code Maat JAR и CSV](https://github.com/adamtornhill/code-maat). Лицензия detekt: [репозиторий](https://github.com/detekt/detekt).

### Что сознательно откладываем

| Кандидат | Почему не в первом результате | Когда вернуться |
|---|---|---|
| DL, Design Rule Hierarchy | В исследовании не установлен простой готовый OSS-путь для Kotlin; потребуется отдельная реализация и проверка метода | Когда появится задача общего сигнала и ресурс на исследование |
| PC, Lakos CCD/ACD/RACD/NCCD | Для части показателей есть готовый ArchUnit API, но транзитивные нормировки сложнее объяснить и связать с действием | Если прямые зависимости не объясняют масштаб структурного риска |
| Статические циклы, Ca/Ce и полный профиль SCC без готового отчёта | Расчёт через API ArchUnit/JGraphT требует своего кода и подготовки графа | Если предметный разбор оставил конкретный вопрос о связях; сначала искать готовый инструмент с нужным отчётом |
| Instability, Abstractness, Distance, JVM visibility | Значение зависит от роли компонента; Kotlin-абстракции и видимость не сводятся к JVM public/abstract | При конкретном вопросе об устойчивости контракта или внешней поверхности |
| Leiden/Louvain, Modularity, CodeCharta как общий сборщик | Нужны дополнительные преобразования, настройки и проверка извлечения связей | Для отдельного исследования новых границ после первичной оценки |
| CRAP, новое подключение coverage, mutation testing | Добавляют настройку тестового измерения и сопоставление функций; отвечают прежде всего на вопросы тестовой защиты | Перед изменением выбранного рискованного участка; готовое покрытие можно прочитать сразу |
| Dependency Analysis Gradle Plugin | Лишние объявления библиотек полезно убирать, но это другой вопрос, чем устройство внутренних ответственностей | Если проблема связана с составом classpath или стоимостью сборки |

Эти ограничения опираются на [каталог и определения исследования, §8](research.md#8-каталог-метрик-и-приоритет-инструментов-для-kotlingradle). Низкая стоимость вычисления сама по себе не делает метрику обязательной.

## 3. Первый результат за половину дня

Целевой бюджет основного этапа — **до четырёх часов работы одного инженера**, включая получение данных и разбор, плюс до 30 минут владельца проекта. Это ограничение трудозатрат пилота, а не обещание времени анализа любого репозитория. Полное календарное время, ожидание сборки и скачивания также записываются. Правила времени тестов и доступа к файлам из AGENTS.md действуют отдельно и имеют приоритет.

### Шаг 0. Зафиксировать область и исходные ожидания — до 30 минут

Выбрать репозиторий и commit; записать JDK, Kotlin, Gradle, source sets и имеющиеся анализаторы. Сначала проверить доступные отчёты и возможность их штатного повторного запуска. Отделить production-код от тестов, генерации, внешних библиотек и build logic. Составить список включённых и пропущенных модулей.

Для интерпретации выбранных файлов использовать существующие функциональные пакеты и Gradle-модули. Достаточно указать принадлежность файлов короткого списка к этим областям и прочитать их ответственности. Полное отображение классов в компоненты и автоматическая агрегация не нужны на этом этапе.

До просмотра результатов попросить владельца назвать один-два недавних трудных изменения и ожидаемые проблемные области. Коротко записать исходную очередь разбора. Это дешёвое основание для последующей проверки: изменили ли инструменты приоритет, локализовали ли причину или лишь повторили известное.

**Выход:** область анализа, доступные штатные отчёты, один-два сценария сопровождения и исходные ожидания. Если истории нет, начать с detekt и названных владельцем участков. Если готовый отчёт требует сборки, а она недоступна, отметить этот пробел; подготовка байткода не должна блокировать независимый анализ исходников и истории.

### Шаг 1. Получить стандартные отчёты — до 90 минут

При наличии пригодной истории подготовить Git-log документированной командой Code Maat, получить `revisions` и `coupling --verbose-results` штатным JAR. Окно первого запуска — последние шесть месяцев до выбранного commit; для молодого проекта указать доступный период. Сохранить CSV без преобразования в собственный формат.

Затем использовать имеющийся отчёт detekt либо запустить готовый CLI с правилами `CyclomaticComplexMethod`, `LongMethod`, `NestedBlockDepth`. При отдельном вопросе о понимании вложенной логики включить `CognitiveComplexMethod`. Сохранить стандартный HTML/XML/SARIF в поддерживаемом выбранной версией формате. Для этого набора не вводить обязательную сборку приложения. [CLI и стандартные отчёты detekt](https://detekt.dev/docs/1.23.8/gettingstarted/cli/).

Если Code Maat уже дал достаточно кандидатов для предметного разбора, новый detekt можно отложить: запуск обоих инструментов не является самоцелью. Проверить, что вход охватывает выбранные пути, а отчёт относится к нужному commit. Правила работы с историей, порогами и baseline приведены ниже.

Первый отчёт содержит:

- Часто изменяемые файлы и пары совместно изменяемых файлов, если история пригодна.
- Находки сложности с координатами, если использован detekt.
- Уже имеющиеся архитектурные результаты, если их удалось получить без доработки.
- Охват, исключения и ограничения результата.

Для первого разбора достаточно просмотреть до десяти кандидатов и выбрать до пяти находок. Сопоставление короткого списка выполнить чтением отчётов и кода. Не создавать автоматическое объединение CSV и SARIF, общий рейтинг или таблицу метрик всех компонентов.

Если инструмент требует собственного кода либо настройка выходит за бюджет, зафиксировать препятствие и перейти к разбору доступных данных. Дополнительную интеграцию рассматривать после первого результата, сравнив с готовыми средствами и адресным чтением кода.

### Шаг 2. Проверить смысл и выдать рекомендации — до двух часов

Выбрать до пяти кандидатов: совместные изменения разных ответственностей, активные файлы со сложной логикой и область одного известного трудного изменения. Не исключать критичные, но редко меняющиеся контракты. Прочитать соответствующие места обращения, интерфейсы и распределение обязанностей. Проверить альтернативные объяснения: нормальное развитие функции, реализация и её тест, массовое форматирование, общая стабильная библиотека.

Агент связывает наблюдения со сценариями и предлагает следующие действия; числа берёт из результатов инструментов. Инженер проверяет существенные выводы по коду, владелец — значимость для сопровождения. Предложение «выделить модуль» требует объяснения ответственности и направления интерфейса; частых совместных изменений или сложной функции недостаточно. Ручное прослеживание нескольких связей не представлять как полный граф проекта.

**Выход первой половины дня:** короткий отчёт с проверяемыми находками и очередью дальнейшего разбора. Его можно принять без подключения остальных инструментов.

## 4. Уточнить приоритеты, только если это меняет решение

Дополнительный бюджет — **до двух часов**, включая интерпретацию. Выбрать полезное дополнение, а не запускать весь список. Сначала использовать уже существующие отчёты проекта. Общий ориентир пилота — один рабочий день; при необходимости расширения явно назвать оставшийся вопрос и ожидаемую пользу.

### Правила чтения истории и её выборочного уточнения

Для отчётов первого этапа единица наблюдения — коммит; не называть её задачей или PR. Использовать документированный формат log и поддерживаемые параметры Git/Code Maat. Явно выявленные массовые форматирования, генерацию и merge-коммиты исключать штатными средствами, если это возможно; иначе отмечать их влияние при разборе кандидатов. Сохранить фильтры и объём исключённого материала. Удалённые и переименованные пути проверять отдельно при сопоставлении с текущими файлами.

Присоединить частоту к конкретным файлам находок, первоначально вручную для короткого списка. Не суммировать частоты файлов в «число изменений компонента»: один коммит может затронуть несколько его файлов. Получить очередь: структурный риск и активность видны в отдельных столбцах. Не вводить произведение «сложность × частота» с произвольными весами. Низкая активность не отменяет критичность стабильного контракта.

В отчёте `coupling --verbose-results` читать число изменений каждого файла и совместных изменений вместе с процентом; сохранить фильтры размера changeset и минимальной поддержки. Разобрать несколько совместных коммитов. Если результат определяется одним массовым изменением, не считать пару надёжным сигналом. Процент coupling не трактовать как вероятность дефекта. При необходимости уточнить встроенные фильтры и повторить тот же анализ. Команды, CSV и параметры описаны в [Code Maat](https://github.com/adamtornhill/code-maat).

При короткой или преимущественно импортированной истории отметить недостаток данных и опереться на исходники и известные сценарии сопровождения. Реконструкция PR/задач, собственная очистка log и сложное восстановление переименований не входят в первый пилот.

### Локальная сложность: что именно трудно внутри участка

Если detekt не понадобился на первом этапе, подключить его при вопросе о трудной логике внутри выбранного участка. Использовать тот же небольшой набор встроенных правил. Конфигурацию, пороги и подавления сохранить. Для первичной оценки старого кода явно учесть действующий baseline: отсутствие новых предупреждений не означает отсутствие накопленных проблем. При необходимости выполнить отдельный диагностический запуск без baseline штатным способом, сохранив рабочую конфигурацию проекта.

Использовать стандартные находки с координатами. Не писать экспорт метрик всех функций ради первого отчёта и не выдавать число предупреждений за полное распределение сложности. Пороги правил — настройки отбора кандидатов, а не границы хорошей архитектуры. Разные правила, сработавшие на одной функции, не считать независимыми доказательствами. [Правила detekt 1.23.8](https://detekt.dev/docs/1.23.8/rules/complexity/); для запуска выбрать документацию именно используемой версии.

PMD CPD подключать только при конкретной гипотезе о повторении бизнес-правила между найденными участками. Достаточно списка совпадений и их содержательной проверки; общая плотность дублей для принятия первого решения не нужна. [Поддержка Kotlin в CPD](https://pmd.github.io/pmd/pmd_languages_kotlin.html).

### Если нужен статический граф зависимостей

Сформулировать оставшийся вопрос, например: «Есть ли обратные зависимости между этими двумя областями?» Сначала проверить уже работающие архитектурные отчёты и готовые OSS-инструменты с подходящим Kotlin/JVM-входом и штатным выводом. ## 5. Минимальные правила интерпретации

| Показатель | Что именно читаем | Чего не заключаем |
|---|---|---|
| Частота файла | Число учитываемых коммитов за окно | Что активность доказывает дефект или измеряет трудозатраты |
| Сложность и размер | Значение/находку конкретного правила и фрагмент кода | Что сложная функция доказывает плохое разбиение системы |
| Совместные изменения | Повторяющиеся пары с достаточным числом наблюдений и содержательным объяснением | Что общая история автоматически требует объединения компонентов |
| Дубли | Конкретные повторяющиеся фрагменты и их ответственности | Что текстовое сходство обязательно означает общее бизнес-правило |
| Имеющийся архитектурный отчёт | Только реально выполненные правила и измерения в указанном охвате | Что отсутствие найденных нарушений доказывает хорошую архитектуру |

При пустом или неполном входе показывать «нет данных» либо ограниченный охват, а не благополучный ноль. Отсутствие отчёта о циклах означает «циклы не измерены». Выбор готовых инструментов сокращает внедрение, но не расширяет автоматически доказательность их показаний.

## 6. Что сохранить по итогам

Достаточно одной папки результатов в согласованном внешнем рабочем каталоге, без новой инфраструктуры:

- **Короткий отчёт:** область, главные выводы, до пяти находок, ограничения, решение о следующем шаге.
- **Основания:** стандартные отчёты инструментов; для находок — ссылки на код выбранного commit и примеры истории. Собственный сводный формат данных не требуется.
- **Повторяемость:** версии инструментов, команды, конфигурация, исключения, окно истории, время настройки/расчёта/разбора. Сохранить только реально использованные данные.

Форма одной находки:

| Поле | Содержание |
|---|---|
| Наблюдение | Проверяемый факт: пара совместно изменяемых файлов, конкретная сложная функция или повторяющееся правило |
| Основание | Отчёт, commit, файлы и координаты |
| Последствие | Как это может затруднить названный сценарий сопровождения |
| Проверка объяснения | Что прочитано; какие альтернативы подтверждены или отвергнуты |
| Решение | Исследовать конкретный контракт/границу, оставить устройство либо получить недостающие данные |
| Приоритет | Причина первоочередности: частота работы, критичность сценария, широта затрагиваемых контрактов |

Числа не превращаются в рекомендацию автоматически. Например, совместные изменения файлов из `orders` и `billing` становятся полезной находкой после чтения коммитов и кода: одно правило расчёта оплаты поддерживается в двух местах, поэтому его изменение требует согласованной правки. Совместная доставка двух независимых функций в одном коммите такого вывода не поддерживает. Это пример формы объяснения, а не результат измерения существующего проекта.

## 7. Как решить, окупился ли пилот

До запуска принять следующие критерии:

1. Первый интерпретированный результат получен в бюджете основного этапа; известны полные затраты, включая настройку и ручной разбор.
2. Все приоритетные находки прослеживаются до кода и измерений; другой инженер может проверить их и повторить команды на том же commit.
3. Владелец проекта подтвердил хотя бы одно полезное решение: новый приоритет, более точную локализацию известной проблемы либо обоснованное снятие подозрения. Сам факт запуска инструментов критерием не служит.
4. Для каждого дополнительного инструмента записано, какую полезную информацию он добавил и сколько стоил. Если решение не изменилось и обоснование не стало существенно точнее, инструмент не включается в минимальный набор следующего запуска.
5. Первый результат получен штатными командами и отчётами, без написания анализатора, обвязки или преобразователей. Потребность в собственном коде оформлена как отдельное продолжение с конкретным ожидаемым результатом.

В итоговом отчёте показать количество просмотренных кандидатов, подтверждённых полезных находок, оправданных особенностей и неразрешённых случаев. Проверка короткого списка не оценивает полноту обнаружения всех проблем и не даёт статистической точности метода.

Возможны три исхода: **повторить минимальный набор** на другом проекте; **сузить или изменить метод** из-за шума и затрат; **остановить расширение**, если ручной разбор отвечает на вопрос дешевле. Даже успешный пилот обосновывает первичную оценку в выбранных условиях. Переход к регулярному мониторингу, CI-ограничениям и проектированию новых границ требует отдельного решения.
