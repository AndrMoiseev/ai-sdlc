# Open Code Review: что использовать для улучшения ревью в sdd-apply

**Да, использовать можно.** Самые полезные заимствования: проверяемый учёт охвата изменения, адресные правила по языку и типу файла, подтверждение находок через связанный код и проверка их привязки к исходникам. Всё это можно выполнять средствами текущего агентского хоста, сохраняя существующих reviewer/verifier в `sdd-apply`.

У Open Code Review (далее OCR) есть и готовый режим **delegation**: CLI выбирает файлы и выдаёт правила, а анализ выполняет агент хоста. Для этих команд OCR не нужен отдельный LLM endpoint. Однако delegation не переносит автоматически весь конвейер полноценного OCR: группировку через LLM, обработку комментариев, проверку позиций и учёт результатов должен обеспечить наш процесс. [Delegate skill][delegate-skill], [реализация CLI][delegate-cli].

**Рекомендация:** сначала усилить собственный протокол reviewer небольшими механизмами, затем сравнить его с необязательным адаптером `ocr delegate`. Полностью подключать управляемый OCR-конвейер или заменять им независимое ревью SDD оснований пока нет. Улучшение качества на наших задачах необходимо измерить; чтение исходников подтверждает применимость механизмов, но не величину эффекта.

## 1. Границы исследования

Изучен upstream-коммит `8eb83340a487b1150af00701b94f01af97e4b4d6` от 16 октября 2026 года и авторский пакет `skills/sdd-apply` на локальном коммите из заголовка. Исследованные локальные файлы пакета не имели изменений относительно HEAD. Установленные копии в `.agents/skills` не использовались как источник контракта. Внешние ссылки закреплены за upstream SHA; относительные локальные ссылки ведут к текущим файлам, для воспроизведения нужен `local_commit`.

Исследование статическое: прочитаны код, prompts, правила, тесты и документация. OCR не устанавливался и не запускался; его тесты, benchmark и поведенческие evals SDD не выполнялись. Исходники скачаны в системный TEMP вне репозитория и коллекций скиллов. Применены [sdd-skill-conductor][conductor], [SOP][sop] и требования к [хранению runtime-данных][runtime]. Пакеты скиллов не изменялись, установка и упаковка не проводились; это не заключение о готовности стороннего скилла к установке.

Фраза «в рамках текущего агента» допускает два прочтения:

| Ограничение | Вывод |
|---|---|
| Сохранить текущий хост, инструменты и его native reviewer; не вводить отдельного LLM-провайдера OCR | Совместимо и с переносом механизмов, и с `ocr delegate` |
| Весь анализ выполняет тот же автор в том же контексте, без независимого reviewer | Технически delegation это позволяет, но такой результат не соответствует действующему контракту `sdd-apply` |

Второе ограничение потребовало бы отдельного решения об изменении SDD: сейчас роли проверки должны быть независимы от авторов, а отсутствие свежего контекста блокирует зависимые от роли действия. В предлагаемом варианте уже назначенный reviewer вызывает OCR CLI; дополнительный пул OCR-агентов не нужен. [Контракт ролей][roles], [последовательное выполнение][sequential].

## 2. Из чего складывается качество OCR

OCR разделяет подготовку входа, анализ моделью и обработку результата. Это полезная архитектура, но не все её части детерминированы.

| Механизм | Что подтверждено исходниками | Значение для SDD |
|---|---|---|
| Отбор файлов | Общий selector классифицирует файлы и причины исключения | Можно сверять ожидаемый и фактический охват |
| Подбор правил | Правила выбираются по пути; есть слои custom/project/global/system и встроенные языковые документы | Загружать конкретные проверки вместо общего длинного checklist |
| Группировка | Для небольших изменений возможна локальная группировка; более крупные наборы группирует LLM, с fallback и ограничением размера | Совместно рассматривать интерфейс, реализацию и потребителей |
| Поиск контекста | Prompts требуют прочитать связанный код, когда фактов недостаточно | Находка должна опираться на путь выполнения, а не только на подозрительную строку |
| Привязка комментария | Сопоставление фрагмента с diff/файлом; попытка переноса в другой файл при единственном совпадении; затем возможен LLM fallback | Часть проверки координат можно вынести из модели |
| Проверка комментариев | Отдельный LLM-проход отбрасывает ограниченный класс фактически неверных замечаний | Полезно отделить поиск проблемы от проверки утверждения |
| Учёт выполнения | Manifest различает complete/partial/failed/skipped и результаты по выбранным файлам | Нулевое число находок не доказывает завершённое ревью |

Источники: [selection][selection], [resolver правил][rules], [grouping][grouping], [основной prompt][main-prompt], [позиционирование][positions], [обработка комментариев][comment-loop], [фильтр][filter-prompt], [manifest][manifest].

Встроенные правила содержат полезные условия применимости. Например, Python-проверки требуют установить, что вход действительно контролируется атакующим, подтвердить конкурентный вызов перед заявлением о race condition и проверить вызывающий код перед замечанием о `None`. Эти уточнения помогают уменьшить ложные срабатывания. При этом тот же документ включает стилистические рекомендации и собственную трактовку блокирующих проблем. Это база гипотез для reviewer, а не готовая нормативная политика SDD. [Python rules][python-rules].

Фильтр комментариев тоже нельзя описывать как универсальную проверку истинности. Он видит diff, а не весь контекст первоначального агента, и по умолчанию сохраняет замечания. Для memory safety, concurrency и ряда других тем предусмотрено безусловное сохранение даже при сомнениях фильтра. Его задача уже, чем полноценное подтверждение дефекта. [System prompt][filter-system], [правила фильтра][filter-prompt].

## 3. Что реально даёт delegation

Базовый интерфейс для будущего эксперимента:

```text
ocr --version
ocr delegate preview --repo <candidate-root> --format json
ocr delegate rule --repo <candidate-root> --format json <path1> <path2>
```

Команды приведены как пример интеграции, в этом исследовании они не выполнялись. Workspace preview подходит для незакоммиченного кандидата; для диапазона есть `--from`/`--to`, для коммита `--commit`. Range использует merge-base: произвольно выбранная базовая ветка может дать область шире одной SDD-задачи. Поэтому scope задаётся нашим снимком и ownership, а не самим фактом успешного preview. [Delegate skill][delegate-skill], [CLI][delegate-cli], [SDD candidate][verification].

Preview возвращает метаданные режима, выбранные файлы и исключения. `rule` объединяет правила с одинаковыми источником, pattern и текстом, чтобы не повторять их для каждого файла. Diff, чтение полных файлов и оценку проблем выполняет агент. Для tracked workspace-файлов инструкция использует diff относительно HEAD, для untracked — чтение содержимого. Идентификатор checklist включает `(path, status)`: staged-удаление и untracked-воссоздание могут иметь один путь. JSON preview/rule имеет `schema_version: "1"`; документация указывает `--format` начиная с v1.9.0. Для range/commit обеим командам нужно передавать одинаковые refs и конфигурацию правил: resolver может читать содержимое target ref для определения языка. [Delegate skill][delegate-skill], [CLI][delegate-cli], [группы правил][rule-groups].

**Что delegation не обеспечивает само:** завершение проверки каждого файла, соответствие находок AC, независимость reviewer, правильность цитат, итоговый `review_result` и сохранность замороженного кандидата. Это обязанности агента и адаптера SDD. Instructions upstream требуют checklist, но команды preview/rule сами не исполняют его. [Delegate skill][delegate-skill], [SDD roles API][roles-code].

Практические ограничения:

- **Фильтры уже, чем scope SDD.** Selector исключает binary, секретные пути, некоторые расширения, default-path patterns и удалённые файлы. Среди default exclusions есть тестовые пути; `.md` отсутствует в allowlist. `sdd-apply` требует проверять также тесты, удаления и конфигурацию. Нужна сверка всех исключений с собственным полным перечнем изменений. Более того, untracked-файлы в некоторых provider-excluded каталогах не перечисляются даже среди исключений preview: одного объединения `reviewable_files` и `excluded_files` недостаточно. [Selection][selection], [default exclusions][default-exclusions], [расширения][extensions], [preview][preview], [SDD reviewer][reviewer].
- **Размер контекста остаётся нашей задачей.** Делегированный режим не запускает managed review и не получает автоматически его управление контекстом. Большие diff нужно читать целиком ограниченными порциями, сохраняя статус каждого файла. [Delegate skill][delegate-skill].
- **Группы правил не являются группами зависимостей.** Два Python-файла могут получить один checklist, но не относиться к одному контракту; интерфейс и его реализация могут попасть в разные группы правил. [Rule groups][rule-groups], [semantic grouping][grouping].
- **Правила зависят от окружения.** Для воспроизводимости необходимо сохранять их текст, источник и версию, включая project/global overrides. Один upstream SHA не фиксирует эффективные правила пользователя. User rule по умолчанию заменяет system rule; добавление встроенного языкового правила требует `merge_system_rule: true`. Широкое пользовательское правило без этого параметра может убрать полезные проверки. [Rule resolver][rules], [документация правил][rules-doc].
- **Нет отдельного endpoint не означает нулевую стоимость.** Анализ расходует контекст и токены текущего хоста. Уменьшение затрат относительно существующего SDD не измерено.

Для готового бинарника не нужен Go toolchain; сборка исследованного исходника объявляет Go `1.26.9`. README указывает Git `>= 2.41`. Для адаптера следует проверять установленную версию OCR и поддерживаемую JSON-схему, а не зависеть от незафиксированного `latest`. NPM launcher поддерживает автоматическое обновление; закреплённый бинарник либо явно отключённое автообновление нужны для воспроизводимого сравнения. [go.mod][go-mod], [README][readme], [delegate CLI][delegate-cli], [установка и обновления][installation].

## 4. Что уже есть в sdd-apply и где полезно усиление

SDD уже обеспечивает свежие роли, независимые проверки, неизменность кандидата, связь с REQ/AC/design, отдельную оценку целостности тестов, бюджеты повторного ревью и журнал технического долга. Повторять эти механизмы вторым оркестратором не требуется. [Roles][roles], [reviewer][reviewer], [verification][verification], [review policy][review-policy].

Однако текущий обработчик `review_result` проверяет наличие полей finding, кандидата, `test_integrity` и trace. В нём нет обязательной машинно проверяемой таблицы исхода для каждого изменённого файла и нет сверки координат цитаты с байтами кандидата. Проверка `proof` устанавливает структуру доказательства; истинность и применимость остаются ответственностью reviewer и координатора. Это конкретные точки для усиления, а не утверждение, что нынешние агенты систематически пропускают файлы. [roles.py][roles-code], [review_policy.py][policy-code].

| Предложение | Приоритет | Как внедрить в существующий процесс | Ожидаемая польза и предел |
|---|---|---|---|
| Manifest охвата всего изменения | Высокий | Список файлов из SDD scope до ревью; результат для каждого после | Делает пропуски видимыми; не доказывает глубину чтения |
| Адресные правила с условиями применимости | Высокий | Короткие references по языку/типу изменения, загрузка reviewer по условию | Помогает искать конкретные дефекты; качество правил нужно проверять |
| Подтверждение находки | Высокий | Сценарий ошибки, источник данных/вызов, последствия, проверка существующей защиты | Уменьшает спекулятивные замечания; эффект пока гипотеза |
| Фрагмент кода и координаты | Средний | Проверять путь, сторону diff, диапазон и совпадение цитаты в frozen candidate | Устраняет часть ошибок адресации; не доказывает сам дефект |
| Проверка связанных файлов | Средний | Проход по интерфейсу, реализации, потребителю, тесту, конфигурации | Помогает увидеть нарушения между файлами; глобальные связи всё равно надо искать |
| Полный managed OCR | Низкий для этой задачи | Отдельный LLM-конвейер и преобразование его результатов | Дублирует orchestration и выходит за выбранное ограничение |

При переносе manifest нельзя наследовать знаменатель OCR без изменений. В managed OCR selected-набор фиксируется после отбора; удалённые файлы не направляются в review subtasks. Его `complete` относится к выбранному набору, а не обязательно ко всему изменению SDD. [Dispatch][agent], [manifest][manifest].

## 5. Предлагаемый протокол reviewer

Ниже проект будущего изменения, не описание уже реализованного API.

1. После `review_start` получить текущий candidate, нормативные источники и полный перечень принадлежащих задаче изменений. Зафиксировать старый/новый путь, тип изменения, отпечаток содержимого и требуемую форму проверки. Внешний preview используется только как дополнительная классификация.
2. Разбить область на небольшие группы по контрактам и связям. Для каждой загрузить применимые правила, diff и необходимый контекст. Выполнить собственный проход для каждого файла; затем проверить связи между ними. Удаления и ослабление тестов входят в этот процесс.
3. Для предполагаемого дефекта установить воспроизводимый сценарий или проверяемую цепочку данных. Проверить вызывающий код, существующие guards и намерение изменения по AC/design. Недостаток доказательств не превращать в подтверждённый дефект.
4. Отдельно сверить факты и координаты находки. Для удаления использовать старую сторону diff либо адресуемый участок изменения, не выдумывать строку в новом файле. Несовпавшую цитату уточнить, сохраняя исходное утверждение для проверки.
5. Сопоставить находку с действующей review policy. Только доказанное нарушение принятого AC, архитектурного решения или проектного правила получает `blocker`; остальные обоснованные предложения попадают в долг. Для конкретного пробела контрактных доказательств применяется `more_checks`.
6. Перед `review_result` проверить полноту manifest и неизменность кандидата. Непроверенный обязательный участок оставляет ревью незавершённым. Пустой findings допустим после полного прохода; пустой/усечённый вход не является основанием для `pass`.

Минимальный проект артефакта охвата: `candidate`, версия протокола/правил, список `{old_path, path, change_kind, fingerprint, status, evidence_ref, reason}`. Статусы должны различать проверенный участок, проверку другим способом и невыполненную проверку. Название `skipped` само по себе не разрешает пропуск. Для binary можно зафиксировать проверку метаданных или профильным инструментом; отсутствие возможности проверить значимое изменение остаётся ограничением результата.

Детерминированная часть проверяет полноту и непротиворечивость записей, существование адресуемого кода и актуальность снимка. Семантику подтверждает reviewer. Делать из наличия поля `evidence_ref` доказательство реального анализа нельзя. Это тот же предел, который уже описан в контракте host attestations SDD. [Роли][roles], [candidate][verification].

Такой протокол помещается внутрь одного существующего раунда ревью. Повторная substantive review после исправлений остаётся новым раундом по текущему бюджету; внутреннее разбиение на группы не должно обнулять счётчик. [Reviewer][reviewer], [roles.py][roles-code].

## 6. Что не переносить буквально

**Политику severity и исправлений.** Upstream Python rules предлагают считать correctness/security блокирующими; delegate skill при запросе review-and-fix разрешает прямые исправления High/Critical. В SDD reviewer не редактирует кандидата, severity не заменяет `proof`, рекомендации не запускают автоматический repair. Ошибка классификации здесь меняет утверждённый scope. [Python rules][python-rules], [delegate skill][delegate-skill], [SDD policy][review-policy].

**Ограничение только новым кодом.** Main/plan prompts исключают удалённый код из предмета замечаний. В SDD удаление проверки прав, негативного теста или обязательного файла может быть главным дефектом. Можно адресовать находку к изменению, сохранив анализ того, какое поведение было потеряно. [Main prompt][main-prompt], [plan prompt][plan-prompt], [SDD reviewer][reviewer].

**Молчаливое отбрасывание сомнительных находок.** Delegate skill предлагает удалять вероятные false positives без сообщения. Для эксперимента полезнее хранить краткий внутренний журнал отклонённых гипотез с причиной: иначе нельзя измерить, убирает ли дополнительный проход шум или реальные дефекты. В пользовательский findings попадают только обоснованные замечания; журнал нужен для оценки, а не для увеличения шума отчёта. [Delegate skill][delegate-skill].

**Полный каталог правил и prompts.** Копирование всех языковых документов увеличит сопровождение и загрузку контекста. Начать следует с языков реальных проектов и проверок, которые дают измеримый прирост. При переносе текста или кода зафиксировать upstream SHA и происхождение; репозиторий распространяется под Apache-2.0, условия воспроизведения и распространения находятся в его LICENSE. [Правила][rules], [лицензия][license].

## 7. Как проверить пользу до интеграции

README сообщает о более высоких precision/F1 и меньшем расходе токенов относительно general-purpose agent, одновременно признавая более низкий recall. Это заявление авторов о собственном benchmark. Оно не доказывает выигрыш delegation или модифицированного `sdd-apply`: отличаются prompts, scope, способы фильтрации, модель и организация вызовов. [README и ссылка на AACR-Bench][readme].

Данные и evaluator AACR-Bench публичны. Дополнительно изучен evaluator на коммите `ee9d7fef70ef31acea2ff7ae316ce0a9575fe4df`: его OCR adapter запускает именно `ocr review`. Текущая документация метрик описывает семантическое сопоставление на уровне файла без жёсткого ограничения по line/side, а отсутствующие result files исключаются из знаменателей. Поэтому внешний benchmark можно использовать дополнительным набором, но завершённость всех запусков и точность адресации надо измерять отдельно. Эти свойства относятся к исследованному evaluator; без зафиксированной конфигурации авторских прогонов нельзя автоматически приписать их каждой опубликованной таблице. [Данные][benchmark-data], [OCR adapter][benchmark-ocr], [метрики][benchmark-metrics].

Предлагаемый эксперимент:

| Вариант | Что меняется |
|---|---|
| A: baseline | Текущий reviewer `sdd-apply` |
| B: перенос механизмов | Manifest, адресные правила, проверка гипотез и координат; OCR не установлен |
| C: delegate adapter | Тот же протокол B, но preview и rules приходят из закреплённого OCR CLI |

Использовать одинаковые замороженные кандидаты, модель, хост и права. Для каждого запуска нужен свежий reviewer-контекст, независимый от автора и других вариантов. Начать с пилота примерно на 12–20 изменениях разных размеров; этого достаточно для поиска явных проблем, но недостаточно для универсальных выводов. Отложить часть случаев для проверки после правок протокола. Несколько повторений на случай покажут нестабильность. При реализации скилла следовать baseline/held-out-процессу [conductor][conductor].

Набор должен включать: реальный дефект на границе файлов; удалённую проверку; ослабленный тест; чистое изменение без дефектов; большое изменение с ошибкой в конце; partial staging и untracked; rename/удаление-воссоздание; конфигурацию/binary; ложноположительный случай с upstream validation; изменение кандидата после preview.

Измерять отдельно:

- долю найденных известных дефектов и долю подтверждённых замечаний;
- пропуски критичных контрактных нарушений и ошибочные блокировки;
- охват всех обязательных файлов, корректность координат и сохранение test integrity;
- количество рекомендаций и трудозатраты на их разбор;
- суммарные токены, wall time, tool calls и повторные repair/review-циклы.

Условия принятия: отсутствие новых пропусков критичных дефектов и ослабления SDD-контракта на отложенных случаях; устранение необъяснённых пропусков файлов; улучшение хотя бы одного показателя качества без неприемлемого роста стоимости. Допустимый рост времени/токенов определить до запуска. Автоматическая полнота manifest проверяется fixtures; семантическое качество оценивается по заранее размеченным дефектам и слепому разбору спорных находок.

## 8. Решение по результатам исследования

**Начать с варианта B:** manifest охвата, проверка применимости конкретных правил и подтверждение находок. Это усиливает уже существующего reviewer и сохраняет текущий агентский хост. Первая реализация затронет reviewer reference/contract, валидацию результата и профильные тесты; основной `SKILL.md` достаточно оставить навигатором.

**Вариант C оставить дополнительным экспериментом.** Он полезен, если готовый каталог правил OCR окажется качественнее и дешевле в сопровождении собственного. При этом собственный scope SDD, связь с candidate и итоговая policy остаются обязательными. Если C не улучшит результаты относительно B, новая CLI-зависимость не оправдана.

Связанное исследование [Code Quality][previous] посвящено в основном автоматическому сбору сигналов анализаторов и тестов. OCR дополняет его методикой самого LLM-ревью. Ни один из инструментов не заменяет принятую спецификацию и независимую проверку реализации.
