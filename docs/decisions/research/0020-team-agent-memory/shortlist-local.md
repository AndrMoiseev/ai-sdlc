# Локальная командная память для агентов. Топ-5 с источником истины в Git

**Для команды с несколькими репозиториями я бы начал с LangChain OpenWiki.** Из этой пятёрки он лучше всего связывает утверждение с конкретными строками и возвращает его на проверку, когда строки меняются. Если значительная часть знаний живёт в Confluence, заметках и материалах разных проектов, первым я бы взял **nvk/llm-wiki**. Он хранит исходные документы рядом с выводами и помогает агенту сопоставлять свидетельства из нескольких источников. [OpenWiki, проверка утверждений](https://github.com/langchain-ai/openwiki/blob/v0.9.0/README.md#grounded-claims) · [llm-wiki, работа с источниками](https://github.com/nvk/llm-wiki/blob/d60674ff785e5c6d35322657d7839a7c0bdd3ca7/AGENTS.md)

**Условие отбора — восстановление из чистого клона.** На другой машине агент должен найти принятое знание, открыть его основание и увидеть в Git, как и почему его исправили. Для этого команда коммитит исходные тексты, принятые правки, их основания и нужные журналы. Markdown, YAML, JSON и JSONL подходят. Поисковый индекс можно построить заново. Все пять инструментов бесплатны и допускают запуск на рабочей машине во внутреннем контуре. Локальный сервер допустим, модель может быть внешней. Поиск за пределами исходного обзора добавил в пятёрку OpenWiki, nvk/llm-wiki и Tigerless agent-memory. Звёзды сверены 21 ноября 2026 года в 12:13 МСК. Все проекты преодолели порог в 100 звёзд. Порядок учитывает качество свидетельств, актуализацию, автономность и поиск между проектами. [Метод получения числа звёзд](https://docs.github.com/en/rest/repos/repos#get-a-repository)

## 1. LangChain OpenWiki · 18 046 звёзд · MIT

В режиме работы с репозиторием в Git попадает каталог `openwiki/`. Рядом со страницами в Markdown лежат `openwiki/.claims/**/*.json` с формулировками утверждений, ссылками вида `repo://src/server.ts#L40-L82` и хешами фрагментов. При `openwiki --update` изменение или исчезновение основания возвращает затронутое утверждение агенту. Он может подтвердить, переписать или отозвать его. Хеш подтверждает, что цитируемый фрагмент сохранился. Насколько он обосновывает вывод, оценивает агент. [Формат утверждения](https://github.com/langchain-ai/openwiki/blob/v0.9.0/src/claims/brains/code/store.ts#L41-L79) · [проверка при обновлении](https://github.com/langchain-ai/openwiki/blob/v0.9.0/README.md#grounded-claims)

После клонирования поиск через MCP строит полнотекстовый индекс в памяти. На новой машине `openwiki link` объединяет локальные клоны для общего поиска. Свидетельства каждого утверждения проверяются в пределах его репозитория. Порог остановки при смысловом противоречии задаёт команда. Для такой же проверки материалов Confluence в репозиторий потребуется положить их текстовые копии. [Реализация поиска](https://github.com/langchain-ai/openwiki/blob/v0.9.0/src/retrieval/wiki.ts#L607-L672) · [связанные репозитории](https://github.com/langchain-ai/openwiki/blob/v0.9.0/README.md#create-wiki-workspaces) · [границы проверки и коннекторы](https://github.com/langchain-ai/openwiki/blob/v0.9.0/README.md#connect-your-sources)

## 2. nvk/llm-wiki · 1 559 звёзд · MIT

Для команды подходит отдельный Git-репозиторий с реестром `wikis.json` и тематическими вики в `topics/`. В каждой теме `raw/` содержит исходные материалы, `wiki/` — выводы со ссылками на источники и оценкой уверенности, `log.md` — историю работы. Для подробного журнала есть `.session-events.jsonl`. После клонирования агент начинает с `_index.md`. Углублённый поиск охватывает также оригиналы и соседние тематические вики. Обязательной БД нет. Важно выбрать общий каталог при настройке, поскольку проектную `.wiki/` авторы рекомендуют добавлять в `.gitignore`. [Структура файлов и журнала](https://github.com/nvk/llm-wiki/blob/d60674ff785e5c6d35322657d7839a7c0bdd3ca7/AGENTS.md#L26-L116) · [режимы поиска](https://github.com/nvk/llm-wiki/blob/d60674ff785e5c6d35322657d7839a7c0bdd3ca7/AGENTS.md#L535-L545)

При разборе спорного тезиса агент может составить таблицу свидетельств за и против. Обычная статья хранит оценку уверенности целиком. Ссылку на точную строку для конкретного вывода нужно сохранить явно. Команда `librarian scan` отмечает статьи, у которых постарели основания или давно не было проверки. Однозначные ошибки ссылок агент может исправлять сам, неоднозначные оставляет на разбор. [Разбор тезисов](https://github.com/nvk/llm-wiki/blob/d60674ff785e5c6d35322657d7839a7c0bdd3ca7/AGENTS.md#L596-L601) · [проверка актуальности](https://github.com/nvk/llm-wiki/blob/d60674ff785e5c6d35322657d7839a7c0bdd3ca7/AGENTS.md#L839-L851) · [правила исправлений](https://github.com/nvk/llm-wiki/blob/d60674ff785e5c6d35322657d7839a7c0bdd3ca7/claude-plugin/skills/wiki-manager/references/linting.md#L461-L470)

## 3. MEX · 1 797 звёзд · MIT

Спецификации, решения и предложения хранятся в `.mex/` в Markdown, принятые изменения также попадают в текстовые журналы. Тезис можно привязать к символу в коде. MEX различает изменившиеся, перемещённые, пропавшие и неоднозначные привязки. В чистом клоне `npx mex-agent@0.8.5 graph rebuild` строит граф из кода, а `npx mex-agent@0.8.5 wiki rebuild-index` восстанавливает поиск по записям. Агент может читать оба индекса через CLI. [Порядок восстановления](https://github.com/mex-memory/mex/blob/v0.8.5/README.md#join-a-repository-already-using-mex-08) · [устройство хранения](https://github.com/mex-memory/mex/blob/v0.8.5/README.md#canonical-markdown-local-indexes) · [проверка привязок](https://github.com/mex-memory/mex/blob/v0.8.5/README.md#grounding-and-drift)

Особенно хорошо подходит для спецификаций одного проекта. Штатный процесс поручает агенту подготовить исправление, а человеку — одобрить публикацию и замену ранее принятого основания. Для автономного цикла это дополнительные обращения к человеку. Общие решения можно держать в командном репозитории, при этом каждый граф кода охватывает свой репозиторий. [Границы полномочий агента](https://github.com/mex-memory/mex/blob/v0.8.5/README.md#human-approval-boundaries)

## 4. Basic Memory · 4 652 звезды · AGPL-3.0

Подходит, если у команды уже есть Markdown и агенты должны читать и редактировать его через MCP. Наблюдения, ссылки `[[…]]`, даты действия и произвольные поля хранятся в самих файлах. На новой машине `bm project add team <путь-к-клону>` регистрирует каталог и индексирует его. Для повторной сборки есть `bm project index team`. Обмен между компьютерами идёт через Git. [Формат заметок](https://github.com/basicmachines-co/basic-memory/blob/v1.0.0/NOTE-FORMAT.md) · [индексация проекта](https://docs.basicmemory.com/local/user-guide#syncing-and-updates)

Проверка `expected_checksum` защищает от перезаписи чужой параллельной правки. Ссылку на версию источника, оценку силы свидетельства и причину пересмотра записывает сам агент. Изменение процитированного фрагмента требует отдельной проверки со стороны агента. [Чтение и правки через MCP](https://docs.basicmemory.com/reference/mcp-tools-reference) · [наблюдения и связи](https://docs.basicmemory.com/concepts/observations-and-relations)

## 5. Tigerless agent-memory · 4 324 звезды · MIT

Сильная сторона — память о работе агентов. Запись в Markdown хранит период действия и связь с заменившей её записью. `mem trace` открывает исходный диапазон сообщений. Чтобы это работало у коллег, в Git нужны также `archive/sessions/`, `archive/provenance/` и журнал решений `dream-reports/decisions.md`. После клонирования `mem --store <путь-к-клону> rebuild` пересоздаёт поисковую БД. Чтобы восстановить прежнюю формулировку после правки на месте, её версию нужно закоммитить. [Хранилище](https://github.com/tigerless-labs/agent-memory#the-store) · [трассировка свидетельств](https://github.com/tigerless-labs/agent-memory/blob/main/docs/design/raw-evidence-reads.md) · [журнал решений](https://github.com/tigerless-labs/agent-memory/blob/main/packages/core/src/agent_memory/core/ledger.py)

Фоновая обработка может самостоятельно применять часть исправлений. Обязательную передачу прямого противоречия человеку придётся задать отдельно. При первоначальной загрузке разнородных документов преимуществ меньше, чем при работе с сессиями. Запрос целиком из кириллицы даёт пустую выдачу в штатном лексическом поиске. Качество опционального векторного поиска на русском требует проверки. [Полномочия фоновой обработки](https://github.com/tigerless-labs/agent-memory/blob/main/docs/design/management-operation-boundaries.md) · [токенизация](https://github.com/tigerless-labs/agent-memory#cjk-chinese-memory) · [обработка пустого запроса](https://github.com/tigerless-labs/agent-memory/blob/main/packages/core/src/agent_memory/core/search_index.py#L102-L105)

## Как сохранить проверяемость решений

Команде стоит различать, **что именно доказывает источник**. Для вывода о поведении реализации строка в зафиксированном коммите GitLab весит больше общего описания. Для вывода о согласованном требовании основанием служит утверждённая версия спецификации. В первом случае в Git достаточно сохранить ссылку с коммитом, путём и строками, если исходный репозиторий также доступен. Во втором для страницы Confluence полезно сохранить её адрес, версию и существенный фрагмент в текстовом файле. Тогда свидетельство можно перечитать после следующей правки страницы.

Порог эскалации остаётся правилом команды. Однозначную правку агент может записать вместе с основанием и причиной замены. Если в одном окружении и одной версии два источника дают противоположные ответы, агент сохраняет оба и приостанавливает решение по этому вопросу до ответа владельца. При подготовке спецификации поводом обратиться к человеку может быть и неоднозначность требования. При реализации по принятой спецификации агент продолжает независимые части работы.

Лидер общего рейтинга GBrain выбыл по конкретной причине. Из Markdown он восстанавливает страницы, но решения об отзыве фактов и часть истории остаются только в БД. После потери БД из одного клона нельзя установить, какие утверждения были отозваны. Порядок в этом исследовании основан на документации и исходном коде проектов. Установку и восстановление на тестовом корпусе я не запускал.
