# Пилот локального сбора событий sdd-apply

Дата: 2026-11-15. Статус: проект первой итерации; реализация и запуски не выполнены.

Основание: [исследование процессных метрик](research.md). Пользователь уточнил результат: нужен набор событий с конкретными полями и описанием сбора, пока только локального. Для журнала принят английский термин `log`.

## Результат и границы

Результат итерации — проверенный контракт событий, автоматическая запись JSONL в домашнем каталоге и локальная проверка полноты и корректности записей. По небольшим контрольным примерам должно быть понятно, как из событий получить выбранные счётчики. Полноценный анализатор, сравнение версий, загрузчик и сервер в эту итерацию не входят.

Основной вопрос: **можно ли без чтения переписки восстановить ход выполнения и посчитать выбранные повторы, сохранив различие между новой работой, повтором запроса и использованием старого результата?**

Рабочее допущение об отказе сбора: разработка продолжается, ошибка журнала явно возвращается вызывающему коду. Это рекомендация автора плана; отдельного выбора пользователя по этой развилке пока нет.

## 1. Где и когда собирать

Предлагаемый корень: `<домашний каталог>/.ai-sdlc/process-metrics/`. Домашний каталог определяет API ОС, например `Path.home()`, а не текущий каталог репозитория. Для пилота допускается явное переопределение корня на другой локальный каталог. Корень разрешается один раз при открытии сессии и сохраняется в её локальных настройках.

```text
<домашний каталог>/.ai-sdlc/process-metrics/
  sessions/
    <process_session_id>/
      session.json
      <process_log_id>.jsonl
      <другой_process_log_id>.jsonl
```

`session.json` содержит только настройки записи: `process_session_id`, абсолютный `root`, ID текущего сегмента `process_log_id`, `schema_version: 1`. Он заменяется атомарно при смене сегмента; это служебный файл, а не история процесса. Журналом служат только JSONL-файлы. История подтверждённых переходов остаётся в штатном `execution` проекта и используется для сверки и восстановления.

Границы сессии:

- Оркестратор явно открывает сессию при входе в `sdd-apply` для начала или продолжения работы. Генерируется случайный `process_session_id`; он передаётся всем командам этого интервала. Одна сессия работает с одним хранилищем выполнения; пересмотр плана внутри него допускается.
- Отдельный вызов `execute.py`, новая оболочка, запуск роли и сокращение контекста при сохранённой идентичности оркестратора не открывают новую сессию. Новый контекст оркестратора или отдельное возобновление работы открывает новую сессию с существующим `run_id`.
- При штатном завершении, возврате из-за блокера или явной остановке сессия закрывается. Это не обязательно завершение выполнения плана.
- При падении процесса событие закрытия может отсутствовать. Таймаут и конец файла не превращаются в событие успешного завершения.

Сбор включается для новых выполнений, выбранных для пилота. Импорт старых выполнений, миграции и чтение прежних версий нового формата не предусмотрены.

## 2. Формат строки и идентичность

UTF-8 без BOM; одна строка — один JSON-объект без внутренних переводов строки, завершённый LF. Все поля из таблиц обязательны, если прямо не сказано иное. `null` означает известное отсутствие значения; пустые массивы означают наблюдаемое отсутствие элементов. Неизвестное значение нельзя заменять нулём. Неописанные поля не допускаются в схеме пилота.

| Поле строки | Тип | Значение и источник |
| --- | --- | --- |
| `schema_version` | integer, только `1` | Версия всего контракта строки, включая вложенное событие |
| `process_log_id` | string, UUID в 32 hex-символах | Случайный ID сегмента, совпадает с именем файла |
| `sequence` | integer ≥ 1 | Порядок добавления строк внутри сегмента; присваивает writer под блокировкой |
| `recording_session_id` | string, UUID в 32 hex-символах | Сессия, которая сейчас записывает строку |
| `recorded_at` | string, RFC 3339 UTC | Время фактического добавления строки, получает writer |
| `process_event` | object | Неизменяемое содержимое факта по следующей таблице |

| Поле `process_event` | Тип | Значение и источник |
| --- | --- | --- |
| `process_event_id` | string, 64 hex-символа | Стабильный ID факта; одинаков при повторной доставке |
| `type` | enum | Один из четырёх типов раздела 3 |
| `occurred_at` | string, RFC 3339 UTC | Время фиксации факта у источника; при восстановлении не меняется |
| `process_session_id` | string, UUID в 32 hex-символах | Сессия, в которой возник факт; может отличаться от `recording_session_id` |
| `run_id` | string или null | Существующий ID выполнения; до инициализации и в ещё не привязанной сессии — `null` |
| `task_id` | string или null | Существующий ID задачи; у событий уровня выполнения и сессии — `null` |
| `data` | object | Поля соответствующего типа события |

ID вычисляется существующей функцией `common.digest` от JSON-массива:

- инициализация: `["process_event", 1, "execution_initialized", run_id]`;
- переход: `["process_event", 1, "execution_transition_committed", исходный_run_id_из_запроса, исходный_event_id]`;
- граница сессии: `["process_event", 1, "process_session_started", process_session_id]` либо тип `"process_session_finished"`.

`common.digest` использует SHA-256 от UTF-8 JSON с `ensure_ascii=True`, `sort_keys=True`, `separators=(",", ":")`. Исходные ID берутся из движка, а не генерируются заново при публикации. Разные типы в массиве разделяют пространства идентификаторов без новых ограничений на native `event_id`.

Расчёт устраняет повторы по `process_event_id`. Содержимое `process_event` у повторов должно совпадать целиком; различие — ошибка данных. `recorded_at`, `recording_session_id`, `sequence` и ID сегмента могут отличаться. Внутри хранилища исполнения порядок переходов задаёт `revision`, не время доставки; `sequence` не задаёт порядок разных файлов.

## 3. Четыре типа событий

### `process_session_started`

Создаётся локальным кодом открытия сессии до первой изменяющей команды. Время получает код, а не языковая модель. `task_id = null`; при продолжении `run_id` берётся из прочитанного состояния, при новом запуске он пока `null`.

| Поле `data` | Тип | Как получить |
| --- | --- | --- |
| `mode` | `start` или `resume` | Явный режим входа оркестратора |
| `host` | `codex`, `claude-code` или `other` | Адаптер запуска |
| `host_version` | string или null | Достоверные данные хоста; при недоступности `null` |
| `os` | `windows`, `linux`, `macos` или `other` | API ОС |
| `skill_fingerprint` | string, SHA-256 | Отпечаток фактически используемого пакета `sdd-apply` |
| `shared_fingerprint` | string SHA-256 или null | Отпечаток используемого `sdd-shared`; `null`, если источник не установлен достоверно |

Правило отпечатка: отсортированный по относительному POSIX-пути массив `[путь, sha256_байтов]` для `SKILL.md` и файлов под `agents`, `flows`, `references`, `scripts`, `schemas`, затем `common.digest` массива. Включаются `.md`, `.py`, `.json`, `.yaml`, `.yml`, `.lock`; исключаются кэши, ссылки на файлы вне пакета и результаты выполнения. Вычислить один раз при открытии сессии. Изменение состава этого правила меняет версию схемы. Отпечаток описывает пакет, но не всю конфигурацию проекта.

### `execution_initialized`

Создаётся внутри `state.initialize` вместе с начальным состоянием. Время начала сохраняется отдельно и больше не заменяется `updated_at`. После успешного сохранения событие публикуется в журнал.

| Поле `data` | Тип | Как получить |
| --- | --- | --- |
| `revision` | integer, `0` | Начальная revision состояния |
| `run_status` | string, `active` | Начальное состояние |
| `work_kind` | `change` или `refactoring` | Проверенное `basis.work_kind`, с текущим default `change` |
| `plan_fingerprint` | string, SHA-256 | `common.digest(basis.tasks)`; содержимое задач в журнал не копируется |
| `tasks` | array объектов | По одному объекту для каждой исходной задачи: `task_id: string`, `review_limit: integer`, `test_repair_limit: integer`; значения из созданного состояния |

Начальное состояние всех этих задач — `pending`; затраченные счётчики равны нулю. Для создания нового `run_id` через пересмотр плана используются поля `revised_plan`, описанные ниже; новое событие инициализации с нулевыми затратами для него не придумывается.

### `execution_transition_committed`

Одна запись на каждый подтверждённый native-переход, включая переходы без выбранной метрики. Это позволяет сверять непрерывность revision. Отклонённый запрос записи этого типа не создаёт. Исходные `run_id` и `task_id` берутся из запроса; `occurred_at` — из времени сохранённой записи истории. Время означает фиксацию результата перехода, а не начало команды.

| Поле `data` | Тип | Как получить |
| --- | --- | --- |
| `source_event_id` | string | Native `event.event_id` |
| `transition` | enum native-типов | Native `event.type` |
| `revision` | integer ≥ 1 | Revision после перехода |
| `run_id_after` | string | ID из состояния после перехода; может измениться на `revised_plan` |
| `run_status_after` | `active`, `blocked` или `completed` | Подтверждённое состояние |
| `task_status_after` | enum состояний задачи или null | Состояние задачи запроса после перехода; `null` для уровня выполнения |
| `task_counts_after` | object | Число задач в каждом состоянии после перехода |
| `blocker_reasons_after` | array enum | Уникальные отсортированные категории из `state.blockers[].reason` по разрешённому списку ниже |
| `details` | object | Поля выбранного перехода по таблице ниже; для остальных — `{}` |

`task_counts_after` всегда содержит девять целочисленных неотрицательных полей: `pending`, `running`, `verifying`, `reviewing`, `integrating`, `repairing`, `committing`, `blocked`, `accepted`. Это же множество задаёт ненулевые значения `task_status_after`. Сумма равна числу текущих задач. Общий снимок нужен, поскольку ремонт одной задачи может изменить состояние зависимых задач.

Разрешённые категории блокеров: `review_limit_reached`, `test_repair_limit_reached`, `required_check_unavailable`, `baseline_failed`, `completion_incomplete`, `lost_role`, `other`. Первые шесть сохраняются только при точном совпадении со значением движка, остальные значения превращаются в `other`. Это важно: native `block` допускает свободный `reason`; переносить его текст в журнал нельзя. Пустой список означает отсутствие блокеров уровня выполнения, но не гарантирует отсутствие блокеров отдельных задач.

Полный enum `transition` для схемы 1 соответствует текущему движку: `block`, `resume`, `spec_conflict`, `revised_plan`, `budget_extend`, `role_register`, `role_result`, `verification_result`, `review_start`, `review_result`, `checks_register`, `checks_extend`, `checks_revise`, `check_setup`, `check_run`, `procedure_begin`, `procedure_result`, `candidate`, `start`, `repair`, `commit`, `accept`, `worktree_create`, `worktree_remove`, `worktree_refresh`, `worktree_refresh_resolve`, `integrate`, `transfer`, `finalize`.

В таблице все перечисленные поля `details` обязательны. `string?` и `integer?` допускают `null`; остальные типы — нет.

| `transition` | Поля `details` | Точный источник и ограничение |
| --- | --- | --- |
| `start` | `role_id: string`, `attempt: integer` | `task.executor`, `task.attempt` после успешного перехода |
| `role_register` | `role_id: string`, `role_kind: executor/explorer/reviewer`, `lens_id: string?`, `host: string`, `requested_model: string?`, `requested_effort: string?`, `observed_model: string?` | Сохранённая роль; запрошенные настройки из `agent_selection.launch.model/reasoning_effort`, если есть. `observed_model` в пилоте `null`: нынешний контракт не удостоверяет фактическую модель. Название пресета не подставляется вместо неё |
| `candidate` | `candidate_commit: string`, `stage: task/integration` | SHA из `task.candidate_commit`; `stage` определяется по `task.worktree.integrated`. Это предъявление кандидата, не число различных SHA |
| `check_run` | `stage: baseline/self/independent/integration`, `outcome: baseline_recorded/passed/failed/unavailable`, `evaluated_check_ids: string[]`, `reused_check_ids: string[]`, `failure_counted: boolean` | `stage` из запроса, `outcome` из результата; `evaluated_check_ids` из `result.executed_check_ids`, `reused_check_ids` из `result.reused_evidence[].check_id`. `failure_counted` означает увеличение `test_repair_cycles_started` на 1 этим переходом |
| `review_start` | `role_id: string`, `lens_id: code/verification`, `started: boolean`, `round_id: string?`, `round_number: integer?`, `new_round: boolean`, `reused_lenses: string[]` | Роль и линза из состояния; `started` подтверждает добавление этой роли в `active_reviewers`; `round_id` из `active_review`. `new_round` определяется увеличением `review_rounds_started` на 1. При ответе `blocked` — `started=false`, `new_round=false`, round-поля `null`, список повторно использованных линз пуст |
| `review_result` | `role_id: string`, `lens_id: code/verification`, `round_id: string`, `round_number: integer`, `verdict: pass/changes/more_checks`, `reported_verdict: pass/changes/more_checks`, `round_completed: boolean`, `round_verdict: string?` | Данные конкретной линзы из добавленной записи `task.reviews`, включая нормализованный `verdict`. `round_completed` — прирост `review_rounds_completed`; только тогда `round_verdict` берётся из результата перехода. Допустимые ненулевые значения: `pass`, `changes`, `more_checks` |
| `repair` | `reopened: boolean` | `result.status == repairing`; подтверждённый переход может вместо ремонта зафиксировать блокировку |
| `accept` | `candidate_commit: string` | SHA принятого интегрированного коммита из результата перехода |
| `finalize` | `result: complete/partial`, `unassessed_criteria_count: integer` | `state.final.result`, длина `state.final.unassessed_criteria`; `partial` не является терминальным неуспехом |
| `revised_plan` | `previous_run_id: string`, `plan_fingerprint_before: string`, `plan_fingerprint_after: string`, `task_ids_after: string[]`, `preserved_task_ids: string[]`, `accepted_scope_task_ids: string[]` | До/после из проверенного основания; списки из нового плана и результата перехода. Новый ID находится в общем `run_id_after`. Сам факт пересмотра отмечается даже при сохранении ID |

Для `check_run` два уточнения:

1. Сейчас ветка успешной baseline-проверки возвращает результат раньше обычного набора полей. Проектор берёт `evaluated_check_ids` из сохранённого baseline-record (`registered_checks[].id`), `reused_check_ids=[]`, `failure_counted=false`. Это явная ветка текущего контракта, а не попытка угадать отсутствующие значения.
2. `evaluated_check_ids` обозначает проверки, рассмотренные в новом пакете без переиспользования. Исходное имя `executed_check_ids` не гарантирует запуск команды: проверка могла оказаться недоступна до запуска или представлять процедуру. Число запусков процессов по этому полю не рассчитывается.

Для `review_start` и `check_run` при проектировании нужно сохранить значения соответствующих счётчиков **до** reducer: он изменяет объект состояния на месте. Для `review_result` данные линзы извлекаются из новой сохранённой review-записи, поскольку результат функции может уже содержать общий вердикт раунда. Модель не заполняет эти поля по памяти.

### `process_session_finished`

Создаётся кодом штатного закрытия сессии после последней публикации событий. `run_id` — текущий ID выполнения или `null`, если инициализация не состоялась; `task_id=null`.

| Поле `data` | Тип | Как получить |
| --- | --- | --- |
| `reason` | `completed`, `blocked`, `stopped` или `error` | `completed` только при подтверждённом `run.status=completed`; `blocked` — при возврате управления из-за блокера; `stopped` — явное завершение интервала пользователем; `error` — пойманная ошибка, завершающая интервал |
| `last_revision` | integer ≥ 0 или null | Последняя подтверждённая revision источника |
| `collection_status` | `complete` или `incomplete` | `complete` только после сверки опубликованных фактов с историей до `last_revision` и проверки самого события открытия; при пропусках — `incomplete` |

Это оценка полноты на указанную revision, а не утверждение о будущих событиях или всех сессиях пользователя. Если закрывающую строку записать не удалось, полнота сессии остаётся неподтверждённой. Отсутствие закрытия не доказывает падение и не обнуляет уже подтверждённые факты.

## 4. Как встроить сбор

| Место | Предлагаемое изменение | Что остаётся источником факта |
| --- | --- | --- |
| Вход и выход оркестратора | Открыть/закрыть сессию, передавать её ID всем командам | Явный режим входа и результат штатного выхода |
| [`execute.py`](../../../../skills/sdd-apply/scripts/execute.py), [`api.dispatch`](../../../../skills/sdd-apply/scripts/lib/api.py) | Принять `process_session_id` как метаданные верхнего уровня запроса и передать сборщику. Не добавлять его в существующий native-envelope с точным набором полей | ID сессии, созданный локальным кодом |
| [`state.initialize`](../../../../skills/sdd-apply/scripts/lib/state.py) | Сформировать неизменяемый факт начала, сохранить его ссылку вместе с начальным manifest | Проверенное основание и созданное состояние |
| [`state.apply`](../../../../skills/sdd-apply/scripts/lib/state.py) | Снять нужные значения до reducer, выполнить reducer, построить проекцию, связать её с новой history-записью и сохранить состояние | Принятый переход и его фактический результат |
| [`state_history.append`](../../../../skills/sdd-apply/scripts/lib/state_history.py) и immutable objects | Хранить небольшую проекцию как объект, достижимый из подтверждённой истории | Один и тот же сохранённый `process_event` для первичной публикации и восстановления |
| После успешного commit состояния | Добавить строку в домашний JSONL, вернуть статус сбора отдельно от результата команды | Сохранённая проекция; повторно reducer не запускается |
| Открытие новой сессии, штатное закрытие и явная сверка | Найти факты в подтверждённой истории, которых нет в журнале, и дописать их с прежними ID и временем | История, достижимая из текущего manifest; потерянные временные объекты не включать |

При повторе native `event_id` ветка идемпотентного возврата может повторить публикацию сохранённого факта. Метрика не растёт. Не следует обходить идемпотентность движка ради восстановления журнала.

Нужен атомарный источник проекций, потому что reducer может менять данные, которые позднее уже нельзя однозначно извлечь из текущего состояния. Проекция и ссылка на неё попадают в ту же фиксацию `state.json`, что и переход. Недостижимая проекция после неудачного сохранения не публикуется. Это часть предлагаемого изменения формата состояния; решение о его версии принимается при реализации, без автоматической миграции старых запусков.

Сбой самого проектора должен дать компактную запись о неполноте в history (`process_event_error: {code: "projection_failed"}`) и диагностический статус команды, сохранив основной результат перехода. Такую revision нельзя объявить полностью собранной или автоматически восстановить из текущего состояния. Ошибка обычной записи авторитетного состояния продолжает подчиняться существующим правилам движка.

Обычная команда публикует только новый факт. Полная сверка выполняется на границах сессии или явно, а не сканирует всю историю после каждой команды. Локальный индекс уже записанных ID допустим как пересоздаваемое ускорение; он не становится источником истины.

## 5. Append-only, повторы и ошибки

Владелец JSONL — локальный writer. Агенты не дописывают строки непосредственно. Writer использует эксклюзивную блокировку на сессию, чтобы параллельные вызовы CLI не перемешивали байты; порядок захвата блокировки между разными командами не считается порядком бизнес-событий.

1. Сериализовать и проверить полную строку в памяти. Под блокировкой назначить `sequence`, дописать байты и LF, выполнить flush и синхронизацию файла. Успех публикации подтверждать после завершения этих действий.
2. Зафиксированная строка никогда не изменяется и не удаляется. Автоматическое удаление журналов и сжатие активных сегментов в пилот не входят.
3. При обрыве последней строки сохранить файл как есть и открыть новый сегмент со случайным `process_log_id`. В старый сегмент больше не писать. Повторить целый сохранённый факт в новом сегменте; не обрезать повреждённый хвост и не дописывать к нему новый JSON.
4. Читатель учитывает только завершённые LF строки. Незавершённый хвост считает диагностикой неполноты, валидный префикс сохраняет. Невалидная полная строка, пропуск sequence или конфликт одного ID с разным содержимым исключают затронутые данные из подтверждённого расчёта до сверки; тихо пропускать их нельзя.
5. При недоступном каталоге или ошибке записи команда сохраняет основной результат и возвращает отдельный статус сбора: `written`, `pending` или `incomplete`, с машинным кодом причины. `pending` означает, что неизменяемый факт сохранён в истории и допускает повторную публикацию; `incomplete` — что полнота не подтверждена, например не удалось построить проекцию. Следующий обычный вызов не повторяет выполненную проверку или Git-операцию из-за этого статуса.

`written` относится к публикации конкретного факта. Его недостаточно для `collection_status=complete` всей сессии. Полностью отсутствующий журнал нельзя обнаружить только чтением журналов: нужен список выбранных для пилота выполнений и сверка с их исходным состоянием.

Статус сбора и коды ошибок возвращаются в ответе команды; свободный текст исключения допустим только в локальной диагностике. В процессный журнал не попадают prompts, исходники, тексты находок, команды, stdout/stderr, абсолютные пути, URL репозиториев и текст пользовательских решений. Для первого набора достаточно идентификаторов, enum, отпечатков и счётчиков.

## 6. Что можно посчитать

Все расчёты используют уникальные `process_event_id` и явно указывают момент среза. Для подтверждённых значений требуется сверка истории до выбранной revision. При неполноте допустим отдельно подписанный наблюдаемый минимум количества; ноль и полная длительность не подставляются.

| Метрика | Единица и формула | Условия |
| --- | --- | --- |
| Состояние выполнения | Один `run_id`: последнее `run_status_after` по revision, до первого перехода — состояние инициализации | `active` и `blocked` — наблюдаемые незавершённые случаи; отсутствие новых событий не означает отказ или отмену |
| Доля принятых задач на срезе | `task_counts_after.accepted / sum(task_counts_after.values())` | Показывать числитель и знаменатель. При нулевом знаменателе значение `null`. Текущее состояние, а не число событий `accept`: приёмка могла потерять применимость после ремонта |
| Предъявления кандидата | Для задачи: число событий `candidate` со `stage=task` | Integration-кандидаты считать отдельно. Повтор доставки не считается; новое предъявление даже того же SHA считается новым действием, но не новым вариантом кода |
| Независимые пакеты и их исходы | Число `check_run`, где `stage=independent` и `evaluated_check_ids` непуст; группировка по `outcome` | Чистое повторное использование свидетельств показывать отдельно. Не смешивать baseline, self и integration. Число зачтённых неуспешных пакетов — сумма `failure_counted`; оно сверяется с бюджетом |
| Начатые раунды ревью | Для задачи: сумма `new_round` у `review_start`; дополнительно уникальные `round_id` | Добавление второй линзы и заблокированный старт не увеличивают счётчик. Начатый незавершённый раунд остаётся в нём |
| Вердикты линз | Число `review_result` по `(lens_id, verdict)`; один результат на `(run_id, task_id, round_id, lens_id)` | Брать принятый вердикт линзы. `reported_verdict` нужен для проверки нормализации. Повторно использованная линза нового результата не создаёт |
| Календарное время до завершения | Для неизменного выполнения: `occurred_at(finalize с complete) − occurred_at(execution_initialized)`, в секундах | Если завершений несколько — брать последнее, которое соответствует состоянию `completed` на срезе. Считать только при непрерывной истории и без пересмотра плана. Включает паузы между сессиями; это не время работы модели |

При отрицательном интервале или регрессии часов длительность равна `null` с причиной. Необнаруженное изменение системных часов остаётся ограничением UTC-разности; монотонное активное время в первой итерации не заявляется.

`revised_plan` помечает всю затронутую цепочку выполнений как «план пересмотрен», включая новые `run_id`. События продолжают собираться, текущие состояния показываются, но переносимые счётчики и длительности не объединяются с неизменными планами. Связь задают `previous_run_id` и `run_id_after`; revision текущего хранилища при смене ID не обязана начинаться с нуля. Исследование этой группы и расчёт затрат всей цепочки откладываются.

Не рассчитываются токены, деньги, число вызовов моделей, активное время человека, качество замечаний, приёмка «с первого раза» и длительности внутренних фаз. Для них пока нет полного операционного определения и подтверждённого источника в выбранном контракте.

## 8. Порядок пилота и критерии готовности

| Шаг | Работа | Проверяемый результат |
| --- | --- | --- |
| 1. Зафиксировать контракт | Перенести таблицы в схему; добавить короткие искусственные примеры четырёх типов и веток `details` | Каждое поле имеет тип, источник и смысл; нет полей, которые агент должен угадывать |
| 2. Встроить сбор | Добавить session-контекст, проекции в атомарную историю и локальный writer | Обычный путь пишет события автоматически; ошибку записи видно отдельно от результата работы |
| 3. Проверить семантику на искусственных данных | Проверить перечисленные ниже случаи через существующие адаптеры и память | Ожидаемые значения совпадают, повторы не завышают счётчики, неполнота обнаруживается |
| 4. Проверить в обычной работе | До начала зарегистрировать выбранные новые выполнения; сохранить реальные локальные журналы и сверить их с историей | Предлагаемый ориентир — три последовательных выполнения, включая возобновление в другой сессии, если оно встретится. Это проверка применимости, не статистическая выборка для сравнения моделей |
| 5. Принять решение | Просмотреть расхождения, накладные расходы и недостающие поля | Принять схему, исправить конкретный источник либо исключить неподтверждаемую метрику. Серверная часть не становится условием завершения |

Минимальные детерминированные случаи:

- Обычная задача: два `review_start` для двух линз дают один раунд и два фактических вердикта; приёмка и `finalize complete` дают ожидаемый результат.
- Пакет из нескольких неуспешных проверок увеличивает бюджетный счётчик на один. Baseline, self, integration, unavailable и чистое повторное использование его не увеличивают.
- В новом раунде verification-линза использует прежний code-вердикт: один новый раунд, один новый фактический вердикт; исходный code-вердикт не дублируется.
- Повтор того же native-запроса и повтор публикации в другой сессии не меняют значения метрик. Изменённый факт с тем же ID обнаруживается как конфликт.
- Сбой между фиксацией состояния и записью JSONL восстанавливается публикацией сохранённого факта; reducer и внешние действия не повторяются.
- Незавершённый хвост сохраняется, продолжение идёт в новый сегмент; два конкурирующих writer не перемешивают строки.
- `finalize partial`, отсутствующее закрытие сессии и история с пропуском не превращаются в завершение, нулевые затраты или полную длительность.
- Пересмотр плана с сохранением и сменой `run_id`, а также утрата применимости приёмки зависимой задачи сохраняют корректный текущий состав и признак изменённого плана.

Комбинации переходов проверять модульно через существующие адаптеры состояния и хранилища. Реальный файловый сценарий допустим только для конкретного риска блокировки/разрыва записи, который адаптер не подтверждает; обоснование нужно оставить в тесте. Новые agent/eval-запуски не требуются для проверки формата. Если позднее потребуется поведенческий сценарий с агентом, он требует отдельного явного согласия по AGENTS.md.

При реализации изменение скилла выполняется только в исходниках с применением `sdd-skill-conductor`; установленные копии не обновляются. Полный обязательный детерминированный набор `sdd-apply` после добавления тестов измеряется последовательно с лимитом 120 секунд по правилам AGENTS.md. В данной задаче изменяются только исследовательские документы и тезаурус.

Критерии завершения пилота:

1. Для каждого выбранного нового выполнения сверены инициализация и все подтверждённые revision до среза: число различных фактов равно ожидаемому, конфликтов ID нет. Отдельно перечислены неполные сессии и revision с ошибками проекции.
2. Все контрольные расчёты из раздела 6 воспроизводятся по журналам; изменённые планы и неизвестные значения отделены явно. Полнота считается относительно списка пилотных выполнений, а не только найденных файлов.
3. Повторная доставка и восстановление не повторяют разработку, проверки и Git-эффекты. Отказы записи видны пользователю и локальной проверке.
4. В журнале отсутствуют запрещённые свободные данные; реально записанные поля соответствуют схеме.
5. Зафиксированы число событий и размер журналов, время построения проекций/добавления строк и время сверки. Это технические замеры локальной проверки, не заявленная метрика эффективности агентов. Предварительный ориентир: добавление строки p95 ≤ 100 мс на целевой машине, без сети и повторного полного чтения истории на каждой команде; если ориентир не выполнен, сначала выяснить и сократить накладные расходы.

Итоговый короткий отчёт пилота должен содержать версии пакетов и схемы, перечень охваченных выполнений, полноту на заданные revision, контрольные значения, расхождения и решение о следующей итерации. Численные результаты появятся только после реализации и фактического сбора.
