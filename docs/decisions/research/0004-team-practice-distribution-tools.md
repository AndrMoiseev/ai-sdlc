# Инструменты распространения общих командных практик

**В короткий список стоит добавить Microsoft APM, Rulesync и Packmind.** Они представляют три разных подхода: воспроизводимые зависимости проекта; общие исходники с генерацией форматов агентов; управление командным набором практик. TeamAI остаётся кандидатом для регулярной синхронизации и обмена опытом. Выбор только между TeamAI и собственным установщиком был слишком узким.

Это продолжение [сравнения с TeamAI](0003-skill-catalog-installer-vs-teamai.md). Критерий отбора — распространение общих практик при разных инструментах и процессах. Близость к формату нашего `skill-catalog-installer` полезна, но не является обязательным условием. Готовые инструменты не оценивались как системы принудительного исполнения инструкций: доставка правила не доказывает его соблюдение агентом.

Исследование статическое: прочитаны первичные документы, метаданные релизов и выбранные участки кода. Инструменты не устанавливались, тесты и пилоты не запускались. Возможности платформ описаны по документации поставщиков, а не по испытанию аккаунтов. Сведения относятся к 1 октября 2026 года; документация сайта может быть новее опубликованного CLI. Для важных технических выводов ниже указаны версии или коммиты.

## Короткий список

| Инструмент | Как решает задачу | Когда особенно полезен | Существенное ограничение |
|---|---|---|---|
| [Microsoft APM](https://github.com/microsoft/apm) | Манифест и lock для инструкций, скиллов и других ресурсов, зависимости и доставка в разные агенты | Общий набор должен быть зависимостью проекта с контролируемым обновлением | Поддержка типов различается по агентам; защита чужих файлов не равна защите правок управляемых копий |
| [Rulesync](https://github.com/dyoshikawa/rulesync) | Общие исходники, подключаемые sources и генерация форматов инструментов | Команда хранит практики в Git и использует несколько агентов | Сгенерированные файлы предполагается пересоздавать; изменения следует вносить в исходники |
| [Packmind](https://github.com/PackmindHub/packmind) | Командный playbook из стандартов, команд и скиллов, пакеты и доставка | Основная боль — формализовать, согласовать и поддерживать практики | Change Proposals доступны в Enterprise; штатная установка доставляет актуальное содержимое |
| [Tessl](https://tessl.io/) | Версионируемые плагины, registry/workspaces, оценка полезности контекста | Важен цикл «создать → проверить → распространить → улучшить» | Нужно оценивать условия платформы и переносимость процесса; self-hosted заявлен в Enterprise |
| [Skill Suitcase](https://github.com/calvinnwq/skill-suitcase) | Git-каталог, варианты практики для агентов, plan/diff/apply и учёт установок | Важны локальная адаптация и управляемая доставка скиллов | Windows не подтверждён; гарантии различаются между режимами применения |

Моя рекомендация для технического пилота — **APM и Rulesync**. Packmind добавить, если команде нужен отдельный процесс авторства, согласования и наблюдения за распространением. Tessl рассматривать, если оценки эффективности практик являются самостоятельной задачей. Skill Suitcase стоит проверить отдельно, если именно варианты скиллов и сохранность локальной адаптации оказываются решающими. Это качественный отбор по соответствию задаче, не рейтинг производительности или надёжности.

## Microsoft APM: наиболее сильная альтернатива собственному CLI

Проверен опубликованный [v0.32.0](https://github.com/microsoft/apm/releases/tag/v0.32.0) от 25 сентября 2026 года, commit `f0509d75f2b35d11c8e983456e90e101768f1ecc`. Репозиторий находится в организации Microsoft; сам проект описывает себя как community-driven. Из этого не следует договорная поддержка Microsoft.

APM уже предоставляет `apm.yml`, `apm.lock.yaml`, точные разрешённые коммиты, учёт развёрнутых файлов, транзитивные зависимости и отдельное обновление. `install --frozen` воспроизводит зафиксированный граф и проверяет согласованность; Git-пакеты могут указывать отдельные подкаталоги. Пакеты можно составлять из скиллов, инструкций, prompts, определений агентов и других ресурсов. Это покрывает значительную часть предметной области нашего change. [Lockfile](https://github.com/microsoft/apm/blob/f0509d75f2b35d11c8e983456e90e101768f1ecc/docs/src/content/docs/reference/lockfile-spec.md), [установка](https://github.com/microsoft/apm/blob/f0509d75f2b35d11c8e983456e90e101768f1ecc/docs/src/content/docs/reference/cli/install.md).

Для разных процессов можно публиковать несколько общих пакетов и выбирать зависимости в каждом проекте. Это предлагаемый способ применения APM, а не утверждение о наличии в нём административной модели ролей TeamAI. Сам CLI также не создаёт содержание практик и не выбирает владельцев: эти решения остаются команде.

Ограничения, значимые именно для нас:

- **Матрица возможностей неодинакова.** Например, инструкции для Codex требуют отдельной компиляции корневого контекста; факт успешного install ещё не означает, что вся практика загружена агентом. Есть нативные Windows-бинарники, но наш сквозной сценарий на Windows не проверен. [Матрица](https://github.com/microsoft/apm/blob/f0509d75f2b35d11c8e983456e90e101768f1ecc/docs/src/content/docs/reference/targets-matrix.md), [способы установки](https://github.com/microsoft/apm/blob/f0509d75f2b35d11c8e983456e90e101768f1ecc/README.md).
- **Принадлежность файла и его локальное изменение — разные проверки.** `check_collision` защищает существующий путь, отсутствующий в managed set, если не указан force. В доставке скиллов есть пути пересоздания каталогов через `rmtree` и `copytree`. Нельзя выводить из этого контракт «любая локальная правка блокирует весь update». [Коллизии](https://github.com/microsoft/apm/blob/f0509d75f2b35d11c8e983456e90e101768f1ecc/src/apm_cli/integration/base_integrator.py#L200), [доставка](https://github.com/microsoft/apm/blob/f0509d75f2b35d11c8e983456e90e101768f1ecc/src/apm_cli/integration/skill_integrator.py#L363).
- **Откат имеет ограниченную область.** В `InstallTransaction` прямо указано, что журнал ограничен подготовленными путями под `apm_modules`; интеграции в каталоги агентов находятся за пределами этой транзакции. Поэтому нельзя обещать предусмотренный нашим design откат всех проектных копий. [Граница транзакции](https://github.com/microsoft/apm/blob/f0509d75f2b35d11c8e983456e90e101768f1ecc/src/apm_cli/install/transaction.py#L75).

**Вывод:** сначала проверить APM на наших пакетах. Собственный резолвер, lock и Git-загрузчик уже нельзя считать очевидно необходимыми. Возможная причина собственной разработки сузилась до конкретных непокрытых контрактов.

## Rulesync: общие исходники и адаптация под агенты

Проверен [v24.0.0](https://github.com/dyoshikawa/rulesync/releases/tag/v24.0.0) от 28 сентября 2026 года, commit `8283005299cb5ba04e1a853e0056b51f1fdfa77b`. Ветка main новее релиза, поэтому ссылки ниже ведут на тег.

Rulesync хранит общий исходный формат в `.rulesync/` и генерирует правила, скиллы, команды, определения агентов, MCP, hooks и permissions для поддерживаемых инструментов. Матрица возможностей зависит от target. Это хороший вариант, если практики должны оставаться в Git, а основная проблема — сопровождение нескольких форматов одних инструкций. [README релиза](https://github.com/dyoshikawa/rulesync/blob/v24.0.0/README.md).

Он уже включает declarative sources из GitHub и произвольного Git; npm transport помечен experimental. Для источников выбираются ref/path и конкретные rules/skills, а `rulesync.lock` хранит SHA, выбор и integrity. Есть `install --frozen`, `--update`, `--outdated`. Не следует приписывать remote sources доставку всех остальных типов: проверенный контракт источников описывает rules и skills. [Sources](https://github.com/dyoshikawa/rulesync/blob/v24.0.0/docs/guide/declarative-sources.md).

Поддержан понятный путь локальной адаптации: локальный одноимённый input вне `.curated` имеет приоритет над скачанным в пределах того же input root. Это позволяет выразить проектное исключение в исходниках. При нескольких roots важен их порядок. Ручные изменения сгенерированных файлов этим механизмом не защищаются. [Правила приоритета](https://github.com/dyoshikawa/rulesync/blob/v24.0.0/docs/guide/declarative-sources.md#how-it-works). Для CI есть `generate --check`. [Конфигурация и проверка outputs](https://github.com/dyoshikawa/rulesync/blob/v24.0.0/docs/guide/configuration.md#target-order-and-file-conflicts).

Ограничение для пилота: несколько targets могут писать один корневой файл, и тогда побеждает последний. Порядок способен изменить итоговый состав `AGENTS.md`. Нужно проверять активные инструкции, а не только отсутствие ошибок CLI. Windows x64 поддержан отдельным executable; npm-установка требует Node 22+. [Конфликты outputs](https://github.com/dyoshikawa/rulesync/blob/v24.0.0/docs/guide/configuration.md#target-order-and-file-conflicts), [установка](https://github.com/dyoshikawa/rulesync/blob/v24.0.0/docs/getting-started/installation.md).

**Вывод:** сильный кандидат для распределённой команды, которая хочет общий Git-источник и разные агенты без отдельной платформы управления. Наличие sources и lock делает его существенно шире простого конвертера правил.

## Packmind: распространение через управление практиками

По GitHub API актуальный CLI — [0.36.1](https://github.com/PackmindHub/packmind/releases/tag/release-cli/0.36.1) от 29 сентября 2026 года. Это версия CLI, не номер серверной платформы. Возможности ниже сверены с текущей документацией сервиса.

Packmind организует стандарты, команды и скиллы в пакеты по технологии, домену или команде. Пакеты доставляются локально либо в Git-репозитории; форматы выбираются под агентов. Это ближе к исходной проблеме, когда знания разбросаны по документации и обсуждениям, а не только к установке уже готовых скиллов. Один артефакт принадлежит одному пакету: общую базу и специализации нужно проектировать с учётом этого правила. [Packages](https://docs.packmind.com/concepts/packages-management), [рендеринг агентов](https://docs.packmind.com/administration/manage-ai-agents).

Есть поток предложения изменений из рабочего проекта с последующим review, однако **Change Proposals — Enterprise-функция**. Документация также предупреждает о перезаписи локальных изменений серверной версией при install. [Change Proposals](https://docs.packmind.com/playbook-maintenance/change-proposals).

Неизменяемые package releases есть, но документация прямо различает историю и доставку: install/distribution отправляет текущие версии компонентов. Поэтому исторический release нельзя автоматически считать аналогом нашего locked install. [Версии пакетов](https://docs.packmind.com/concepts/packages-management#package-versions).

Доступны Cloud и самостоятельное развёртывание; публичный репозиторий имеет Apache-2.0. Это не означает, что Enterprise-возможности включены в открытый комплект. [Self-hosted](https://docs.packmind.com/security/security-privacy-self-hosted), [лицензия](https://github.com/PackmindHub/packmind/blob/main/LICENSE).

**Вывод:** сильный кандидат рядом с TeamAI для управления общими практиками. Для небольшой команды, которой достаточно Git-review и доставки пакетов, платформа может оказаться избыточной.

## Tessl: распространение вместе с оценкой полезности

Актуальная документация использует плагины и `.tessl-plugin/plugin.json`; старые поисковые результаты про tiles не использованы как текущий CLI-контракт. Плагин объединяет rules, skills, MCP и hooks. Поддержка событий зависит от агента. [Формат](https://docs.tessl.io/reference/configuration).

Есть registry/workspaces, публикация версий и установка вида `workspace/plugin@1.0.0`. Роли различают потребление и публикацию; это ещё не доказательство обязательного содержательного review. [Распространение](https://docs.tessl.io/distribute/distributing-via-registry), [роли](https://docs.tessl.io/administrators/roles).

Отличительная часть предложения — evaluation практик: сравнение выполнения задач с соответствующим контекстом и без него. Для нашей задачи это полезный вопрос: улучшила ли практика результат, а не сколько раз её установили. Эффективность наших скиллов этим исследованием не проверена. [Описание оценок](https://docs.tessl.io/support/faqs).

Документация заявляет несколько агентов и Windows/macOS/Linux; для Windows есть особенность junctions и повторной установки после перемещения проекта. Enterprise-предложение включает self-hosted/single-tenant, поэтому Tessl нельзя описывать как исключительно SaaS. Подтверждения открытой лицензии всей платформы не найдено. [Платформы](https://docs.tessl.io/support/supported-platforms), [условия продукта](https://tessl.io/pricing).

**Вывод:** кандидат для инфраструктуры качества и распространения практик; перед выбором нужно проверить стоимость эксплуатации, работу со своими Git-исходниками и необходимый объём сервисной зависимости.

## Skill Suitcase: близок к нашему каталогу, учитывает варианты практики

Проверен v0.20.0 от 14 сентября 2026 года, snapshot `936a7c3fe593756fa92ba2d404d3b70ed84a079a`. В Git-каталоге можно описывать variants для разных agents и assignments, затем использовать plan/diff/apply и receipts. Для намеренных локальных улучшений есть `import-target`. Это интересно именно при условии пользователя, что инструменты и способы работы могут различаться. [README](https://github.com/calvinnwq/skill-suitcase/tree/936a7c3fe593756fa92ba2d404d3b70ed84a079a), [модель переносимости](https://github.com/calvinnwq/skill-suitcase/blob/936a7c3fe593756fa92ba2d404d3b70ed84a079a/docs/portability-matrix.md).

Подтверждены кодом plan-lock с проверкой commit, entries и файловых хешей, а также транзакция копирования с backup и попыткой отката затронутых скиллов. Однако это не доказательство эквивалентности всем сценариям нашей спецификации. [Plan lock](https://github.com/calvinnwq/skill-suitcase/blob/936a7c3fe593756fa92ba2d404d3b70ed84a079a/src/core/planning/plan-lock.ts), [транзакция](https://github.com/calvinnwq/skill-suitcase/blob/936a7c3fe593756fa92ba2d404d3b70ed84a079a/src/core/apply/copy-write-transaction.ts).

Существенная оговорка: artifact-mode для обычных missing/behind записей берёт текущий catalog source, а не всегда подготовленные байты. Поэтому для строгой проверки согласованного применения следует отдельно испытать plan-lock mode. CI проверенного снимка использует Ubuntu, build содержит POSIX-команды; native Windows не подтверждён. [Границы режимов](https://github.com/calvinnwq/skill-suitcase/blob/936a7c3fe593756fa92ba2d404d3b70ed84a079a/docs/portability-matrix.md), [CI](https://github.com/calvinnwq/skill-suitcase/blob/936a7c3fe593756fa92ba2d404d3b70ed84a079a/.github/workflows/ci.yml).

**Вывод:** заслуживает отдельной технической проверки до собственной реализации, особенно если подход APM к производным копиям нам не подходит. Пока не основание объявлять найденной готовую замену с гарантиями Windows.

| [agr v0.8.4](https://github.com/computerlovetech/agr/releases/tag/v0.8.4), 15.04.2026 | `agr.toml`, `agr.lock`, bundles и транзитивные зависимости | Репозиторий прямо объявляет отсутствие активного сопровождения; скорее архитектурный reference или база собственного fork |

Важные уточнения к таблице:

- **Vercel Skills:** проверенный `runInstallFromLock` не сравнивает результат с прежним `computedHash`, по умолчанию восстанавливает в `.agents/skills`. Явный SHA source ref поддерживается, поэтому утверждение «никакого pinning нет» было бы неверным. Installer очищает target; сохранность локальных правок не обеспечивается одним наличием lock. [Install](https://github.com/vercel-labs/skills/blob/7407f3893ad4dceab546ac002c3ef806e4000c73/src/install.ts), [Git fetch](https://github.com/vercel-labs/skills/blob/7407f3893ad4dceab546ac002c3ef806e4000c73/src/git.ts), [installer](https://github.com/vercel-labs/skills/blob/7407f3893ad4dceab546ac002c3ef806e4000c73/src/installer.ts), [CI](https://github.com/vercel-labs/skills/blob/7407f3893ad4dceab546ac002c3ef806e4000c73/.github/workflows/ci.yml).
- **Ruler:** backup обычных configs нельзя считать гарантией для всех ресурсов. Subagents пересоздаются при apply; skills/subagents в релизе экспериментальные. Проверенная CI только Ubuntu. [Ограничения](https://github.com/intellectronica/ruler/blob/v0.3.44/README.md#limitations), [CI](https://github.com/intellectronica/ruler/blob/v0.3.44/.github/workflows/ci.yml).
- **DotAI:** CLI поддерживает не только branch, но и tag/commit. При этом `skip` оставляет любой существующий файл, `overwrite` заменяет его; это не определение локальных изменений относительно предыдущей установки. Переносимый content lock не обнаружен. Документирован PowerShell installer, но фактическая работа на Windows не проверялась. [Sync](https://github.com/bajinzhi/dotai/blob/5386ba20ef6f23c47f12db64b05205746b4fe2cc/packages/cli/src/commands/sync.ts), [adapter](https://github.com/bajinzhi/dotai/blob/5386ba20ef6f23c47f12db64b05205746b4fe2cc/packages/core/src/adapters/base.ts), [README](https://github.com/bajinzhi/dotai/blob/5386ba20ef6f23c47f12db64b05205746b4fe2cc/README.md).
- **skills-lock:** в snapshot `4e37719a163b6022d4a2828850567421f9de7825` копирование последовательно вызывает удаление destination; поздняя ошибка может оставить частично обновлённые цели. Windows не проверен. [Код установки](https://github.com/luisalima/skills-lock/blob/4e37719a163b6022d4a2828850567421f9de7825/src/install.mjs).
- **agr:** актуальное описание репозитория называет проект учебным и не сопровождаемым активно. Функциональная близость к нашему решению не снимает ответственность за дальнейшую поддержку. [Репозиторий](https://github.com/computerlovetech/agr).

## Как выбирать

Практический выбор зависит от того, где сейчас находится основная работа:

| Потребность | Начать проверку с |
|---|---|
| Сделать практики воспроизводимыми зависимостями проекта | APM |
| Содержать общие правила и адаптировать их под разные агенты | Rulesync |
| Собрать знания команды, согласовывать изменения и распространять пакеты | Packmind и TeamAI |
| Измерять полезность практик вместе с их распространением | Tessl |
| Сохранять варианты скиллов по агентам и возвращать локальные улучшения | Skill Suitcase, с отдельной проверкой Windows и plan-lock |
| Просто установить несколько готовых скиллов | Vercel Skills как минимальный baseline |

Эти подходы могут дополнять друг друга, но начинать со связки нескольких менеджеров не стоит: два владельца одних целевых файлов создают отдельную проблему. В первом пилоте каждый кандидат должен управлять своим тестовым проектом.

Предлагаемый компактный сценарий сравнения:

1. Подключить наши три пакета и один неизменённый сторонний скилл в чистый проект для Codex и Claude Code.
2. Добавить общую практику в форме правила или документа и две разные специализации процесса. Проверить, что участник получает подходящий состав и понимает, когда его применять.
3. Проверить чистый clone, закреплённую версию, обновление и возврат прежнего состояния.
4. Изменить существующую ручную копию, управляемую копию и только одну агентскую цель. Проверить фактическую сохранность каждой категории данных.
5. Внести улучшение в общий источник и доставить другому участнику через принятый review.
6. Выполнить небольшую реальную задачу в обеих средах. Оценивать качество результата и ручные вмешательства, а не только наличие файлов.

Рекомендация предыдущего исследования уточняется: **пилот TeamAI остаётся полезным, но перед собственной реализацией нужно проверить как минимум APM и Rulesync**. Именно они могут снять значительную часть необходимости создавать свой инструмент, сохранив исходники практик и процесс review в Git. Если ограничения окажутся принципиальными, они дадут конкретные основания для более узкого собственного решения.
