# Идеи ProjectStore для развития SDD

Рекомендую заимствовать три связанных механизма: сохранять фактические связи принятой реализации с требованиями, использовать их при следующем планировании и отдельно проверять действующие требования после последующих изменений кода. В нашем проекте это развитие связки `sdd-apply` → `sdd-kb` → `sdd-spec` с использованием `sdd-shared` для чтения нормативных записей. Общий поиск, граф документов, независимое ревью и проверка свидетельств уже существуют.

Исследован `main`, commit [`d862758079ab4fbc9a875cbc36b15526fd435a82`](https://github.com/SmartAndPoint/ProjectStore/commit/d862758079ab4fbc9a875cbc36b15526fd435a82), от 14 ноября 2026 года; версия в [package.json](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/package.json#L3) — `0.30.18`. Основание выводов — чтение исходников и инструкций. Код ProjectStore, установка и поведенческие проверки не запускались.

## Как адаптировать к нашим скиллам

### 1. Сохранить связи принятой реализации с требованиями

Для `sdd-apply` предлагается производное представление: требование → критерий приёмки → принятая задача → точный коммит → фактические пути → исходное заключение и свидетельства. Коммиты и заключения уже сохраняются; [finalize](../../skills/sdd-apply/flows/finalize.md) сводит их без нового запуска проверки. Значимую связь конкретного кода с критерием следует брать из проверенных ссылок рецензента. Список файлов Git показывает, что менялось, но сам по себе не доказывает, где реализован каждый критерий.

Новый обзор должен строиться из существующих записей после приёмки, сохранять различие предложенных и фактических путей и оставаться восстанавливаемым. Нормативные документы не переписываются. При переносе изменения в архив ссылки должны сохранять исходный коммит и находить новое расположение документов. Обновление обзора можно включить в существующее формирование отчёта; дополнительная обязательная роль не нужна.

**Польза:** следующий архитектор сможет найти проверенный пример реализации и причину выбора. **Стоимость:** извлечение связей, обработка переименований, архива и недоступных свидетельств. **Приоритет:** первый, поскольку на этих данных основаны следующие предложения.

### 2. Давать sdd-spec небольшую выборку прошлых решений

В [исследовании](../../skills/sdd-spec/flows/explore.md) добавить обращение к существующему `sdd-kb` по затрагиваемым требованиям и путям: найти релевантные завершённые изменения, их решения и фактическую реализацию; прочитать первоисточники и проверить применимость к текущему коду. Сохранять полезный вывод в уже существующем `research.md` нового изменения. Так история становится входом решения без отдельного обязательного документа «уроков».

От ProjectStore полезны типы связей, ограничение глубины/объёма и явные признаки усечения. Сам его planner требует читать **все** epic; это правило не стоит переносить. Предлагаемая адаптация соединяет его механизм ограниченных запросов с нашим исследовательским флоу. Поиск с усечением не позволяет заключить, что других зависимостей нет; найденный старый образец не становится обязательной архитектурой.

**Польза:** меньше повторного поиска и повторения уже разобранных ошибок. **Стоимость:** соединить записи SDD с существующим индексом и определить границы выборки. **Приоритет:** вместе с первым предложением. Начать можно с существующего поиска и ссылок, добавляя специальные запросы только под повторяющиеся вопросы.

### 3. Отдельно проверять действующие требования после новых изменений кода

Перед новым изменением или по отдельному запросу выбирать ограниченную область текущих спецификаций. По сохранённым связям находить реализацию и проверки, сопоставлять текущий код с исходным подтверждённым состоянием, выдавать находки и явно перечислять непроверенные требования. Например, задача A подтвердила запрет записи за пределы проекта, а более поздняя задача B изменила разрешение путей: проверка B сама по себе ещё не доказывает сохранение требования A.

Изменение файла — повод проверить требование, а отсутствие изменения не доказывает его выполнение: могут измениться зависимости, конфигурация или вызывающий код. Выборка по путям должна сообщать свои ограничения. При расхождении предложение идёт через обычный пересмотр в `sdd-spec`; реализация исправления — через согласованный план `sdd-apply`. Подгонять спецификацию под обнаруженный код автоматически нельзя.

Это отдельная работа с действующими требованиями, а не новый обязательный финальный прогон `sdd-apply`: [текущий finalize](../../skills/sdd-apply/scripts/lib/finalize.py) суммирует принятые задачи и не запускает роли. Оценку соответствия нужно согласовать с нашей существующей политикой свидетельств: цитата строки кода не заменяет подтверждение поведения.

**Польза:** обнаружение противоречий, возникших между изменениями. **Стоимость:** выше первых двух предложений; нужны отбор области, проверка полноты связей и отдельное содержательное ревью. **Приоритет:** после появления пригодных фактических связей; сначала как явно выбираемая проверка.

### 4. Пересматривать решения, когда меняются их основания

Опциональное `review_by` ProjectStore полезно для решения о версии внешнего API, временном ограничении среды или ожидаемой нагрузке. У нас начать можно с условия пересмотра в тексте существующего решения: что должно измениться и какое наблюдение потребует нового рассмотрения. Новое поле схемы и календарный срок для каждого DEC пока не обоснованы. Приоритет ниже трёх основных предложений.

## Оценка через FPF

- **C.11.CRC:4** задаёт сравнение с текущей конфигурацией. База сравнения включает существующие `sdd-kb`, линзы, проверку свидетельств и checkpoint; их пользу нельзя повторно приписать заимствованию.
- **SYSE.24:4.4** требует учитывать полную стоимость получения результата. Подключение всего ProjectStore добавило бы vault, Node, hooks, установку и согласование жизненных циклов. Адаптация трёх механизмов использует имеющиеся данные и инструменты. Сохранение текущего ручного поиска остаётся разумным для проектов с короткой историей.
- **A.11.OP:4** проверяет необходимость каждого нового обязательного шага. Получение связей оправдано, если ими пользуется следующая работа; проверка расхождений оправдана для выбранных требований. Обязательные ретроспективы, чтение всего архива и ещё одно финальное ревью этим сравнением не обоснованы.

Горизонт сравнения — следующее изменение в уже затронутой области и проверка требований после него. Ожидаемые результаты: быстрее находить применимые решения, видеть зависимости и обнаруживать конкретные противоречия. Издержки: объём прочитанного контекста, время исследования и обслуживание связей. Численного выигрыша чтение исходников не устанавливает.

Начать стоит с первых двух предложений. Для будущей проверки полезны три случая: найти основание прежнего решения по пути кода; после переименования и архива сохранить путь к первоисточнику; при неполной выборке или недоступной проверке явно вернуть ограничение. Проверку расхождений затем оценивать на известном нарушении старого требования и на изменении кода, которое его сохраняет. Поведенческие проверки этих предложений в рамках исследования не проводились.

## Механизмы, подтверждённые исходниками

### 1. Связи между решениями, спецификациями и работой

`lineage` возвращает типизированные связи `supersedes`, `spec-covers`, `spec-implements-adr`, `epic-contains`, `amends`. Обход ограничен глубиной и количеством узлов, устойчив к циклам. Обычные ссылки из текста не входят в этот обход; переход от истории к её epic не втягивает остальные истории. Это позволяет получить основания конкретной работы без загрузки всего хранилища. Есть отдельные `neighbors` и обратный поиск `codeRefs`: путь в коде → связанные документы. Неоднозначное имя вызывает ошибку, а усечение результата сообщается явно. [Код запросов](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/scripts/query.mjs#L609).

**Идея переноса:** перед подготовкой изменения получать связанные действующие требования, решения и завершённые изменения по затрагиваемым путям. Использовать существующую базу знаний проекта, если она уже предоставляет нужные связи.

### 2. Фактическая реализация становится входом следующего планирования

`planner` сначала изучает `code_refs` предыдущих epic и проверяет пути в коде. Результат содержит размещение изменения, пригодные для повторного использования функции, примеры соглашений, ловушки и ожидаемые пути. После реализации `reviewer` вычисляет предлагаемые `code_refs` из Git через `diff-refs.mjs`; запись выполняется отдельно. Это замыкает связь «как планировали → где реализовали → на что опираться дальше». [Planner](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/agents/planner.md#L26), [reviewer](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/agents/reviewer.md#L191).

**Ограничение:** диапазон Git по времени начала истории может включить чужую работу либо пропустить нужную. Источник прямо требует явный диапазон при сомнительном результате. Для переноса предпочтительнее использовать уже известные точные коммиты принятой задачи. [Вычисление путей](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/scripts/diff-refs.mjs#L1).

### 3. Отдельная проверка расхождения действующих контрактов с кодом

`spec-drift.mjs` собирает факты для одной активной спецификации: контракты и даты изменений, связанные истории и их состояния, `code_refs`, исходники, тесты, интерфейсные файлы, цитаты контрактов и историю Git. Скрипт не выносит заключение. [Сбор данных](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/scripts/spec-drift.mjs#L259).

Независимый reviewer оценивает каждый выбранный контракт как `holds`, `drifted`, `cannot tell` или `removed`. По умолчанию допускается до восьми контрактов; остальные явно остаются непроверенными. Несуществующие пути и отсутствие цитат перечисляются отдельно, а не объявляются расхождением. При расхождении reviewer предлагает изменить спецификацию или код через новую/открытую историю. В этом режиме он ничего не записывает. [Процедура проверки](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/agents/reviewer.md#L68).

**Идея переноса:** отдельная проверка действующих требований после последующих изменений, дополнительно к проверке завершения текущей задачи. Даты и частота изменений помогают выбрать область чтения, но отсутствие новых коммитов не доказывает выполнение контракта. Найденная строка реализации также не заменяет проверку поведения.

### 4. Общие правила автора и рецензента

Для каждого вида документа есть guide с обязательными пунктами и типичными ошибками. Его читают автор и critic; проектная версия имеет приоритет над поставляемой. Critic перед подробным чтением формулирует наиболее вероятные проблемы, затем проверяет их и значимые ссылки на источники. [Инструкция critic](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/agents/critic.md#L34).

**Идея переноса:** один источник критериев для подготовки и ревью документа. Полезность зависит от того, устранит ли это существующее расхождение инструкций; отдельная новая роль для этого не требуется.

### 5. Детерминированные факты и восстановимые представления

CLI и MCP используют общие функции чтения; ответы содержат ограничения, количество найденного и статус неполного сканирования. `reconcile` пересчитывает производные представления непосредственно перед записью и заменяет файл атомарно; обнаруженная конкурентная правка вызывает повторное вычисление. Пользовательский текст вокруг управляемой таблицы сохраняется. [Контракт чтения](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/scripts/query.mjs#L1), [запись представлений](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/scripts/reconcile.mjs#L255).

**Идея переноса:** переиспользовать валидируемые записи как источник обзоров и связей, а не поручать модели поддерживать их дубликаты. Нужен только там, где аналогичный механизм ещё отсутствует.

### 6. Срок пересмотра принятого решения

`doctor` сообщает о принятом ADR с истёкшим `review_by`, пока его не рассмотрели после указанной даты. Это информационная находка, а не автоматическая отмена решения. [Проверка срока](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/scripts/doctor.mjs#L3357).

**Идея переноса:** назначать пересмотр для решений с изменчивыми основаниями. Всеобщий срок для каждого решения добавил бы обслуживание без установленной пользы.

## Что не стоит переносить буквально

- **`review_status: reviewed` как гарантию актуальности.** Команда выставляет статус и дату после применения правок; найденная проверка `doctor` требует лишь наличие даты. Это слабее привязки ревью к конкретному содержимому. [Команда](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/commands/review.md#L81), [проверка](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/scripts/doctor.mjs#L2228).
- **Цитату контракта как доказательство тестирования.** `doctor` ищет токены по всему проекту; корректный токен в документации тоже учитывается как покрытие. Reviewer обязан отдельно проверить смысл теста. Лучше сохранять различие «ссылка найдена», «проверка существует», «поведение проверено». [Сканирование и подсчёт](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/scripts/doctor.mjs#L3040), [обязанность reviewer](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/agents/reviewer.md#L157).
- **Полную церемонию записи.** Отдельные подтверждения каждой правки, clerk, обновление vault, hooks и интерфейсы установки обслуживают продукт ProjectStore. Для заимствования перечисленных механизмов весь плагин не нужен. [Путь записи](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/docs/how-it-works.md#L6).
- **Напоминания как жёсткий контроль исполнения.** Hook после нескольких записей лишь напоминает открыть историю; записи через shell могут обойти его. `doctor` добавляет проверку постфактум. [Описанные границы](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/docs/how-it-works.md#L224).
- **Пропуск вопроса как выбор рекомендации.** Инструкция planner допускает записать рекомендуемый вариант при пропуске вопроса. В нашем `sdd-spec` существенная развилка требует явного решения или действующего делегирования. [Выход planner](https://github.com/SmartAndPoint/ProjectStore/blob/d862758079ab4fbc9a875cbc36b15526fd435a82/agents/planner.md#L99), [наш контракт обсуждения](../../skills/sdd-spec/references/discussion.md).

Основная гипотеза для сравнения с SDD: завершённое выполнение сохраняет фактические пути реализации; подготовка следующего изменения использует их вместе с основаниями; последующая независимая проверка выявляет расхождения действующих требований с кодом. Это предложение по использованию механизмов, а не установленный результат их эффективности.
