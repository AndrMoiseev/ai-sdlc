# Работа со скиллами

При создании, изменении, проверке и упаковке скиллов применяй
[sdd-skill-conductor](skills/sdd-skill-conductor/SKILL.md), включая его требования
к окружению, временным данным и проверке чистоты пакета.

# Запуск Python через uv

На любой ОС используй один общий доступный для записи каталог `uv-runtime`
вне проекта и коллекций скиллов. Сохраняй унаследованные `UV_CACHE_DIR`
и `UV_TOOL_DIR`. Если они отсутствуют, определи системный временный каталог
через API текущей среды и задай абсолютные пути `uv-runtime/cache`
и `uv-runtime/tools` соответственно. Переменные окружения задавай для текущего
процесса средствами доступной оболочки; пути собирай средствами ОС.

Перед первым запуском в сессии создай отсутствующие каталоги, проверь
`uv cache dir` и реальную возможность записи в оба каталога. При запрете записи
выбери другой общий каталог в разрешённой области и обнови соответствующие
переменные процесса. Повторно используй выбранные пути между задачами.
Окружения и результаты храни вне проекта и коллекций скиллов. Общий кэш работает
из любого рабочего каталога; пути скриптов и входных файлов передавай абсолютными.

Один раз в сессии найди системный Python, совместимый с `requires-python`
скрипта, командой `uv python find --system --no-managed-python "<версия>"`.
Для скриптов с PEP 723 и соседним lock-файлом используй найденный абсолютный путь:

```text
uv run --python "<путь к Python>" --locked --script "<путь к скрипту.py>" <аргументы>
```

Если нужен управляемый Python uv, проверь доступность его каталога для записи;
при необходимости задай `UV_PYTHON_INSTALL_DIR` в общем каталоге `uv-runtime/python`.
Повторно используй выбранный интерпретатор. uv хранит окружение скрипта в общем
кэше и повторно использует его при тех же зависимостях и интерпретаторе.
После очистки кэша или изменения зависимостей обычный запуск может снова
скачать пакеты.

# Доступ к файлам при запуске скриптов

Перед запуском определи, куда скрипт и его дочерние процессы будут писать:
кэш, временные файлы, результаты и рабочие копии. Используй разрешённые
каталоги вне проекта по правилам выше. Успешная запись из PowerShell ещё
не доказывает, что Python или pytest смогут читать созданные ими каталоги.

В этой Windows-среде уже наблюдался `PermissionError: [WinError 5]` у pytest
на `pytest-of-Andrew` и на новом каталоге, переданном через `--basetemp`.
Тот же набор прошёл вне файловой песочницы. При повторении этой конфигурации
сразу запрашивай для конкретной команды штатное разрешение
`sandbox_permissions: require_escalated`, указав эту причину. Не трать полный
прогон на воспроизведение уже известного ограничения. Это запрос разрешения
среды, а не требование запуска от администратора; AGENTS.md не выдаёт его сам.

Для нового сценария с неизвестными правами сначала проверь создание, запись,
чтение и перечисление временного каталога тем же интерпретатором и способом,
которым будет запущен скрипт. После отказа доступа прочитай первый traceback,
установи проблемный путь и прекрати неизменённые повторы. При необходимости
используй штатный запрос расширенного доступа; сохраняй sandbox и ACL.

Для pytest задавай уникальный абсолютный `--basetemp` во внешнем временном
каталоге, если runner не задаёт его сам. Каталог должен принадлежать только
этому прогону: pytest может удалять его содержимое. Первый запуск после
изменения окружения выполняй с `-x`, чтобы ошибка подготовки не повторялась
для каждого теста. Полный успешный набор всё равно обязателен.

Повторно применяй выбранные `UV_CACHE_DIR`, `UV_TOOL_DIR` и
`PYTHONDONTWRITEBYTECODE=1` в каждом новом процессе оболочки: переменные
предыдущего вызова инструмента могут не сохраниться. Скрипты с PEP 723
запускай через `uv` по шаблону выше. На Windows фоновые процессы запускай
с `Start-Process -WindowStyle Hidden`; контролируй код выхода, сохраняй
stdout/stderr вне проекта и по тайм-ауту останавливай всё дерево процессов.

# Ограничение времени тестов

Приоритет тестов — корректность самого скилла. Проверки инфраструктуры эвалов
ограничивай минимальным набором контрактов, необходимым для достоверной оценки.

Новый интеграционный тест с настоящим браузером, Git, файловой системой, сетью
или отдельным процессом добавляй только при доказанной необходимости. В тесте
кратко укажи конкретный риск и почему его нельзя надёжно проверить модульным
тестом или через существующий адаптер. Выбирай минимальное число реальных
сценариев; комбинации правил и повторения проверяй без внешнего I/O.

При добавлении нового теста обязательно измерь полное время обязательного
набора в последовательном режиме после изменения. Принимай тест только
если весь набор проходит не дольше 60 секунд. Если норма превышена, переделай
тест и его подготовку либо откажись от избыточного теста; обязательное поведение
должно остаться покрытым. Если исходный набор уже превышает норму, сначала
оптимизируй его — исходное превышение не разрешает добавлять новые тесты.
Зафиксируй команду, состав набора и полное время. Успех отдельного теста,
нулевой код выхода и параллельный прогон не заменяют эту проверку.

Лимит 60 секунд действует отдельно на каждый однократный прогон обязательного
набора одного скилла. Наборы разных скиллов измеряй отдельно: например, прогоны
`sdd-spec`, `sdd-shared` и `sdd-apply` имеют каждый свой лимит 60 секунд,
даже если запускаются последовательно в рамках одной задачи или команды.
Их суммарное время не сравнивай с лимитом одного набора.
Повторный запуск после завершения или остановки предыдущего начинает новый
прогон с новым лимитом; время предыдущих прогонов к нему не прибавляй.
Измеряй реальное время всех составляющих одного прогона команд, включая запуск
среды, подготовку фикстур, установку зависимостей, ожидания и внутренние повторы.
При параллельном запуске учитывай время команды целиком, а не сумму времён
воркеров. Разбиение набора одного скилла на команды или группы не обнуляет лимит:
время всех частей этого прогона учитывай вместе.

Если по любой причине время одного прогона превышает 60 секунд, немедленно
останови текущую работу и ещё выполняющиеся процессы этого прогона.
Сообщи пользователю команды, затраченное время и известную причину задержки;
рекомендуй сначала оптимизировать тесты. Продолжай работу только после
нового указания пользователя. Установка, сеть, ошибки и нестабильность среды
не являются исключениями из этого правила.
