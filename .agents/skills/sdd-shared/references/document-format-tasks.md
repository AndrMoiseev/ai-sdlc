# Формат задач и проверок

Читай вместе с [общей основой](document-format.md) перед созданием, изменением
или проверкой tasks и при исполнении verification в sdd-apply. Разрешение
планирования и финальный gate проверяй по [plan](../../sdd-spec/flows/plan.md).

Запись `sdd_record: task` содержит number, covers, depends_on, status, verification
и необязательный cannot_parallel_with сверх id/sdd_record. Каждый AC изменения,
включая результат удаления, принадлежит ровно одной задаче; covers непустой.

### Задача и ее проверка

`number` — перестановка 1..N; `depends_on` — TASK-ID того же изменения. Циклы, зависимости на себя и отсутствующие задачи ошибочны. `cannot_parallel_with` — симметричное ограничение без навязывания порядка. Наличие общего файла само по себе не запрещает параллельную работу: рассмотрите разделение участков и контракты.

`status`: pending/in_progress/done/blocked; новый план начинает с pending. Прогресс определяется количеством done, не максимальным номером; статус не доказывает прохождения тестов. Пилот не исполняет план.

`verification` — непустой список объектов `criteria`, `test_description`, `location`, `run`. criteria — непустое подмножество covers; объединение покрывает все covers. test_description описывает проверяемое поведение и ожидаемый результат. Тесты, включая интеграционные, входят в задачу реализации критерия.

`location` — один путь к определению проверки: тестовому файлу, каталогу тестов или документу с процедурой. Указывай путь относительно корня проекта, с `/` между сегментами; при исполнении в worktree используй его корень независимо от `cwd` команды. Путь ведёт внутрь проекта, ниже корня и вне `.git`; абсолютные пути, `..`, URL, glob, якоря, селекторы тестов и shell-синтаксис недопустимы. Пробелы внутри имени допустимы. Команду и селектор указывай в run, пояснение — в test_description, логи результата — в свидетельствах исполнения. Для нескольких независимых мест создай отдельные элементы verification. Для ручной проверки location может совпадать с файловой частью run.procedure.

`run` — mapping ровно с одним ключом `command`, `procedure` или `setup_required`:

- `command` — непустой массив строк: исполняемый файл и отдельные аргументы, например `["pytest", "-q", "tests/test_feature.py"]`. Первый элемент непустой; NUL недопустим во всех элементах. Пустые аргументы допустимы. Передавай пути с пробелами одним элементом без дополнительных shell-кавычек. Исполнение использует `shell=False`: операторы, переменные и маски оболочки автоматически не раскрываются.
- `procedure` — ссылка на существующий файл проектной процедуры (возможен `#anchor`).
- `setup_required` — создание проверки или подготовка её запуска внутри этой задачи. Используй этот вариант и для будущего теста с уже известной командой; сохрани команду в описании подготовки. Существующие обязательные проверки остаются обязательными отдельно.

`procedure` и `setup_required` содержат непустой текст. Для проверки, которой необходима оболочка, укажи интерпретатор явно в массиве, например `["bash", "scripts/verify.sh"]`. Строка кода через `-c`/`/c` остаётся исполняемым кодом и требует проверки целиком; не подставляй в неё недоверенные данные. На Windows `.bat`/`.cmd` также используют оболочку; предпочитай непосредственный исполняемый файл либо явно зарегистрированный запуск интерпретатора. Старые строковые `command` не исполняются и не разбираются автоматически. Обновляй их через пересмотр плана с сохранением смысла проверок и актуальным согласованием; sdd-apply не переписывает утверждённый план самостоятельно.

На этапе plan валидатор проверяет форму и границы location, не требует существования будущего пути и не определяет готовность команды. Рецензент проверяет соответствие location описанию проверки и выбор run. В baseline отсутствие ещё не подготовленной проверки допускается только при явном setup_required; отсутствие пути при command/procedure блокирует исполнение. После подготовки и при проверке результата location должен быть существующим файлом или каталогом для любого run; отсутствие означает unavailable. Наличие пути само по себе не доказывает запуск нужных проверок и покрытие AC.
