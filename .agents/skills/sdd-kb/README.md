# sdd-kb — база знаний проекта

Один скилл для поиска по документации, её обновления и построения карты связей.
Основан на [Ontoship](https://github.com/vakovalskii/ontoship), но устанавливается
как самостоятельный скилл. Документы остаются обычными Markdown-файлами в Git.

`SKILL.md` — короткий роутер. Он выбирает внутренний маршрут по запросу пользователя
и загружает нужную инструкцию. Исходные `kb-search`, `kb-curate` и команды `kb`,
`kb-map`, `doc`, `onto-doc` объединены внутри. `dev-flow` и команда `ship` исключены.

## Установка

Скопируйте каталог `sdd-kb` целиком в каталог скиллов вашего агента, например
`.agents/skills/sdd-kb` для проекта Codex или `.claude/skills/sdd-kb` для Claude Code.
Сохраните `scripts/`, `references/`, лицензию и файл `gitmark.py.lock`.
Отдельный плагин Ontoship и другие его скиллы не нужны.

Понадобятся [uv](https://docs.astral.sh/uv/getting-started/installation/) и Git.
При первом запуске uv установит Python 3.10+ при необходимости и зависимости
из lock-файла. Среда хранится в пользовательском кэше, а не внутри скилла или
виртуального окружения проекта. На Windows для `UV_CACHE_DIR` используется
`uv-runtime/cache` в системном временном каталоге. После очистки кэша обычный
запуск восстановит зависимости; для этого нужен доступ к сети.

## Примеры запросов

В Codex используйте `$sdd-kb`, в Claude Code — `/sdd-kb`. Далее синтаксис одинаков:

| Задача | Пример |
|---|---|
| Найти ответ в документации | `$sdd-kb как проверяется подпись billing webhook?` |
| Найти конкретный термин | `$sdd-kb search MAX_RETRIES` |
| Показать действующие решения | `$sdd-kb какие архитектурные решения имеют статус active?` |
| Запросить метаданные | `$sdd-kb query type=decision status=active` |
| Посчитать планы по сервисам | `$sdd-kb query type=plan --count-by service` |
| Найти непроверенные документы | `$sdd-kb query "generated.by?" trust=unverified` |
| Обновить один документ | `$sdd-kb doc опиши проверку подписи webhook по коду src/billing` |
| Зафиксировать решение | `$sdd-kb doc решение: сохраняем PostgreSQL; причины и альтернативы в приложенных заметках` |
| Перенести документ | `$sdd-kb перенеси docs/auth.md в docs/reference/auth.md и исправь ссылки` |
| Создать базу знаний | `$sdd-kb onto-doc` |
| Документировать часть репозитория | `$sdd-kb build services/api services/billing` |
| Построить карту | `$sdd-kb map` |
| Выбрать путь карты | `$sdd-kb kb-map artifacts/knowledge-map.html` |
| Проверить качество | `$sdd-kb health` |
| Проверить структуру и ссылки | `$sdd-kb lint` |
| Перестроить поисковый индекс | `$sdd-kb index` |
| Показать статистику | `$sdd-kb` |

Старые имена команд распознаются **внутри запроса к `sdd-kb`**. Установка одного
скилла не регистрирует отдельные `/kb`, `/doc` и другие slash-команды в интерфейсе.

## Что получится

**Поиск** вернёт ответ со ссылками на файлы и строки. GitMark использует SQLite
FTS5, ранжирование по содержимому и метаданным, поиск подстрок и нечёткие совпадения.
Он поддерживает кириллицу и формы слов. Это лексический поиск: для отсутствующего
термина агент попробует синоним или другое написание. Структурные вопросы идут
через `query`, а не через полнотекстовый поиск.

**Редактирование** сначала найдёт существующий документ, затем обновит его или
создаст новый. Агент добавит тип документа, краткое описание, связи с кодом и
другими страницами, обновит README-индекс и проверит ссылки. Метки `generated`,
`verified` и `stale_after` позволяют отличать авторство, реальную проверку и срок
актуальности. Скилл не выдаёт собственную проверку за человеческую.

**Построение базы** изучит репозиторий и заполнит пробелы в документации. При
наличии субагентов независимые области обрабатываются параллельно, общие индексы
собираются координатором. Без субагентов работа выполняется последовательно.
Существующие документы и проектные инструкции сохраняются и дополняются.

**Карта** — один HTML-файл с деревом, просмотром документов и интерактивным графом.
Его можно открыть локально без сервера. Для HTTP-просмотра есть `$sdd-kb serve`.
Карта отражает состояние на момент генерации и обновляется повторным запуском.

## Файлы и границы

Исходная документация обычно живёт в `docs/`, а `docs/README.md` служит её входом.
Скилл учитывает существующий формат проекта. Поиск и карта работают и без
frontmatter; правила онтологии нужны при структурировании и проверке базы.
Полная модель описана в [ontology.md](references/ontology.md).

Производные файлы находятся в проекте:

```text
.gitmark/
  index.db
  docs-map.html
```

Добавьте `.gitmark/` в `.gitignore`. Содержимое можно пересоздать из Markdown.
Пользовательский HTML по явно заданному пути хранится там, где вы указали.
Кэш, база и отчёты не должны попадать внутрь установленного скилла.

В Git-репозитории индексируются отслеживаемые и неигнорируемые новые `.md`.
Чтобы убрать копии документации или тестовые данные, перечислите их пути от
корня проекта в `.gitmarkignore`, по одному на строку. Каталоги установки агентов
и файлы самого скилла исключаются автоматически. Вне Git `.gitignore` не применяется.

`query` считает только документы с frontmatter. `lint --strict` возвращает ненулевой
код при ошибках, но предупреждения надо оценивать отдельно. Старые проблемы вне
области запроса показываются в отчёте. Для неизвестных фактов агент отмечает пробелы,
а не придумывает архитектурные решения. Разработка фич, релизы и деплой в скилл не входят.

## Запуск CLI вручную

Из корня целевого проекта, подставив абсолютный путь установленного скилла:

```text
uv run --locked --script "<skill-dir>/scripts/gitmark.py" --root "." index
uv run --locked --script "<skill-dir>/scripts/gitmark.py" --root "." search "billing webhook"
uv run --locked --script "<skill-dir>/scripts/gitmark.py" --root "." query "type=decision" "status=active"
uv run --locked --script "<skill-dir>/scripts/gitmark.py" --root "." lint --strict --json
uv run --locked --script "<skill-dir>/scripts/gitmark.py" --root "." map
```

Полный список: `… gitmark.py --help`. Параметр `--root` идёт перед командой.
Для обычного использования достаточно естественного запроса к агенту.
