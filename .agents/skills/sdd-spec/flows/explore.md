# Исследование

Оркестратор передаёт исследовательский синтез и подготовку развилок
[архитектору](../references/architect.md). В шагах ниже архитектор изучает
содержание и возвращает предложения; оркестратор ведёт диалог, журнал, Q и checkpoint.

Для ограниченного поиска по нескольким источникам используй
[research-поручение explorer](../references/explorer.md). До change ID работай
с project scope и null work/task; верни пользователю абсолютную точку продолжения.
Подтверждённые факты передай архитектору для сохранения в research.md по
[контракту исследования](../references/research.md). До первой устойчивой записи
выбери вид работы, change-id и корень по [правилам входа](../references/entry.md); каталог может
начинаться с исследования и пары state без нормативного комплекта.

До исследования зависимых решений выбери маршрут по [правилам рефакторинга](../references/refactoring.md#выбор-маршрута). Для refactoring исследуй исходные обязательства и всех потребителей, сообщи границы; неоднозначность или конфликт поведения оставь открытым до выбора пользователя.

Будь партнером по исследованию: следуй интересующим пользователя направлениям, проверяй предположения и меняй подход при новых свидетельствах. Свободное обсуждение не превращай в анкету и не требуй от него обязательного предложения. Если схема помогает, рисуй ее; для выровненных текстовых схем используй ASCII.

1. Прочитай существующие документы выбранного изменения и релевантные инструкции проекта. До фактического вопроса исследуй исходники, тесты, конфигурацию и документацию. Сообщи существенный вывод со ссылками. При конфликте или недоступности источников обозначь ограничение; не заставляй пользователя повторять проверяемый факт.
2. Установи условия успеха и проверь существенные предпосылки по [правилам обсуждения](../references/discussion.md#проверка-предпосылок). Используй доступные источники; оставшиеся существенные пробелы обработай по следующим шагам.
3. Выполни [цикл обсуждения](../references/discussion.md): отдели факты исследования от существенных развилок и материальных требований, включая собственные предложения. Сохрани авторство и отдельные ответы пользователя в decisions.md, каждый неразобранный выбор — своим Q-ID в questions.md. Начни с результата и границ до API и модели данных; при изменении раннего ответа пересмотри зависимые предположения.
4. Покажи существенные вопросы в сообщении с вариантами, последствиями и рекомендациями. Можно несколько сразу, с отдельным Q-ID для каждого выбора; по просьбе пользователя задавай по одному. Предложи обсуждение либо делегирование показанного списка по discussion. Закрывай только решённые вопросы; новые требуют нового решения. Пользователь может сделать паузу, сменить направление или отложить обсуждение.
5. После смыслового этапа учти [выбор гуманизации](../references/editorial-pass.md) и сохрани [checkpoint](../references/checkpoint.md) со ссылками на вопросы и решения. Незавершённый существенный выбор остаётся блокирующим; неблокирующая отсрочка имеет причину и конкретный `return_at`.
6. Если пользователь хочет документы, переходи к [draft](draft.md); если правку существующих — к [revise](revise.md). После черновика продолжи обсуждение или ограниченное делегирование по discussion. При закрытых вопросах предложи планирование или ревью; с готовым планом — ревью или утверждение комплекта. Пользователь может сам запросить ревью с открытыми вопросами после исправления структуры. При паузе сохрани очередь и точку продолжения.

Проверка завершения: доступные факты изучены, ближайший выбор понятен, предположения не названы согласованиями, checkpoint сохранен. Этот флоу исследует и записывает плановые документы; код и конфигурацию продукта не изменяй.
