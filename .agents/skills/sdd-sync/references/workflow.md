# Перенос завершённого изменения

## 1. Выбери область

Используй change-id из запроса или однозначного контекста. Иначе перечисли активные
каталоги в `sdd/changes/`, исключая `archive`; единственный можно выбрать автоматически.
При нескольких кандидатах запроси выбор. Объяви выбранные проект и изменение.
Несколько явно названных изменений обрабатывай последовательно: сначала проверь
пересечения требований и зависимости, затем согласуй неоднозначный порядок.
Не выбирай победителя по времени файла.

Если активного каталога нет, найди архив по исходному change-id, включая `sync.md`.
При единственном совпадении сообщи «уже в архиве» и его путь без записи или
повторного применения старых требований. При нескольких совпадениях уточни выбор.

При существующем `sync.md`, продолжении прерванного переноса или переходе из
«без архива» к архивированию сначала прочитай [правила продолжения](recovery.md).
Они определяют проверку прежних записей и архивной цели до новых правок.

Для нового переноса назначь архив `sdd/changes/archive/YYYY-MM-DD-<change-id>/`
по текущей локальной дате. Если имя уже содержит такой префикс, второй не добавляй. SDD v1 принимает
change-id с начальной буквой; правило префикса полезно для ранее созданных архивов,
но не расширяет допустимые ID активных изменений.
Если цель уже существует при наличии активного изменения, остановись до любых
правок. Не объединяй каталоги, не перезаписывай архив и не выбирай другой суффикс
молча. Для режима без архива проверка этой цели не требуется.

## 2. Проверь завершение

Прочитай proposal, design, все `specs/**/spec.md`, tasks, state, вопросы и отчёты,
которые существуют. Спецификации изменения являются единственным источником
операций; не выводи отсутствующие требования из proposal или кода.

При наличии `execution/state.json` выполни операцию `read` через
`uv run --locked --script "<apply-root>/scripts/execute.py" --request "<request-file>"`,
где `<request-file>` содержит JSON
`{"operation":"read","args":{"directory":"<absolute-change-root>/execution"}}`.
Сохрани request вне каталогов скиллов и проекта. Требуй корректное состояние
`completed`, все задачи `accepted`, подтверждённую финальную проверку и совпадение
нормативных файлов с сохранённым basis. Прочитай связанные свидетельства и проверь,
что реализация с принятыми коммитами доступна в выбранной ветке проекта.
Отчёт `completed` другой версии документов не разрешает перенос.
Не изменяй state, integrity, статусы задач или журналы, чтобы пройти проверку.

При отсутствии исполнения используй явную приёмку пользователя и существующие
результаты проверок. Сами наличие tasks или отметка «готово» от исполнителя не
доказывают завершение. Если основание отсутствует, запроси его. Укажи в отчёте,
что реализацию приняли вне sdd-apply, и назови источник; новый прогон реализации
не требуется, если имеющихся свидетельств достаточно.

Открытая блокирующая задача, вопрос или провал проверки оставляет изменение
активным. Покажи конкретный блокер. Превью можно подготовить с этим предупреждением,
но текущие спецификации должны отражать только завершённое поведение.

До первого слияния проверь исходные документы; для ранее выполненных операций
используй сохранённые свидетельства только по [правилам продолжения](recovery.md):

```text
uv run --locked --script "<shared-root>/scripts/check.py" --project-root "<project-root>" --change "<change-id>" --stage documents
```

При наличии tasks добавь проверку `--stage plan`. Exit 0 подтверждает структуру,
а не завершение реализации. Ошибки и невыполненную проверку не объявляй успехом.
При отсутствии delta specs проверь основание завершения и архивируй без
синхронизации; общий check требует spec, поэтому к этому случаю неприменим.
Не создавай пустую capability для удовлетворения check.

## 3. Подготовь слияние

Составь таблицу для каждого REQ: операция, исходный файл/ID, целевой файл/ID,
результат (`изменить`, `уже применено`, `конфликт`) и затронутые AC.
Примени [правила слияния](merge.md) ко всем capabilities до записи первой.
Конфликт одной из них останавливает весь перенос этого изменения.

Для нового запуска сохрани снимок байтов исходных документов и затрагиваемых
текущих spec. Подготовь итоговые файлы вне рабочего дерева и проверь их смысл,
ID, AC, ссылки и сохранность незатронутого. Сравни реальные пути и хэши исходных
файлов перед записью: параллельные правки требуют нового анализа.

Если итоговые spec ссылаются на будущий архив, проверь их в отдельной копии проекта
с итоговым размещением: текущие spec содержат подготовленные байты, выбранное
изменение уже лежит по запланированному архивному пути. Включи нужные конфигурации
и входы проектного проверяющего средства; примени к этой копии ту же проверку
локальных ссылок. Сохрани команду, результат и хэши проверенных файлов. При
невозможности такой проверки сообщи ограничение и остановись до записи.
Это проверка будущего размещения, не успех проверки ещё не существующего архива.

В превью покажи эту таблицу, diff, основание завершения и будущий архив. Заверши
без записи spec, отчёта, временных файлов в проекте или архива.

## 4. Запиши и проверь текущие спецификации

Перед первой записью сохрани `sync.md` в активном изменении как обычный Markdown,
без нового `document_type`. Если такой файл уже существует, сначала определи,
является ли он отчётом предыдущего переноса; чужой документ не перезаписывай.
В отчёте укажи:

- исходный change-id, режим, основание завершения и выбранный архив;
- SHA-256 исходных файлов изменения;
- для каждого целевого файла путь, SHA-256 до и после переноса; отсутствие файла
  обозначь явно, включая запланированное удаление;
- операции по REQ/AC, место резервных копий и результаты проверок;
- состояние операции: подготовлена, спецификации проверены или перенос прерван.

Запиши подготовленные файлы. Проверь каждый по запланированному хэшу и перечитай
итоговое содержание по [формату текущих спецификаций](../../sdd-shared/references/current-specifications.md).
Исполни существующую проектную проверку текущих spec, если она есть. Проверку
ссылок на будущий архив подтверди результатом подготовленной копии и совпадением
записанных байтов; повтори её в рабочем проекте после перемещения. Остальные
проверки выполняй на месте. Общий
`check.py` проверяет комплект изменения, а не baseline; не выдавай его exit 0
за проверку текущих спецификаций и не запускай его на baseline как на изменении.

Перед архивом проверь:

- [ ] Все операции всех capabilities отражены в текущем содержании.
- [ ] Незатронутые требования и AC сохранены; нет дубликатов или потерянных связей.
- [ ] В baseline не попали operation/source, критерии удалённого требования,
      tasks, design, review или метаданные change-id из дельты.
- [ ] Исходные документы изменения не переписаны; текущие spec прошли доступные проверки.

Повторный расчёт слияния должен дать пустой diff. Сохрани результат в `sync.md`.
При режиме «без архива» заверши здесь и явно назови активный каталог.

При сбое записи перейди к [восстановлению](recovery.md) до дальнейших изменений.
После успешной проверки всех capabilities в режиме с архивом прочитай
[перемещение в архив](archive.md) и выполни его. В превью этот шаг не выполняется.
