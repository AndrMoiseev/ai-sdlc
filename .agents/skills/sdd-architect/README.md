# SDD Architect

Скилл готовит конкретные рекомендации по рефакторингу Kotlin/JVM-проекта на Gradle.
Вы получаете до пяти обоснованных изменений, очередь вопросов для проверки и
объяснение отклонённых находок. Приоритеты: модульность, снижение риска регрессий,
скорость разработки.

Запускайте явно: `$sdd-architect` в Codex или `/sdd-architect` в Claude Code.
Вызов без дополнительного текста запускает четыре последовательные фазы для
текущего проекта:

1. Explorer изучает проект и предлагает настройки анализа. Основной агент
   сохраняет настройки и план сбора данных в пределах запроса.
2. Другой Explorer собирает метрики и выполняет назначенные проверки. Сохраняет
   результаты и указывает, какие данные получить не удалось.
3. Архитектор выбирает от 8 до 12 связанных групп кандидатов. Каждую группу разбирает
   отдельный архитектор по её исходникам и потребителям. Если область запроса
   меньше, групп тоже может быть меньше.
4. Новый архитектор сопоставляет диагнозы, проверяет зависимости между изменениями
   и готовит итоговый отчёт с обоснованными приоритетами.

Между фазами дополнительное подтверждение не требуется. Найденные готовые отчёты
проверяются на пригодность в этом же цикле. Разобрать только указанные материалы
или отдельное изменение можно по явному запросу из примеров ниже.

При работе с исходниками файл `.sdd/architect/collection.json` содержит настройки
анализа. При каждом запуске скилл сверяет их с текущим проектом и сохраняет изменения. В отчёте
указывает, создал ли он файл, обновил его или подтвердил актуальность настроек.
Итоговый отчёт сохраняется в `docs/reports/{report-name}/report.md` внутри проекта.
В том же каталоге остаются все промежуточные материалы: план сбора, снимки метрик,
исходные отчёты инструментов, логи, анализ, заметки диагностики и карточки рекомендаций,
поручения агентам, их результаты и состояние работы.
Имя отчёта можно задать в запросе; иначе скилл выберет его по дате и теме анализа.
Для нового отчёта с занятым именем он добавит числовой суффикс. Кэши и служебные
окружения хранятся вне проекта.

После перерыва скилл сверяет сохранённые материалы с текущими исходниками и
настройками, затем продолжает незавершённую часть. Изменившиеся данные требуют
пересмотра зависимых выводов. Для дополнительного исследования агент формулирует
вопрос и объясняет, как ответ повлияет на рекомендацию.

Скилл оценивает модульность по ответственности пакетов, публичным контрактам и
направлению зависимостей. Для предложенных границ указывает проверки ArchUnit.
Рекомендации опираются на метрики и чтение исходников. Если доступны только отчёты,
результатом будут гипотезы и адресные проверки.

Для выбранных участков скилл явно подключает точечную диагностику
[sdd-code-design](../sdd-code-design/README.md). Она проверяет контракты и инварианты,
затем выбирает применимые правила проектирования. Например, сервис часто меняется,
а причина риска находится в используемом им доменном типе. Такой тип тоже входит
в проверку. Известный риск или предстоящая задача дают основание для диагностики,
даже если метрики не выделяют этот код.

Диагностика возвращает находки с доказательствами и вариантами изменений.
`sdd-architect` сопоставляет их последствия и затраты, затем определяет приоритет
рекомендаций. Нарушение эвристического правила само по себе не обосновывает
рефакторинг. В отчёте указана исследованная область и то, что осталось непроверенным.

В AI SDLC разбор предшествует планированию изменений. Выбранную рекомендацию
можно передать в [sdd-spec](../sdd-spec/README.md) для подготовки плана рефакторинга.
Общие обязанности архитекторов и Explorer заданы в [sdd-shared](../sdd-shared/README.md);
последовательность их работы и состав отчёта определяет `sdd-architect`.
Сам скилл завершает работу отчётом; реализация требует отдельного поручения.

| Задача | Пример запроса | Результат |
| --- | --- | --- |
| Полный цикл по умолчанию | `$sdd-architect` | Снимок метрик текущего проекта, точечная диагностика выбранных участков и очередь конкретных рекомендаций |
| Полный цикл для выбранной области | `$sdd-architect собери доступные метрики этого Kotlin/Gradle-проекта и предложи первые изменения. Начни с пакетов заказов и расчёта цен.` | Снимок измерений, проверенные кандидаты и очередь рекомендаций для указанной области |
| Разбор готовых отчётов | `$sdd-architect используй отчёты из указанного каталога и проверь находки по текущим исходникам. Особенно интересуют циклы пакетов.` | Проверка пригодности отчётов, диагнозы и конкретные варианты изменений |
| Отчёты без исходников | `$sdd-architect доступны только detekt, граф зависимостей и история. Определи, что стоит проверить в коде.` | Приоритетная очередь проверок с условиями принятия решения |
| Сравнение предложений | `$sdd-architect сравни рекомендации R1 и R2 из отчёта pricing-audit по их доказательствам и текущим исходникам. Объясни, с какой начать.` | Сопоставление последствий, затрат и зависимостей; обоснованный порядок или равный приоритет |
| Разбор изменения | `$sdd-architect оцени изменение между main и текущей веткой, включая потребителей за пределами diff.` | Рекомендации для затронутой области с учётом сопоставимости снимков |
| Проверка выполненного рефакторинга | `$sdd-architect проверь эффект рекомендации R1 после переноса расчёта цены. Исходный отчёт и ревизия указаны в карточке.` | Проверка поведения, границ и связанных метрик; пересмотр неподтверждённых ожиданий |
| Продолжение после перерыва | `$sdd-architect продолжи аудит pricing-audit из docs/reports/pricing-audit. Проверь актуальность сохранённых материалов и заверши отчёт.` | Проверка выполненной части и текущих исходников, продолжение с нужной фазы и ссылка на итоговый отчёт |

Числовой порог служит поводом исследовать код. Стабильный общий тип или допустимая
зависимость могут остаться без изменений даже при высоких показателях. Скилл
не обещает экономии времени по значениям метрик.
