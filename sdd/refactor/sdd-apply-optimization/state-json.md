# state.json в sdd-apply: устройство и назначение

Дата описания: 2026-10-28.
Статус: справочный материал исследования, не предложение изменить формат.
Основа: разбор текущего исходного кода в `skills/sdd-apply` и предыдущее
объяснение в разговоре. Исходная ревизия при подготовке материалов:
`b995d8bd64b36feedb1564248d9731d693a4fa35`; рабочее дерево может содержать
дополнительные изменения. Поведение при дальнейших изменениях нужно сверять
с указанными исходниками.

## Назначение

state.json — сохранённое состояние выполнения утверждённого плана:
какие задачи выполняются, кто ими занимается, что проверено, сколько осталось
попыток исправления и что мешает завершению.

Файл содержит текущие управляющие данные и ссылки. История, отчёты и снимки
могут храниться отдельно. Поэтому логическое содержимое состояния больше,
чем JSON, непосредственно видимый в state.json.

## 1. Расположение и версии

### Удалённые поля

В ходе оптимизации удалены следующие поля. Таблицы ниже описывают состояние
после этих изменений; старые сохранённые файлы автоматически не переписываются
и могут по-прежнему содержать исторические значения.

| Удалённое поле | Прежнее назначение | Что используется теперь |
|---|---|---|
| `basis.dirty_paths` | Список незакоммиченных изменений при допуске; защита от включения этих файлов в результат задачи. | Допуск требует чистого дерева. Проверки текущей чистоты Git и границ задачи сохраняются; исходный пустой список не хранится. |
| `basis.checks` | Полные отчёты допуска документов и плана. | Проверки выполняются при допуске; их отчёты используются внутри `validate()` и не сохраняются в основании. |
| `parallel_request` | Отдельная запись разрешения на параллельное выполнение, обычно дублировавшая инструкцию запуска. | `basis.instruction`. Отдельный параметр инициализации удалён. |
| `mode` | Выбор режима выполнения. | Выполнение всегда использует изолированные worktree; поле и параметр инициализации удалены. |
| `owner` | Идентификатор оркестратора, с которым сравнивался owner входящего события. | Проверка владельца удалена. Согласованность записи обеспечивают существующие проверки run_id, revision и файловая блокировка; они не определяют владельца запуска. |
| `previous_owner` | Предыдущий оркестратор после передачи владения. | Поле и событие `handoff` удалены. |
| `tasks[…].worktree.owner` | Копия идентификатора оркестратора в записи worktree. | Не сохраняется; привязка worktree к задаче остаётся. |
| `basis.document_records` | Сохранённая копия разобранных записей утверждённых документов. | Нужные runtime записи извлекаются из `HEAD` основной рабочей ветки через парсер sdd-shared. |
| `basis.plan_commit` | Отдельная ссылка на коммит утверждённого плана. | Документы читаются из `HEAD` репозитория `basis.project_root`. Исторический коммит допуска уже сохранён в `basis.head`. |
| `basis.sdd_shared` | Сохранённый абсолютный путь к runtime-зависимости. | `sdd-shared` загружается только из соседнего со `sdd-apply` каталога; при отсутствии критической зависимости выполнение останавливается. |
| `basis.document_paths` | Список документов, зафиксированный при запуске. | Фиксированные имена документов и список `specs/**/spec.md` из Git-дерева `HEAD` основной ветки вычисляются при обращении. |

Связанные изменения вне state.json:

- `owner` удалён из параметров `initialize` и конверта события; старые запросы
  с этим параметром больше не соответствуют API.
- Удалено сравнение context_id регистрируемой роли с owner оркестратора.
  Проверки независимости проверяющих от исполнителей сохраняются.
- `approved_documents` удалён из пакетов агентов. Вместо копии записей пакеты
  содержат пути `sources` и `project_root`, из `HEAD` которого читаются документы.

### Текущий формат

Обычное изменение:

```text
sdd/changes/<change-id>/execution/state.json
```

Рефакторинг:

```text
sdd/refactoring/<change-id>/execution/state.json
```

Runtime создаёт и принимает `schema_version: 3`. Вложенный `basis` имеет
собственную версию — `2`. Это разные форматы, их номера не обязаны совпадать.
Обычное чтение старое состояние автоматически не мигрирует.

В предварительном разборе обнаружена устаревшая JSON Schema версии 2,
не подключённая к runtime. Она уже удалена. Проверки формата и инвариантов
находятся в исполняемом коде:
[state.py](../../../skills/sdd-apply/scripts/lib/state.py),
[state_objects.py](../../../skills/sdd-apply/scripts/lib/state_objects.py),
[state_history.py](../../../skills/sdd-apply/scripts/lib/state_history.py)
и обработчиках переходов. Общее описание:
[state-storage.md](../../../skills/sdd-apply/references/state-storage.md).

## 2. Верхний уровень

| Поле | Содержание и назначение |
|---|---|
| `schema_version` | Версия состояния, сейчас `3`. |
| `change_id` | Идентификатор изменения или рефакторинга. |
| `work_kind` | Для рефакторинга явно записывается `refactoring`; отсутствие трактуется как `change`. |
| `run_id` | ID текущего запуска: UUID в виде hex-строки. При замене утверждённого плана создаётся новый. |
| `revision` | Номер сохранённого перехода. Начинается с `0`, увеличивается при каждом принятом новом событии. |
| `status` | Состояние выполнения: `active`, `blocked`, `completed`. |
| `basis` | Зафиксированное основание: план, документы, разрешение пользователя и исходное состояние Git. |
| `tasks` | Словарь состояний задач с ключами `TASK-…`. |
| `roles` | Реестр исполнителей, проверяющих и ревьюеров. |
| `baseline` | Начальный снимок документов текущего изменения и состояния Git. |
| `execution_head` | Ожидаемый HEAD основного дерева; обновляется при предусмотренных переходах и позволяет обнаруживать внешние изменения. |
| `event_head` | Ссылка на последнее принятое событие. Изначально `null`. |
| `event_index` | Ссылка на индекс событий по ID. Изначально `null`. |
| `blockers` | Причины блокировки выполнения и условия продолжения. |
| `updated_at` | Время последнего сохранённого перехода. |
| `final` | Результат финальной приёмки; до неё `null`. |
| `integrity` | SHA-256 сериализованного манифеста без самого поля `integrity`. |

Поля отдельных сценариев:

| Поле | Когда появляется |
|---|---|
| `previous_run` | При замене утверждённого плана через `revised_plan`. |
| `acceptance` | Для рефакторинга: записи критериев приёмки из плана, индексированные по ID. |
| `verification` | Для рефакторинга: записи проверок из плана, индексированные по ID. |
| `final_checks` | После регистрации проверок результата всего плана. Для рефакторинга необходимы; для обычного изменения могут добавляться отдельно. |

Выполнение использует изолированные worktree.
Зависимости, пересечения файлов и ресурсов ограничивают фактический параллелизм.

Источник: [state.py](../../../skills/sdd-apply/scripts/lib/state.py).

## 3. Основание выполнения: basis

basis отвечает на вопрос: на основании какого утверждённого объёма работ
началось выполнение?

| Поле | Значение |
|---|---|
| `schema_version` | `2`, версия входного основания. |
| `project_root` | Абсолютный путь к исходному проекту. |
| `work_kind`, `change_id`, `change_root` | Тип, идентификатор и каталог работы. |
| `instruction` | Текст разрешения пользователя и его источник. |
| `tasks` | Записи задач из утверждённого tasks.md. |
| `acceptance`, `verification` | Дополнительные записи плана рефакторинга. |
| `head` | Коммит допуска: начальный `execution_head`, часть идентичности основания проверок и сравнение при `revised_plan`. |
| `branch` | Рабочая ветка выполнения; смена ветки блокирует продолжение и приёмку. |

Список документов не хранится в basis. Он вычисляется из фиксированных имён
proposal.md, design.md, tasks.md и, для обычного изменения, путей `specs/**/spec.md`
в Git-дереве `HEAD` основной рабочей ветки. Незакоммиченные файлы в него не входят.

Здесь намеренно сохранены несколько представлений:

- `basis.tasks` — утверждённый список задач;
- `tasks["TASK-…"].plan` — план конкретной задачи рядом с её текущим состоянием.

Разобранные документы больше не сохраняются в basis. Runtime читает нужные
записи из `HEAD` основной рабочей ветки (`basis.project_root`) через парсер
sdd-shared. Пакеты агентов содержат пути `sources` и `project_root`.
HEAD отдельных worktree и незакоммиченные правки не используются для чтения
документов. Изменения объёма работы по-прежнему требуют `revised_plan`, поскольку
сохранённые задачи, критерии и проверки не обновляются автоматически.

Источник: [inputs.py](../../../skills/sdd-apply/scripts/lib/inputs.py).

## 4. Начальные поля задачи

| Поле | Начальное значение | Назначение |
|---|---|---|
| `plan` | Запись плана | Описание задачи, зависимости, покрываемые критерии и проверки. |
| `status` | `pending` | Текущая стадия задачи. |
| `attempt` | `0` | Счётчик запусков, увеличивается при `start`; это не счётчик исправлений. |
| `candidate` | `null` | Зафиксированный кандидат результата для проверок и ревью. |
| `evidence` | `[]` | Накопленные доказательства проверок. |
| `reviews` | `[]` | Результаты ревью. |
| `commits` | `[]` | Записи коммитов результата. |
| `blockers` | `[]` | Блокировки конкретной задачи. |
| `checks` | `[]` | Зарегистрированные проверки задачи. |
| `worktree` | `null` | Информация об изолированном рабочем дереве. |
| `roles` | `[]` | ID ролей, связанных с задачей. |
| `paths` | `[]` | Конкретные файлы, которыми владеет задача, относительно проекта. |

Бюджеты и циклы:

| Поле | Начальное значение | Назначение |
|---|---|---|
| `review_limit` | `3` | Максимальное число начатых раундов ревью. |
| `review_rounds_started` | `0` | Число зарезервированных/начатых раундов. |
| `review_rounds_completed` | `0` | Число завершённых раундов. |
| `active_review` | `null` | ID текущего раунда ревью. |
| `test_repair_limit` | `5` | Максимальное число циклов исправления после провала проверок. |
| `test_repair_cycles_started` | `0` | Число начатых циклов исправления. |
| `active_repair` | `null` | ID активного цикла, например `cycle-1`. |
| `repair_cycles` | `[]` | История завершённых циклов исправления. |
| `budget_decisions` | `[]` | Явные решения пользователя об увеличении лимитов. |

Бюджеты относятся к жизни задачи. Смена сессии, повторная попытка и интеграция
не обнуляют расход. При замене плана код переносит бюджетные поля
незавершённых задач.

Источники: [state.py](../../../skills/sdd-apply/scripts/lib/state.py),
[budgets.py](../../../skills/sdd-apply/scripts/lib/budgets.py).

## 5. Статусы задачи

| Статус | Смысл |
|---|---|
| `pending` | Задача ещё не запущена. |
| `running` | Исполнитель работает над задачей. |
| `verifying` | Кандидат зафиксирован, выполняются проверки. |
| `reviewing` | Идёт независимое ревью. |
| `integrating` | Результат подготовлен к переносу в основное дерево. |
| `committing` | Стадия фиксации и приёмки проверенного результата. |
| `repairing` | Выполняется исправление обнаруженного дефекта. |
| `blocked` | Продолжение задачи заблокировано. |
| `accepted` | Задача принята. |

Это не строго линейная последовательность. После интеграции нужно проверять
интегрированный кандидат. Дефект может вернуть задачу в repairing.
Изменение принятого предшественника может заблокировать зависимые принятые
задачи до повторной проверки.

Статус accepted у всех задач ещё не означает completed у всего выполнения:
нужна финальная приёмка на итоговом HEAD.

Источники: [transitions.py](../../../skills/sdd-apply/scripts/lib/transitions.py),
[roles.py](../../../skills/sdd-apply/scripts/lib/roles.py),
[budgets.py](../../../skills/sdd-apply/scripts/lib/budgets.py).

| `start_snapshot` | Снимок состояния при начале работы. |

| `check_registry` | Версионируемый реестр проверок с историей и подтверждением изменений. |
| `procedures` | Зарегистрированные незавершённые процедурные проверки. |

| `repairing_result` | Признак исправления уже полученного результата. |
| `candidate_commit` | Запись коммита, подготовленного для фиксации кандидата. |

Не все поля присутствуют одновременно. Их добавляют обработчики событий.
Это обзор основных полей, а не исчерпывающая машинная схема каждого перехода.

## 7. Кандидат и доказательства

candidate обычно содержит ссылку следующего вида; значения в угловых скобках
показаны как поясняющие placeholders:

```json
{
  "candidate_id": "candidate-<sha256>",
  "sha256": "<sha256>",
  "path": "candidates/<sha256>.json",
  "root": "<путь к рабочему дереву>"
}
```

Артефакт кандидата содержит source, manifest, checks, root. Это отдельный
формат ссылки, отличный от универсального `$object`.

Кандидат связывает ревью и проверки с конкретным состоянием кода и набором
проверок. Старый успешный прогон не становится доказательством для нового
кандидата автоматически.

Обычная запись evidence:

| Поле | Значение |
|---|---|
| `check_id` | Выполненная проверка. |
| `stage` | Стадия, например `self`, `independent`, `integration`, `final`. |
| `role_id` | Кто выполнил проверку. |
| `candidate` | Проверявшийся кандидат. |
| `outcome` | Исход; при изменении состояния во время прогона может быть `stale`. |
| `log` | Путь к подробному журналу. |
| `log_hash` | Контрольная сумма журнала. |
| `time` | Время регистрации. |
| `head` | Git HEAD проверяемого дерева. |

Подробный журнал дополнительно содержит состояние до и после проверки,
результаты команд и идентификаторы запуска и задачи.

Снимки source/baseline содержат хеши файлов только внутри текущего каталога
SDD-работы, исключая execution. Исходный код идентифицируется коммитом и чистым
состоянием Git; полного списка хешей файлов проекта runtime не строит.

Источники: [candidates.py](../../../skills/sdd-apply/scripts/lib/candidates.py),
[verification.py](../../../skills/sdd-apply/scripts/lib/verification.py),
[state.py](../../../skills/sdd-apply/scripts/lib/state.py).

## 8. Роли и worktree

Корневой roles — словарь полных записей ролей. Сохраняются параметры
регистрации, включая идентификаторы роли и контекста, вид роли, сведения
о запуске и возможностях хоста. Код добавляет:

- `task_id`;
- `status`, первоначально `active`;
- `registered_at`;
- после завершения — `result` и `trace`.

Основные виды ролей: executor, verifier, reviewer, final_verifier.
При восстановлении потерянный контекст может получить статус lost.
`tasks[…].roles` содержит ID связанных ролей. Сохранённое active само по себе
не доказывает, что агент ещё жив.

Начальное содержимое worktree:

| Поле | Значение |
|---|---|
| `path` | Путь к рабочему дереву задачи. |
| `workspace` | Общий каталог размещения worktree. |
| `base` | Исходный коммит. |
| `branch` | Ветка задачи. |
| `integrated` | Перенесён ли результат в основное дерево. |
| `resources` | Выделенные ресурсы: порты, БД и т. п. |
| `snapshot` | Исходный снимок. |

После удаления добавляется `removed: true`. История результата сохраняется
после удаления рабочего дерева.

Источники: [roles.py](../../../skills/sdd-apply/scripts/lib/roles.py),
[worktrees.py](../../../skills/sdd-apply/scripts/lib/worktrees.py).

## 9. Блокировки и финальная приёмка

blockers существует на уровне всего выполнения и отдельной задачи.
Минимальный смысл записи:

```json
{
  "reason": "причина",
  "resume_condition": "что нужно для продолжения"
}
```

По ситуации добавляются task_id, пути, журнал, ожидаемый HEAD, материалы
конфликта и другие данные. Примеры причин: spec_conflict, baseline_failed,
execution_head_changed, review_limit_reached, test_repair_limit_reached,
final_incomplete.

final_checks хранит проверки результата всего плана:

| Поле | Назначение |
|---|---|
| `checks` | Текущий набор обязательных финальных проверок. |
| `revision`, `history` | Версия набора и история изменений. |
| `evidence` | Доказательства финальных прогонов. |
| `procedures` | Незавершённые процедурные проверки. |
| `failures` | Зарегистрированные провалы. |
| `inventory` | Основание выбора проверок. |
| `repairs` | При появлении — история назначенных исправлений. |

После finalize поле final содержит:

| Поле | Значение |
|---|---|
| `head`, `time` | Коммит и время приёмки. |
| `accepted_criteria` | Подтверждённые критерии. |
| `missing` | Неподтверждённые обязательства и причины. |
| `evidence` | Доказательства финальной приёмки. |
| `recommendations` | Рекомендации/технический долг из ревью. |
| `decisions` | Решения по рекомендациям: defer или reject с причиной. |
| `commits` | Коммиты по задачам. |
| `result` | complete или partial. |

Для отдельных сценариев добавляются project_checks, а для рефакторинга —
основание проверки, выведенные из действия проверки, принятые задачи
и критерии целого результата.

При partial выполнение становится blocked; при успешной финальной
приёмке — completed.

Источники: [final_checks.py](../../../skills/sdd-apply/scripts/lib/final_checks.py),
[finalize.py](../../../skills/sdd-apply/scripts/lib/finalize.py).

## 10. Внешние объекты: $object

Вместо массива отчётов или большого объекта в сохранённом JSON может быть
ссылка. Ниже схематический пример, а не валидный реальный дескриптор:

```json
{
  "$object": {
    "path": "objects/ab/<полный-sha256>.json",
    "sha256": "<полный-sha256>",
    "bytes": 12345,
    "kind": "array"
  }
}
```

| Часть ссылки | Смысл |
|---|---|
| `path` | Путь относительно execution; первые два символа hash задают подкаталог. |
| `sha256` | Контрольная сумма сохранённых JSON-байтов. |
| `bytes` | Длина этих байтов. |
| `kind` | Тип значения: object, array или string. |

В отдельные объекты принудительно выносятся непустые истории и снимки,
включая evidence, reviews, commits, repair_cycles, budget_decisions, roles,
check_registry, baseline, start_snapshot, prior_result.

Другие значения выносятся при размере более 4096 байт сериализованного
представления, с исключениями для управляющих структур basis, tasks
и объектов задач. Размер оценивается с учётом упаковки дочерних значений.

Поэтому начальное `evidence: []` после накопления результатов обычно
становится ссылкой. Логически это по-прежнему список доказательств.
Одинаковые канонические JSON-байты используют один объект.
Загрузка выполняется по мере обращения к полям.

Источник: [state_objects.py](../../../skills/sdd-apply/scripts/lib/state_objects.py).

## 11. История и сохранение переходов

Внутри state.json нет растущего массива events.

- event_head указывает на последнее событие; каждое событие связано с предыдущим.
- event_index указывает на индекс по ID событий для поиска повторных запросов.
- revision защищает от записи поверх более нового состояния.
- integrity позволяет обнаружить изменение манифеста.

Переход передаётся через полный конверт события:

```json
{
  "event_id": "unique-operation-id",
  "run_id": "saved-run-id",
  "expected_revision": 12,
  "type": "event-name",
  "task_id": null,
  "payload": {}
}
```

Для события задачи вместо null передаётся её ID. Повтор того же конверта
возвращает сохранённый результат без повторного перехода. Использование
того же ID с другим содержимым отклоняется.

Под эксклюзивной блокировкой сначала записываются неизменяемые объекты
и новая история, затем атомарно заменяется state.json. Эта замена фиксирует
ревизию. Если она не состоялась, прежнее состояние остаётся действующим,
а оставшиеся новые объекты не считаются принятыми событиями.

Для восстановления прерванных Git-операций дополнительно сохраняются
журналы намерений внешних действий. Поэтому журнал событий и манифест
не являются единственными данными восстановления.

При замене плана прежний манифест архивируется, run_id меняется, результаты
предыдущих попыток связываются через объекты. Архивные ссылки — одна
из причин не удалять объекты во время активного выполнения.

Хеши обеспечивают проверку целостности, но не аутентификацию против того,
кто способен переписать всё хранилище.

Источники: [state.py](../../../skills/sdd-apply/scripts/lib/state.py),
[state_history.py](../../../skills/sdd-apply/scripts/lib/state_history.py),
[effects.py](../../../skills/sdd-apply/scripts/lib/effects.py),
[resume.py](../../../skills/sdd-apply/scripts/lib/resume.py).

## 12. Чтение и аудит

| Операция | Что показывает или проверяет |
|---|---|
| `read`, `view: "compact"` | Статусы, ревизию, блокировки, бюджеты, активные роли и доступные задачи. |
| `read`, `view: "full"` | Сохранённый манифест со ссылками; вложенные истории целиком не раскрывает. |
| `read_object` | Один объект по дескриптору с проверкой целостности; вложенные ссылки сохраняются. |
| `audit` | Все текущие объекты и полную цепочку/индекс событий. |

Обычное чтение проверяет манифест, привязку к корню, ограничения статусов,
голову истории и прочитанные объекты. Оно не является полным аудитом истории.
resume и finalize выполняют полный аудит перед переходом.

available_tasks отражает допустимость по зависимостям и конфликтам,
но не заменяет остальные проверки допуска задачи.

Для резервной копии нужен весь каталог execution. Одного state.json
недостаточно. Ручная правка полей обходит протокол переходов; штатные записи
выполняются через execute.py.

Контракт API: [api.md](../../../skills/sdd-apply/references/api.md).

## 13. Что это даёт исследованию оптимизации

Описание показывает несколько разных обязанностей состояния: управление
задачами, доказательства приёмки, восстановление, учёт бюджетов и история.
Наличие похожих данных в разных местах пока не доказывает избыточность.

При изучении каждого кандидата на сокращение нужно установить его потребителя,
время жизни, способ восстановления и связь с проверками целостности.
Конкретные решения об удалении полей, объектов или операций ещё не приняты.
