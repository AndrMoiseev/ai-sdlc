# Контракт Git-чекпойнтов

Основание: [decisions.md](decisions.md), задача 1 [plan.md](plan.md).
Контракт реализован в задачах 2–5; результаты — в [implementation.md](implementation.md).
Этот документ не является машинным SDD-пакетом.
Маршруты `sdd/changes/<change-id>` и `sdd/refactoring/<change-id>` сохраняются.

## Термины и границы доверия

| Термин / поле | Значение |
|---|---|
| Принятая точка / `accepted_commit` | Коммит, на который сейчас указывает служебная Git-ссылка выбранной работы и worktree. |
| Текущее состояние / `head` | Полный OID текущего `HEAD`; сокращённые SHA и имена веток не сохраняются как коммиты. |
| Переход / `base_commit` → результат | Одна выполняемая работа от принятой точки, с проверкой полного набора изменений. |
| Принятие состояния / `state_acceptance` | Явное решение пользователя считать конкретный коммит допустимым основанием. |
| Поручение / `work_authorizations` | Действующее разрешение на конкретную работу; содержит область и источник решения. |
| Основание ревью / `reviewed_commit` | Неизменяемый коммит, содержимое которого действительно читали рецензенты. |

Принятие состояния снимает возражение к состоянию и исторической актуальности
документов. Оно не выдаёт поручения, не одобряет план вместо пользователя и
не закрывает вопросы решениями, которых пользователь не принимал. Уже выданное
поручение сохраняется до выполнения, отмены или замены; исполнение поручения
не отменяет его из-за изменения документов. Скрипт проверяет структуру записи,
но не может удостоверить, что пользователь действительно произнёс её текст.
Основной агент устанавливает этот факт из разговора и передаёт решение скрипту.

## Идентичность и Git-ссылка

Ключ работы: `{work_kind, change_id}`, где `work_kind` — `change|refactoring`,
а `change_id` проходит существующую проверку slug. Корень репозитория находят
через Git; каталог проекта сам по себе не доказывает идентичность репозитория.

Каноническая ссылка:

```text
refs/sdd/checkpoints/<work_kind>/<change-id>/<worktree-key>
```

`worktree-key` — полный SHA-256 UTF-8 строки канонического абсолютного пути
Git-каталога данного worktree (`git rev-parse --absolute-git-dir`, затем
`realpath` и платформенный `normcase`). Это хэш идентичности расположения,
не манифест документов и не доказательство согласования. Разные worktree
имеют разные Git-каталоги, даже когда разделяют common-dir и change-id.
Ветка не входит в имя: смена ветки обнаруживается по отличию `HEAD` от ссылки;
смена ветки на тот же коммит не меняет принятого содержимого.

Перемещение/пересоздание worktree или clone может дать отсутствующую ссылку:
нужно принять исходную точку заново. Старые ссылки не подбираются эвристически
по одному change-id и автоматически не удаляются. Несуществующий объект,
ссылка на не-коммит или символическая checkpoint-ссылка — ошибка с диагностикой;
не следовать ей при записи. Использовать Git-команды, не прямые записи `.git`.
Не предполагать перенос этих ссылок обычным clone/push.

## Наблюдение и переходы

Наблюдение охватывает весь репозиторий: индекс, unstaged, untracked, удаления,
переименования, конфликты и грязные submodule. Игнорируемые Git файлы не входят
в состояние автоматически. Если результат работы должен включать такой файл,
он становится явно выбранным отслеживаемым файлом до проверки результата.
Читать NUL-разделённый статус; пути с пробелами и Unicode не разбивать по строкам.

| Наблюдение на входе | Следующий шаг |
|---|---|
| Git недоступен / это не репозиторий | Вернуть `git_unavailable` / `not_repository`, не создавать Git автоматически. |
| Нет исходного коммита | `unborn_head`: пользователь определяет первоначальный набор и создание исходного коммита. |
| Есть конфликты или незавершённая Git-операция | `git_operation_in_progress`: завершить или отменить её отдельным решением; не создавать чекпойнт. |
| Дерево грязное | `dirty`: показать изменения, получить выбор «удалить» или «закоммитить». Ничего не удалять автоматически. После выбранного действия повторить наблюдение. |
| Дерево чистое, ссылки нет | `acceptance_required`: пользователь принимает конкретный `HEAD`. |
| Дерево чистое, ссылка отличается | `head_mismatch`: показать оба OID и разницу деревьев, включая отсутствие общего предка; пользователь принимает текущий коммит либо отдельно поручает восстановление. |
| Дерево чистое, ссылка равна `HEAD` | `ready`: продолжить только действующее поручение. |

При грязном дереве принятие `HEAD` не принимает грязные файлы. Коммит по выбору
пользователя сначала проверяется и создаётся, затем принимается как конкретный
коммит. Чистота нужна на входе и выходе; собственные правки внутри открытого
перехода нормальны и не вызывают предложение удалить их при каждом вызове.

Открытый переход хранит в памяти вызывающего агента `base_commit`, имя ссылки,
ожидаемое старое значение, поручение и проверенный набор изменений. После потери
контекста грязное дерево не объявляется автоматически своей работой: агент
показывает сохранённое поручение и изменения, затем получает выбор пользователя.
Не нужен постоянный журнал всех переходов для допуска к работе.

## API операций и результаты

Добавить `sdd_shared.checkpoints` и CLI `scripts/checkpoint.py` с командами
`inspect`, `accept`, `create`. Все команды принимают `project_root`, `work_kind`,
`change_id`; запись доступна основному агенту. Python API отделяет Git-адаптер
от чистой классификации состояний для детерминированных модульных тестов.

```text
inspect(project_root, work_kind, change_id)
accept(..., expected_head, expected_accepted, decision)
create(..., expected_head, expected_accepted, reviewed_changes, instruction, message)
```

`expected_accepted=null` означает проверку отсутствия ссылки, а не отсутствие
проверки. `decision` содержит `id`, `response`, `source`, `date` и
`accepted_commit`; целевой коммит обязан равняться `expected_head`.
`instruction` содержит непустые `text` и `source`, а также доступные USER-ID;
это аттестация вызывающего агента, а не автоматически найденное разрешение.

`reviewed_changes` — временное наблюдение проверенного перехода: точный набор
путей и ожидаемое содержимое/режимы Git-дерева, включая удаления и обе стороны
переименований. Одних имён файлов недостаточно: файл мог измениться после
проверки. Допустимо вычислять временный tree OID через отдельный индекс вне
рабочего дерева. Этот объект не превращать в сохраняемый манифест согласований.

JSON-результат имеет `schema_version: 2`, `operation`, `status`, `work_kind`,
`change_id`, `checkpoint_ref`, `head`, `accepted_commit`, `dirty`, `changes`,
`diagnostics`. Для записи добавить `previous_accepted`, `created_commit`
(null при отсутствии нового коммита) и `ref_updated`. Не писать туда ответ
«успех» при неизвестном исходе Git-команды. Диагностика содержит машинный `code`
и понятные `message`, `next_action`. Exit 0 — успешно завершённая операция
(для inspect любое успешно прочитанное состояние); 1 — условие перехода
не выполнено; 2 — невозможность проверки или ошибка инструмента.

### Принятие

`accept` проверяет чистоту, точный `HEAD`, прямую ссылку и ожидаемое старое
значение. Затем выполняет compare-and-swap через `git update-ref` с явным
старым OID (нулевой OID для отсутствующей ссылки). По возможности включить
проверку текущего head-ref и обновление checkpoint-ref в одну транзакцию
`update-ref --stdin`; после операции повторно прочитать `HEAD`, ссылку и статус.
Изменение `HEAD`/дерева до завершения даёт `concurrent_change`, а не `ready`.
Ссылка всё ещё обозначает только явно принятый коммит, не неожиданное новое состояние.
Повторное принятие уже принятого чистого коммита — `unchanged`, без коммита.

Решение можно записать reflog-сообщением с USER-ID/source. Это локальная
диагностика, не обязательный исторический журнал. Постоянная USER-запись
попадает в следующий обычный чекпойнт и ссылается на уже существующий принятый
коммит. Не изменять рабочие файлы внутри `accept`, иначе операция сама нарушит
условие чистоты. Если следующей работы нет, достаточно сообщения результата
и Git-ссылки; специальный коммит только ради собственного OID не нужен.

### Создание и сбои

1. Проверить `HEAD == expected_head == expected_accepted`, отсутствие чужой
   Git-операции, действующее поручение и весь набор изменений. При неизвестных
   файлах или изменённом после ревью содержимом вернуть `changes_changed`.
2. Если изменений нет, вернуть `unchanged`; не создавать пустой коммит.
3. Подготовить индекс только явными проверенными путями (без `git add -A`
   без pathspec). Проверить staged tree против проверенного дерева. Чужие
   staged-изменения нельзя молча включать, сбрасывать или заменять.
4. Создать обычный Git-коммит с hooks, затем проверить его единственного
   родителя, дерево, фактический `HEAD` и чистоту. Hook может изменить файлы
   или индекс: несовпадение означает ошибку, а не принятие изменённого результата.
5. Обновить checkpoint-ref только compare-and-swap от исходного OID.
   Успех требует повторной проверки `HEAD == ref == created_commit` и чистоты.

Git не предоставляет общей атомарной блокировки ветки, индекса, файлов и
произвольных редакторов. Основной агент сериализует собственные операции;
проверки до/после обнаруживают внешние гонки. Не обещать полной изоляции от
постороннего процесса. Увиденную гонку не исправлять reset/clean или
безусловным повтором записи. Данные сохраняются, следующий шаг — новое наблюдение.

| Отказ | Результат и восстановление |
|---|---|
| До commit / hook отказал, `HEAD` прежний | `commit_failed`, ссылка прежняя; оставить рабочие файлы и индекс, описать их фактическое состояние. |
| Commit появился, но проверка дерева/родителя/чистоты не прошла | `commit_created_unaccepted`, вернуть OID; ссылку не двигать, показать изменения. |
| Commit успешен, ref CAS не прошёл | `commit_created_unaccepted`, показать старую и наблюдаемую ссылку; не перетирать чужую запись. |
| Потерян ответ команды / процесс завершился между commit и ref | Повторный inspect покажет расхождение; после рестарта принять текущий чистый коммит решением пользователя. Не угадывать успешность по сообщению коммита. |
| Ref уже обновлён, но финальная проверка выявила новое изменение | `concurrent_change`, сообщить `ref_updated=true`; не откатывать ни чужой HEAD, ни ссылку автоматически. |

Такой путь восстановления намеренно обходится без долговечного transaction
journal: обычное принятие текущего состояния закрывает частичный сбой.

## Схемы документов и отчётов

Поднять публичный `api_version` до 2 и версию JSON-ответов check/checkpoint до 2.
Поднять до `schema_version: 2` только изменённые форматы `state`, `review`,
`decisions` (журнал USER-записей). Нормативные proposal/spec/design/tasks,
questions, summary и индекс линз остаются версии 1: их структуры не меняются.
`document_schema` выбирает допустимую версию по work_kind И document_type.
Все новые форматы требуют явных `work_kind` и `change_id`.

В `state.yaml` сохранить существующие поля процесса; заменить
`checks: {structure, freshness}` на `checks: {structure}`. Не добавлять
сохранённое `ready` или «текущую» ссылку как источник истины. Git-состояние
вычисляется на чтении. `state.md` остаётся прозой с поручением, выполненной
частью, источником решения и следующим шагом. Не сохранять собственный OID
в создающем его коммите. `base_commit` допустим в диагностике перехода,
но не требует равенства текущему HEAD после завершения.

Отчёт ревью v2 сохраняет прежние поля, кроме `inputs`, `inputs_after`,
`freshness`. Их заменяет единственный `reviewed_commit`. Рецензент читает
неизменяемое дерево этого коммита; все линзы одного запуска имеют один OID.
Авторские правки сначала становятся чекпойнтом, затем запускается ревью;
сам отчёт входит в следующий коммит. Изменение рабочего дерева во время ревью
не меняет основание отчёта. Если рецензент читал рабочие файлы без гарантии
соответствия коммиту, результат `incomplete`, а не выдуманный reviewed_commit.

USER-запись v2 сохраняет `sdd_record`, `id`, `kind`, `scope`, `response`, `date`,
существующие optional-поля и правила supersedes/status; требует явную
идентичность работы. Вместо `inputs` использовать `basis_commit` — существующий
коммит, к которому относился ответ. Для нового `kind: state_acceptance`
использовать `accepted_commit` вместо `basis_commit`, `scope: {}` и обязательный
`message` как источник ответа. Такой record не входит в work_authorizations.
Для остальных kind сохранить прежнюю структуру scope и не расширять её
принятием состояния. План одобряется `plan_approval`, исполнение подтверждается
поручением из сессии/входа sdd-apply. Один ответ пользователя может явно
содержать оба решения; агент записывает их отдельно.

OID проверяется по object-format репозитория: полный hex SHA-1 либо SHA-256,
с проверкой типа объекта для текущих операций. Недоступный исторический
коммит отчёта означает диагностический `evidence_unavailable`, не требование
заново одобрить уже принятое состояние. Не обращаться к объектам всей истории
при каждом продолжении. Структурная ошибка нового текущего пакета остаётся
ошибкой формата; это отдельно от устаревшего исторического основания.

## Проверки, миграция и потребители

`check.py` разделяет `checkpoint_status`, `review_status`, `approval_status`
и `discussion_status`. Только checkpoint_status отвечает за совпадение Git
и чистоту на входе. Старый отчёт относительно нового HEAD получает
диагностику `changed_since_review` (при необходимости — diff); она не делает
действующее поручение неприменимым. Отсутствующее ревью, открытые находки и
последствия изменений остаются видимыми. Не требовать повторного ревью только
из-за несовпадения OID, если состояние уже принято пользователем или проверенным
собственным переходом. `approval_status.approved` означает существующее
действующее решение нужного kind, `ready` — применимое разрешение плюс
структурно пригодный текущий пакет и разрешённые текущие блокирующие вопросы;
никаких сравнений исторических manifests с текущими файлами.

Пакет v1 не считается принятым автоматически, даже если старые хэши совпали.
Вернуть `migration_required`, показать старые решения как контекст, получить
принятие текущего чистого HEAD, затем мигрировать текущие state/журнал/отчёты
отдельным разрешённым переходом. Для старого отчёта без достоверного OID не
подставлять текущий HEAD: сохранить его как legacy evidence вне активного
v2-набора. Старые поручения можно подтвердить из разговора без повторного
одобрения содержания; при неизвестном источнике не выдумывать подтверждение.
Обновить связку потребителей вместе; нет бессрочного двойного режима и
требования одновременно предъявлять manifest и Git-ссылку.

| Потребитель | Замена |
|---|---|
| shared snapshots.py / snapshot CLI | Убрать из нового публичного пути byte manifests нормативных документов; команда сообщает о переходе на checkpoint inspect, не возвращает правдоподобный старый формат. |
| shared documents/reviews/validation | Версии по типам, commit-поля, раздельная диагностика/разрешения; удалить исторические hash-gates. |
| spec resume/checkpoint/review/user-review/plan | Вход по Git; ревью коммита; поручение действует при собственных ожидаемых правках; основной агент делает checkpoint. |
| spec explanation/preview | Ссылка на исходный коммит вместо manifest документов; самостоятельный хэш HTML для соответствия проверенного HTML оставить. |
| apply inputs.py | Проверить общий API v2, принятую точку и поручение. Вместо `basis.manifest` хранить `basis.plan_commit` и `basis.document_paths` (список существующих нормативных путей без хэшей). |
| apply state/assert_basis, resume, roles, final_checks | Удалить сравнение текущих нормативных bytes с basis.manifest. Пути читать из document_paths; содержание исходного утверждённого плана при необходимости из plan_commit. Изменённый принятый план согласовать с областью исполнения, не считать acceptance разрешением новых задач. |
| apply candidates/state_objects/check_registry/transfer | Сохранить независимую целостность кандидата, отчётов проверок, реестра и transfer-пакета. Слово manifest здесь само по себе не основание удалить проверку. |

При смене нормативного basis активного исполнения нужен явный переход текущей
области задач: показать последствия и сохранить выполненные результаты.
Исторические нормативные хэши не служат скрытым запретом такого перехода.
Версию формата persisted execution basis повысить там, где старый manifest
заменяется plan_commit/document_paths; старое состояние требует явной миграции,
а не KeyError или тихого присвоения текущего HEAD старому решению.

## Проверяемые свойства реализации

Детерминированные автотесты скриптов покрывают таблицы состояний и отказов,
CAS с отсутствующей ссылкой, разные kind/worktree, неприменимость acceptance
как поручения, сохранение поручения после собственного перехода, schema migration
и отсутствие historical hash-gates. Минимальные настоящие Git-тесты нужны для
семантики индекса, Unicode/rename/delete, hooks и CAS; варианты правил проверять
через адаптер. Лимит и окружение — по AGENTS.md, каждый обязательный набор
отдельно, не более 60 секунд. Модельные/поведенческие эвалы исключены.

В задаче 1 тесты и Git-записи не запускались; создан только этот документ.

## Уточнения по результатам реализации и ревью

Вход apply имеет schema_version 2, состояние исполнения — schema_version 3.
В основание вместе с `plan_commit` и `document_paths` входят неизменяемые
`document_records`: роли и итоговые критерии используют принятый план,
а не более поздние правки файлов. Замена плана остаётся отдельным переходом.

`execution_head` хранит известный коммит основной рабочей копии исполнения.
Собственные проверенные коммиты обновляют его. При resume грязная основная
копия блокирует продолжение до выбора пользователя; неизвестный чистый HEAD
требует точного явного принятия с текстом ответа и его источником. Такое
принятие не меняет основание плана или состав задач. Создание worktree,
интеграция и refresh не могут молча принять внешний HEAD; сначала требуется
согласовать его через resume. Уже выполняемая работа в task worktree сохраняется.

Checkpoint-инспекция отвергает assume-unchanged/skip-worktree флаги индекса,
которые могут скрыть незакоммиченные изменения от обычного Git status.
Диагностика не меняет эти флаги, файлы или принятую ссылку.
