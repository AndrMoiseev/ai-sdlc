# Маршрут рефакторинга SDD

## Выбор маршрута и его границы

```yaml
sdd_record: requirement
id: REQ-refactoring-entry
operation: add
```

Маршрут сохраняет функциональность, совместимость наблюдаемых контрактов и
действующие ограничения. Он допускает изменение внутреннего устройства и
архитектурных решений. Пользователь выбирает его явно либо агент выбирает его
по смыслу пользовательского ввода без обязательного подтверждения. При сомнении
агент уточняет желаемый флоу. При обоих способах выбора он сообщает выбранный
маршрут и ограничения до зависимой работы.

Выбор маршрута не отменяет явного вызова sdd-spec/sdd-apply и их условий
согласования и выполнения. При resume сохраняются основание выбора и факт
уведомления; смена маршрута требует нового уведомления. Обнаруженный выход за
границы не маскируется как рефакторинг.

Основание: [выбор](../../decisions.md#неявный-выбор-агентом),
[границы](../../decisions.md#принятая-граница-сохранения).

### Явный и неявный выбор

```yaml
sdd_record: acceptance
id: AC-refactoring-entry-notice
requirement: REQ-refactoring-entry
conditions: Пользователь явно просит рефакторинг либо агент уверенно выбирает его по смыслу запроса в активном SDD-процессе
expected: Агент сообщает маршрут и ограничения, сохраняет основание выбора и продолжает без обязательного вопроса о подтверждении маршрута
```

### Сомнение или функциональное изменение

```yaml
sdd_record: acceptance
id: AC-refactoring-entry-conflict
requirement: REQ-refactoring-entry
conditions: Запрос неоднозначен либо для предложенного преобразования требуется изменить наблюдаемый контракт
expected: Агент обозначает неопределённость или конфликт и получает выбор пользователя до зависимой работы, сохраняя доступное исследование и уже выполненную часть
```

## Размещение и комплект документов

```yaml
sdd_record: requirement
id: REQ-refactoring-documents
operation: add
```

Работа размещается в `sdd/refactoring/<id>/`. Нормативный комплект — proposal
и design, а после разрешённого планирования также tasks. Отдельные specs не
создаются и не требуются. Журнал, вопросы, state, премортем, ревью и материалы
исполнения сохраняются по общему процессу относительно корня этой работы.

Поиск, явный выбор, ссылки, снимки, согласования и исполнение различают работы
с одинаковым ID в `sdd/changes` и `sdd/refactoring`. Неоднозначный выбор не
разрешается случайным порядком каталогов. Правила безопасности путей сохраняются.

Основание: [комплект](../../decisions.md#документы-рефакторинга),
[расположение](../../decisions.md#размещение-рефакторингов).

### Комплект без specs

```yaml
sdd_record: acceptance
id: AC-refactoring-no-specs
requirement: REQ-refactoring-documents
conditions: Проверяется полный комплект работы рефакторинга без каталога specs
expected: Documents проверяет proposal и design, plan дополнительно проверяет tasks; отсутствие specs не является ошибкой и вымышленная функциональная дельта не требуется
```

### Однозначная идентичность работы

```yaml
sdd_record: acceptance
id: AC-refactoring-work-identity
requirement: REQ-refactoring-documents
conditions: В двух корнях существуют работы с одинаковым ID либо предложен путь вне допустимого корня
expected: Выбор по полному контексту маршрута разрешается однозначно, выбор только по неоднозначному ID требует уточнения, выход за допустимый корень отклоняется
```

## Контракт и архитектура в design

```yaml
sdd_record: requirement
id: REQ-refactoring-design-contract
operation: add
```

Design описывает исходные и целевые границы, область преобразования, сквозные
результаты и их проверяемые части, сохраняемые обязательства и архитектурные
решения. Ссылки на существующие спецификации и свидетельства задают исходное
основание; отсутствие baseline явно фиксируется, известные пробелы не выдаются
за доказанное поведение. Доступные факты исследуются до согласования.

Новые или пересмотренные DEC связываются с критериями этого design без
искусственных REQ. Для пересмотра сохраняется ссылка на исходное решение и
объяснение замены. Проверка отсутствия регрессии и проверка достижения новой
структуры остаются разными обязательствами. Изменение утверждённого внешнего
поведения требует пересмотра области, а не изменения теста ради зелёного прогона.

Основание: [модель](../../decisions.md#декомпозиция-по-результату-и-модулям),
[изменение границ](../../decisions.md#изменение-тестов-при-изменении-границ).

### Архитектурное решение без функционального требования

```yaml
sdd_record: acceptance
id: AC-refactoring-design-decision
requirement: REQ-refactoring-design-contract
conditions: Design вводит выделенный тип идентификатора или пересматривает границу модулей при сохранении внешнего поведения
expected: Решение связывается с проверяемыми критериями design и исходными решениями при пересмотре, отдельный REQ в specs не требуется
```

### Неполное исходное основание

```yaml
sdd_record: acceptance
id: AC-refactoring-baseline-gap
requirement: REQ-refactoring-design-contract
conditions: Для сохраняемого обязательства отсутствует спецификация или достаточное свидетельство поведения
expected: Документы фиксируют доступные источники и пробел, задача подготовки проверки обеспечивает исходное свидетельство до изменения соответствующего поведения, существенная неопределённость не скрывается как доказанная эквивалентность
```

## Декомпозиция по результату и области

```yaml
sdd_record: requirement
id: REQ-refactoring-task-contract
operation: add
```

Каждая задача содержит стабильный ID, область, локально проверяемый результат,
ссылки на результаты design, сохраняемые обязательства, зависимости и проверки.
Номера, статусы и ограничения параллельности сохраняют прежнее назначение.
Декомпозиция учитывает части результата, модули, объём и зависимости.

Несколько задач могут вносить вклад в один сквозной критерий. Ссылка на критерий
не означает его полного выполнения. План проверяется на полноту области и
вклада задач; завершённость целого подтверждается отдельно. Для одного результата
не требуется одна задача на всю кодовую базу или отдельный критерий design на
каждый файл. Необходимые тесты входят в задачи преобразования.

Основание: [согласованная декомпозиция](../../decisions.md#декомпозиция-по-результату-и-модулям).

### Массовое изменение типа

```yaml
sdd_record: acceptance
id: AC-refactoring-cross-module-plan
requirement: REQ-refactoring-task-contract
conditions: Выделенный тип идентификатора внедряется в core и несколько потребляющих модулей
expected: План допускает отдельные задачи по частям результата и модулям, несколько задач ссылаются на один сквозной критерий, каждая имеет собственные локальные критерии и проверки
```

### Покрытие и граф

```yaml
sdd_record: acceptance
id: AC-refactoring-plan-validation
requirement: REQ-refactoring-task-contract
conditions: В плане пропущен критерий design, отсутствует локальный результат, нарушена ссылка или есть цикл зависимостей
expected: Структурные дефекты диагностируются с ID, смысловая проверка выявляет пропущенную область даже при формально существующей ссылке; множественный вклад в один критерий сам по себе не является ошибкой
```

## Работоспособные промежуточные состояния

```yaml
sdd_record: requirement
id: REQ-refactoring-intermediate-state
operation: add
```

Каждая принятая задача оставляет работоспособное состояние с выполненными
локальными критериями и сохраняемыми обязательствами. Частично выполненная
сквозная цель допустима, неработоспособность принятого состояния — нет.
Внутри ещё не принятой задачи обычная разработка и исправления допускаются.

Временные адаптеры и преобразования описываются в design; удаление включается
в план и итоговые критерии. Зависимости и интеграция обеспечивают проверяемость
промежуточных состояний. Существующие правила независимой проверки, ревью и
интеграции продолжают действовать.

Основание: [промежуточные результаты](../../decisions.md#работоспособность-промежуточных-результатов).

### Переход через адаптер

```yaml
sdd_record: acceptance
id: AC-refactoring-adapter-migration
requirement: REQ-refactoring-intermediate-state
conditions: Часть модулей использует новый тип, часть ещё использует прежнее представление
expected: Задачи принимаются только с работающими согласованными преобразованиями и проверками поведения; план включает удаление временных обходов, итог подтверждает их отсутствие
```

## Срок действия критериев и проверок

```yaml
sdd_record: requirement
id: REQ-refactoring-check-lifecycle
operation: add
```

Различаются постоянные результаты, переходные локальные критерии и сквозные
итоговые критерии. Сохраняемые обязательства действуют во всей применимой области
на протяжении преобразования и в финале. Переходный критерий имеет заранее
согласованный шаг прекращения применимости и критерии заменяющего состояния.

Исходное состояние сохраняет доступные свидетельства; отсутствие ещё не
достигнутой целевой структуры не считается исходной регрессией. Проверки
сохраняемого поведения и действующие обязательные проверки не исключаются
под предлогом недостигнутой архитектуры.

Смена применимого набора проверок происходит по согласованному основанию с
подтверждением нового состояния, сохранением прежних свидетельств и обновлением
привязки к текущему кандидату. Старая проверка не становится пройденной на новом
состоянии оттого, что потеряла применимость.

Основание: [срок действия](../../decisions.md#срок-действия-критериев-и-проверок).

### Замена переходной проверки

```yaml
sdd_record: acceptance
id: AC-refactoring-transition-check
requirement: REQ-refactoring-check-lifecycle
conditions: Поздняя задача удаляет адаптер, проверенный ранней задачей
expected: Приёмка подтверждает согласованное заменяющее состояние и сохраняемое поведение; после неё прежняя переходная проверка не требуется в финале, история её запуска сохранена, отсутствие адаптера проверяется по итоговому контракту
```

### Неподтверждённое отключение

```yaml
sdd_record: acceptance
id: AC-refactoring-check-guard
requirement: REQ-refactoring-check-lifecycle
conditions: Исполнитель исключает проверку без согласованного основания, заменяющая проверка недоступна или свидетельства относятся к прежнему набору
expected: Задача не принимается на таком основании, прежние свидетельства не переписываются, необходимые проверки нового кандидата выполняются заново
```

## Изменение тестов вместе с границами модулей

```yaml
sdd_record: requirement
id: REQ-refactoring-test-evolution
operation: add
```

Design и план задают проверяемые свойства, прежние и новые границы, группы
проверок и основания добавления, переноса, адаптации или удаления. Исполнитель
выбирает конкретные тесты и файлы внутри этих пределов без отдельного согласия
на каждый тест. Изменение согласованного обязательства или архитектуры требует
возврата к sdd-spec.

Тест сохраняемого поведения переносится или заменяется на подходящем уровне.
Тест только отменённого архитектурного ограничения может быть удалён без
искусственной замены на то же ограничение. В смешанном тесте поведенческие
обязательства сохраняют проверку. Для новых границ добавляются необходимые
контрактные, интеграционные и архитектурные проверки по риску.

Независимое ревью проверяет основания потери прежних проверок и достаточность
нового покрытия. Число тестов, процент покрытия и зелёный прогон сами по себе
не доказывают сохранение обязательств. Постоянное правило проекта не отменяется
простым удалением соответствующего теста.

Основание: [принятые полномочия и правила](../../decisions.md#изменение-тестов-при-изменении-границ).

### Исчезновение старой границы

```yaml
sdd_record: acceptance
id: AC-refactoring-old-boundary-tests
requirement: REQ-refactoring-test-evolution
conditions: Два модуля объединяются, тест старого внутреннего вызова также проверяет атомарность внешней операции
expected: Проверка старого вызова может быть удалена по принятому решению, проверка атомарности сохраняется или переносится; ревью оценивает обе роли теста
```

### Новая граница и детализация тестов

```yaml
sdd_record: acceptance
id: AC-refactoring-new-boundary-tests
requirement: REQ-refactoring-test-evolution
conditions: Выделяется модуль и план задаёт проверяемые свойства и группы проверок без точного перечня тест-кейсов
expected: Исполнитель добавляет необходимые проверки нового контракта и взаимодействия внутри согласованной области без отдельных разрешений на файлы; непокрытые обязательства выявляются ревью
```

## Финальное подтверждение всего результата

```yaml
sdd_record: requirement
id: REQ-refactoring-final-verification
operation: add
```

Принятые задачи не заменяют доказательство сквозного результата. Финальное
завершение требует независимых свидетельств на текущем интегрированном HEAD:
все сквозные критерии, сохраняемые обязательства, действующие постоянные
локальные результаты и применимые обязательные проверки подтверждены.

Итог различает вклад завершённых задач, подтверждённые критерии целого и
остающиеся пробелы. Неприменимые переходные проверки показываются с основанием
и историей, а не как успешные финальные. Финальная находка связывается с
ответственными задачами; если причина не установлена или отсутствует необходимая
задача, работа сохраняется частично завершённой до установления основания ремонта
или пересмотра плана. Отдельная фиктивная задача для владения всеми итоговыми
проверками не требуется.

Основание: [проверка целого](../../decisions.md#декомпозиция-по-результату-и-модулям).

### Пропущенный потребитель

```yaml
sdd_record: acceptance
id: AC-refactoring-final-gap
requirement: REQ-refactoring-final-verification
conditions: Все локальные задачи приняты, но один потребляющий модуль в согласованной области сохранил прежнее представление идентификатора
expected: Сквозной критерий остаётся неподтверждённым, исполнение не завершается успешно и сообщает непокрытую область с необходимостью ремонта или пересмотра плана
```

### Актуальность итоговых свидетельств

```yaml
sdd_record: acceptance
id: AC-refactoring-final-evidence
requirement: REQ-refactoring-final-verification
conditions: После проверки меняется интегрированный код, нормативное основание или применимый набор проверок
expected: Старые свидетельства не подтверждают новый результат, итог требует соответствующих независимых проверок на актуальном состоянии
```

### Финальные проверки проекта в обычном исполнении

```yaml
sdd_record: acceptance
id: AC-refactoring-final-project-checks
requirement: REQ-refactoring-final-verification
conditions: Обычное исполнение должно после приёмки задач выполнить дополнительные обязательные проверки проекта; пользователь согласовал последующую задачу вместо повторного ремонта принятого результата
expected: Новая задача допускается с сохранением принятых задач и их бюджетов; дополнительный финальный реестр не требует фиктивной задачи-владельца, выполняется только в final независимым проверяющим и допускает complete лишь при достаточных актуальных свидетельствах одного HEAD, манифеста и реестра, сохраняя прежние covers и обычное исполнение без этого реестра
```

Этот критерий добавлен по поручению пользователя 2026-10-26. Его владелец —
последующая задача 9; принятые критерии и задачи 1–8 не переназначаются.

## Общий процесс и восстановление

```yaml
sdd_record: requirement
id: REQ-refactoring-continuity
operation: add
```

Маршрут использует существующие условия обсуждения, ревью документов и плана,
согласований, явной команды планирования и запуска apply. Он поддерживает
принятые режимы выполнения, настройки ролей, бюджеты и восстановление.

Снимок documents рефакторинга содержит proposal/design, plan добавляет tasks;
основание согласования и исполнения включает идентичность маршрута. Изменение
нормативных критериев, групп проверок или их срока действия требует пересмотра
актуальности по обычным правилам. Детализация конкретных тестов в утверждённой
области отражается в исполняемом реестре и его свидетельствах.

Resume восстанавливает маршрут, применимость критериев и проверок, ревизии
реестра, принятые задачи и незавершённые переходы. Одних статусов либо наличия
tasks недостаточно для разрешения работы. Существующие обычные изменения и их
проверки сохраняют прежний смысл.

Основание: [общий процесс](../../decisions.md#маршрут-внутри-общего-процесса).

### Снимок и согласование

```yaml
sdd_record: acceptance
id: AC-refactoring-review-basis
requirement: REQ-refactoring-continuity
conditions: Рецензируется работа рефакторинга или согласование с совпадающими ID и байтами пытаются использовать для другой работы
expected: Снимок учитывает соответствующий комплект без specs, согласование проверяется вместе с маршрутом и ID и не переносится между разными работами
```

### Восстановление изменения набора проверок

```yaml
sdd_record: acceptance
id: AC-refactoring-resume-checks
requirement: REQ-refactoring-continuity
conditions: Исполнение прервано во время замены проверок старой границы новыми
expected: Resume восстанавливает последний подтверждённый набор и незавершённый переход, не считает старые свидетельства доказательством нового набора и не требует повторного согласия на оставшуюся утверждённую работу
```

## Различение видов документов и совместимость

```yaml
sdd_record: requirement
id: REQ-refactoring-format-compatibility
operation: add
```

Документы рефакторинга и обычного изменения являются разными видами документов
с совпадающими именами файлов. Их схемы выбираются по виду работы и типу документа.
Номер версии относится к развитию соответствующей схемы и не используется
для различения этих видов. Одинаковая версия не означает одинаковый контракт.

Обновлённый комплект продолжает читать и исполнять обычные изменения без
автоматического переписывания документов и сохранённых исполнений. Несовпадение
вида документа с выбранной работой, неподдерживаемый вид или неизвестная версия
его схемы сообщаются явно; разбор по схеме другого вида недопустим.

Основание: [уточнение пользователя](../../decisions.md#разные-виды-документов).

### Разные схемы при одинаковых именах и версиях

```yaml
sdd_record: acceptance
id: AC-refactoring-document-dispatch
requirement: REQ-refactoring-format-compatibility
conditions: Проверяются tasks обычного изменения и tasks рефакторинга с одинаковым номером версии схемы
expected: Для обычного изменения действуют прежние covers и правила владения AC, для рефакторинга действуют вклад и локальная приёмка; выбор определяется видом работы и документа, а не номером версии
```

### Старые работы без миграции

```yaml
sdd_record: acceptance
id: AC-refactoring-legacy-format
requirement: REQ-refactoring-format-compatibility
conditions: Обновлённый комплект читает существующую обычную работу и сохранённое исполнение
expected: Работа использует прежние правила и согласования при сохранении их оснований, файлы не переписываются автоматически, новый маршрут не меняет семантику covers
```

### Явное отклонение несовместимого вида или схемы

```yaml
sdd_record: acceptance
id: AC-refactoring-version-rejection
requirement: REQ-refactoring-format-compatibility
conditions: Вид документа не соответствует выбранной работе, неизвестна версия его схемы или комплект не поддерживает документы рефакторинга
expected: Операция сообщает точную причину и способ исправить выбор либо обновить комплект, не применяет схему другого вида и сохраняет документы и свидетельства
```
