# Вопросы изменения

### Граница сохранения

```yaml
sdd_record: question
id: Q-preservation-boundary
text: Должен ли флоу рефакторинга сохранять совместимость наблюдаемых контрактов, или достаточно прежних бизнес-возможностей при допустимых изменениях интерфейсов?
blocking: true
status: resolved
resolution: decisions.md#принятая-граница-сохранения
```

Причина: ответ определяет допустимые изменения и критерии проверки.
Рекомендация агента: сохранять наблюдаемые контракты и действующие ограничения; изменения интерфейсов с потерей совместимости выделять в функциональную часть.
Компромисс: более широкая трактовка допускает больше архитектурных миграций, но требует отдельного учёта изменений для потребителей.
Основание: [предложение](decisions.md#сохранение-поведения-и-структурный-результат).
Ответ пользователя 2026-10-24: «первый вариант». Принято сохранение совместимости наблюдаемых контрактов и действующих ограничений.

### Устройство флоу

```yaml
sdd_record: question
id: Q-flow-shape
text: Выделять маршрут в общем процессе SDD, самостоятельный жизненный цикл или инструкции внутри нынешних флоу?
blocking: true
status: resolved
resolution: decisions.md#маршрут-внутри-общего-процесса
```

Рекомендация агента: маршрут в общем процессе, сохраняющий общие согласования и восстановление. Самостоятельный цикл увеличивает стоимость сопровождения; одни инструкции могут не устранить ограничения формата.
Основание: [предложение](decisions.md#маршрут-внутри-общего-процесса).
Ответ пользователя 2026-10-24: «Да, отдельный маршрут.» Выбран отдельный маршрут с общими стадиями и механизмами SDD.

### Явный и неявный выбор

```yaml
sdd_record: question
id: Q-flow-selection
text: Достаточна ли однозначная просьба изменить устройство без изменения поведения для выбора рефакторинга без самого слова «рефакторинг», или нужно отдельно получить явный выбор маршрута?
blocking: true
status: resolved
resolution: decisions.md#неявный-выбор-агентом
```

Причина: пользователь одновременно потребовал явно указывать необходимость рефакторинга и информировать при неявном выборе. Нужно установить порог выбора без догадки об авторизации.
Пример: «Раздели этот модуль на части, сохранив поведение».
Рекомендация агента: считать такой однозначный запрос достаточным, сообщать маршрут и ограничения; при неоднозначном «улучши модуль» уточнять флоу до продолжения зависимой работы.
Альтернатива: без явного названия рефакторинга всегда спрашивать выбор, даже если намерение описано однозначно.
Основание: [решение и открытая интерпретация](decisions.md#выбор-маршрута-и-информирование).
Ответ пользователя 2026-10-24 сохранён дословно в [принятом уточнении](decisions.md#неявный-выбор-агентом): агент может сам выбрать рефакторинг по пользовательскому вводу без отдельного подтверждения; информирование обязательно, сомнения требуют вопроса.

```yaml
sdd_record: question

blocking: true
status: resolved
resolution: decisions.md#документы-рефакторинга
```

Принято пользователем 2026-10-24: «Набор документов принимаю, отдельные спецификации не нужны.» Контракт рефакторинга и критерии размещаются в design, отдельные specs не нужны. Вопрос закрыт в части выбора комплекта; оставшаяся часть о покрытии задач выделена в Q-task-model и этим ответом не считается решённой.
Предложение и последствия: [документы рефакторинга](decisions.md#документы-рефакторинга).

### Модель задач рефакторинга

```yaml
sdd_record: question
id: Q-task-model
text: Разрешаем ли нескольким задачам по частям результата и модулям совместно достигать сквозного критерия design, с локальной приёмкой задач и отдельной итоговой проверкой этого критерия?
blocking: true
status: resolved
resolution: decisions.md#декомпозиция-по-результату-и-модулям
```

История: первоначально обсуждались результат с единственным владельцем и сохраняемые обязательства. Пользователь указал на массовые изменения и задал декомпозицию по результату и модулям. Рекомендация пересмотрена: допустить несколько задач для одного сквозного критерия, задавать проверяемый локальный результат каждой задачи и проверять полноту покрытия и итоговое интегрированное состояние. Сохраняемые обязательства по-прежнему проверяются во всех затрагивающих их задачах.
Альтернатива — дробить все критерии design до масштаба задач ради сохранения единственного владельца; это увеличивает нормативный документ и связывает его с деталями исполнения.
Основание и последствия: [модель задач](decisions.md#модель-задач-рефакторинга).
Уточнение пользователя и обновлённое предложение: [декомпозиция](decisions.md#декомпозиция-по-результату-и-модулям).
Ответ пользователя 2026-10-24: «да, согласен». Приняты критерии целого в design, локальные результаты и области задач, несколько задач на один сквозной критерий. Машинный формат ещё не подготовлен; правила промежуточных состояний вынесены в Q-intermediate-state.

### Промежуточные состояния

```yaml
sdd_record: question
id: Q-intermediate-state
text: Должна ли каждая принимаемая задача оставлять работоспособное состояние с допустимыми временными адаптерами, или разрешаем неработоспособные промежуточные задачи с групповой приёмкой?
blocking: true
status: resolved
resolution: decisions.md#работоспособность-промежуточных-результатов
```

Рекомендация агента: работоспособность после каждой принятой задачи; временные адаптеры описать в design и удалить по плану. Это сохраняет нынешнюю модель исполнения и позволяет проверять миграцию по частям. Групповая приёмка может уменьшить временный код, но увеличивает неделимую область изменений и требует нового механизма выполнения и восстановления.
Основание: [варианты и источники](decisions.md#работоспособность-промежуточных-результатов).
Ответ пользователя 2026-10-24: «да». Выбраны работоспособность после каждой принятой задачи и временные адаптеры с запланированным удалением.

### Срок действия проверок

```yaml
sdd_record: question
id: Q-check-lifecycle
text: Различаем ли постоянные и переходные критерии задач, задавая для переходных запланированный шаг замены и проверку нового состояния вместо повторения прежнего теста в финале?
blocking: true
status: resolved
resolution: decisions.md#срок-действия-критериев-и-проверок
```

Причина: текущий финал apply повторяет все проверки задач, но принятый план может требовать удалить временную конструкцию, которую проверяла ранняя задача.
Рекомендация агента: явно задавать срок действия переходных критериев и их замену в согласованном плане; сохранять исторические свидетельства и проверять весь итоговый контракт. Постоянные обязательства не теряют силу из-за завершения ранней задачи.
Альтернатива: требовать, чтобы каждый критерий задачи оставался истинным до конца; это ограничивает использование проверяемых временных шагов и может укрупнять задачи.
Основание: [предложение и пример](decisions.md#срок-действия-критериев-и-проверок).
Пользователь согласился 2026-10-24 и добавил сценарий изменения границ модулей с добавлением и удалением тестов; полный ответ сохранён в журнале.

### Детализация изменений тестов

```yaml
sdd_record: question
id: Q-test-evolution
text: Достаточно ли согласовать свойства, границы и группы изменяемых проверок, оставив выбор конкретных тестов исполнителю, или нужно заранее перечислить каждый изменяемый и удаляемый тест?
blocking: true
status: resolved
resolution: decisions.md#изменение-тестов-при-изменении-границ
```

Рекомендация агента: согласовывать проверяемые обязательства, изменения границ, группы проверок и основания замены/удаления; конкретные файлы и тест-кейсы определяет исполнитель в этих пределах. Удаление сохраняемого обязательства или новое архитектурное решение требует пересмотра. Независимое ревью проверяет обоснование изменения набора и достаточность покрытия.
Альтернатива: точный перечень тестов заранее и пересмотр при отклонениях; более жёсткий контроль ценой остановок на деталях реализации.
Основание: [изменение тестов при изменении границ](decisions.md#изменение-тестов-при-изменении-границ).
Ответ пользователя 2026-10-24: «да, согласен». Выбран уровень свойств, границ и групп проверок; конкретные тесты определяет исполнитель в согласованных пределах.

### Версия и совместимость

```yaml
sdd_record: question
id: Q-format-compatibility
text: Выделяем ли новый формат v2 для рефакторинга с сохранением v1 обычных работ и исполнений без автоматической миграции, или расширяем единственную v1-схему профилем?
blocking: true
status: resolved
resolution: decisions.md#разные-виды-документов
```

История: агент рекомендовал отдельный v2. Пользователь отверг саму предпосылку вопроса: это другие документы с совпадающими именами, а не новые версии существующих.
Ответ пользователя 2026-10-24 дословно: «Выделять версию неправильно, это не новая версия существующих документов, это другие документы с совпадающими именами.»
Принято различение по виду работы и документа; прежнее предложение сохранено в [истории](decisions.md#версия-формата-рефакторинга), новое решение — в [журнале](decisions.md#разные-виды-документов).
Обновлены [design](design.md#виды-документов-и-совместимость), REQ-refactoring-format-compatibility и его критерии в [spec](specs/sdd-refactoring/spec.md#различение-видов-документов-и-совместимость).
