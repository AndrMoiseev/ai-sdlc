# Дизайн маршрута рефакторинга

## Контекст, цели и исключения

Цели и границы заданы в [proposal](proposal.md), контракт — в
[spec](specs/sdd-refactoring/spec.md). Основания выбора сохранены в
[журнале](decisions.md#сводка-согласованной-модели).

Это черновик технического устройства согласованной модели. Формат примеров
ниже ещё не поддерживается кодом. Он не является tasks текущего изменения
и не разрешает выполнение изображённых задач.

Найденные ограничения текущей реализации:

| Узел | Нынешнее правило | Необходимое изменение для рефакторинга |
|---|---|---|
| `sdd_shared/paths.py`, `sdd-apply/inputs.py` | Корень `sdd/changes` | Явная идентичность вида работы и новый корень |
| `sdd_shared/documents.py` | Одна схема для каждого document_type; AC только в spec, DEC с REQ | Выбор схемы по виду работы и типу документа |
| `sdd_shared/validation.py` | Один владелец AC, verification внутри covers | Разделение вклада, локальной приёмки и сохранения |
| `sdd_shared/snapshots.py`, reviews | Proposal/design/specs, затем tasks | Снимок нужного комплекта и привязка к виду работы |
| `sdd-apply/verification.py` | Реестр регистрируется и расширяется | Подтверждённая смена применимых проверок |
| `sdd-apply/finalize.py` | Итог выводится из covers принятых задач | Независимое подтверждение критериев целого |

Полные пути этих модулей находятся в [карте изменений](#карта-изменений).
Прежние спецификации планирования и исполнения описывают универсальные правила,
но часть исторических формулировок уже отличается от действующих скиллов.
Для текущего поведения использованы сами инструкции и исходники; новая capability
добавляет маршрут, не переписывая правила обычного изменения.

## Термины

| Термин | Значение в этом изменении |
|---|---|
| Работа | Конкретный комплект документов и его исполнение, идентифицируемые видом и ID |
| Вид работы | Обычное изменение `change` или рефакторинг `refactoring`; это не текущий флоу explore/draft/review |
| Сквозной результат | Проверяемое целевое состояние всей объявленной области или значимой части этой области |
| Сохраняемое обязательство | Поведение или действующее ограничение, остающееся верным при преобразовании |
| Локальный результат | Проверяемое состояние в области одной задачи, достаточное для её приёмки |
| Вклад | Связь задачи со сквозным результатом, не утверждающая его полное достижение |
| Переходный критерий | Локальный критерий с заранее заданным шагом прекращения применимости |
| Проверка | Команда или процедура, дающая свидетельство о критериях; она не тождественна отдельному тест-кейсу |

Существующие имена `TASK`, `AC`, `DEC`, `verification`, `location`, `run`,
`depends_on`, `cannot_parallel_with` сохраняются по смыслу. `covers` остаётся
полем задач обычного изменения; использовать его для вклада в сквозной результат было
бы сменой значения существующего термина. Для вклада предложено `contributes_to`,
для сохраняемых обязательств — `preserves`. Новые обозначения технические;
отдельный глобальный thesaurus этим изменением не создаётся.

## Модули и контракты

Авторские инструкции, маршрутизация обсуждения и шаблоны принадлежат sdd-spec.
Парсер, правила ссылок и покрытия, разрешение путей, проверки и снимки принадлежат
sdd-shared. Исполнение, реестры проверок, свидетельства, роли и прогресс — sdd-apply.
Документы обоих видов работы обрабатываются общими механизмами с выбором своей схемы.
Копия независимого процесса для рефакторинга не создаётся.

### Общий процесс с явной идентичностью работы

```yaml
sdd_record: decision
id: DEC-refactoring-work-identity
requirements: [REQ-refactoring-entry, REQ-refactoring-documents, REQ-refactoring-continuity]
```

Основание подхода принято: [маршрут](decisions.md#маршрут-внутри-общего-процесса),
[размещение](decisions.md#размещение-рефакторингов).
Техническая конкретизация для черновика:

- Полная идентичность — пара `work_kind` и `change_id`. Старое имя `change_id`
  сохраняется в общих метаданных; новый work_id, дублирующий его, не вводится.
- `change` разрешается в `sdd/changes/<id>`, `refactoring` — в
  `sdd/refactoring/<id>`. Проверка slug, containment и существующих symlink-родителей
  применяется до чтения и записи. Произвольный корень из ввода не принимается.
- Общие CLI check/snapshot/resolve добавляют необязательный
  `--work-kind change|refactoring`; прежний вызов без него означает `change`.
  API apply получает аналогичный аргумент; существующие прямые вызовы сохраняют
  прежнюю семантику. Новые инструкции выбора просматривают оба корня и передают
  установленный вид явно. Одинаковый ID в двух корнях требует контекста или выбора.
- Манифест содержит прежний список относительных путей и хешей, но основание
  ревью, USER-разрешения и исполнения включает также полную идентичность работы.
  Совпадение байтов в разных работах не переносит согласования.
- Документный снимок рефакторинга: proposal и design. Плановый: те же документы
  и tasks. Источники baseline читаются отдельно; их наблюдённые версии сохраняются
  в основании исследования/исполнения. Их значимое изменение требует сверки,
  даже если нормативные байты не изменились.
- Смена вида уже начатой работы не делается переименованием каталога внутри apply.
  Конфликт возвращается в sdd-spec с сохранением исходных документов и исполненного.

Альтернатива — определить вид только по наличию specs или имени каталога.
Она позволяет потерянному файлу изменить семантику работы, поэтому явная
идентичность проверяется вместе с размещением и видом документа.

## Виды документов и совместимость

### Отдельные схемы по виду работы

```yaml
sdd_record: decision
id: DEC-refactoring-document-kinds
requirements: [REQ-refactoring-format-compatibility, REQ-refactoring-documents, REQ-refactoring-continuity]
```

Основание принято: [разные виды документов](decisions.md#разные-виды-документов).
Это решение заменяет прежнее предложение DEC-refactoring-format-version.

`sdd/changes/<id>/tasks.md` и `sdd/refactoring/<id>/tasks.md` имеют одинаковое
имя файла, но представляют разные документы. То же относится к proposal и
design. Различие определяется видом работы и типом документа. Оно не является
обновлением прежней схемы до v2 и не создаёт миграцию между двумя форматами.

Для технического выбора схемы используется ключ
`(work_kind, document_type, schema_version)`. Документы рефакторинга явно
содержат `work_kind: refactoring`, сохраняют привычные document_type и имеют
свою начальную `schema_version: 1`. Номер версии описывает развитие конкретной
схемы внутри своего вида, а не отличает рефакторинг от обычного изменения.

У существующих документов обычного изменения отсутствие work_kind сохраняет
прежнюю семантику change в их допустимом корне. Отсутствие поля не разрешает
интерпретировать скопированный документ как рефакторинг. Парсер проверяет
совпадение объявленного вида с контекстом работы и корнем каталога, затем
применяет соответствующую схему. Одинаковые schema_version и document_type
в двух видах работ не означают одинаковые поля или правила покрытия.

Общие state, вопросы и review сохраняют назначение и связываются с идентичностью
работы. Исполнение также выбирает обработчик по виду работы; добавление маршрута
само по себе не требует повышать версию существующего состояния. Прежние
документы и сохранённые исполнения не переписываются, их история не пересчитывается.

API sdd-shared расширяется совместимыми операциями и параметрами с прежними
значениями по умолчанию. Consumer проверяет поддержку вида refactoring до
зависимой операции. Отсутствие поддержки этого вида — ограничение установки,
а не повод читать его документы как обычное изменение. Неизвестная версия
внутри уже известного вида остаётся отдельной диагностикой.

Обновление поставляется согласованным комплектом sdd-spec/sdd-shared/sdd-apply.
Ранее предложенное различение видов номером версии отвергнуто пользователем;
история сохранена в журнале.

## Формат design рефакторинга

### Критерии целого и архитектурные решения

```yaml
sdd_record: decision
id: DEC-refactoring-design-criteria
requirements: [REQ-refactoring-design-contract, REQ-refactoring-task-contract]
```

Основание принято: [документы](decisions.md#документы-рефакторинга),
[декомпозиция](decisions.md#декомпозиция-по-результату-и-модулям).
Следующая схема — техническая конкретизация документа design для вида refactoring.

В design рефакторинга предлагается запись `sdd_record: criterion` с ID `AC-...`.
Она имеет `purpose: result|preservation`, `conditions`, `expected` и `scope`
(непустой список описанных областей). Для части результата допустим `parent`
на другой result того же design. Граф ацикличен. Родитель не считается выполненным
автоматически по дочерним критериям; у него есть собственная проверка целого.

У preservation обязателен `source`: существующий контракт/спецификация либо
доступные свидетельства и явно записанное отсутствие baseline, по прежней
семантике source. Разбитая ссылка не заменяется утверждением, что baseline нет.
Область и ограничения свидетельств описываются рядом. Результат с несколькими
частями не требует раскладывать каждую область до файлов в design.

DEC рефакторинга имеет непустой `criteria` на критерии design вместо `requirements`.
Необязательный `supersedes` содержит ссылки на исходные решения с путём и ID
или якорем. Пересмотр объясняется текстом: какое решение и в какой области
теряет силу, что остаётся действующим. Исторический источник не переписывается
ради удаления противоречия; приёмка использует согласованное новое основание.

Пример будущего design; внешняя рамка исключает его из записей этого документа:

````text
```yaml
sdd_record: criterion
id: AC-product-id-domain
purpose: result
scope: [Домен товара и внутренние потребители идентификатора]
conditions: Преобразование завершено во всей согласованной области
expected: Внутренние операции используют выделенный тип; числовое представление остаётся только на оговорённых внешних границах
```
```yaml
sdd_record: criterion
id: AC-product-api-preserved
purpose: preservation
scope: [Внешний API товара]
conditions: Выполняются существующие запросы API, включая ошибки
expected: Форматы, значения и ошибки соответствуют исходному контракту
source:
  kind: specification
  path: docs/specs/products.md
  requirement: REQ-product-api
```
```yaml
sdd_record: decision
id: DEC-product-id-type
criteria: [AC-product-id-domain, AC-product-api-preserved]
```
````

Это иллюстрация: файлы и ID продукта не утверждаются существующими в данном
репозитории. Полный рабочий пример для eval должен поставляться отдельной фикстурой.

## Формат tasks рефакторинга

### Вклад, локальная приёмка и сохранение

```yaml
sdd_record: decision
id: DEC-refactoring-task-model
requirements: [REQ-refactoring-task-contract, REQ-refactoring-intermediate-state, REQ-refactoring-check-lifecycle]
```

Основание принято: [модель](decisions.md#декомпозиция-по-результату-и-модулям),
[промежуточные состояния](decisions.md#работоспособность-промежуточных-результатов).

Задача рефакторинга сохраняет `sdd_record: task`, ID `TASK`, number/status/depends_on,
необязательный cannot_parallel_with и verification. Вместо covers используются:

| Поле | Контракт |
|---|---|
| `scope` | Непустой список областей с названием модуля/компонента и относительными путями, когда они известны; будущий путь допустим, выход за проект запрещён |
| `contributes_to` | Непустой список result-критериев design; несколько задач могут ссылаться на один критерий |
| `preserves` | Применимые preservation-критерии design; пустой список требует `preservation_reason` с объяснением, проверяемым ревью |
| `verification` | Прежние test_description/location/run и criteria, с добавлением стабильного локального `id` проверки |
| `test_changes` | Необязательный список согласованных действий с группами проверок; см. ниже |

Локальный результат — отдельная запись `sdd_record: acceptance`, ID `AC`, в tasks.
Она имеет `task: TASK-ID`, `conditions`, `expected`, `lifetime: persistent|transitional`.
У каждой задачи хотя бы одна такая запись. Локальные AC и design AC уникальны
внутри работы. Поле requirement в документах рефакторинга не применяется.

Для transitional обязательны `until_task` и непустой `replaced_by` на критерии
нового состояния. `until_task` — другая задача, достижимая по графу зависимостей
от владельца критерия. Замена подтверждается при приёмке этой задачи, не в момент
начала или по одному её статусу. Циклические замены запрещены. Критерии замены
должны проверяться этой задачей либо подтверждёнными предшественниками с новой
проверкой на её кандидате; отложенный только до финала критерий не разрешает
снять защиту раньше времени.

В task.verification.criteria разрешены локальные AC этой задачи и AC из preserves.
Каждый локальный AC и каждое указанное сохраняемое обязательство имеют проверку.
Сам вклад contributes_to не требует полного выполнения сквозного критерия при
приёмке задачи. Номер, а не ID, меняется при перестановке.

Стабильный ключ проверки задачи — `TASK-ID/verification.id`; менять порядок
списка недостаточно, чтобы сменить её идентичность. Прежний контракт command
как массива аргументов, procedure, setup_required и location сохраняется.

````text
```yaml
sdd_record: task
id: TASK-convert-orders
number: 2
scope:
  - module: orders
    paths: [src/orders, tests/orders]
contributes_to: [AC-product-id-domain]
preserves: [AC-product-api-preserved]
depends_on: [TASK-introduce-product-id]
status: pending
verification:
  - id: orders-product-id
    criteria: [AC-orders-use-product-id]
    test_description: Проверить использование нового типа в операциях заказов
    location: tests/orders
    run:
      setup_required: Подготовить проверки типизации и запуска операций заказов
  - id: product-api-regression
    criteria: [AC-product-api-preserved]
    test_description: Проверить прежние ответы и ошибки API в затронутых сценариях
    location: tests/contracts/products
    run:
      command: [pytest, -q, tests/contracts/products]
```
```yaml
sdd_record: acceptance
id: AC-orders-use-product-id
task: TASK-convert-orders
conditions: Выполняются затронутые внутренние операции модуля orders
expected: Используется выделенный тип идентификатора, локальные проверки проходят
lifetime: persistent
```
````

План не обязан создавать один AC design на каждый модуль. Локальное разбиение
может меняться при пересмотре tasks без искусственной функциональной дельты.
Подготовительная задача допустима, когда имеет проверяемый результат, область
и вклад, например доступный работающий тип. Задача «потом добавить все тесты»
не заменяет проверки задач преобразования.

## Группы тестов и пересмотр исполняемых проверок

### Смена проверки сохраняет её обязательство или основание неприменимости

```yaml
sdd_record: decision
id: DEC-refactoring-check-evolution
requirements: [REQ-refactoring-test-evolution, REQ-refactoring-check-lifecycle, REQ-refactoring-continuity]
```

Основание принято: [тесты и границы](decisions.md#изменение-тестов-при-изменении-границ),
[срок действия](decisions.md#срок-действия-критериев-и-проверок).

Элемент task.test_changes содержит стабильный локальный `id`,
`action: add|adapt|move|remove`, описание `group`, список затронутых `criteria`
и `reason`. Для снятого структурного ограничения указывается `decision` на DEC
design и источник старой границы в описании группы. При сохранении свойства
`replacement_criteria` указывает, чем оно проверяется после изменения.
Для чисто структурной отменённой проверки список замены может быть пустым;
основание тогда состоит в согласованном архитектурном решении.

Это разрешение работы с группой проверок, а не полный перечень файлов. Исполнитель
отображает фактически затронутые тесты и записи реестра на разрешённую группу.
Изменение сохраняемого обязательства либо архитектуры не укладывается в эту
детализацию и возвращается на нормативный пересмотр. Неизменённые применимые
обязательные проверки проекта остаются обязательными. Изменение CI или процедуры
их запуска требует собственного основания в плане и проектных правилах.

Исполнение получает операцию пересмотра реестра, принадлежащую скриптам apply.
Конкретное имя события — деталь реализации; контракт операции следующий:

1. До преобразования сохраняются исходные наблюдения и версия набора. Новая
   проверка ещё не созданного результата может иметь planned_absence по setup_required.
   Если необходима характеристическая проверка поведения, её сначала выполняют
   на исходной реализации. Один новый зелёный тест после изменения не даёт этого
   свидетельства. При невозможности восстановить исходное основание фиксируется пробел.
2. Запрос содержит точные старые и новые записи/команды, ссылку на test_changes
   либо переходный критерий, проверяемые обязательства, основание неприменимости
   и актуальную ревизию реестра. Исторические записи не удаляются физически.
3. Применимость проверок к новому кандидату оценивается по согласованному целевому
   состоянию задачи. Поэтому старый тест уже удалённой границы не обязан пройти
   на кандидате удаления, но его исходное свидетельство и основание замены доступны.
4. Независимые проверки и ревью подтверждают новый набор, сохранение обязательств
   и основания снятия старых записей. Неудача оставляет задачу непринятой; разрешение
   пересмотра не превращает failed/unavailable в pass и не сбрасывает бюджеты ремонта.
5. Приёмка фиксирует новую применимость атомарно с подтверждённым состоянием задачи.
   После перерыва незавершённый переход восстанавливается как незавершённый.
   Новая ревизия реестра/кандидата инвалидирует затронутые прежние свидетельства.

Для проверки обязательства могут измениться путь, тестовые фикстуры и способ
запуска. Постоянный критерий при этом сохраняет идентичность; перенос теста
не делает сам критерий переходным. Удаление старой границы без сохраняемого
обязательства оформляется как архитектурная замена, даже если тест прежде
считался постоянным. Это отдельный случай от заранее временного адаптера.

## Проверки целого и прогресс

### Отдельные критерии завершения работы

```yaml
sdd_record: decision
id: DEC-refactoring-final-contract
requirements: [REQ-refactoring-final-verification, REQ-refactoring-task-contract, REQ-refactoring-check-lifecycle]
```

Основание принято: [покрытие и итог](decisions.md#декомпозиция-по-результату-и-модулям).

В tasks рефакторинга предлагаются записи `sdd_record: verification`, ID `CHECK-...`, для
проверок целого. Они имеют `criteria`, `test_description`, `location`, `run`
по прежнему контракту исполнения, но не принадлежат отдельной задаче. Их
criteria ссылается на критерии design и при необходимости постоянные локальные
AC. Непустой список проверок целого покрывает каждый критерий design; сохранение
постоянных локальных результатов обеспечивается применимыми проверками задач
или явно заменяющими их проверками целого. Структурно проверяется отсутствие
пробелов в этом объединении, семантически — достаточность проверок.

Проверки целого обязательны на финальном интегрированном HEAD. Их подготовка,
если нужна, назначается существующим задачам с собственными локальными результатами;
необязательное раннее выполнение не подменяет итоговую проверку. Проверка ещё
недостигнутого результата не запускается как обязательное условие каждой ранней
задачи. Для setup_required в записи целого указывается `setup_task`, существующая
задача подготовки; отсутствие готовой проверки в финале означает unavailable.

Порядок финала:

1. Все задачи приняты, подтверждены коммиты и применимость переходных критериев.
2. По плану и подтверждённым ревизиям реестров строится применимый финальный набор.
   Снятие проверки сопровождается основанием, а не записью об успехе.
3. Независимые от авторов проверяющие выполняют проверки целого и оставшиеся
   обязательные проверки на одном финальном состоянии с привязкой к HEAD,
   нормативному манифесту, идентичности работы и набору проверок.
4. Сквозные и сохраняемые критерии подтверждаются свидетельствами. Статусы задач
   или перечень contributes_to не вычисляют успех этих критериев.
5. Неизвестный владелец дефекта устанавливается до ремонта. Пропущенная область
   возвращается на пересмотр плана, если для неё нет разрешённой задачи. После
   изменений актуальность свидетельств проверяется вновь по прежним правилам.

Прогресс показывает отдельно принятые задачи и подтверждённые критерии целого.
Итог содержит непокрытые области, недостаточные/недоступные проверки и переходные
проверки, утратившие применимость, с их основаниями. Наличие всех локальных pass
не скрывает отсутствие полного преобразования.

## Проверка структуры и смысла

Структурный валидатор выбирает схему по виду работы и типу документа, проверяет
поддерживаемую версию этой схемы, соответствие пути, уникальность
ID, принадлежность локального AC задаче, типы ссылок, граф parent/depends_on/
until_task, покрытие критериев, наличие оснований замены и форму run/location.
Нельзя сослаться на DEC вместо критерия, прекратить действие preservation через
until_task или сослаться на несуществующую задачу удаления.

Смысловые проверки агента и независимого ревью отвечают за полноту области,
реальные зависимости, обоснованность пустого preserves, отсутствие нового
функционального поведения, достаточность исходных свидетельств и покрытия тестами.
Список ссылок и успешный check не доказывают сохранение поведения.

Все новые модели из этого design должны быть выражены в общих справочниках и
шаблонах обоих скиллов. Текущий черновик проверяется старым валидатором как
обычное функциональное изменение добавления маршрута; это не тест нового формата.

## Проверочные сценарии для будущей реализации

- Явный выбор; самостоятельный выбор агентом; сомнение; попытка скрыто добавить
  функциональное изменение. Проверяется уведомление и отсутствие лишнего запроса
  при уверенном выборе, а не только наличие ключевого слова.
- Одинаковые ID в двух корнях; попытка выхода путём/symlink; снимок без specs;
  невозможность переноса USER-разрешения между работами.
- Тип идентификатора в core и нескольких потребителях: размер задач, полнота
  области, независимость локальной приёмки от сквозного критерия, забытый модуль.
- Адаптер с последующим удалением: допустимая смена теста, отказ заменяющей
  проверки, перерыв до фиксации новой применимости, устаревшее свидетельство.
- Слияние/разделение модулей: чисто структурный тест, смешанный тест, новая
  интеграционная проверка, попытка удалить сохраняемую проверку без основания.
- Параллельные локально успешные изменения, нарушающие обязательство после
  интеграции; итоговая независимая проверка выявляет дефект.
- Обычные работы и сохранённые исполнения без переписывания; разные виды
  документов при одинаковом номере версии; несоответствие work_kind и корня;
  неподдерживаемый вид, неизвестная версия внутри вида, смешанная и перемещённая установка.

Поведенческие eval используют чистые независимые контексты и фикстуры с доступным
полным комплектом зависимостей по sdd-skill-conductor. Сравнение с текущим пакетом
показывает отсутствие поддержки нового маршрута. Runtime-кеши, окружения и
сгенерированные отчёты eval остаются вне каталогов скиллов. Перед поставкой
проверяются чистота пакетов, lock-файлы и работа после перемещения. Эти проверки
не выполнялись при подготовке данного черновика.

## Риски и открытые вопросы

[Премортем](premortem.md) остаётся применимым: возможны неполная область,
необоснованное снятие проверки, смешение поведения со старой структурой и
ложный успех по локальным задачам. Новые признаки риска — перенос согласования
между одинаковыми ID и потеря применимости проверок при resume; их покрывают
контракты выше и сценарии проверки.

[Q-format-compatibility](questions.md#версия-и-совместимость) закрыт уточнением
пользователя: документы разных видов работы различаются своим назначением и
схемой, а не номером версии. Открытых вопросов обсуждения сейчас нет.
Независимое ревью и согласование версии этого комплекта ещё не выполнялись.
