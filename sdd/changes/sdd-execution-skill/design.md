# Устройство скилла выполнения плана

## Контекст

Цель и границы описаны в [proposal](proposal.md), поведение в
[spec](specs/sdd-execution/spec.md). Основания заимствований и отличий от
NeoPilot находятся в [research](research.md). Это черновой дизайн;
пользователь подтвердил автономное выполнение всего плана, последовательный
режим по умолчанию и параллельный режим только по явному запросу.
Скилл работает в паре с `sdd-spec`, заканчивает работу набором коммитов
по задачам и с первой версии предоставляет HTML-дашборд. Подготовка
спецификаций и автоматическое переписывание проектных инструкций исключены
из его назначения.

В новом пакете короткий SKILL.md с выбором действий: начало,
исполнение, исправление, возврат к спецификации, продолжение и приёмка.
Инструкции ролей и адаптеры среды загружаются по необходимости.
Все операции с однозначными правилами выполняются скриптами пакета.
Инструкции ролей вызывают эти скрипты и не предлагают агенту вручную
повторять их алгоритмы. Решения о смысле требований, реализации
и качестве кода остаются за агентами.

## Термины

**Основание исполнения**: проверенный манифест плана, согласования
и поручение выполнять выбранное изменение.

**Попытка**: запуск исполнителя с определёнными входами и границами работы.
Исправление продолжает попытку; новая попытка сохраняет причину её замены.

**Цикл исправления тестов**: зарегистрированная работа после неуспешной
обязательной проверки задачи до результата следующего полного назначенного
набора проверок. Включает правки и повторную проверку либо обоснованный
повтор без правок. Номер цикла считается отдельно от попыток исполнителя
и раундов код-ревью.

**Приёмка задачи**: подтверждение критериев задачи проверками и независимым
ревью на определённой версии с последующей фиксацией коммита в ветке
исполнения. Сообщение исполнителя и коммит без проверок сами по себе
не подтверждают приёмку.

## Модули и контракты

| Часть | Ответственность | Результат |
|---|---|---|
| Вход и продолжение | Найти изменение, проверить основание через установленный sdd-spec, сверить состояние проекта | Проверенное основание или конкретная блокировка |
| Выбор задач | Прочитать граф и ограничения из tasks, сопоставить с принятыми результатами | Список задач, которые можно выполнять сейчас |
| Оркестратор | Запускать роли, сохранять результаты и управлять исправлениями | Актуальная запись исполнения |
| Исполнитель | Реализовать одну задачу в заданной области и выполнить её verification | Изменения и ссылки на доказательства по AC |
| Рецензент | Проверить соответствие и качество определённой версии | Замечания с основаниями и условиями устранения |
| Проверяющий | Самостоятельно запустить обязательные тесты и линтеры, не будучи автором изменений | Результаты команд на зафиксированной версии и исходные логи |
| Приёмка результата | Проверить все AC и общий сценарий на итоговой версии | Полный или частичный результат |
| Коммиты задач | Проверить состав изменений и сохранить принятый результат в ветке исполнения | Связь TASK-ID с SHA коммитов |
| HTML-дашборд | Показать сохранённый прогресс и обновлять снимок | Живое представление и HTML для просмотра без сервера |
| Адаптер среды | Запускать чистые контексты, определять доступность ролей и изоляции | Реальные возможности Codex или Claude Code |

Исполнитель получает пути к задачам, связанным REQ/AC, обязательным решениям
design, инструкциям проекта и сводке готовых интерфейсов. Возвращает статус,
принадлежащие ему файлы, результаты verification, незакрытые критерии
и ограничения. Длинные логи хранятся отдельно; краткий результат ссылается
на них. Формат записи исполнения описан ниже; это предложение для первой
версии, которое предстоит проверить на примерах запуска и продолжения.

## Формат записи исполнения

Каталог `execution/` содержит `state.json`, `summary.md`, `dashboard.html`, `dashboard-state.js`
и каталог `runs/`. Источником состояния служит JSON; Markdown-сводка
и дашборд строятся из него и ссылок на доказательства. Ручная правка
сводки или HTML не меняет прогресс.
У каждой записи есть `schema_version: 1` и `change_id`; неизвестная версия
останавливает разбор с понятной диагностикой.

`state.json` хранит номер `revision`, активный `run_id`, состояние запуска,
ссылку на основание, режим `sequential` или `parallel`, ссылку на явный
запрос пользователя для `parallel`, записи задач и следующий шаг. Задача определяется
по TASK-ID; её запись содержит состояние, номер попытки, причину блокировки,
ссылки на доказательства, принятый снимок кода и коммиты с SHA.
Для код-ревью сохраняются общий лимит раундов, число начатых
и завершённых раундов, идентификаторы ревью и решения пользователя
о дополнительных раундах. У запуска есть причина ожидания пользовательского
решения; `review_limit_reached` блокирует дальнейшую работу всего плана.
Для исправлений тестов записываются `test_repair_limit: 5`,
`test_repair_cycles_started`, активный `test_repair_cycle_id`, исходное
падение, результаты каждого цикла и решения об увеличении лимита.
Причина `test_repair_limit_reached` также блокирует весь план в любом режиме.
Состояния задачи: `pending`, `running`, `verifying`, `reviewing`, `integrating`, `repairing`,
`committing`, `blocked`, `accepted`.
Состояния запуска: `active`, `blocked`, `completed`. Завершённая с ошибкой
попытка остаётся в истории, а её задача становится `blocked`.

Для запуска создаётся `runs/<run-id>/input.json`: манифест нормативного
комплекта, ссылки на согласования, поручение пользователя, ветка исполнения, исходный HEAD,
снимок исходных локальных изменений, лимит пяти циклов исправления тестов
и лимит трёх раундов код-ревью. Новый согласованный
комплект создаёт новый запуск, сохраняя связь с предыдущим. Доказательства
лежат в `runs/<run-id>/tasks/<TASK-ID>/<attempt>/`; их записи хранят вид
проверки, связанные AC, команду или процедуру, рабочий каталог, время,
результат, код выхода при наличии, ограничения, путь и хеш лога.
Также сохраняются роль и идентификатор запуска проверяющего, этап проверки,
Git tree или снимок проверенных файлов, версия набора команд и конфигурации.
Для worktree записываются TASK-ID, владелец, абсолютный путь, режим
`detached HEAD`, исходный SHA, снимок незакоммиченных изменений
и состояние переноса в ветку исполнения. Отдельной ветки задачи нет.

Снимок кода содержит основание diff, список путей и SHA-256 проверенных
байтов; удаления отмечаются отдельно. Для проверки, зависящей от других
модулей или конфигурации, фиксируется и эта область. Коммит обязателен
для принятой задачи, но не заменяет снимок проверенной рабочей копии.
Перед приёмкой состав коммита сопоставляется с этим снимком. Неизвестная
область зависимости требует повторной проверки перед приёмкой.

Состояние записывает только скрипт, вызванный оркестратором.
Оркестратор и остальные агенты не редактируют `state.json` напрямую.
Скрипт получает структурированное событие и ожидаемый `revision`,
захватывает блокировку изменения, перечитывает состояние и проверяет переход.
Новая версия, увеличенный `revision` и запись события сохраняются вместе
через временный файл и атомарную замену. Конфликт версии
или занятая блокировка возвращает ошибку без перезаписи. Устаревшая
блокировка снимается лишь после проверки отсутствия владельца; возраст
файла сам по себе этого не доказывает. Два активных оркестратора не могут
одновременно вести одно изменение.

`accepted` требует проверок всех назначенных AC, актуального независимого
ревью, отсутствия блокирующих замечаний и подтверждённого коммита
в ветке исполнения. `completed` требует приёмки всех задач, их коммитов
и итогового результата. Условия проверяются по записям и существующим
доказательствам; их содержательную достоверность устанавливают агенты.
Пути записей ограничены каталогом изменения, пути исходников и команд
разрешаются относительно явно указанного корня проекта. Произвольные пути
из результатов исполнителя не становятся разрешением записи.

### Детерминированные операции через скрипты

```yaml
sdd_record: decision
id: DEC-scripted-execution
requirements: [REQ-scripted-execution, REQ-autonomous-execution, REQ-execution-record, REQ-independent-verification, REQ-resume-execution]
```

Скрипты пакета содержат единые правила исполнения. Если операция описывается
схемой, таблицей переходов, сравнением файлов или последовательностью
команд с проверяемыми условиями, она реализуется в скрипте. Агент вызывает
готовую операцию, получает структурированный результат и выбирает следующий
содержательный шаг. Отсутствие готового скрипта означает пробел реализации
скилла; инструкция «сделай то же вручную» этот пробел не закрывает.

| Операция | Что делает скрипт | Что остаётся агенту |
|---|---|---|
| Входы и граф | Вызывает штатные check/snapshot sdd-spec, сверяет манифест, разбирает зависимости, вычисляет доступные задачи и ограничения режима | Разрешает смысловую неоднозначность входов |
| Состояние | Проверяет событие, переход, зависимости, бюджет, основания приёмки; записывает состояние и историю | Подаёт событие с причиной и ссылками на материалы |
| Роли | Готовит входной пакет, регистрирует запуск и результат, проверяет разделение автора и проверяющего | Запускает роль средствами адаптера среды и выполняет содержательную работу |
| Проверки | Запускает заданную команду без её подмены, сохраняет stdout/stderr, код выхода, длительность и снимки входов | Проверяющий инициирует независимый запуск и оценивает достаточность проверок вместе с рецензентом |
| Git и worktrees | Создаёт и учитывает деревья, собирает полный пакет изменений, применяет его, сверяет индекс, создаёт коммит и проверяет условия удаления | Определяет принадлежность неоднозначной правки, разрешает смысловой конфликт |
| Продолжение | Сверяет файлы, процессы, версии и Git, находит выполненные операции и устаревшие доказательства | Решает обнаруженные неоднозначности и содержательные блокировки |
| Представления | Генерирует summary, dashboard-state.js и HTML, вычисляет счётчики и следующий доступный шаг | Объясняет пользователю результат и ограничения |

Прямая поддержка запуска агентов зависит от среды. Если этот запуск доступен
только как инструмент оркестратора, скрипт готовит и проверяет его данные,
а адаптер вызывает инструмент. Скрипт не имитирует недоступного агента.
Готовые механизмы Git, тестовые инструменты и валидатор sdd-spec вызываются
из скриптов; их логика не переписывается внутри пакета.

Команда состояния получает `event_id`, `run_id`, TASK-ID при наличии,
`expected_revision`, тип события, идентификатор роли и ссылки на доказательства.
Типизированные события выражают действие: начало задачи, передача кандидата,
результат проверки, результат ревью, запрос исправления, перенос, фиксация
коммита, блокировка, продолжение или завершение. Универсального назначения
произвольного статуса и режима обхода проверок нет. Обновление доказательств,
счётчиков, режима и причин блокировки также проходит этот интерфейс,
даже если статус задачи не меняется.

Скрипт проверяет схему и известные ID, текущую версию, допустимость события,
зависимости и ограничения режима, бюджет исправлений, актуальность снимка,
результаты обязательных команд, независимость зарегистрированных ролей,
отсутствие блокирующих замечаний и фактический коммит, когда он нужен.
Скрипт проверяет наличие и структуру заключения; за истинность
содержательного вывода отвечает независимый агент.
Программа не превращает произвольное поле `passed` от исполнителя
в доказательство успешного запуска команды.

Основные переходы задачи заданы таблицей. События могут дополнять материалы
в текущем состоянии, но также проходят проверку и запись версии.

| Переход | Условие |
|---|---|
| `pending` в `running` | Приняты предшественники, действуют входы, доступны роль и ресурсы, соблюдён режим; в sequential все ранее начатые задачи приняты, заблокированной текущей задачи нет |
| `running` или `repairing` в `verifying` | Зафиксирован кандидат, передан состав изменений, исполнитель прекратил запись |
| `verifying` в `reviewing` | Независимый запуск обязательных проверок успешен на текущем кандидате |
| `reviewing` в `verifying` | Рецензент запросил дополнительные проверки того же кандидата |
| `reviewing` в `integrating` | В параллельном режиме проверки и ревью разрешают перенос |
| `reviewing` в `committing` | В последовательном режиме кандидат в рабочей ветке прошёл проверки и ревью |
| `integrating` в `committing` | Перенос завершён; актуальны независимые проверки интеграции и ревью затронутых правок |
| `committing` в `accepted` | Подтверждён коммит нужного состава в рабочей ветке и сохранены все основания приёмки |
| `running`, `verifying`, `reviewing`, `integrating` или `committing` в `repairing` | Есть замечание, неуспешная обязательная проверка или изменившийся кандидат; соблюдены применимые лимиты тестовых исправлений и код-ревью; при исправлении тестов скрипт резервирует номер цикла; затронутые доказательства помечены устаревшими |
| Любое незавершённое состояние в `blocked` | Сохранены причина, материалы и условие продолжения; в sequential блокировка задачи также переводит весь запуск в blocked |
| `blocked` в разрешённое состояние продолжения | Скрипт сверил фактическую фазу работы, устранение блокировки и условия целевого состояния |
| `accepted` в `repairing` или `blocked` | Новое доказательство выявило дефект или потерю актуальности; коммиты сохранены, затронутые зависимости пересчитаны; исправление тестов требует остатка общего лимита и регистрации цикла, иначе запуск блокируется |

Для перехода из `active` в `completed` требуются приёмка всех задач и итоговая проверка.
Если продолжение невозможно, запуск становится `blocked`; возврат к `active`
требует устранённой причины. В последовательном режиме заблокированная
текущая задача всегда блокирует запуск. Возврат к `active` разрешает
продолжить эту задачу; новую можно начать только после её приёмки.
Новое подтверждённое нарушение после
`completed` открывает исправление или блокировку по тому же правилу,
сохраняя прежнюю историю. Автоматический аудит может снять применимость
доказательства и заблокировать работу, но не выдать новое согласование
или успешную приёмку. У зависимых задач с изменившимся основанием
прежние доказательства также проверяются на применимость.

Отклонённое событие возвращает ненулевой код выхода, код причины и список
невыполненных условий; состояние и `revision` остаются прежними. Скрипт
может сохранить отдельный диагностический лог, не изображая переход
успешным. Повтор уже выполненного `event_id` с теми же данными возвращает
сохранённый результат без повторного эффекта; тот же ID с другими данными
отклоняется. При конфликте версии агент перечитывает состояние, а не
перезаписывает его. Прямая правка или повреждение записи при продолжении
вызывает проверку согласованности с историей, снимками и Git; неподтверждённое
состояние не принимается за новое основание. Это контроль процесса,
не криптографическая защита от агента с произвольным доступом к файлам.

Для операций с внешним эффектом, включая перенос и коммит, скрипт сначала
сохраняет намерение и проверяемое исходное состояние, затем выполняет
операцию и фиксирует наблюдаемый результат. После сбоя он сверяет Git
и файлы, чтобы продолжить без повторного эффекта. Запись JSON и Git-коммит
не объявляются одной атомарной транзакцией. Сбой генерации панели после
успешной записи состояния исправляется повторной генерацией, без отмены
выполненной задачи и без повторного коммита.

Имена команд и разбиение скриптов определяются при реализации. Правила
переходов и изменения состояния имеют одну реализацию, общую для всех
адаптеров среды. Проверки скриптов включают запрещённые переходы, гонку
двух запросов, повтор события, устаревшее доказательство и сбой между
внешней операцией и записью её результата.

### Отдельное хранение исполнения

```yaml
sdd_record: decision
id: DEC-separate-execution
requirements: [REQ-approved-input, REQ-execution-record, REQ-resume-execution]
```

Предлагается каталог `sdd/changes/<change-id>/execution/` с основанием
запуска, прогрессом, результатами ролей и доказательствами. Изменения
нормативного комплекта здесь не хранятся. Исходный `state.md` остаётся
точкой продолжения `sdd-spec`; у исполнения своя точка продолжения.

Так сохраняются существующие хеши и согласования. Альтернатива требует
изменить правила вычисления манифеста `sdd-spec`, проверить миграцию
и обновить ранее сохранённые основания. Для первой версии это лишняя
связь с другим пакетом.

### Последовательное выполнение как исходный режим

```yaml
sdd_record: decision
id: DEC-controlled-concurrency
requirements: [REQ-autonomous-execution, REQ-independent-review]
```

При новом исполнении режим по умолчанию `sequential`. Оркестратор ведёт
одну задачу до приёмки с проверенным коммитом, включая проверки, ревью
и исправления. Только после приёмки он выбирает следующую доступную задачу.
Автономное продолжение не требует подтверждения каждой задачи.
Блокировка текущей задачи останавливает весь последовательный запуск,
даже если в плане есть независимые задачи. Скрипт сохраняет её правки,
материалы и условие продолжения; после устранения причины возобновляется
та же задача. Остановка не разрешает пропустить её или начать другую
в отдельной рабочей копии. Нужды освобождать общую рабочую копию ради
следующей задачи нет: до приёмки текущей она не запускается.
Исчерпание лимита исправлений тестов или необходимость код-ревью сверх
лимита раундов в любом режиме останавливает весь запуск до решения
пользователя, включая независимые доступные задачи.

Режим `parallel` включается только по явному запросу пользователя для этого
исполнения. Перед запуском оркестратор сохраняет запрос и его область.
Наличие независимых задач, изоляции или свободных слотов не меняет режим
автоматически. Даже при явном запросе параллельный запуск допустим только
в отдельных Git Worktrees с контролируемой интеграцией, по зависимостям
и ограничениям плана. Сначала проверяется результат задачи в её копии,
затем результат интеграции. Если изоляция недоступна, оркестратор сообщает
причину и продолжает последовательно.

При продолжении того же исполнения проверяются сохранённый запрос и его
область, включая позднюю отмену или замену. Действующий выбор не запрашивается
повторно. Без подтверждённого разрешения режим `parallel` не восстанавливается.
При возврате к `sequential` сохраняют работу всех ранее начатых задач.
Их доводят до приёмки до запуска новых; блокировка любой из них сохраняет
остановку запуска. Переходы состояния проверяют выбранный режим
и не разрешают второй активный цикл задачи в `sequential`.
После смены сессии скрипт восстанавливает текущую незавершённую задачу;
наличие независимой задачи не меняет условия продолжения.

Оркестратор сохраняет исходный HEAD, исходные локальные изменения
и принадлежность новых файлов. Для ревью материал включает новые,
индексированные и неиндексированные изменения конкретной задачи.
Общий `git add -A` не используется как способ выделить её результат.
После проверок и ревью коммит задачи обязателен; создание коммитов входит
в поручение исполнить план. Детали фиксации результата описаны ниже.

### Раздельные инструкции оркестратора

```yaml
sdd_record: decision
id: DEC-mode-instructions
requirements: [REQ-autonomous-execution, REQ-scripted-execution, REQ-resume-execution, REQ-portable-package]
```

Оркестратор получает отдельный сценарий для выбранного режима.
Предлагаемое разбиение пакета: `flows/execute-sequential.md` и
`flows/execute-parallel.md`. Короткий входной раздел SKILL.md выбирает
один сценарий по проверенному состоянию и поручению пользователя.
Входной раздел содержит правила выбора и ссылки, без обоих алгоритмов.
При обычном последовательном запуске параллельный сценарий не читается,
даже если независимые задачи и свободные агенты доступны.

Последовательный сценарий описывает полный цикл одной задачи до приёмки
и переход к следующей только после приёмки; блокировка останавливает
весь последовательный запуск до продолжения текущей задачи.
Параллельный сценарий описывает
допуск одновременных задач, worktrees, координацию ролей, последовательную
интеграцию и остановку активных задач. Это два самостоятельных документа;
общий большой сценарий с условием режима на каждом шаге не заменяет разделение.
Ссылки выбранного сценария не должны косвенно загружать алгоритм другого.

Общими остаются схема состояния, программные правила переходов, контракты
ролей и доказательств, критерии приёмки, лимит ревью и скрипты операций.
Такие материалы подключаются по необходимости и не содержат инструкций
запуска другого режима. Общий шаг выносится в отдельный ресурс, только
если его смысл и условия одинаковы в обоих сценариях. При разном порядке
действий или риске смешения допускается повтор короткой инструкции внутри
каждого сценария. Приоритет изоляции выше сокращения повторов; копировать
реализацию скриптов и заводить расходящиеся источники правил не требуется.

При продолжении входной раздел снова выбирает сценарий по сохранённому
режиму и действующему разрешению. Если режим меняется после загрузки
его инструкций, прежний оркестратор сохраняет работу и передаёт управление
свежему контексту с состоянием, общими контрактами и новым сценарием.
История инструкций прежнего режима не переносится. Активная работа
завершается или сохраняется по уже определённым правилам смены режима;
блокировка владения запуском допускает только одного оркестратора.
Недоступность свежего контекста фиксируется как ограничение продолжения,
а не как обещание удалить уже прочитанный текст. Если недоступность
параллельной изоляции выявлена до загрузки сценария, входной раздел
сразу выбирает последовательный сценарий и сообщает причину.

При проверке пакета нужно проследить фактически загруженные инструкции
для каждого режима и смены режима. Проверяется отсутствие алгоритма
другого режима в контексте и сохранение единых контрактов и скриптов.
Поведение дублирующихся коротких инструкций должно оставаться согласованным.

### Изоляция через Git Worktrees

```yaml
sdd_record: decision
id: DEC-worktree-isolation
requirements: [REQ-worktree-isolation, REQ-task-commits, REQ-resume-execution]
```

Для каждой параллельной задачи оркестратор создаёт linked worktree
через `git worktree add --detach` от сохранённого SHA ветки исполнения,
содержащего принятых предшественников. Путь включает запуск и TASK-ID,
регистрируется в состоянии и находится вне пакетов скиллов. Исполнитель
меняет файлы только в назначенном дереве и не создаёт коммитов.
Результатом служат незакоммиченные изменения. Проверяющий получает замороженный кандидат:
на время проверки и ревью исполнитель прекращает запись. Любая новая
правка отменяет применимость затронутых доказательств.

Worktrees разделяют рабочие файлы, HEAD и индекс, но используют общий
репозиторий. Это не граница полномочий процесса. Управление worktrees,
общими refs и переносом принадлежит оркестратору; исполнитель не меняет
чужие ветки и глобальную конфигурацию. Порты, базы данных, временные
каталоги и изменяемые кэши тестов выделяются на задачу. Если это невозможно,
конфликтующие запуски выполняются последовательно; при недоступности
worktrees параллельное исполнение целиком заменяется последовательным.
Основание: [документация Git](https://git-scm.com/docs/git-worktree).

Ветку исполнения изменяет только оркестратор, по одной задаче. После
проверок и ревью в worktree он сохраняет пакет переноса относительно
исходного SHA: патч и манифест путей, операций, режимов файлов и хешей.
Пакет включает индексированные и неиндексированные изменения, удаления,
переименования, бинарные файлы и новые файлы задачи. Обычный `git diff`
без учёта новых файлов недостаточен. Скрипт собирает снимок через временный
индекс, формирует полный бинарный патч и проверяет его полноту по манифесту.
Игнорируемые результаты сборки и чужие файлы не включаются; нужный задаче
игнорируемый файл требует явного учёта. Неподдерживаемый вид изменения
блокирует перенос с объяснением, а не пропускается.

Оркестратор записывает исходный HEAD ветки исполнения и хеш пакета,
проверяет отсутствие пересечения с чужими правками и применяет патч
к актуальному состоянию ветки. Простая замена файлов их копиями из worktree
недопустима: она может затереть уже принятые изменения других задач.
Для переноса используется применение патча с учётом исходной версии,
например `git apply --3way`; внутренние Git-объекты не являются коммитами.
Конфликт разрешается в рамках задачи; проверяющий запускает проверки
интеграции, рецензент проверяет разрешение конфликта и затронутые контракты.
Перенос без конфликта также требует проверок. После успеха оркестратор
создаёт коммит задачи только в ветке исполнения, сохраняет SHA и приёмку.
Вспомогательные коммиты и cherry-pick в этой схеме не нужны.

Сбой между переносом и коммитом оставляет задачу в `integrating` или
`committing`. Продолжение сверяет пакет, текущие изменения и историю,
чтобы не применить патч и не создать коммит повторно. До подтверждения
результата исходный worktree и пакет переноса сохраняются.

При продолжении сверяются зарегистрированные пути, ветки, SHA и фактический
список worktrees. Незавершённые деревья и изменения сохраняются. После
приёмки и сохранения SHA оркестратор удаляет worktree задачи. В нём по
замыслу остаются незакоммиченные исходные правки, поэтому чистота дерева
не служит условием удаления. Перед удалением проверяются принадлежность,
абсолютный путь в зарегистрированной рабочей области, отсутствие активных
писателей и новых неучтённых данных. Каждый изменённый или новый файл должен быть частью
сохранённого пакета либо известным воспроизводимым результатом запуска.
Только после этих проверок допустим `git worktree remove --force`;
неизвестные файлы или новые изменения сохраняют дерево и блокируют очистку.
Ошибка очистки не отменяет подтверждённый коммит и не создаёт его повторно.

### Коммиты как итог исполнения

```yaml
sdd_record: decision
id: DEC-task-commits
requirements: [REQ-task-commits, REQ-execution-record, REQ-final-acceptance, REQ-resume-execution]
```

До запуска сохраняются локальная ветка исполнения и её исходный HEAD,
проверяется возможность создавать коммиты. По умолчанию используется текущая
локальная ветка, если пользователь или правила проекта не определили другую.
Отсутствие Git, доступной ветки или необходимых настроек записи блокирует
реализацию с конкретной причиной. Глобальные настройки Git скилл не меняет.

Оркестратор переводит задачу в `committing`, фиксирует ожидаемого родителя
и состав проверенных изменений. Он добавляет только файлы и участки задачи,
проверяет индекс перед коммитом, сохраняет TASK-ID в сообщении и SHA
в состоянии. Чужие индексированные изменения сохраняются отдельно от этой
операции и не попадают в коммит. Если разделить изменения надёжно нельзя,
задача блокируется до разрешения конфликта принадлежности.

В последовательном режиме результат сразу фиксируется в ветке исполнения.
В параллельном режиме Git Worktrees изолируют реализацию, а оркестратор
переносит результаты в ветку исполнения по одной задаче и проверяет
интеграцию. Итоговый SHA относится к этой ветке. Исполнитель оставляет
незакоммиченные изменения; все коммиты создаёт оркестратор. Merge с целевой веткой проекта
не выполняется: ветка исполнения остаётся локальным результатом.

При потере сессии в `committing` продолжение сверяет историю после
сохранённого родителя, TASK-ID и фактическое содержимое коммита. Найденный
результат связывается с задачей без повторного коммита. Неоднозначность
остаётся блокировкой. Ошибка Git не позволяет перевести задачу в `accepted`.
Исправление уже принятой задачи снова проходит проверки и ревью и получает
дополнительный коммит с тем же TASK-ID. Автоматические amend и переписывание
истории не используются.

Итоговая приёмка проверяет совокупный результат коммитов. Отчёт и дашборд
содержат их список по задачам. Служебные материалы исполнения сохраняются
в `execution/`; они не создают отдельного этапа финальной актуализации
проектных инструкций или отдельного коммита обслуживания проекта.

### Дашборд из состояния исполнения

```yaml
sdd_record: decision
id: DEC-live-dashboard
requirements: [REQ-progress-dashboard, REQ-execution-record, REQ-portable-package]
```

Дашборд создаётся из собственного шаблона пакета до первой задачи.
Из NeoPilot берётся принцип периодической загрузки соседнего JS-файла
и встроенного снимка, без копирования HTML или `sync.py`.
Единственный источник состояния: `state.json`. После его сохранения
детерминированный скрипт проверяет схему и генерирует `dashboard-state.js`
с `change_id`, `run_id`, `revision`, временем обновления и данными панели.
Тот же скрипт создаёт HTML со встроенным снимком. Агент не пишет JS вручную;
изменение производного файла не меняет состояние исполнения.

По умолчанию пользователь открывает `dashboard.html` с диска через
`file://`. JavaScript страницы каждые две секунды повторно загружает
соседний `dashboard-state.js` как обычный скрипт, с параметром против
устаревшего кэша. Новый запрос начинается после завершения или тайм-аута
предыдущего. Полученные данные сверяются по идентификаторам и `revision`;
более старый ответ не заменяет свежий. При новой версии обновляются
элементы страницы, без перезагрузки HTML. Чтение JSON через `fetch(file://)`
не используется. Встроенный снимок даёт начальный экран и сохраняет
возможность открыть один HTML без соседнего файла.

JS-файл содержит только фиксированную обёртку и сериализованные данные.
Генератор экранирует строки и встроенный снимок; отображение использует
текстовые узлы, без интерпретации сообщений как HTML или кода. Секреты
и полные логи проверок в панель не включаются. Скрипт атомарно заменяет
каждый производный файл под блокировкой генерации; их общая `revision`
позволяет обнаружить незавершённое обновление и восстановить файлы из JSON.

Локальный сервер не запускается в основном режиме. Если встроенный
просмотр среды блокирует соседние файлы, предлагается обычный браузер
либо запасной HTTP-просмотр на loopback. Он отдаёт только панель
и разрешённые данные, использует тот же таймер и не добавляет команд
управления исполнением. Работа через `file://` и отсутствие устаревшего
кэша проверяются в поддерживаемых браузерах при реализации; HTTP-просмотр
не заменяет эту обязательную проверку.

Верхняя часть показывает изменение, режим, число принятых задач и общее
состояние. Таблица задач содержит TASK-ID, название, статус, текущий этап,
проверки, ревью, блокировку и SHA. Отдельно видны время последнего обновления
и ограничения проверки. Число завершённых задач считается по `accepted`,
а не по последнему номеру задачи. При потере связи сохранённые данные остаются
видимыми с отметкой об отсутствии обновлений.

Ошибка генерации или чтения данных фиксируется отдельно от результата
задачи; панель сохраняет последнюю успешную версию, показывает время
данных и недоступность обновлений. Успешное чтение файла не выдаётся за
новое событие исполнения: время последнего изменения состояния видно
отдельно. При продолжении скрипт сверяет `revision` и восстанавливает
производные файлы. Пользователь получает путь к HTML, а URL только при
запуске запасного сервера. После завершения создаётся финальный снимок.
Если сервер запускался, останавливается только процесс этого исполнения.
При недоступности соседнего файла HTML явно работает как снимок;
само открытие через `file://` не означает потери живых обновлений.

### Роли с проверяемыми результатами

```yaml
sdd_record: decision
id: DEC-fresh-roles
requirements: [REQ-autonomous-execution, REQ-independent-review, REQ-final-acceptance, REQ-portable-package]
```

Работа над каждой задачей начинается в новом контексте. Исправления можно вернуть
её исполнителю, пока контекст доступен. Рецензент запускается отдельно
и получает необходимые исходные материалы, без истории автора. Для первой
версии предлагается свежий рецензент задачи, который раздельно оценивает
соответствие и качество. Итоговый проверяющий также получает чистый контекст.

В NeoPilot два рецензента сохраняют контекст между задачами. Это может уменьшать повторное
чтение и помогать замечать расхождения между задачами. Здесь сначала
проверяется более простой вариант со свежим контекстом; связи между задачами
доступны через design, код и сводку интерфейсов. Выигрыш от длительного сохранения контекста
рецензентов требует сравнительного испытания.

Адаптер различает недоступный механизм запуска, временно занятые слоты
и потерянного агента. Запуск встроенными средствами среды предпочтителен; отдельный CLI допустим,
если подтверждены чистый контекст, доступ к файлам и аутентификация.
Нельзя объявлять инструкцию «только чтение» жёстким ограничением прав среды.

### Доказательства определяют завершение

```yaml
sdd_record: decision
id: DEC-evidence-completion
requirements: [REQ-execution-record, REQ-independent-review, REQ-final-acceptance]
```

Состояния исполнения отражают работу, ревью, исправление, блокировку
и приёмку. Только принятое состояние удовлетворяет зависимость.
Ошибка предшественника сохраняет блокировку потомков. Проверяющий механизм
отклоняет недопустимый переход, а не ограничивается предупреждением.

Для verification используется согласованная команда, процедура или
предусмотренная подготовка запуска. Число тестов и exit 0 не заменяют
проверку того, что нужный AC действительно проверен. Ответственность
за запуск и основания приёмки определены ниже.

### Лимит раундов код-ревью и решение пользователя

```yaml
sdd_record: decision
id: DEC-review-round-limit
requirements: [REQ-independent-review, REQ-scripted-execution, REQ-autonomous-execution, REQ-progress-dashboard, REQ-resume-execution]
```

На TASK-ID в рамках исполнения разрешено суммарно не более трёх раундов
код-ревью. Первый раунд имеет номер 1 и входит в общий лимит 3; отдельного
счётчика повторных ревью нет. После замечаний в раунде 1 допустимы
исправления, проверки и раунд 2; после замечаний в нём допустим раунд 3.
Четвёртый раунд автоматически не запускается. Если третий раунд успешен
и выполнены остальные условия приёмки, задача завершается обычным образом.

Скрипт резервирует номер при принятии события начала раунда, до запуска
рецензента. Один раунд объединяет заключения по соответствию и качеству
одного зафиксированного кандидата, даже если их дают разные рецензенты.
Повтор доставки события и продолжение прерванного раунда на той же версии
не занимают новый номер. Технический сбой без заключения оставляет раунд
незавершённым; его восстановление не обнуляет счётчик. Новая версия кода
или новое содержательное ревью требует нового раунда.

Любое новое код-ревью задачи, в том числе после интеграции или исправления
дефекта итоговой приёмки, расходует тот же общий лимит. Запуски тестов
и проверка общего сценария не являются раундами код-ревью. Если требуется
новое ревью, а три раунда уже использованы, оно не пропускается ради лимита:
работа останавливается. Смена исполнителя, рецензента, worktree, фазы
или сессии лимит не восстанавливает. При пересмотре плана история
сохраняется; новый лимит для прежней задачи требует решения пользователя.
Исправления после неуспешных тестов и линтеров, включая повторы без правок,
ограничиваются пятью циклами по DEC-test-repair-limit. Они не расходуют
раунды код-ревью. Замечание рецензента без падения проверки расходует
только бюджет ревью; если при его исправлении падают тесты, действуют оба лимита.

После третьего раунда с блокирующими замечаниями либо при необходимости
ещё одного обязательного раунда скрипт
переводит задачу и запуск в `blocked` с причиной `review_limit_reached`.
Новые задачи, исправления, ревью, переносы и коммиты не запускаются,
включая независимые задачи. В параллельном режиме оркестратор останавливает
выдачу работы и приводит активные роли к сохранённой точке остановки.
Уже начатая файловая или Git-операция сверяется до однозначного результата;
её фактический эффект записывается, но новая работа не начинается.
Частичные изменения, worktrees, логи и существующие коммиты сохраняются.
Запрос решения отправляется после фиксации этой точки остановки.

Пользователь получает TASK-ID, лимит и использованные раунды, оставшиеся
замечания с привязкой к критериям и файлам, что менялось между попытками,
результаты тестов и ревью и состояние остальных задач. Дашборд показывает
счётчик и ожидание решения. Оркестратор предлагает конкретные варианты:
добавить указанное число раундов, передать проблему на пересмотр через
`sdd-spec` или закончить текущее исполнение с частичным результатом.
Спорное замечание можно направить на отдельный разбор по явному решению;
это не разрешает автоматически принять нарушение обязательного критерия.

Продолжение требует сохранённого явного решения пользователя с областью
и новым конечным лимитом. Скрипт проверяет ссылку на это решение и остаток
бюджета; запись оркестратора «продолжаем» сама по себе не является основанием.
Общее поручение автономно выполнить план, истечение времени и смена сессии
не снимают остановку. Счётчик не обнуляется: дополнительные раунды увеличивают
лимит, сохраняя историю. Отказ от продолжения оставляет частичный результат
и не переводит запуск в `completed`. Ослабление согласованных критериев
требует пересмотра через `sdd-spec`; лимит не заменяет обязательные проверки.

### Пять циклов исправления тестов

```yaml
sdd_record: decision
id: DEC-test-repair-limit
requirements: [REQ-independent-verification, REQ-scripted-execution, REQ-autonomous-execution, REQ-resume-execution, REQ-progress-dashboard]
```

Пользователь установил лимит 5 на исправления после падения тестов.
До начала работы скрипт записывает этот предел на каждый TASK-ID.
Он применяется к обязательным тестам и линтерам на всех этапах:
самопроверке, независимой проверке, интеграции и итоговой приёмке.
Первое падение, исходная реализация и успешные проверки без предшествующей
ошибки не расходуют цикл. Единица учёта определяется результатом проверки,
а не числом файлов, команд или перезапусков исполнителя.

После падения скрипт принимает событие `start_test_repair`, связанное
с исходным логом, TASK-ID, версией кандидата и `event_id`. До начала
исправления он атомарно резервирует номер и увеличивает
`test_repair_cycles_started`. Один цикл включает пакет исправлений
и результат следующего назначенного набора проверок. Несколько упавших
тестов этого набора относятся к одному циклу. Следующие правки после
нового падения либо повтор проверки без правок требуют нового номера.
Проверка исправленного кандидата завершает цикл; её падение само по себе
ещё не начинает следующий. Исполнитель не может скрыть цикл, назвав
исправление продолжением прежней попытки.

Повтор доставки события с теми же данными и восстановление прерванного
цикла на сохранённом кандидате не расходуют новый номер. Новый `event_id`
не разрешает начать второй активный цикл или повторно обработать то же исходное
падение. Потеря агента сохраняет активный цикл; после его проверки работа
продолжается с тем же номером. Техническая недоступность проверки оставляет
цикл незавершённым и блокирует работу до восстановления возможности запуска.
Автоматические повторы при неизменной причине недоступности не выполняются.

Лимит общий для задачи: успешная промежуточная проверка, передача работы,
смена фазы, режима, сессии, worktree или попытки его не сбрасывают.
При пересмотре плана история прежней задачи переносится вместе с работой.
Дефект итоговой проверки сначала связывается с задачей; если принадлежность
неясна, фиксируется блокировка до её определения. Исходная проблема вне
согласованного объёма также требует блокировки и возврата в `sdd-spec`.

После пятого неуспешного цикла либо при необходимости шестого скрипт
переводит задачу и весь запуск в `blocked` с причиной
`test_repair_limit_reached`. Применяется порядок сохранения активных работ
из DEC-review-round-limit: новые задачи, исправления, ревью, переносы
и коммиты не начинаются; уже начатые внешние операции сверяются и сохраняются.
Успешный пятый цикл допускает проверки, ревью и приёмку по обычным условиям.
Само достижение числа 5 не блокирует успешный результат.

Пользователь получает историю пяти циклов, оставшиеся ошибки и состояние
остальных задач. Дашборд показывает расход и лимит циклов отдельно от ревью.
Продолжение требует явного решения с новым конечным лимитом; скрипт проверяет
его область и сохраняет прежний счётчик. Дополнительные циклы не увеличивают
лимит код-ревью и не обходят другую действующую причину остановки.
Без такого решения сохраняется частичный результат и остановка.

Альтернатива в виде общего числа попыток исполнителя отклонена: одна попытка
может содержать много исправлений и не задаёт проверяемого предела.
Отдельный счётчик циклов позволяет однозначно проверить остановку даже
до первого код-ревью.

### Независимый запуск тестов и линтеров

```yaml
sdd_record: decision
id: DEC-independent-verification
requirements: [REQ-independent-verification, REQ-independent-review, REQ-final-acceptance]
```

До реализации оркестратор извлекает готовые обязательные команды и записи
`verification.run.setup_required` из плана, инструкций проекта и конфигурации CI,
связывает их с AC и сохраняет набор проверок. Он указывает проверки задачи,
проверки интеграции и полный
обязательный набор для завершения, включая линтеры. Если назначение команды
неясно, фиксируется пробел; исполнитель не выбирает более слабый набор
самостоятельно. Отсутствие применимого линтера фиксируется с основанием,
без выдуманного успешного запуска. Обязательная, но недоступная команда
остаётся блокировкой, кроме ожидаемого отсутствия до подготовки,
прямо предусмотренной `setup_required` в согласованной задаче.

Для `setup_required` до первой правки сохраняются исходный снимок проекта,
TASK-ID, связанные AC, текст подготовки из плана и причина отсутствия
готового запуска. Независимый проверяющий выполняет уже существующие
обязательные проверки. Если таких проверок нет, это записывается как
отсутствие исходного запуска; успешный результат не заявляется.
Сбой существующей проверки сохраняет обычную блокировку и не может быть
переименован в плановую подготовку.

Исполнитель получает разрешение на подготовительные действия в пределах
`setup_required`: например, создать предусмотренный запускатель тестов
и его конфигурацию. После подготовки он передаёт конкретную команду,
рабочий каталог и конфигурацию. Оркестратор связывает их с исходными AC
и через скрипт сохраняет новую версию набора проверок в записи исполнения.
Согласованный `tasks.md` остаётся неизменным. Если команда или требуемая
подготовка выходит за согласованный объём, работа блокируется для пересмотра
через `sdd-spec`.

После подготовки проверка становится обязательной для дальнейшей работы
по этим AC. Свежий проверяющий самостоятельно запускает команду на
зафиксированном кандидате до приёмки; сообщение исполнителя о готовности
окружения не заменяет запуск. Недоступность команды на этом этапе блокирует
работу, а падение тестов подчиняется лимиту исправлений. Ожидаемое отсутствие
запускателя до подготовки не считается падением теста и не расходует цикл.
При продолжении скрипт сверяет записанную команду и фактическую подготовку:
завершённая подготовка не позволяет снова объявить запуск ожидаемо отсутствующим.
Вновь созданные проверки не выдаются за проверку исходной версии проекта.

| Когда | Кто запускает | Что проверяет |
|---|---|---|
| До первой правки | Независимый проверяющий по поручению оркестратора | Исходное состояние существующих обязательных тестов и линтеров; ожидаемое отсутствие запуска по setup_required записывается отдельно |
| После предусмотренной планом подготовки проверки | Свежий проверяющий, не автор подготовки | Конкретная команда из записи исполнения на зафиксированном кандидате; результат не считается проверкой исходного состояния |
| Во время реализации и перед передачей | Исполнитель | Проверки своей задачи для поиска и исправления ошибок |
| После передачи замороженного кандидата | Свежий проверяющий, не автор | Сам запускает обязательные проверки задачи; сохраняет исходные результаты |
| Перед приёмкой, после переноса из worktree | Независимый проверяющий по поручению оркестратора | Проверки задачи на новом основании и регрессии затронутых контрактов |
| После всех коммитов, перед `completed` | Свежий итоговый проверяющий | Полный обязательный набор тестов и линтеров и общие сценарии из плана на итоговом HEAD |

В последовательном режиме кандидат уже находится в ветке исполнения,
поэтому отдельного переноса и дублирующего этапа проверки нет. Набор задач
и регрессий определяется до проверки по плану и затронутым контрактам;
при неизвестной области влияния используется полный обязательный набор.
При совпадении команд они выполняются один раз в пределах этапа.

Проверяющий получает требования, команды и код без вывода автора о готовности.
Он запускает команды собственными инструментами и сохраняет вывод и коды
выхода. Пересказ исполнителя не заменяет этот запуск. Рецензент отдельно
проверяет связь assertions с AC, отрицательные случаи, изменения тестов,
skip/xfail, настройки линтеров и подмену команд. При нехватке доказательств
он задаёт воспроизводимый дополнительный сценарий; проверяющий выполняет
его, исполнитель исправляет код или добавляет тест. Ослабление обязательной
проверки для получения успеха не принимается. Эти роли логически разделены;
в первой версии их может выполнять один свежий агент, если он не писал
реализацию и явно сохраняет оба результата: запуск и содержательное ревью.

На время проверки кандидат фиксируется, а запись в него прекращается.
Проверяющий сверяет снимок до и после запуска; автоисправления линтера
относятся к реализации и требуют новой передачи. Оркестратор сопоставляет
команды, логи, проверенную версию и состав коммита. Если hook изменил
содержимое при коммите, приёмка не происходит до повторной проверки;
исправления оформляются дополнительным коммитом. После изменений кода,
зависимостей, конфигурации или разрешения конфликта затронутые доказательства
становятся устаревшими. Новая сессия может использовать результат только
при подтверждении той же версии и условий запуска.

Исходно падающая, пропущенная, недоступная или нестабильная обязательная
проверка не считается успешной. Ожидаемое отсутствие по `setup_required`
до согласованной подготовки не запрещает эту подготовку и также не означает
успеха проверки. Исправления и повторы после падения
подчиняются DEC-test-repair-limit и сохраняют все результаты;
выбор только удачного прогона не закрывает
проблему. Если исправление выходит за согласованный объём, фиксируется
блокировка и обращение к `sdd-spec`. Оркестратор не переводит задачу
в `accepted`, а весь план в `completed` при незакрытой обязательной проверке.
Независимый запуск подтверждает выполнение команд; содержательное ревью
снижает риск недостаточных тестов. Ни один из них не доказывает отсутствие
всех возможных дефектов.

Дашборд различает самопроверку исполнителя, независимую проверку задачи,
проверку интеграции и итоговый прогон. Для каждого результата доступны
версия кода, команда, время, код выхода и ссылка на лог; устаревшие
и пропущенные проверки не выглядят успешными.

### Изменение согласованного контракта

```yaml
sdd_record: decision
id: DEC-return-to-spec
requirements: [REQ-spec-revision, REQ-resume-execution]
```

Возврат содержит ссылку на критерий или решение, наблюдаемую проблему,
минимальное воспроизведение и список затронутых задач. Это материал для
`sdd-spec`, без правки нормативного комплекта. После пересмотра новый
манифест образует новое основание исполнения. Совпадающие TASK-ID помогают
найти прежнюю работу, но не доказывают применимость старой приёмки:
сверяются критерии, зависимости и версия кода.

## Зависимости и установка

Пакет обнаруживает установленный `sdd-spec` через возможности среды
и использует его штатные read-only check/snapshot. Код парсера SDD
не копируется в новый пакет. Недоступная или несовместимая версия зависимости
даёт явное ограничение, а не упрощённую проверку по заголовкам.

Собственные Python-скрипты исполнения получают явные корни проекта и изменения.
Каждая точка входа содержит метаданные PEP 723 с версией Python и зависимостями,
включая `dependencies = []` для стандартной библиотеки. Рядом поставляется
`<script>.lock`; штатная команда использует абсолютный путь:
`uv run --locked --script "<script>"`. Зависимости проекта-потребителя
не изменяются, отдельная подготовка его окружения не нужна.

Окружениями управляет uv через общий пользовательский внешний кэш.
Применяются действующие требования
[package-runtime](../../../skills/sdd-skill-conductor/references/package-runtime.md).
На Windows `UV_CACHE_DIR` указывает на `uv-runtime/cache` в системной
временной папке; для сторонних uvx применяется соседний `UV_TOOL_DIR`.
Пути задаются пользовательской настройкой. Собственный менеджер окружений,
маркеры готовности и кэши по хешу пути копии пакета не создаются.
Пакет проверяет фактический доступ к хранилищу и сообщает ограничения среды.

При обычном первом запуске uv устанавливает отсутствующие зависимости;
после очистки временного кэша тот же запуск восстанавливает окружение.
`--offline` используется только по явному требованию офлайн-режима.
Устаревший lock-файл приводит к отказу `--locked` без перезаписи;
обновление зависимостей выполняется отдельным явным действием.
Точки входа отключают байткод до локальных импортов; дочерние Python-процессы
используют `sys.executable` с `-B`. Кэш pytest отключён либо вынесен из пакетов.
Перед упаковкой проверяются первый и повторный запуск из исходной
и установленной копий, внешний рабочий каталог и конфликтующие зависимости
проекта. Проверяются также отказ офлайн-запуска с пустым кэшем,
неизменность lock-файлов и отсутствие runtime-файлов, включая скрытые
и игнорируемые Git, в каталогах скиллов.

Сохраняемые результаты пишутся
в каталог изменения или явно выбранную рабочую область. Относительные
пути пользовательских данных разрешаются от указанного корня проекта.

## Проверка реализации и риски

До написания инструкций нужен изолированный прогон одного согласованного
плана без нового скилла. Затем сравниваются исполнение, продолжение,
ложный DONE, устаревший план, неуспешный предшественник, потеря агента
и возврат к спецификации. Детерминированные проверки должны отклонять
недопустимые переходы; испытания агентов должны показывать реальное
соблюдение процесса. Установка проверяется из отдельной копии и стороннего
рабочего каталога, включая отсутствие runtime-файлов внутри пакета.

Риски разобраны в [premortem](premortem.md). Формат записи исполнения
требует проверки на тестовых запусках при реализации. Миграция
существующих SDD-изменений не требуется: новый запуск
добавляет материалы исполнения только выбранному изменению.
