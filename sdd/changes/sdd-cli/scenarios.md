# Реестр сценариев SDD CLI

Эталон для сравнения — рабочие вызовы Python из `sdd-setup`, `sdd-architect`, `sdd-spec` и `sdd-apply` на коммите `89b40724dfaa44259dcf64781f30493b42b52191`. Реестр охватывает 77 семейств. Соответствие точек входа Go командам Python приведено в [руководстве CLI](../../../cli/README.md#команды).

## Пилот — проверка обычного изменения

Восемь случаев проверяют `check.py` для `work_kind=change`. Для каждого случая запускатель создаёт обычный каталог проекта с пробелами в имени вне Git-репозитория. В `sdd/changes/sample-change/` он кладёт `proposal.md`, `design.md`, `tasks.md` и `specs/sample-capability/spec.md` из шаблонов эталонной версии. Базовый проект не содержит записей согласования. Варианты ниже меняют только указанную часть этой фикстуры. [Готовая фикстура и тесты процесса](../../../skills/sdd-spec/tests/test_check_command.py) · [Шаблоны документов](../../../skills/sdd-spec/templates)

Обе команды запускаются из одного внешнего рабочего каталога с одинаковыми аргументами после точки входа. Python-вызов использует обёртку из `sdd-spec`, которая загружает `sdd-shared`. Для Go запускатель передаёт абсолютный путь к собранному `sdd`. [Рабочие команды скилла](../../../skills/sdd-spec/references/runtime-setup.md) · [Обёртка](../../../skills/sdd-spec/scripts/check.py) · [Сравнительный тест](../../../cli/tests/pilot.py)

```text
uv run --python "<python>" --locked --script "<sdd-spec>/scripts/check.py" --project-root "<project>" --change sample-change --stage <stage>
sdd check --project-root "<project>" --change sample-change --stage <stage>
```

| ID | Изменение фикстуры | `--stage` | Независимое ожидание |
|---|---|---|---|
| P01 | Полный комплект | `documents` | Код 0, `schema_version=2`, `errors=[]`, `approval_status.approved=false` |
| P02 | Полный комплект | `plan` | Код 0, `errors=[]`, план прочитан, согласование отсутствует |
| P03 | Удалён `tasks.md` | `documents` | Код 0. Документы можно проверять до создания плана |
| P04 | Удалён `tasks.md` | `plan` | Код 2. Диагностика указывает на отсутствующий вход |
| P05 | В записи задачи заменено `number: 1` на `number: 2` | `plan` | Код 1. У структурной ошибки есть поля `code`, `path`, `element_id`, `message` |
| P06 | Удалён `proposal.md` | `documents` | Код 2, непустой `errors` |
| P07 | В `proposal.md` заменено `schema_version: 1` на `schema_version: 99` | `documents` | Код 2, диагностика неподдерживаемой версии |
| P08 | Всё содержимое `proposal.md` заменено одним байтом `FF` | `documents` | Код 2, диагностика ошибки чтения UTF-8 |

**Правило прохождения для каждого ID**

1. Обе реализации отдельно выполняют ожидание строки. Таймаут, сбой подготовки uv или отсутствие соседнего скилла — ошибка прогона. В частности, такой сбой не может подтвердить ожидаемый код 2 для P04 и P06–P08.
2. Коды завершения совпадают. Каждый stdout разбирается целиком как один JSON-документ UTF-8. Сравниваются состав полей, типы, значения и порядок элементов массивов, включая тексты и порядок диагностик и все статусы. Пробелы оформления и порядок ключей объекта несущественны. Отсутствующее поле, `null`, пустой список и `false` различаются. stderr сравнивается отдельно, побайтово.
3. До каждого вызова и после него сравниваются относительные пути, типы записей, в том числе пустые каталоги, и SHA-256 файлов проекта. Первый вызов, изменивший фикстуру, проваливает сценарий. Обе реализации читают данные по одному абсолютному пути, поэтому сравнение диагностик не требует удаления путей.
4. При расхождении отчёт называет ID, аргументы, реализацию, канал и первое различие, например `P02 /stdout/approval_status/approved: Python=false, Go=true`. Для проверки самого компаратора подменить это поле в сохранённом ответе и убедиться, что отчёт указывает на него. Подмена проверяет запускатель и не входит в восемь случаев.

## Сравнительная проверка

Каждому ID соответствует рабочая команда или тип события. В сравнительных тестах фиксируются версия эталона, входы и ожидаемый результат. Интерпретатор Python запускает извлечённый эталон, бинарник Go работает с таким же проектом по тому же пути. Скиллы продолжают использовать Python. Команды для повторного прогона приведены в [руководстве CLI](../../../cli/README.md#сравнение-с-python).

| Срез | Что сравнивается | Запускатель |
|---|---|---|
| P01–P08, D01–D03 | Документы и рефакторинг, граф задач, следы ревью и согласования, выбор роли и инструкции модели | [spec.py, набор spec](../../../cli/tests/spec.py) |
| D04–D07 | OID, содержимое дерева, индекс, регистрация worktree, состояние ref при конкурирующей записи | [spec.py, набор checkpoint](../../../cli/tests/spec.py) |
| S00–S09 | Вывод инструментов и их рабочий каталог, настройки, хэши инспекции, diff, повторная инспекция и откат ошибки записи | [setup.py](../../../cli/tests/setup.py) |
| A01–A10 | Отчёты, свидетельства и статус аудита, ошибки чтения и состояние после отказа | [architect.py](../../../cli/tests/architect.py) |
| O01–O13, E01–E29 | JSON-протокол, сохранённые объекты и журналы, роли, сроки, проверка кандидата, бинарный перенос, конфликт Git, возобновление и финальные документы | [apply.py](../../../cli/tests/apply.py) · [События](../../../cli/tests/apply_events.py) · [Ревизии проверок](../../../cli/tests/apply_registry.py) · [Операции с worktree](../../../cli/tests/apply_transfers.py) |

Сравнение учитывает формат результата. В Git фиксируются автор и время, чтобы сравнивать OID напрямую. Для UUID, часов и портов проверяются связи с сохранённым состоянием. Целостность объектов и патчей проверяется по байтам. Для сетевого отказа в `setup` сопоставляется результат обращения к недоступному источнику и наличие диагностики. Для дробных архитектурных метрик допускается относительное расхождение до `2 × 10⁻¹⁵` из-за округления. Для HTTP 404 проверяются код и сообщение. На этапе приёмки E08 используются подготовленное состояние рефакторинга и фактический вывод Git-проверки. Действия ролей моделируются входными записями протокола.

При изменении Python-контракта обновите ссылку на эталон, вход и независимое ожидание в соответствующем тесте. При расхождении сохраните команду, ОС и путь к тестовой фикстуре из вывода запуска.
