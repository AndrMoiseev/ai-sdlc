# Дизайн поясняющих документов

## Контекст и границы

[Предложение](proposal.md) добавляет необязательное пояснение к черновику
sdd-spec. Контракт поведения описан в
[solution-explanation](specs/solution-explanation/spec.md).

Сейчас flows/draft.md завершает подготовку структурной проверкой и предложением
ревью. scripts/lib/snapshots.py включает в документный манифест только proposal,
design и specs. Пакет common-dependencies уже содержит archify. Эти свойства
позволяют добавить пояснение через инструкции и шаблоны без нового типа SDD
и изменений проверяющих скриптов.

## Модули и контракты

| Часть sdd-spec | Предлагаемое изменение |
|---|---|
| SKILL.md | Добавить маршрут к подготовке или обновлению пояснения по запросу пользователя. |
| flows/draft.md | После редактуры черновика предложить пояснение, учесть ранее выданное поручение, сохранить выбор. |
| flows/explain.md, новый файл | Готовить пояснение, вызывать archify, вставлять превью и передавать незавершённую проверку. |
| references/explanation.md, новый файл | Описать содержание, обозначения, размещение, актуальность и контракт продолжения. |
| templates/explanation.md, новый файл | Дать структуру пояснения с местом для ссылок на источники, диаграмм и подписей. |
| templates/preview-handoff.md, новый файл | Дать промпт с конкретными путями, поисковыми маркерами и условиями завершения. |
| flows/revise.md и flows/resume.md | Проверять выбор пользователя и актуальность производных материалов. |
| references/document-format.md | Описать необязательные производные файлы и сохранить нынешний нормативный манифест. |
| references/editorial-pass.md | Включить русскую авторскую прозу пояснения и промпта в текущий проход редактуры с защитой путей, ID и исходных результатов инструментов. |
| references/runtime-setup.md и README.md | Описать обнаружение archify и ограничение при его отсутствии; ручное подключение требует отдельной зависимости. |
| evals и tests/test_package_contract.py | Проверить сценарии поведения и наличие новых ресурсов в полном пакете. |

archify отвечает за схемы диаграмм, генерацию HTML, проверки и снимки.
sdd-spec выбирает содержание, связывает его с документами изменения и сообщает
статус результата. Код archify, его шаблоны и зависимость в APM не изменяются.
check и snapshot sdd-spec продолжают проверять основной комплект; ссылки
пояснения и актуальность артефактов агент проверяет по инструкциям.

## Термины

Пояснение - производный документ для чтения предлагаемого решения. Основной
комплект - proposal, design и все specs изменения. Превью - снимок диаграммы,
полученный при проверке archify и пригодный для вставки в пояснение.
Статус изменения описывает отличие элемента от исходного состояния. Статус
проверки описывает выполненную работу и её результат; эти статусы независимы.

### Необязательный этап и производный документ

```yaml
sdd_record: decision
id: DEC-optional-derived-explanation
requirements: [REQ-offer-explanation, REQ-explanation-content, REQ-explanation-freshness]
```

Новый маршрут explain вызывается после выбора пользователя или по его прямому
запросу. Отказ, отложенный выбор и отсутствие возможности создать превью
не добавляют условий готовности основного комплекта.

По умолчанию создаётся explanation.md. Для самостоятельных тем материал можно
разделить на explanation/modules.md, explanation/processes.md и
explanation/scenarios.md, сохранив входной explanation.md со ссылками.
Разделение определяется объёмом и читаемостью, без обязательного числа файлов.

Пояснение содержит краткое объяснение проблемы и решения, обзор изменений,
подписи к диаграммам и ссылки на требования или разделы design. Таблица покрытия
показывает, где объясняется каждый затронутый модульный фрагмент, процесс и сценарий
основного комплекта. Отдельные SCN-ID не вводятся: достаточно ссылок на AC,
заголовки и соответствующие разделы. Для неприменимых представлений указана причина.

Альтернатива с обязательным пояснением добавляла бы задержку для небольших
изменений. Включение изображений в нормативный манифест заставило бы повторять
согласование после замены заглушек. Выбранный подход сохраняет текущие границы.

### Отображение статусов средствами archify

```yaml
sdd_record: decision
id: DEC-existing-archify-fields
requirements: [REQ-archify-diagrams, REQ-change-markers]
```

| Элемент | Поле и правило |
|---|---|
| Компонент architecture | tag со статусом; назначение сохраняется в label и sublabel. |
| Связь architecture | label с маркером изменения и смыслом зависимости. |
| Шаг workflow | tag со статусом; условия и ответственность остаются в содержании узла. |
| Переход workflow | label с маркером; направление и роль перехода сохраняются. |
| Участник sequence | sublabel со статусом и нужным пояснением роли. |
| Сообщение sequence | Маркер в label; note для краткого объяснения изменения. |

Текстовые обозначения едины: «Новый», «Изменён», «Без изменений», «Удаляется».
Для коротких подписей используются [+], [~], [=], [-]. Расшифровка находится
в видимой части диаграммы. Статус не прячется в интерактивной карточке.
Слишком длинная подпись требует изменить компоновку или разделить диаграмму.

type продолжает обозначать назначение компонента. variant: emphasis допустим
как дополнительный акцент; он не заменяет возврат, асинхронность или другой
смысл стиля. Легенда archify допускает только предусмотренные схемой ключи,
поэтому произвольные записи статусов в meta.legend не добавляются. Расшифровку
можно дать через поддерживаемые текстовые элементы и cards, проверив её видимость
в выбранном превью.

Перекодировка external/cloud/backend в статусы отвергнута: она искажает типы
компонентов. Ручная правка CSS или HTML после генерации также не нужна и нарушила
бы привязку проверок archify к артефакту.

Диаграммы показывают предлагаемое состояние с контекстом существующей системы.
При удалениях или сложном изменении порядка допустима пара «До» и «После»;
удалённый шаг не должен выглядеть исполняемым в будущем сценарии. Цвет не является
обязательным способом различения статусов.

### Размещение и основания актуальности

```yaml
sdd_record: decision
id: DEC-artifact-index
requirements: [REQ-explanation-artifacts, REQ-explanation-freshness]
```

Пример структуры, где угловые скобки обозначают подставляемые имена:

```text
sdd/changes/<change-id>/
  explanation.md
  explanation/                 # только при разделении пояснения
  archify/
    index.md
    preview-handoff.md         # при незавершённых превью
    <diagram-id>/
      candidate.json
      diagram.html
      <результаты archify>
      <каталог проверки со снимками>/
```

ID диаграммы включает её предмет и сохраняется при продолжении. Новые варианты
и повторные проверки размещаются по правилам archify о сохранении прежних
результатов. Вызовам явно передаются пути внутри archify/, чтобы не возникал
отдельный каталог .archify в корне проекта. Имена файлов результатов берутся
из ответов установленного инструмента.

index.md записан в обычном Markdown без нового document_type. Он хранит манифест
основного комплекта, полученный через существующий snapshot documents, и записи
диаграмм: ID, тип, предмет, документы и места вставки, пути candidate/HTML,
ссылки на результаты проверок и выбранные PNG, ограничения и следующий шаг.
Сведения о проверке берутся из результатов archify. Наличие PNG само по себе
не доказывает его связь с текущим HTML.

При любом изменении исходного манифеста весь комплект пояснения требует сверки.
Агент обновляет затронутые части и подтверждает применимость остальных; новый
манифест записывается только после сверки всего комплекта. До этого пояснение
и index.md явно сообщают об устаревании. При переносе в другую среду сравнение
повторяется. Внешние источники кода проверяются отдельно по необходимости.

Выбор пользователя о создании или отказе сохраняется в читаемой части state.md
вместе с областью и исходным манифестом. Он не добавляется как новый kind USER
в реестр согласования нормативных документов. Наличие старого пояснения само
по себе не разрешает новую область работы.

### Проверка со снимками и передача между средами

```yaml
sdd_record: decision
id: DEC-browser-check-handoff
requirements: [REQ-checked-previews, REQ-preview-handoff, REQ-explanation-artifacts]
```

После создания candidate агент следует процедуре установленного archify.
В изученной версии finalize включает browser-check без изображений, а visual-check
выполняет проверку со снимками. Для пояснения нужны снимки из этой проверки;
отдельный конвейер генерации превью не вводится. Если соответствующая проверка
уже выполнена для тех же байтов HTML, используются её результаты.

Готовое изображение вставляется как кликабельное превью. В explanation.md
ссылка может выглядеть так; реальные имена PNG берутся из результата проверки:

```markdown
[![Изменения модулей](archify/module-map/captures/preview.png)](archify/module-map/diagram.html)
```

Для explanation/modules.md относительные ссылки получают префикс ../.
До появления подходящего PNG используется видимая заглушка:

```markdown
> ARCHIFY_PREVIEW_PENDING:module-map
> Превью ожидает проверки в среде с браузером.
> [Открыть HTML-диаграмму](archify/module-map/diagram.html)
```

Причина в заглушке соответствует фактическому результату: отсутствие браузера,
ошибка проверки или непригодный снимок. Ненулевой результат finalize не называется
успехом. Если HTML уже создан и доступные детерминированные проверки прошли,
его сохраняют с честным статусом оставшейся работы.

Промпт preview-handoff.md задаёт корень проекта и change-id, документы и index.md,
точные ID заглушек, пути candidate/HTML и известную диагностику. Он поручает:

1. Прочитать установленный archify и проверить исходный манифест и привязку HTML.
2. При устаревании сначала согласовать или выполнить уже порученное обновление
   содержания; при несовпадении области остановить только зависимую работу.
3. Завершить необходимые проверки по archify и получить снимки при проверке.
4. Осмотреть снимки, выбрать читаемые изображения и заменить соответствующие
   заглушки относительными ссылками.
5. Обновить index.md и checkpoint, сохранить прочие документы и сообщить
   оставшиеся заглушки и ограничения.

Промпт не предполагает установленный путь скилла из прежней среды, не обещает
исправить содержательный дефект одним переносом и не переписывает утверждённое
решение ради снимка.

### Предлагаемое решение и факты репозитория

```yaml
sdd_record: decision
id: DEC-proposed-state-evidence
requirements: [REQ-explanation-content, REQ-archify-diagrams]
```

Исходное состояние устанавливается по спецификациям и проверенному коду.
Будущее состояние основывается на документах изменения. В тексте и подписях
явно обозначается, что диаграмма описывает предложение.

В archify доказательства repository-backed привязаны к зафиксированному коммиту.
Новый модуль или ещё не сохранённый в коммите design нельзя выдавать за такой
источник. Для смешанного текущего и предлагаемого состояния используется путь
archify для описания системы, а реальные источники и ссылки на требования
сохраняются в пояснении и index.md. Если отдельная диаграмма отражает только
проверенный коммит, допустим repository-backed путь с его полными проверками.

## Проверка изменения

Реализация должна пройти процедуры sdd-skill-conductor с временными данными
вне пакетов. Сценарии поведения проверят:

- предложение пояснения, отказ, поздний запрос и отсутствие повторного вопроса;
- набор из трёх типов диаграмм с независимыми статусами узлов и связей;
- получение и вставку снимков в среде с браузером;
- заглушки и перенос работы в другую среду без браузера в исходном прогоне;
- дефект при доступном браузере, частичный результат и повторный запуск;
- устаревание после правки design, сохранение согласований при замене превью,
  перенос набора документов и отсутствие установленного archify.

Поведенческие прогоны разделяют исполнение archify и подставленные результаты
инструмента. Подставленный результат проверяет ветвление инструкций, но не
подтверждает реальную генерацию или браузерную совместимость. Изменённый пакет
проверяется на полноту ссылок и отсутствие созданных окружений, снимков и логов.
Нынешние проверки sdd-spec должны продолжить работать с изменениями без пояснений.

## Риски и открытые вопросы

Читаемость меток зависит от компоновки и подтверждается осмотром снимков.
Большой сценарий может потребовать нескольких диаграмм. Доступная версия archify
может отличаться от изученной, поэтому точные команды и поля берутся из её
инструкций. Пояснение без браузера сохраняет полезный HTML, но остаётся без
завершённой проверки и превью.

Блокирующих вопросов к этому черновику нет. Способ обозначения изменений принят
пользователем; остальные решения представлены для рассмотрения в составе
черновика. История и следующий шаг находятся в [state.md](state.md).
