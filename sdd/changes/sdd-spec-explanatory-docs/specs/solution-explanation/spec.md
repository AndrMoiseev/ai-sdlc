# Пояснение предлагаемого решения

### Предложение после черновика

```yaml
sdd_record: requirement
id: REQ-offer-explanation
operation: add
```

После подготовки и редактуры черновика proposal, specs и design агент предлагает
создать отдельное пояснение до предложения независимого ревью. При незакрытом
вопросе пояснение может описывать текущее предложение с явным обозначением
неопределённости. Наличие пояснения не устраняет блокирующий вопрос.

Предложение допускает один документ, набор документов или отказ. Если пользователь
уже поручил подготовить пояснение в этой области, агент выполняет поручение
без повторного вопроса. При отказе основной процесс продолжается. Молчание
не разрешает генерацию и не запрещает дальнейшую работу над основным комплектом.
Выбор и версия черновика сохраняются для продолжения без повторного предложения
того же материала. Поздний запрос пользователя позволяет вернуться к пояснению.

### Предложение и отказ

```yaml
sdd_record: acceptance
id: AC-offer-and-decline
requirement: REQ-offer-explanation
conditions: Агент завершил черновик; ранее пользователь не поручал создавать пояснение.
expected: Агент предлагает пояснение; до выбора не генерирует его. Отказ сохраняется и не препятствует основному процессу, а при resume предложение той же версии не повторяется.
```

### Ранее выданное поручение

```yaml
sdd_record: acceptance
id: AC-reuse-explanation-request
requirement: REQ-offer-explanation
conditions: Пользователь ранее явно попросил пояснение для текущего изменения и не отменял поручение.
expected: Агент готовит пояснение в согласованной области без повторного разрешения; отдельные условия ревью и планирования сохраняются.
```

### Содержание и источники пояснения

```yaml
sdd_record: requirement
id: REQ-explanation-content
operation: add
```

Пояснение описывает задачу, предлагаемый подход, изменения относительно исходного
состояния и существенные последствия. Текст связывает диаграммы с требованиями
и решениями через относительные ссылки. Источник обязательств остаётся в specs
и design; новое обязательство, обнаруженное при пояснении, проходит обычный
пересмотр основного комплекта.

Пояснение охватывает затронутую структуру модулей, все новые и изменённые процессы
и сценарии, описанные в основном комплекте. Допускаются группировка и несколько
диаграмм, если сохраняются различия и условия. Для неприменимого вида представления
агент объясняет причину. Неизменённый контекст включается в объёме, необходимом
для понимания границ изменения. Неподтверждённое исходное поведение отмечается
как неизвестное, а предлагаемое поведение отделяется от уже существующего.

### Полнота и отсутствие исходных данных

```yaml
sdd_record: acceptance
id: AC-explanation-coverage
requirement: REQ-explanation-content
conditions: Пользователь выбрал пояснение; основной комплект описывает несколько изменённых процессов и сценариев, а часть исходного поведения не подтверждена.
expected: Пояснение содержит ссылки и представления для каждого описанного изменения; неизвестное обозначено явно. Для неприменимых представлений есть причина, а новые обязательства не остаются только в пояснении.
```

### Использование существующего archify

```yaml
sdd_record: requirement
id: REQ-archify-diagrams
operation: add
```

Диаграммы генерируются установленным скиллом archify: architecture для модулей
и их зависимостей, workflow для процессов, sequence для сценариев взаимодействия.
Агент читает инструкции и схемы доступной версии. Все необходимые пути задаются
для текущего проекта; расположение archify в авторском репозитории не предполагается.

archify и его схемы сохраняются без изменений. При недоступной зависимости или
невозможности выполнить её требования агент сообщает конкретное ограничение,
сохраняет выполненную часть и следующий шаг. Непроверенный результат не объявляется
успешным. Ограничение необязательного пояснения само по себе не блокирует основной
процесс sdd-spec.

### Типы диаграмм и недоступная зависимость

```yaml
sdd_record: acceptance
id: AC-diagram-types-and-dependency
requirement: REQ-archify-diagrams
conditions: Пояснение требует структуры модулей, процесса и сценария; в отдельном прогоне archify недоступен.
expected: При доступном archify используются соответственно architecture, workflow и sequence. Во втором прогоне сохранены доступный текст и описание ограничения; нет заявления о сгенерированных диаграммах и изменений archify.
```

### Обозначение изменений

```yaml
sdd_record: requirement
id: REQ-change-markers
operation: add
```

На каждой диаграмме явно различаются новые, изменённые и неизменённые элементы.
Если показаны удаления, они имеют отдельную метку. Основные обозначения текстовые:
«Новый», «Изменён», «Без изменений», «Удаляется». Короткие формы [+], [~], [=]
и [-] допустимы с расшифровкой на диаграмме. Метки видны без наведения и других
действий и сохраняются на превью. Цвет допустим как дополнительный признак.

Статус узла и статус связи определяются отдельно: неизменённые модули могут
получить новую зависимость. В сценарии обозначаются конкретные сообщения,
а статус участников показывается независимо. Тип компонента, направление,
условия, возврат и асинхронность сохраняют свой смысл. Неизвестное исходное
состояние не получает метку «Без изменений» без основания.

### Независимые статусы и читаемость

```yaml
sdd_record: acceptance
id: AC-visible-independent-statuses
requirement: REQ-change-markers
conditions: Диаграммы содержат два неизменённых модуля с новой связью, изменённый шаг процесса и изменённое сообщение существующего участника.
expected: Статусы модулей, шагов и связей различимы отдельно на HTML и доступном превью. Текстовые метки сохраняют смысл без цвета; типы компонентов и возвратных сообщений не подменяются ради оформления.
```

### Превью из проверки

```yaml
sdd_record: requirement
id: REQ-checked-previews
operation: add
```

Агент получает превью в ходе проверки archify со снимками и использует полученные
файлы. Само прохождение проверки без снимков не доказывает наличие превью.
Агент сверяет привязку результатов к текущему HTML и осматривает выбранные снимки:
подписи и обозначения читаются, нужная часть диаграммы не обрезана. При необходимости
допустимы несколько превью для большой диаграммы.

В пояснение вставляется изображение со ссылкой на соответствующий HTML.
Пути относительные и разрешаются из документа. Подпись поясняет содержание.
Генерация HTML, браузерная проверка, получение снимков и их осмотр отмечаются
по фактически выполненной работе. Актуальные снимки повторно не генерируются.

### Вставка проверенного изображения

```yaml
sdd_record: acceptance
id: AC-preview-from-check
requirement: REQ-checked-previews
conditions: Проверка текущей диаграммы в среде с браузером сохранила пригодный PNG и результаты с привязкой к HTML.
expected: Агент осматривает PNG, вставляет его в пояснение со ссылкой на этот HTML и использует существующий результат без отдельной повторной генерации изображения.
```

### Недоступный браузер и продолжение проверки

```yaml
sdd_record: requirement
id: REQ-preview-handoff
operation: add
```

Доступность браузера определяется возможностью выполнить проверку archify
в текущей среде, включая доступный локальный Chrome/Chromium. Отсутствие отдельного
браузерного инструмента агента само по себе не доказывает отсутствие браузера.

Если браузер недоступен, агент сохраняет созданный HTML и результаты доступных
проверок. Вместо каждого недостающего превью он вставляет видимый поисковый маркер
ARCHIFY_PREVIEW_PENDING:<diagram-id> и ссылку на существующий HTML. Для ещё
не созданного HTML сохраняется описание незавершённой работы без неработающей ссылки.

Агент предлагает готовый промпт для другой среды с браузером и сохраняет его
в изменении. Промпт указывает документы, исходники диаграмм, HTML и заглушки;
поручает проверить актуальность, выполнить проверку со снимками, осмотреть их
и заменить только соответствующие заглушки. Повторный запуск использует актуальные
результаты и не дублирует вставленные изображения.

Ошибка диаграммы или проверки отличается от недоступного браузера. При ошибке
сохраняются диагностика и незавершённый статус. Если превью получить не удалось
по иной причине, промпт указывает эту причину и требуемое исправление; перенос
в другую среду не объявляется достаточным решением ошибки.

### Работа без браузера

```yaml
sdd_record: acceptance
id: AC-no-browser-placeholder
requirement: REQ-preview-handoff
conditions: HTML создан, но archify не может запустить браузер в текущей среде.
expected: Документ содержит видимую заглушку ARCHIFY_PREVIEW_PENDING с ID и ссылкой на HTML. Сохранён и предложен промпт проверки со снимками в другой среде; успешная браузерная проверка не заявлена.
```

### Продолжение и повторный запуск

```yaml
sdd_record: acceptance
id: AC-handoff-idempotence
requirement: REQ-preview-handoff
conditions: Другая среда открывает изменение с заглушками и частью уже готовых актуальных превью, затем повторяет тот же запрос.
expected: Агент завершает недостающие проверки и заменяет соответствующие заглушки. Готовые актуальные изображения сохраняются; повторный запрос не дублирует изображения и не меняет смысл диаграмм.
```

### Дефект диаграммы

```yaml
sdd_record: acceptance
id: AC-preview-failure-not-absence
requirement: REQ-preview-handoff
conditions: Браузер доступен, но проверка сообщает дефект геометрии или ошибку выполнения.
expected: Агент сохраняет причину и незавершённый результат, действует по правилам исправления archify и не называет ошибку отсутствием браузера. Промпт продолжения содержит диагностику неустранённой ошибки.
```

### Расположение и переносимость

```yaml
sdd_record: requirement
id: REQ-explanation-artifacts
operation: add
```

Один поясняющий документ хранится как explanation.md в каталоге изменения.
При разделении explanation.md служит точкой входа, а дополнительные документы
располагаются в explanation/. Все сохраняемые артефакты archify, включая исходники,
HTML, снимки, результаты проверок, сведения об актуальности и промпт продолжения,
находятся внутри sdd/changes/<change-id>/archify/.

У каждой диаграммы есть стабильный ID и собственный каталог. Файлы разных
диаграмм и результаты повторных проверок не перезаписывают чужие данные.
Временные данные инструментов хранятся по их правилам вне пакетов скиллов.
Перенос всего каталога изменения сохраняет ссылки между пояснением и артефактами.

### Несколько документов и диаграмм

```yaml
sdd_record: acceptance
id: AC-portable-artifact-layout
requirement: REQ-explanation-artifacts
conditions: Пояснение разделено на несколько документов и содержит несколько диаграмм с повторными проверками.
expected: У документов есть общая точка входа, а все сохраняемые артефакты archify находятся внутри изменения. После переноса каталога ссылки разрешаются, ID однозначны, прежние результаты не потеряны.
```

### Актуальность производных материалов

```yaml
sdd_record: requirement
id: REQ-explanation-freshness
operation: add
```

При создании пояснения сохраняется манифест исходных proposal, design и всех specs.
При revise, resume и продолжении проверки агент сверяет его с текущими файлами.
Добавление, удаление или правка исходного документа означает необходимость
перепроверить пояснение и диаграммы. До сверки содержания они отмечены как устаревшие;
устаревшее изображение не выдаётся за превью текущего решения.

Для новой версии агент обновляет затронутые материалы и подтверждает применимость
оставшихся. Актуальность превью отдельно сверяется с текущим HTML по результатам
archify. Внешние источники проверяются по необходимости; манифест SDD не объявляется
автоматическим наблюдением за кодом репозитория.

Пояснение и archify не входят в нормативный манифест SDD. Изменение только превью,
заглушки или текста пояснения не меняет согласование основного комплекта. Если
обнаружено изменение требований или решения, действует обычный revise и прежние
согласования этого комплекта становятся устаревшими.

### Устаревшее пояснение

```yaml
sdd_record: acceptance
id: AC-stale-explanation-on-revision
requirement: REQ-explanation-freshness
conditions: После создания пояснения изменён design или добавлен spec; затем выполнен resume либо промпт получения превью.
expected: Агент обнаруживает несовпадение исходного манифеста и не выдаёт прежние диаграммы за текущие. После сверки и нужных правок он сохраняет новые основания актуальности.
```

### Согласования при замене превью

```yaml
sdd_record: acceptance
id: AC-preview-keeps-normative-manifest
requirement: REQ-explanation-freshness
conditions: Агент заменил заглушки проверенными превью, сохранив байты proposal, design и specs.
expected: Нормативный манифест SDD не изменился; согласование основного комплекта не объявлено устаревшим только из-за вставки превью.
```
